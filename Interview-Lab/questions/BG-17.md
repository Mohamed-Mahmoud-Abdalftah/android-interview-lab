# BG-17

## Original interview question

A business requirement asks for second-perfect periodic background execution. What Android limitations matter?

## What the interviewer evaluates

Reject second-perfect periodic execution promises under Android power/background limits.

## Explanation in Arabic

Android مش منصة تضمن job كل ثانية في الخلفية: Doze, standby, scheduler quotas, network loss وprocess death بتؤخر أو توقف execution. WorkManager periodic حدها الأدنى وفترات التنفيذ مرنة، exact alarms لحالات reminder دقيقة مش polling كل ثانية، وFGS مش loophole لعمل background loop بلا حاجة user-visible. نعيد تعريف requirement كـevent-driven/server-side أو foreground session واضح.

## Practical walkthrough

طلب “كل ثانية تمامًا في الخلفية” يصطدم بـDoze، standby، quotas، permissions، وقيود foreground services. وضح للمنتج الفرق بين latency الهدف والضمان الحقيقي. لو alarm للمستخدم، exact alarm بشروطها؛ لو telemetry، batch/WorkManager؛ لو stream مباشر أثناء session، foreground user-visible mode وفق القواعد. server-side scheduling أفضل لو الحدث يجب أن يقع حتى والجهاز مطفأ. قس التأخير الفعلي عبر device matrix.

## Why it matters and how it works

If exact per-second computation is a business rule, run it on a server or dedicated controlled hardware, not an arbitrary consumer Android process. For user-visible live sessions, an eligible foreground service may run while the session is active but still cannot promise perfect timing through power loss. Persist and reconcile timestamps/events after reconnect.

## Trade-offs and decision criteria

Server-side scheduling improves timing under controlled infrastructure but adds connectivity and cost. A foreground session can improve live UX with notification/power use. Deferrable local sync via WorkManager is battery-friendly but has flexible timing. Explain these tradeoffs to product before committing an SLA.

## Failure modes

Building a loop with delay(1000) in an application scope dies with process. Repeated exact alarms may be restricted and drain battery. A Worker configured every 15 minutes cannot satisfy per-second behavior. Hidden FGS can violate platform policy and user trust.

## Production perspective

A logistics app lets backend own per-second dispatch deadlines. Android client displays last-known status, listens for push while possible, and catches up by server cursor. An active driver navigation session may use eligible foreground execution with notification, but backend remains authoritative.

## Interview answer — short

“Android cannot guarantee arbitrary per-second background execution. I move authoritative timing server-side, use WorkManager for deferrable sync and an eligible foreground service only for a visible live session. I state delay and offline behavior explicitly.”

## Interview answer — structured

“I would challenge the exact requirement. WorkManager is flexible and respects Doze; periodic work is not a one-second timer. AlarmManager exact alarms are for real reminders and subject to special rules, not continuous polling. A coroutine loop dies with the process, and a foreground service needs a justified visible operation and still cannot survive power loss perfectly. If a business deadline truly needs second-level enforcement, the backend should own it, while Android displays state and catches up after reconnect.”

## Interview answer — deep senior

“I would make the SLA explicit: does the user need a display updated each second while an active screen is visible, or does the business require an action even when the phone is idle or off? The first can use an in-process timer for presentation, with server timestamps; the second belongs on backend infrastructure. Android background scheduling is constrained by Doze, standby, quotas and network availability. WorkManager gives durable deferrable execution, not exact time; exact alarms are narrow permission-sensitive reminders; foreground service is for ongoing visible work and still not a universal timing guarantee. I design event IDs/cursors so the client reconciles missed updates, show freshness and test poor connectivity/power loss. Persist and reconcile timestamps/events after reconnect. I ask whether the real need is a user-facing alarm, a live session, fresh data, or a backend deadline. Those map to different mechanisms. Periodic WorkManager has a minimum interval and inexact timing; Doze and standby can defer execution. A foreground service is constrained and must match a visible ongoing use case, while exact alarms are narrowly justified and permission-sensitive. If the business event must happen even when the phone is off, the backend owns the schedule and the app displays the result when available. I make the latency budget explicit and test on target devices, reporting observed delay distributions rather than promising second-level periodic execution.”

## How to answer in the interview

- **Why:** OS cannot promise arbitrary second-perfect work.
- **How:** translate SLA to supported execution mode.
- **Trade-off:** freshness versus battery and permission.
- **Failure case:** promise exact periodic polling with WorkManager.
- **Production solution:** server schedule or qualified visible session.
