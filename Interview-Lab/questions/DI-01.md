# DI-01

## Original interview question

What is DI and which problems does it solve?

## What the interviewer evaluates

- Define dependency injection as supplying collaborators from outside the consumer.
- Explain ownership, replaceability, construction order, and test seams without claiming DI solves all architecture problems.
- Distinguish manual DI from frameworks such as Hilt/Dagger.

## Concept and technical explanation

Dependency injection (DI) means that a consumer declares required collaborators and receives them from an external composition root or container instead of constructing them internally. This makes dependencies visible and provides a test seam, but it does not require an interface for every class, automatically implement the Dependency Inversion Principle, prevent memory leaks, or guarantee good architecture. Manual constructor wiring is DI; Hilt/Dagger help build larger graphs and integrate Android entry points. Scopes and semantic binding choices still require review.

## Practical walkthrough (English)

A ProfileViewModel receives a ProfileRepository through its constructor. App wiring constructs the repository with an API and DAO, while a unit test supplies a fake repository that returns controlled success or failure. The ViewModel does not know how either repository was built. This is a conceptual design example, not a standalone Hilt project; Hilt integration would also require an Android entry point and the necessary bindings.

## Explanation in Arabic

الفايدة العملية إنك تقدر تمرر Fake في Test، وتراجع Object Graph وScopes بدل ما تعتمد على Global Singleton مخفية. DI لا تتطلب Interface لكل Class؛ تقدر تحقن Concrete Type لو ده أبسط. وهي لا تساوي Dependency Inversion Principle تلقائيًا: لو الـ ViewModel تعتمد على Concrete Network Client، حتى لو Injected، الحد المعماري لسه ضعيف.

Manual DI بتمرير Constructor كفاية في Graph صغيرة. Hilt/Dagger بتساعد في بناء Graph أكبر ودمج Android Entry Points وScopes، لكن لازم تختار Binding وLifetime صح. Compiler ممكن يكشف Missing Binding في Graph مبنية، لكنه مش هيعرف وحده إنك ربطت Production بـ Sandbox Gateway بالغلط.

## Practical walkthrough

في شاشة Profile، الـ `ProfileViewModel` محتاجة `ProfileRepository`. App Module بتبني Repository مع API وDAO وتدخلها للـ ViewModel. في Unit Test، أدي ViewModel Fake Repository ترجع Success أو Error محدد، فأختبر قرار الـ UI من غير Network. لو المشروع صغير، Wiring يدوي في Composition Root ممكن يبقى أوضح. لو الـ Android Entry Points والـ Graph كبروا، Hilt تقلل كود التوصيل، لكن `@HiltViewModel` وBindings وScopes تبقى جزء من الإعداد الحقيقي.

## Why it matters and how it works

The consumer names a contract and its required dependencies; a composition root constructs concrete implementations and passes them in. This exposes the dependency graph at startup or compile time instead of hiding it in scattered constructors. A DI container can resolve bindings and scopes but does not remove the need to decide who owns data, sessions, cancellation, or side effects. Constructor injection makes required dependencies explicit; optional runtime parameters need a separate mechanism.

## Worked example

This small Kotlin/JVM example uses manual constructor injection and a deterministic fake. The Android version can use the same constructor contract with Hilt after declaring the required bindings.

```kotlin
interface ProfileSource {
    fun displayName(id: String): String?
}

class ProfileService(private val source: ProfileSource) {
    fun label(id: String): String = source.displayName(id) ?: "Unknown"
}

class FakeProfileSource : ProfileSource {
    override fun displayName(id: String): String? =
        if (id == "42") "Mona" else null
}

fun main() {
    val service = ProfileService(FakeProfileSource())
    check(service.label("42") == "Mona")
    check(service.label("missing") == "Unknown")
}
```

## Trade-offs and decision criteria

Manual DI is transparent and sufficient for a small graph, but wiring can become repetitive as Android entry points and variants grow. Hilt/Dagger provide compile-time binding checks and scoped components at the cost of generated-code/debugging and build configuration. Service locator hides dependencies at call sites and can make tests/order harder. Avoid injecting an interface for every trivial value solely to satisfy a pattern.

## Failure modes

A singleton graph retains Activity Context and leaks screens. A binding for `PaymentGateway` accidentally points to a sandbox implementation in release. A test fake is constructed differently from production and misses a missing binding. A dependency cycle prevents graph construction. Review scopes and variants, run compile-time checks, and test a production-like graph in integration tests.

## Production perspective

For a commerce app, put API/Room/SDK creation in app composition modules, expose small domain contracts to features, and scope session-specific collaborators deliberately. Test core logic with fakes and one integrated graph per variant. Log configuration failures without credentials and verify release bindings before rollout.

## Interview answer — short

Dependency injection means a class receives its collaborators from outside rather than constructing them internally. Constructor injection makes dependencies explicit and lets tests supply fakes without starting the real API or database. Manual wiring is enough for a small graph; Hilt and Dagger help manage larger Android graphs and scopes. DI does not automatically enforce good interfaces or prevent lifetime mistakes.

## Interview answer — structured

Suppose a ProfileViewModel constructs Retrofit and its repository internally. Its behavior is now tied to environment setup, which makes isolated tests cumbersome. With constructor injection, it declares a ProfileRepository dependency; an app composition root supplies the production implementation and a test supplies a fake.

This separates construction from behavior and makes the graph visible. It does not mean every dependency needs an interface, or that DI alone enforces the Dependency Inversion Principle. A singleton that captures an Activity Context can still leak it.

For a small app, manual constructor wiring is often clear enough. For many Android entry points, variants, and scopes, Hilt/Dagger can reduce wiring and catch missing bindings in the graph they compile. I still test a production-like graph because compile-time validation cannot tell me that a release PaymentGateway binding points to a sandbox implementation.

## Interview answer — deep senior

DI moves object-graph construction outside the consumer. The consumer states required collaborators in its constructor; a composition root or container chooses implementations and lifetimes. This is a form of inversion of control, but it is separate from the Dependency Inversion Principle, which concerns the direction of source-code dependencies toward abstractions. DI can inject a concrete network client and still leave a high-level policy coupled to infrastructure.

On Android, the platform constructs Activities, Fragments, and Services, so wiring many entry points manually can become repetitive. Hilt supplies lifecycle-related components and Dagger validates known bindings at compile time. An @Inject constructor on one implementation does not automatically bind an interface; the graph may need @Binds or @Provides. Scope is a correctness decision: a singleton holding Activity Context or session state can retain stale objects.

A ProfileViewModel unit test can pass a deterministic fake repository and cover success and failure without a network call, regardless of whether Hilt is used in production. Integration checks must also verify the real graph for relevant build variants. Compilation can reveal a missing binding, but not a semantically wrong sandbox gateway bound in release. Framework-generated wiring has configuration and debugging costs, while manual wiring has repetition costs. Choose from graph size and ownership needs, then verify lifetimes, variants, and behavior rather than assuming the DI library solves them.

## How to answer in the interview

- **Why:** construction inside consumers couples behavior to environment.
- **How:** constructor contract plus app composition root.
- **Trade-off:** manual DI stays simpler for small graphs.
- **Failure case:** singleton captures Activity or release binds sandbox.
- **Production solution:** scope inventory and variant graph smoke tests.

## Deep-dive talking points

Discuss composition root, explicit constructor requirements, scoped ownership, manual versus generated graph, and integration testing of bindings.

## Follow-up questions

- **Interviewer:** "Is Hilt required for DI?"
  **Answer:** "No. Passing dependencies from a composition root into constructors is manual DI. Hilt helps with larger graphs and Android entry points."

- **Interviewer:** "Does every dependency need an interface?"
  **Answer:** "No. Use an interface where it models a meaningful boundary or test seam; concrete classes can be injected too."

- **Interviewer:** "Can Hilt prevent all lifecycle leaks?"
  **Answer:** "No. A binding scoped too broadly can retain an Activity Context or stale session state. Scope and ownership still need review."

## Self-check rubric

Define DI, show a constructor seam, compare manual and Hilt wiring, and identify a lifecycle or variant binding failure.
