# DI-01

## Original interview question

What is DI and which problems does it solve?

## What the interviewer evaluates

- Define dependency injection as supplying collaborators from outside the consumer.
- Explain ownership, replaceability, construction order, and test seams without claiming DI solves all architecture problems.
- Distinguish manual DI from frameworks such as Hilt/Dagger.

## Explanation in Arabic

`Dependency Injection` معناها إن الكلاس يستقبل dependencies من برّه بدل ما ينشئها جوّاه. لو `CheckoutViewModel` عمل `Retrofit.Builder()` وRoom وpayment SDK بنفسه، بقى مسؤول عن business flow والتكوين والـlifecycle معًا وصعب تختبره. لما يستقبل `CheckoutRepository` في constructor، الـcomposition root أو Hilt graph يحدد implementation وعمره. ده يساعد في الاختبارات واستبدال backend واختيار scope صحيح، لكنه لا يصلح API سيئ أو state races تلقائيًا. ممكن تعمل DI يدويًا في تطبيق صغير؛ Hilt يوفر wiring قابل للقياس والتوسع لتطبيق Android كبير.

## Practical walkthrough

في feature دفع، لو `CheckoutViewModel` تبني Retrofit بنفسها، أي test لازم تشغّل شبكة حقيقية أو تعمل monkey patch. خليها تستقبل `CheckoutRepository` من constructor، والـapp تختار real implementation والـunit test تختار fake. راجع scope: repository ممكن تعيش مع العملية، لكن Activity context ما تدخلش process singleton. DI بتحسن حدود الإنشاء والاختبار، لكنها لا تحدد لك transaction semantics تلقائيًا.

## Why it matters and how it works

The consumer names a contract and its required dependencies; a composition root constructs concrete implementations and passes them in. This exposes the dependency graph at startup or compile time instead of hiding it in scattered constructors. A DI container can resolve bindings and scopes but does not remove the need to decide who owns data, sessions, cancellation, or side effects. Constructor injection makes required dependencies explicit; optional runtime parameters need a separate mechanism.

## Worked example

`class CheckoutViewModel @Inject constructor(private val repository: CheckoutRepository) : ViewModel()` receives an interface whose production implementation uses Room and an API client. A JVM test passes a deterministic fake repository to exercise failure and retry behavior without networking. This line is illustrative: Hilt ViewModel integration also needs `@HiltViewModel`, an Android entry point, and bindings for the interface and transitive dependencies.

## Trade-offs and decision criteria

Manual DI is transparent and sufficient for a small graph, but wiring can become repetitive as Android entry points and variants grow. Hilt/Dagger provide compile-time binding checks and scoped components at the cost of generated-code/debugging and build configuration. Service locator hides dependencies at call sites and can make tests/order harder. Avoid injecting an interface for every trivial value solely to satisfy a pattern.

## Failure modes

A singleton graph retains Activity Context and leaks screens. A binding for `PaymentGateway` accidentally points to a sandbox implementation in release. A test fake is constructed differently from production and misses a missing binding. A dependency cycle prevents graph construction. Review scopes and variants, run compile-time checks, and test a production-like graph in integration tests.

## Production perspective

For a commerce app, put API/Room/SDK creation in app composition modules, expose small domain contracts to features, and scope session-specific collaborators deliberately. Test core logic with fakes and one integrated graph per variant. Log configuration failures without credentials and verify release bindings before rollout.

## Interview answer — short

“DI supplies a class's collaborators from outside rather than constructing them internally. It makes requirements explicit, simplifies replacement in tests, and centralizes object lifetime and configuration decisions.”

## Interview answer — structured

“I use DI to separate a consumer's behavior from constructing its collaborators. A ViewModel receives a repository contract; the app's composition root chooses a Room/API implementation for production and a fake for a unit test. This makes dependencies visible and enables focused tests, alternate environments, and deliberate scopes. Manual constructor wiring is valid for a small app; Hilt or Dagger helps when the graph spans many Android components and modules. A DI framework does not repair a poor contract, incorrect concurrency, or a singleton that holds an Activity, so I review ownership and lifecycle as carefully as the binding syntax.”

## Interview answer — deep senior

“Dependency injection is an ownership and composition technique. A consumer declares collaborators, ideally as constructor parameters, and a composition root assembles concrete implementations at an application or feature boundary. This allows me to test checkout behavior with a deterministic fake and to swap a gateway adapter without editing business rules. In Android the graph also expresses lifetime: a process-level network client can be shared, while UI-specific state must live with an Activity or ViewModel and not be captured by a singleton. Hilt/Dagger make complex graphs and missing bindings visible at compile time, but introduce build tooling and generated-code complexity; manual DI can be cleaner in a small graph. I still test real variant wiring, because a syntactically valid graph can point release traffic at a sandbox, and I review cycles, qualifiers, session invalidation, and cancellation independently. DI is useful only when the contracts and ownership are sound. For example, in checkout I would make a fake repository return success, timeout, and a delayed stale response, then assert the ViewModel publishes the right state. The app composition root binds the real network-backed implementation. That makes a change from staging to production configuration testable without editing checkout logic. I would inspect the release graph as well, since DI cannot detect that a syntactically valid Retrofit client points at the wrong host.”

## How to answer in the interview

- **Why:** construction inside consumers couples behavior to environment.
- **How:** constructor contract plus app composition root.
- **Trade-off:** manual DI stays simpler for small graphs.
- **Failure case:** singleton captures Activity or release binds sandbox.
- **Production solution:** scope inventory and variant graph smoke tests.

## Deep-dive talking points

Discuss composition root, explicit constructor requirements, scoped ownership, manual versus generated graph, and integration testing of bindings.

## Follow-up questions

- Does DI require Hilt? **Answer:** no; manually passing constructor dependencies is DI, while Hilt automates graph wiring for larger Android apps.
- Can DI prevent an Activity leak by itself? **Answer:** no; a wrongly scoped singleton can still retain Activity or View references.
- Why test the production graph? **Answer:** unit fakes prove consumer behavior but may not catch missing or wrong variant bindings.

## Self-check rubric

Define DI, show a constructor seam, compare manual and Hilt wiring, and identify a lifecycle or variant binding failure.
