# DI-01

## Original interview question

What is DI and which problems does it solve?

## What the interviewer evaluates

- Define dependency injection as supplying collaborators from outside the consumer.
- Explain ownership, replaceability, construction order, and test seams without claiming DI solves all architecture problems.
- Distinguish manual DI from frameworks such as Hilt/Dagger.

## Explanation in Arabic

ما هو نمط حقن التبعيات (Dependency Injection - DI) وما هي المشاكل الحقيقية التي يحلها في Android؟

1. المفهوم الجوهري:
   - التبعية (Dependency) هي أي كائن أو خدمة يحتاجها كلاس آخر ليؤدي وظيفته (مثل `UserRepository` أو `HttpClient` داخل `OrderViewModel`).
   - نمط الـ DI هو تطبيق لمبدأ الـ Inversion of Control (IoC): بدلاً من أن يقوم الكلاس بإنشاء تبعياته بنفسه من الداخل (`val repo = UserRepositoryImpl()`)، يتم تمرير هذه التبعيات إليه جاهزة من الخارج عبر الـ Constructor (`Constructor Injection`).

2. المشاكل الكبرى التي يحلها الـ DI:
   - **الاقتران الصلب (Tight Coupling)**: بدون DI، يرتبط الكلاس بتنفيذ ملموس محدد (Concrete Class) وبإعداداته. مع DI، يرتبط فقط بـ Interface أو Abstraction، مما يجعل استبداله سهلاً دون تعديل الكود المستهلك.
   - **استحالة الاختبار المعزول (Testability)**: بدون DI، لا يمكنك تشغيل Unit Test سريع على الـ JVM للـ ViewModel دون الاتصال بشبكة وقاعدة بيانات حقيقية. مع DI، تمرر ببساطة `FakeUserRepository` في ثوانٍ.
   - **فوضى إدارة دورة الحياة والذاكرة (Lifecycle & Scoping)**: بدون إدارة مركزية، تتكرر كائنات ثقيلة مثل الـ Database Client في كل مكان، أو يتم تسريب الـ Context داخل كائنات عامة.
   - **إعادة استخدام الكود (Reusability)**: الكلاسات تصبح نقية وتعتمد فقط على مدخلاتها.

## Practical walkthrough

المقارنة بين كلاس ينشئ تبعياته بنفسه وكلاس يطبق الـ Dependency Injection:
```kotlin
// ❌ بدون DI: اقتران صلب، استحالة للـ Unit Test، وإنشاء متكرر لكائنات ثقيلة:
class BadProfileViewModel : ViewModel() {
    // الكلاس متحكم في كيفية بناء التبعية ومقيد بـ Implementation محدد:
    private val api = Retrofit.Builder().baseUrl("https://api.example.com").build().create(Api::class.java)
    private val repository = ProfileRepositoryImpl(api)
    
    fun loadProfile() { /* ... */ }
}

// ✅ مع Dependency Injection (Constructor Injection النقي):
@HiltViewModel
class GoodProfileViewModel @Inject constructor(
    private val repository: ProfileRepository // التبعية تمرر من الخارج عبر الـ Constructor
) : ViewModel() {
    val profileState = repository.getProfileStream()
}

// في الـ JVM Unit Test: اختبار فوري بدون تشغيل Hilt أو Android Framework:
@Test
fun profileViewModelLoadsDataCorrectly() = runTest {
    val fakeRepo = FakeProfileRepository(testUser)
    val viewModel = GoodProfileViewModel(fakeRepo) // تمرير Test Double في ثوانٍ!
    assertEquals(testUser, viewModel.profileState.first())
}
```

## Why it matters and how it works

The consumer names a contract and its required dependencies; a composition root constructs concrete implementations and passes them in. This exposes the dependency graph at startup or compile time instead of hiding it in scattered constructors. A DI container can resolve bindings and scopes but does not remove the need to decide who owns data, sessions, cancellation, or side effects. Constructor injection makes required dependencies explicit; optional runtime parameters need a separate mechanism.

## Worked example

`class CheckoutViewModel @Inject constructor(private val repository: CheckoutRepository) : ViewModel()` receives an interface whose production implementation uses Room and an API client. A JVM test passes a deterministic fake repository to exercise failure and retry behavior without networking. This line is illustrative: Hilt ViewModel integration also needs `@HiltViewModel`, an Android entry point, and bindings for the interface and transitive dependencies.

## Trade-offs and decision criteria

Manual DI is transparent and sufficient for a small graph, but wiring can become repetitive as Android entry points and variants grow. Hilt/Dagger provide compile-time binding checks and scoped components at the cost of generated-code/debugging and build configuration. Service locator hides dependencies at call sites and can make tests/order harder. Avoid injecting an interface for every trivial value solely to satisfy a pattern.

## Failure modes

A singleton graph retains Activity Context and leaks screens. A binding for `PaymentGateway` accidentally points to a sandbox implementation in release. A test fake is constructed differently from production and misses a missing binding. A dependency cycle prevents graph construction. Review scopes and variants, run compile-time checks, and test a production-like graph in integration tests.

## Production perspective

For a commerce app, put API/Room/SDK creation in app composition modules, expose small domain contracts to features, and scope session-specific collaborators deliberately. Test core logic with fakes and one integrated graph per variant. Log configuration failures without credentials and verify release bindings before rollout.

## Interview answer — short

Dependency Injection is a design pattern where an object receives its collaborators from an external provider rather than creating them itself. It decouples classes from concrete implementations, enables effortless JVM unit testing using test doubles, and centralizes lifecycle and object graph management across the application.

## Interview answer — structured

Dependency Injection is a concrete implementation of Inversion of Control where a class defines *what* collaborators it needs in its constructor, and an external assembler provides them.

It solves three fundamental engineering problems in Android.

First, with Tight Coupling, when a ViewModel constructs its own `Retrofit` instance or `RoomDatabase`, it is tightly bound to external infrastructure. With DI, the class depends on an abstract interface (`UserRepository`), allowing implementation details to change without touching consumer code. Next, with Unit Testability, hardcoded dependencies make isolated JVM tests impossible because you cannot swap live networking or persistence with fast in-memory Fakes. Constructor injection makes test seams trivial.
Finally, with Lifecycle & Scoping Management, Android components have complex lifecycles (Process, Application, Activity, ViewModel). DI frameworks like Hilt manage object scopes cleanly, preventing memory leaks and avoiding redundant, memory-heavy object allocations.


## Interview answer — deep senior

A crucial distinction senior engineers make is that **DI is an architectural pattern, not a framework**. You can execute pure Manual DI using pure Kotlin constructor parameters and an `AppContainer`. Frameworks like Dagger and Hilt simply automate graph assembly at compile-time to eliminate manual factory boilerplate.

Without DI, codebases inevitably degrade into **Service Locator anti-patterns** or global mutable singletons (`object ServiceRegistry`). Service Locators hide dependencies inside method bodies (`ServiceLocator.get<AuthManager>()`), breaking the explicit dependency contract, making refactoring treacherous, and risking runtime crashes if a collaborator is uninitialized. Constructor-based DI forces all dependencies to be explicit, immutable (`val`), non-null, and validated at compile time.


## How to answer in the interview

- **Why:** construction inside consumers couples behavior to environment.
- **How:** constructor contract plus app composition root.
- **Trade-off:** manual DI stays simpler for small graphs.
- **Failure case:** singleton captures Activity or release binds sandbox.
- **Production solution:** scope inventory and variant graph smoke tests.

## Deep-dive talking points

Discuss composition root, explicit constructor requirements, scoped ownership, manual versus generated graph, and integration testing of bindings.

## Follow-up questions

- **Interviewer:** "What is the difference between DI and a Service Locator?"
  **Answer:** "DI pushes dependencies into a class via its constructor (Inversion of Control), making dependencies explicit. A Service Locator pulls dependencies from an ambient registry inside the class, hiding dependencies and deferring missing dependencies to runtime failures."

- **Interviewer:** "Does DI improve app performance?"
  **Answer:** "Not directly at runtime. In fact, reflection-based DI slows startup, while compile-time DI (Dagger/Hilt) generates standard factory code with zero reflection overhead. The primary gains are maintainability, test seams, and lifecycle safety."

## Self-check rubric

Define DI, show a constructor seam, compare manual and Hilt wiring, and identify a lifecycle or variant binding failure.
