# DI-18

## Original interview question

An Activity Context was accidentally captured in a Singleton. Where is the DI design error?

## What the interviewer evaluates

- Trace the complete retention path and scope mismatch.
- Propose a safe redesign that preserves UI capability.
- Show how to prove the leak is fixed.

## Concept and technical explanation

Capturing an Activity Context inside a Singleton represents a critical architectural failure in dependency injection design that causes severe memory leaks. Because Singletons persist for the lifetime of the application process, retaining an Activity Context holds a strong reference to the entire destroyed Activity, its Window, DecorView, and associated resource hierarchies long after the user navigates away or rotates the screen. The root architectural cause stems from improper scoping boundaries, ambiguous unqualified Context bindings, and inverted layer dependencies. Proper DI design requires using Hilt's @ApplicationContext qualifier on all singleton dependencies, preventing child UI scopes from escaping into parent components, and passing transient Activity references exclusively via method parameters rather than constructor injection.

## Practical walkthrough (English)

Identifying and fixing Context retention in a Singleton:
```kotlin
// ERROR: Leaking Activity Context inside Singleton
@Singleton
class BadLocationManager @Inject constructor(
    // Defect: Unqualified Context injected! If provided by ActivityModule, it leaks!
    private val context: Context 
)

// PRODUCTION FIX: Strict Qualifier and architectural boundary enforcement
@Singleton
class SafeLocationManager @Inject constructor(
    // Guaranteed by Hilt to be the process-wide ApplicationContext
    @ApplicationContext private val context: Context,
    private val fusedLocationProvider: FusedLocationProviderClient
) {
    // If an operation strictly requires an Activity (e.g. resolving location settings dialogs),
    // pass the Activity as a transient method parameter, NEVER in the constructor!
    fun promptEnableGps(activity: Activity) {
        val intent = Intent(Settings.ACTION_LOCATION_SOURCE_SETTINGS)
        activity.startActivity(intent)
    }
}
```

## Explanation in Arabic

تم التقاط مرجع `Activity Context` بالخطأ داخل كائن `@Singleton`. أين يكمن الخطأ المعماري في تصميم الـ DI وكيف تصححه؟

1. تشريح الخطأ المعماري (Root Cause Analysis):
   - **عدم تطابق نطاقات دورة الحياة (Scope Lifetime Mismatch)**: كائن `@Singleton` يعيش طوال فترة عمل التطبيق (`Application Lifetime`). بينما الـ `Activity` تعيش فقط حتى يتم تدميرها (مثل عند دوران الشاشة).
   - عندما يحتفظ الـ Singleton بمرجع للـ Activity (سواء كـ Context، أو عبر Callback أو Listener مسجل بـ Anonymous Class):
   - مجمع القمامة (Garbage Collector) يعجز عن تحرير الـ Activity المدمرة لأن هناك مسار وصول حي (GC Strong Reference) إليها من جذر الـ GC Root (الـ SingletonComponent).
   - النتيجة: تسريب الـ Activity كاملة بشاشتها وجميع مكونات الـ Views والصور المرتبطة بها (تسريب 20-50MB مع كل تدوير للشاشة حتى الـ OOM Crash).

2. التصحيح المعماري الحاسم:
   - **إذا كان الكائن يحتاج Context فقط للوصول لموارد عامة أو خدمات النظام**: استبدل الـ Context بـ `@ApplicationContext context: Context`.
   - **إذا كان الكائن يحتاج Activity فعلياً للتعامل مع الـ UI/Navigation**: انزع عنه نطاق `@Singleton` وانقله إلى `ActivityComponent` بنطاق `@ActivityScoped`، أو مرر الـ Activity كمعامل في الدالة (`Method Parameter`) بدلاً من تخزينها كحقل في الـ Constructor.

## Why it matters and how it works

The application component owns its scoped binding until process teardown. A strong reference from that binding to a destroyed Activity retains its views and resources. Hilt's normal component hierarchy limits some direct injection mistakes, but a manual provider, callback, or SDK registration can still capture a shorter-lived owner. A weak reference alone may mask an ownership design problem and make UI behavior unreliable.

## Worked example

`AnalyticsManager` is Singleton and stores `ScreenTracker(activity)` from `MainActivity`. After rotation, its callback captures the old Activity. Change the manager to store only event data and a process-safe client. Let the live Activity register a short-lived tracker with a returned close handle in `onStart` and close it in `onStop`, then check the old instance is collectible.

### Kotlin / Hilt example

A process-owned service may retain application context; UI work belongs in a live Activity owner.

```kotlin
import android.content.Context
import dagger.hilt.android.qualifiers.ApplicationContext
import javax.inject.Inject
import javax.inject.Singleton

@Singleton
class SessionFiles @Inject constructor(
    @ApplicationContext private val context: Context
) {
    fun file(name: String) = context.getFileStreamPath(name)
}
```

If an operation needs the current theme, window, permission prompt, or view, move that operation to an Activity-owned collaborator rather than storing the Activity here.

## Trade-offs and decision criteria

Application Context is suitable for process-level storage or resources but cannot replace a live window owner. A scoped UI collaborator can be recreated and costs little compared with retaining a view tree. Passing a context at call time is safe only if the callee does not store it beyond the call or asynchronous operation.

## Failure modes

A provider function hides an Activity in a closure. An observer is registered and never removed. A long-running coroutine captures the Activity indirectly. A superficial patch changes the qualifier yet breaks dialogs because application Context has no appropriate UI window.

## Production perspective

Use heap retaining-path analysis, lifecycle tests across repeated rotation/navigation, and a code-review check for Android owner types in process-scoped bindings. Verify callback cleanup and actual UI behavior after redesign.

## Interview answer — short

The DI design error is failing to use Hilt's @ApplicationContext qualifier on the singleton dependency and allowing a short-lived Activity Context to be bound to a process-wide container. Singletons must never hold Activity references in their constructors. To fix this, annotate the Context parameter with @ApplicationContext, and if an operation requires an Activity, pass it transiently as a method argument from the UI layer.

## Interview answer — structured

Accidentally capturing an Activity Context inside a Singleton reveals multiple compounding errors in dependency injection design and lifecycle management.
The immediate structural error is the absence of explicit context qualifiers. In Android DI graphs, providing a generic, unqualified Context allows accidental binding of an Activity Context to a long-lived object. Because a Singleton instance persists in memory for the life of the application process, retaining an Activity Context prevents the Android Garbage Collector from reclaiming the destroyed Activity instance, its View hierarchy, layouts, and bitmap caches after screen destruction or rotation.
The architectural design error is inverted lifecycle ownership. A long-lived singleton service residing in SingletonComponent should only depend on components that equal or exceed its own lifespan. It must strictly depend on ApplicationContext.
To prevent this error, engineers enforce two architectural rules: first, all singleton constructor parameters requiring a context must be annotated with Hilt's built-in @ApplicationContext qualifier. Second, if a service requires an Activity to perform a UI-bound operation such as showing a dialog or launching an intent, the Activity must be passed transiently as a method parameter from the UI layer, never retained as a member property.

## Interview answer — deep senior

Under the hood, Dagger and Hilt enforce component scoping hierarchies that strictly forbid child component bindings from being injected into parent components. For instance, a class scoped with @Singleton residing in SingletonComponent cannot directly inject an @ActivityScoped dependency or an @ActivityContext parameter because the child ActivityComponent resides lower in the Directed Acyclic Graph.
This leak typically occurs through two subtle design flaws: first, when a developer writes a manual @Provides method inside an unscoped or custom module that provides a generic Context by grabbing an Activity reference; second, when an object is designed as a mutable singleton cache where an Activity registers itself as a listener or passes its Context to a configuration method without clearing the reference upon onDestroy().
Staff engineers implement multi-layered defenses against this failure mode. At the static analysis level, custom Android Lint rules and Detekt checks flag any @Singleton or @Inject constructor that accepts a raw Context without the @ApplicationContext qualifier. At the testing level, automated LeakCanary integration in debug builds detects leaked Activity instances during automated UI sweeps, failing test runs before memory regressions reach production. By combining static linters with automated memory analysis, teams eradicate Activity retention bugs permanently and protect mobile heap resources.

## Follow-up questions

- **Interviewer:** "Can passing an Activity into a suspending function cause a leak?"
  **Answer:** "Yes. If the coroutine is launched in a long-lived scope (like GlobalScope or ApplicationScope) and suspends for a long time, it retains the Activity context in the coroutine continuation frame until completion."

- **Interviewer:** "How do you verify the leak is permanently resolved?"
  **Answer:** "Run an automated test that rotates the Activity repeatedly (`activityScenario.recreate()`), asserts zero retained instances in LeakCanary, and inspects the Android Studio Memory Profiler heap dump."
