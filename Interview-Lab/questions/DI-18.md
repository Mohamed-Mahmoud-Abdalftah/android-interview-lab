# DI-18

## Original interview question

An Activity Context was accidentally captured in a Singleton. Where is the DI design error?

## What the interviewer evaluates

- Trace the complete retention path and scope mismatch.
- Propose a safe redesign that preserves UI capability.
- Show how to prove the leak is fixed.

## Explanation in Arabic

تم التقاط مرجع `Activity Context` بالخطأ داخل كائن `@Singleton`. أين يكمن الخطأ المعماري في تصميم الـ DI وكيف تصححه؟

1. تشريح الخطأ المعماري (Root Cause Analysis):
   - **عدم تطابق نطاقات دورة الحياة (Scope Lifetime Mismatch)**: كائن `@Singleton` يعيش طوال فترة عمل التطبيق (`Application Lifetime`). بينما الـ `Activity` تعيش فقط حتى يتم تدميرها (مثل عند دوران الشاشة).
   - عندما يحتفظ الـ Singleton بمرجع للـ Activity (سواء كـ Context، أو عبر Callback أو Listener مسجل بـ Anonymous Class):
   - مجمع القمامة (Garbage Collector) يعجز عن تحرير الـ Activity المدمرة لأن هناك مسار وصول حي (GC Strong Reference) إليها من جذر الـ GC Root (الـ SingletonComponent).
   - النتيجة: تسريب الـ Activity كاملة بشاشتها وجميع مكونات الـ Views والصور المرتبطة بها (تسريب 20-50MB مع كل تدوير للشاشة حتى الـ OOM Crash).

2. التصحيح المعماري الحاسم:
   - **إذا كان الكائن يحتاج Context فقط للوصول لموارد عامة أو خدمات النظام**: استبدل الـ Context بـ `@ApplicationContext context: Context`.
   - **إذا كان الكائن يحتاج Activity فعلياً للتعامل مع الـ UI/Navigation**: انزع عنه نطاق `@Singleton` وانقله إلى `ActivityComponent` بنطاق `@ActivityScoped`، أو مرر الـ Activity كمعامل في الدالة (`Method Parameter`) بدلاً من تخزينها كحقل في الـ Constructor.

## Practical walkthrough

إصلاح تسريب الـ Activity Context وإثبات الحل عبر الكود والتحقق:
```kotlin
// ❌ الخطأ الكارثي: Singleton يحتفظ بمرجع Activity Context:
@Singleton
class ToastHelper @Inject constructor(
    private val context: Context // لو تم تمرير Activity -> تسريب دائم لكل Activity تفتحها!
) {
    fun showToast(msg: String) { Toast.makeText(context, msg, Toast.LENGTH_SHORT).show() }
}

// ✅ التصحيح 1: إذا كان يحتاج مجرد Context عام -> استخدام @ApplicationContext:
@Singleton
class ToastHelperFixed @Inject constructor(
    @ApplicationContext private val context: Context // آمن 100% ولا يسرّب Activity أبداً
)

// ✅ التصحيح 2: إذا كان يحتاج Activity فعلياً (مثل فتح Dialog أو Transition) -> تغيير الـ Scope:
@ActivityScoped
class DialogHelper @Inject constructor(
    @ActivityContext private val activityContext: Context // مسموح: كلاهما يموت معاً في onDestroy
)

// التحقق: في LeakCanary أو Android Studio Memory Profiler:
// التأكد من عدم وجود Retained Instances للـ Activity بعد استدعاء activity.recreate()!
```

## Why it matters and how it works

The application component owns its scoped binding until process teardown. A strong reference from that binding to a destroyed Activity retains its views and resources. Hilt's normal component hierarchy limits some direct injection mistakes, but a manual provider, callback, or SDK registration can still capture a shorter-lived owner. A weak reference alone may mask an ownership design problem and make UI behavior unreliable.

## Worked example

`AnalyticsManager` is Singleton and stores `ScreenTracker(activity)` from `MainActivity`. After rotation, its callback captures the old Activity. Change the manager to store only event data and a process-safe client. Let the live Activity register a short-lived tracker with a returned close handle in `onStart` and close it in `onStop`, then check the old instance is collectible.

### Kotlin / Hilt example

A process-owned service may retain application context; UI work belongs in a live Activity owner.

```kotlin
import android.content.Context
import dagger.hilt.android.qualifiers.ApplicationContext
import javax.inject.Inject
import javax.inject.Singleton

@Singleton
class SessionFiles @Inject constructor(
    @ApplicationContext private val context: Context
) {
    fun file(name: String) = context.getFileStreamPath(name)
}
```

If an operation needs the current theme, window, permission prompt, or view, move that operation to an Activity-owned collaborator rather than storing the Activity here.

## Trade-offs and decision criteria

Application Context is suitable for process-level storage or resources but cannot replace a live window owner. A scoped UI collaborator can be recreated and costs little compared with retaining a view tree. Passing a context at call time is safe only if the callee does not store it beyond the call or asynchronous operation.

## Failure modes

A provider function hides an Activity in a closure. An observer is registered and never removed. A long-running coroutine captures the Activity indirectly. A superficial patch changes the qualifier yet breaks dialogs because application Context has no appropriate UI window.

## Production perspective

Use heap retaining-path analysis, lifecycle tests across repeated rotation/navigation, and a code-review check for Android owner types in process-scoped bindings. Verify callback cleanup and actual UI behavior after redesign.

## Interview answer — short

The architectural defect is a scope-lifetime mismatch: a process-lived @Singleton captures an ephemeral ActivityContext, holding a strong reference that prevents garbage collection on rotation. Fix it by replacing the dependency with @ApplicationContext, or re-scoping the collaborator to @ActivityScoped in ActivityComponent.

## Interview answer — structured

The design defect is a **Scope-Lifetime Mismatch** where a component with an application-level lifetime retains an instance of a short-lived framework lifecycle component.

1. **Root Cause**: When an Activity Context is injected into an `@Singleton` service, the singleton retains a strong reference to that specific Activity instance. When the user rotates the device or presses back, Android calls `onDestroy()`, but ART's garbage collector cannot free the Activity because a strong reference path leads from the GC Root (the singleton container) into the destroyed Activity. This leaks the entire DecorView, window manager, and all rendered bitmaps.

2. **The Architectural Fix**:
   - If the singleton only needs system services, file directories, or application resources, switch the parameter to `@ApplicationContext private val context: Context`.
   - If the collaborator genuinely requires an Activity (e.g. for window manipulation or custom dialogs), it must **not** be a Singleton. Demote its scope to `@ActivityScoped` and install its module in `ActivityComponent`, or pass the Activity transiently as a function parameter rather than retaining it as an injected constructor property.

## Interview answer — deep senior

To detect, diagnose, and prevent this class of leaks in CI/CD pipelines and production:

1. **Detection via LeakCanary**: LeakCanary intercepts destroyed Activities via `ActivityLifecycleCallbacks.onActivityDestroyed()`, waits 5 seconds, forces a GC, and if the reference persists, dumps the HPROF heap and computes the shortest retention path to the GC Root. The retention path will show `SingletonComponent_Impl -> LeakyService.context -> DestroyedActivity`.

2. **Dagger Compile-Time Prevention**: In Hilt, if you try to inject `@ActivityContext` into a class installed in `SingletonComponent`, Dagger will **fail compilation** immediately with: `[Dagger/IncompatiblyScopedBindings] ActivityContext is scoped to ActivityComponent and cannot be provided to SingletonComponent`.

The bug typically slips in when developers use a generic un-annotated `Context` binding or manually pass `this` from an Activity into a singleton repository method, bypassing Dagger's compile-time graph validator.

## How to answer in the interview

- **Why:** process and Activity lifetimes differ.
- **How:** application context for process work, UI dependency in Activity scope.
- **Trade-off:** moving UI work out adds boundary code.
- **Failure case:** indirect lambda capture leaks old Activity.
- **Production solution:** rotation leak detection and fresh-instance test.

## Deep-dive talking points

Trace reference roots, transitive closure, lifecycle cleanup, context qualifiers, and verification with heap evidence.

## Follow-up questions

- **Interviewer:** "Can passing an Activity into a suspending function cause a leak?"
  **Answer:** "Yes. If the coroutine is launched in a long-lived scope (like GlobalScope or ApplicationScope) and suspends for a long time, it retains the Activity context in the coroutine continuation frame until completion."

- **Interviewer:** "How do you verify the leak is permanently resolved?"
  **Answer:** "Run an automated test that rotates the Activity repeatedly (`activityScenario.recreate()`), asserts zero retained instances in LeakCanary, and inspects the Android Studio Memory Profiler heap dump."

## Self-check rubric

Show a retention chain, state the scope mismatch, redesign registration, and name a memory verification step.
