# DI-18

## Original interview question

An Activity Context was accidentally captured in a Singleton. Where is the DI design error?

## What the interviewer evaluates

- Trace the complete retention path and scope mismatch.
- Propose a safe redesign that preserves UI capability.
- Show how to prove the leak is fixed.

## Explanation in Arabic

الخطأ في ownership: Singleton يعيش على مستوى application component بينما Activity Context عمره شاشة/Activity instance. لو Singleton يحتفظ بالـContext أو callback/adapter ماسكه، GC لن يستطيع تحرير Activity بعد rotation. ابحث عن binding التي أدخلت reference قصير العمر في graph طويل العمر؛ لا تكتفِ بتبديل `@ActivityContext` إلى `@ApplicationContext` إن كان الكود يحتاج window أو theme. افصل الخدمة العامة عن خطوة UI، أو مرر Activity وقت تنفيذ قصير من owner حي، وألغِ listener عند الإغلاق.

## Why it matters and how it works

The application component owns its scoped binding until process teardown. A strong reference from that binding to a destroyed Activity retains its views and resources. Hilt's normal component hierarchy limits some direct injection mistakes, but a manual provider, callback, or SDK registration can still capture a shorter-lived owner. A weak reference alone may mask an ownership design problem and make UI behavior unreliable.

## Worked example

`AnalyticsManager` is Singleton and stores `ScreenTracker(activity)` from `MainActivity`. After rotation, its callback captures the old Activity. Change the manager to store only event data and a process-safe client. Let the live Activity register a short-lived tracker with a returned close handle in `onStart` and close it in `onStop`, then check the old instance is collectible.

## Trade-offs and decision criteria

Application Context is suitable for process-level storage or resources but cannot replace a live window owner. A scoped UI collaborator can be recreated and costs little compared with retaining a view tree. Passing a context at call time is safe only if the callee does not store it beyond the call or asynchronous operation.

## Failure modes

A provider function hides an Activity in a closure. An observer is registered and never removed. A long-running coroutine captures the Activity indirectly. A superficial patch changes the qualifier yet breaks dialogs because application Context has no appropriate UI window.

## Production perspective

Use heap retaining-path analysis, lifecycle tests across repeated rotation/navigation, and a code-review check for Android owner types in process-scoped bindings. Verify callback cleanup and actual UI behavior after redesign.

## Interview answer — short

“A process-scoped binding retained a shorter-lived Activity owner. I trace the reference chain, move UI work to the live owner, and verify old Activities are collectable.”

## Interview answer — structured

“The scope contract is wrong at the binding or registration boundary. A Singleton may have no direct `Activity` field yet keep one through a listener or lambda. I inspect that chain and split the process-safe service from UI coordination. The screen registers a callback only while active and unregisters it deterministically. I use Application Context only for APIs that support it, then test rotation and heap reachability so the fix is evidence-based.”

## Interview answer — deep senior

“I would first reproduce the retention after a few Activity recreations and use a heap trace to identify the path from the application component to the old instance. The obvious field may be a Context, but commonly the leak is transitive: a provider returns a listener that closes over the screen, or an SDK registration never removes its callback. The design error is that an object with process lifetime owns a reference whose valid lifetime ends with one Activity. I redesign that edge, rather than applying a weak reference indiscriminately. A Singleton can own a process-safe analytics client and immutable events; an Activity-owned coordinator can subscribe while the UI is live and dispose of its handle. When a window operation is required I keep a live Activity at the call site, because Application Context is not a drop-in UI replacement. I verify both sides: the old Activity is no longer retained after rotation and the screen still performs its intended operation. I add a regression test for cleanup plus a review rule on scoped providers and indirect captures.”

## Deep-dive talking points

Trace reference roots, transitive closure, lifecycle cleanup, context qualifiers, and verification with heap evidence.

## Follow-up questions

- Would a weak reference alone solve the design? **Answer:** it may hide retention but leaves unclear ownership and unreliable UI calls.
- Can Hilt prevent every such leak? **Answer:** no; manual providers and callbacks can capture an Activity outside direct graph checks.
- Why not always use Application Context? **Answer:** UI windows and themes require a live Activity owner.

## Self-check rubric

Show a retention chain, state the scope mismatch, redesign registration, and name a memory verification step.
