# BG-09

## Original interview question

How do you cancel or replace unique background work?

## What the interviewer evaluates

Explain cancel/replace unique work and limits around already-committed side effects.

## Explanation in Arabic

WorkManager تسمح `cancelUniqueWork(name)` أو enqueue unique work بسياسة KEEP/REPLACE. `KEEP` تسيب work الموجودة، `REPLACE` تلغي القديمة وتضيف جديدة؛ لكن إلغاء الـWorker local signal، ما يلغيش request اتقبلت في backend. لازم نحدد هل المطلوب إلغاء scheduling، وقف upload محلي، أو cancel business operation رسمي على السيرفر.

### Practical walkthrough in Egyptian Arabic

Unique work policy قرار business مش optimization فقط. `KEEP` يحافظ على sync جارية، `REPLACE` يلغي القديمة ويبدأ جديدة، لكن إلغاء worker لا يلغي server request ربما وصل. `APPEND` يضيف سلسلة ويحتاج التعامل مع فشل/إلغاء السابق. لو upload لنفس draft تغير، احفظ generation/version واقرأ أحدث state قبل الإرسال؛ لا تجعل replace تمحو التزام payment غير محسوم.

## Why it matters and how it works

Cancellation is cooperative for CoroutineWorker and may arrive mid-call. Observe WorkInfo for scheduler state, but use repository operation state for business outcome. Replacing work must preserve pending operation IDs if they were accepted; a new work chain should drain durable rows rather than lose them.

## Worked example

Android example; `SyncWorker` is app-owned and each run reads current outbox state.

```kotlin
import androidx.work.ExistingWorkPolicy
import androidx.work.OneTimeWorkRequestBuilder
import androidx.work.WorkManager

fun refreshSchedule(manager: WorkManager) {
    manager.enqueueUniqueWork(
        "outbox", ExistingWorkPolicy.REPLACE,
        OneTimeWorkRequestBuilder<SyncWorker>().build(),
    )
}
fun stopSchedule(manager: WorkManager) { manager.cancelUniqueWork("outbox") }
```

## Trade-offs and decision criteria

KEEP avoids churn while an operation is running; REPLACE can apply changed constraints but interrupts current work. CANCEL frees local resources but may leave business Pending. A server cancellation API may have its own race with completion.

## Failure modes

REPLACE during a payment call can produce unknown status, then new worker charges with a new key. UI that treats WorkInfo.CANCELLED as payment cancelled lies to user. A non-cooperative SDK may continue after worker stop.

## Production perspective

A file upload queue uses stable item IDs and resumes byte range if server supports it; replacing its scheduler never deletes pending records. A payment reversal can only be marked cancelled after server confirms cancellation or final status.

## Interview answer — short

“Unique work policies control local schedules. KEEP retains existing work; REPLACE cancels it and enqueues new work. Cancellation does not roll back server effects, so business status remains pending until reconciled.”

## Interview answer — structured

“I separate three meanings of cancel. WorkManager can cancel a named schedule, which stops or prevents local execution. A CoroutineWorker should cooperatively stop and release resources. But a server may already have accepted the request, so the business operation can still complete. I use stable operation IDs and query server status before showing a final outcome. KEEP is useful for an outbox drain already scheduled; REPLACE is appropriate only when changed scheduling policy justifies interrupting the current chain.”

## Interview answer — deep senior

“Unique work prevents multiple local chains with the same name, not multiple effects at the backend. REPLACE cancels the old chain and creates a new one; if the old worker had sent a payment or upload chunk, that external work is not atomically undone. Therefore I keep accepted operations in Room, never derive transaction outcome solely from WorkInfo, and reuse the same idempotency key when a replacement worker resumes. Explicit user cancellation has a separate server protocol with a race against completion. Tests trigger REPLACE during network send, stop a CoroutineWorker and verify local Pending plus authoritative reconciliation. If a user edits a draft while an upload is active, replacement may be appropriate only if the remote protocol can cancel or version the old upload safely. Canceling a Worker stops local execution cooperatively; it does not undo a request already received by the server. For a payment or reversal, I generally preserve the durable obligation and reconcile it before changing work generation. I keep the logical operation state in Room and use unique work as a scheduler convenience. Tests launch old and new generations around a delayed response, then assert that stale completion cannot overwrite the newer draft or erase an unresolved financial action.”

## How to answer in the interview

- **Why:** work replacement affects unfinished effects.
- **How:** choose policy from operation ownership.
- **Trade-off:** freshness versus preserving in-flight work.
- **Failure case:** replace drops unresolved reversal.
- **Production solution:** version operation and reconcile first.
