# DI-08

## Original interview question

What is a qualifier? Compare @Named and custom qualifiers.

## What the interviewer evaluates

- Explain that type alone is insufficient when multiple bindings of the same type exist.
- Compare string-keyed `@Named` with semantic, type-safe custom qualifier annotations.
- Apply the same qualifier at provider and injection site, including transitive client configuration.

## Explanation in Arabic

لو graph فيها `OkHttpClient` للـpublic API وواحد للـpayment API، النوع وحده لا يحدد أي واحد يُحقن. `Qualifier` تضيف هوية للـbinding. `@Named("payments")` حل سريع لكنه يعتمد على string ممكن يتكتب غلط أو يعاد تسميته بلا فحص قوي. Custom qualifier مثل `@PaymentsClient` يوضح المعنى ويجعل التسمية جزءًا من type-safe API. ضع نفس qualifier على provider وعلى parameter المطلوب. لا تحقن client غير مؤهل في repository حساس وتفترض أن endpoint وحده سيعوض إعدادات TLS/auth/interceptors.

## Practical walkthrough

لو عندك public API وpayments API الاتنين Retrofit، النوع وحده مش كفاية. `@Named("payments")` يشتغل لكنه string ممكن يتكتب غلط؛ custom `@Qualifier` أوضح في code review ويخلي wiring typed. حط qualifier على provider وعلى injection site، وافضل version/URL من config مقيّدة. اختبر release graph عشان payments client ما يروحش sandbox.

## Why it matters and how it works

Dagger's binding key includes type and qualifier. Two providers returning `OkHttpClient` without distinct keys are ambiguous; a qualified request selects one. `@Named` is a standard qualifier with a String value; a custom annotation marked `@Qualifier` communicates domain meaning and survives refactoring better. A qualifier does not determine scope or safety by itself; each client's configuration and owner still need review.

## Worked example

Define `@Qualifier @Retention(AnnotationRetention.BINARY) annotation class PaymentsClient` and annotate both `@Provides @PaymentsClient fun providePaymentsClient(...): OkHttpClient` and a `@PaymentsClient client: OkHttpClient` constructor parameter. A different `@PublicClient` binding serves catalog traffic. This is an abbreviated Hilt/Dagger example; imports, module installation, and actual TLS/interceptor configuration are intentionally omitted and must be compiled in the app.

### Kotlin / Hilt example

Both the provider and consumer carry the same qualifier. The app should supply the real base URL from its build configuration.

```kotlin
import dagger.Module
import dagger.Provides
import dagger.hilt.InstallIn
import dagger.hilt.components.SingletonComponent
import javax.inject.Inject
import javax.inject.Qualifier
import retrofit2.Retrofit

@Qualifier
@Retention(AnnotationRetention.BINARY)
annotation class PaymentsApi

@Module
@InstallIn(SingletonComponent::class)
object PaymentsNetworkModule {
    @Provides @PaymentsApi
    fun paymentsRetrofit(): Retrofit = Retrofit.Builder()
        .baseUrl("https://payments.example.org/")
        .build()
}

class PaymentGateway @Inject constructor(
    @PaymentsApi private val retrofit: Retrofit
)
```

## Trade-offs and decision criteria

`@Named` is fast for a small number of simple alternatives, but string values can drift and make intent opaque. Custom qualifiers add definitions and imports but support clearer code review for security-sensitive clients. Sometimes distinct wrapper types are even better when two clients have different capabilities rather than merely different endpoints. Avoid proliferating nearly identical qualifiers for configuration that should be unified.

## Failure modes

A provider is qualified but the injection parameter is not, causing a missing or wrong binding. A test substitutes only one of two qualified clients and unintentionally contacts production. A payments Retrofit uses catalog OkHttp interceptors and sends an auth token to the wrong host. Compile each variant, verify base URLs and interceptors, and add integration tests for host routing.

## Production perspective

For a financial app, use semantic qualifiers for gateway and customer APIs, keep secrets out of build constants, and enforce host allowlists where appropriate. Test both qualified graph paths with fake servers and inspect release variant wiring. On incident, qualifiers make it easier to trace which client produced a request without logging credentials.

## Interview answer — short

“A qualifier distinguishes bindings that have the same type. `@Named` uses a string label; a custom qualifier expresses a stable domain meaning and is usually clearer for important clients.”

## Interview answer — structured

“Dagger resolves a dependency by its binding key, which includes type and optional qualifier. If I provide two `OkHttpClient` instances, one for public content and one for payments, an unqualified request is ambiguous. I put the same qualifier on the provider and injection site. `@Named("payments")` is convenient but string-based; a custom `@PaymentsClient` annotation makes intent clearer and safer to refactor. Qualifiers do not set lifetime or security policy, so I still review the actual host, interceptors, credentials, and scope. I test release graph wiring to ensure the payments client cannot accidentally use the catalog configuration.”

## Interview answer — deep senior

“A qualifier makes a same-type dependency choice explicit in the graph. For multiple network clients, the binding key is not merely `OkHttpClient` but `OkHttpClient` plus a semantic identity. `@Named` is fine for a small graph, yet string literals are easy to mistype or reuse inconsistently; custom `@Qualifier` annotations such as `@PaymentsClient` communicate architectural intent at both binding and injection sites. I apply qualifiers to the entire chain where needed—client, Retrofit, API service—so a payment adapter cannot silently inherit public-API interceptors or host configuration. Scope is an independent decision. For highly different capabilities I may use distinct wrapper interfaces instead of two same-type clients. I compile variants, test routing with fake servers, and inspect release configuration because a technically valid qualifier can still point to the wrong endpoint or expose a token through a misconfigured interceptor. In payments, I would name the endpoint qualifier `PaymentsApi`, apply it to both provider and gateway constructor, and build a separate public API client. In the release variant I would assert the gateway’s configured host points to the live environment. A missing qualifier causes a graph error; a matching qualifier wired to a sandbox host compiles, so the environment assertion covers the remaining operational risk.”

## How to answer in the interview

- **Why:** same-type bindings need distinct identity.
- **How:** tag both provider and consumer.
- **Trade-off:** Named brevity versus typed custom annotation.
- **Failure case:** release payments client binds sandbox.
- **Production solution:** variant-specific graph smoke test.

## Deep-dive talking points

Discuss binding key, provider/request symmetry, string fragility, semantic annotations, endpoint security, and variant tests.

## Follow-up questions

- Does a qualifier make a binding Singleton? **Answer:** no; scope annotations control sharing, while a qualifier selects among same-type bindings.
- What happens if two unqualified clients are provided? **Answer:** Dagger usually reports an ambiguous/duplicate binding for an unqualified request.
- Why test the payment client routing? **Answer:** a wrong qualifier or binding can send authenticated traffic to the wrong host or use incorrect interceptors.

## Self-check rubric

Define a binding key, write provider/request qualifiers, compare Named/custom, and identify a misrouted-client risk.
