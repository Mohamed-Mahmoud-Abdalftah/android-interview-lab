# DI-08

## Original interview question

What is a qualifier? Compare @Named and custom qualifiers.

## What the interviewer evaluates

- Explain that type alone is insufficient when multiple bindings of the same type exist.
- Compare `@Named` with semantic custom qualifier annotations without treating either as a runtime string lookup.
- Apply the same qualifier at provider and injection site, including transitive client configuration.

## Concept and technical explanation

A Dagger binding key combines a type with an optional qualifier annotation instance. Two `OkHttpClient` bindings for authenticated and public traffic therefore need distinct keys. `@Named("auth")` is itself a qualifier; its string value is part of the compile-time key, not a runtime service-locator lookup. A typo at a request site normally produces a missing-binding compile error, assuming the graph is compiled. A custom annotation marked `@Qualifier` names the role through a Kotlin/Java symbol, which generally makes rename refactoring and code review clearer. Both choices are valid; neither verifies an endpoint or interceptor configuration. A qualifier selects *which* binding, whereas a scope such as `@Singleton` controls reuse within its component. Neither guarantees thread safety.

## Practical walkthrough (English)

The two approaches express the same binding distinction; this Android/Hilt sketch needs the app's imports and graph compilation:
```kotlin
// Qualifier annotation symbols identify the two client roles.
@Qualifier
@Retention(AnnotationRetention.BINARY)
annotation class AuthOkHttpClient

@Qualifier
@Retention(AnnotationRetention.BINARY)
annotation class PublicOkHttpClient

// Provide distinct keys in the Hilt module.
@Module
@InstallIn(SingletonComponent::class)
object NetworkModule {
    @Provides @Singleton @AuthOkHttpClient
    fun provideAuthOkHttpClient(authInterceptor: AuthInterceptor): OkHttpClient =
        OkHttpClient.Builder().addInterceptor(authInterceptor).build()

    @Provides @Singleton @PublicOkHttpClient
    fun providePublicOkHttpClient(): OkHttpClient =
        OkHttpClient.Builder().build()
}

// Request the same key at the injection site.
class UserRepository @Inject constructor(
    @AuthOkHttpClient private val okHttpClient: OkHttpClient
)
```

For a small graph, `@Named("auth")` on both provider and request is also legitimate. A misspelled name generally fails graph compilation when no matching binding exists. A correctly matched but wrongly configured binding still passes compilation, so verify host routing and interceptor behavior in an integration test.

## Practical walkthrough

المثال ده شكل توضيحي لـHilt؛ لازم يتجمع داخل Android app فيها الاعتماديات والـImports المناسبة:
```kotlin
// Custom Qualifiers بتسمّي الدور برمز قابل لإعادة التسمية.
@Qualifier
@Retention(AnnotationRetention.BINARY)
annotation class AuthClient

@Qualifier
@Retention(AnnotationRetention.BINARY)
annotation class PublicClient

@Module
@InstallIn(SingletonComponent::class)
object NetworkModule {
    @Provides @Singleton @AuthClient
    fun provideAuthenticatedOkHttpClient(authInterceptor: AuthInterceptor): OkHttpClient {
        return OkHttpClient.Builder().addInterceptor(authInterceptor).build()
    }
    
    @Provides @Singleton @PublicClient
    fun providePublicOkHttpClient(): OkHttpClient {
        return OkHttpClient.Builder().build()
    }
}

// في الـRepository: استخدم نفس الـQualifier الموجود على الـProvider.
class UserRepository @Inject constructor(
    @AuthClient private val httpClient: OkHttpClient
)
```

بديل صغير بنفس الفكرة: حط `@Named("auth_client")` على دالة الـProvider وعلى Parameter اللي بيطلبها. لو القيمة اختلفت ومفيش Binding مطابق، الـGraph غالبًا يفشل وقت الـCompile.

لو أخطأت في اسم `@Named` ومفيش Binding بنفس الاسم، الفشل بيظهر غالبًا في Graph Compilation. أما لو الحقن صحيح لكن الـInterceptor أو الـBase URL غلط، محتاج Test لوجهة الطلب؛ الـQualifier وحده مش كفاية.

## Why it matters and how it works

Dagger's binding key includes type and qualifier. Two providers returning `OkHttpClient` without distinct keys are ambiguous; a qualified request selects one. `@Named` is a standard qualifier with a String value; a custom annotation marked `@Qualifier` communicates domain meaning and survives refactoring better. A qualifier does not determine scope or safety by itself; each client's configuration and owner still need review.

## Worked example

Define `@Qualifier @Retention(AnnotationRetention.BINARY) annotation class PaymentsClient` and annotate both `@Provides @PaymentsClient fun providePaymentsClient(...): OkHttpClient` and a `@PaymentsClient client: OkHttpClient` constructor parameter. A different `@PublicClient` binding serves catalog traffic. This is an abbreviated Hilt/Dagger example; imports, module installation, and actual TLS/interceptor configuration are intentionally omitted and must be compiled in the app.

### Kotlin / Hilt example

Both the provider and consumer carry the same qualifier. The app should supply the real base URL from its build configuration.

```kotlin
import dagger.Module
import dagger.Provides
import dagger.hilt.InstallIn
import dagger.hilt.components.SingletonComponent
import javax.inject.Inject
import javax.inject.Qualifier
import retrofit2.Retrofit

@Qualifier
@Retention(AnnotationRetention.BINARY)
annotation class PaymentsApi

@Module
@InstallIn(SingletonComponent::class)
object PaymentsNetworkModule {
    @Provides @PaymentsApi
    fun paymentsRetrofit(): Retrofit = Retrofit.Builder()
        .baseUrl("https://payments.example.org/")
        .build()
}

class PaymentGateway @Inject constructor(
    @PaymentsApi private val retrofit: Retrofit
)
```

## Trade-offs and decision criteria

`@Named` is fast for a small number of simple alternatives, but string values can drift and make intent opaque. Custom qualifiers add definitions and imports but support clearer code review for security-sensitive clients. Sometimes distinct wrapper types are even better when two clients have different capabilities rather than merely different endpoints. Avoid proliferating nearly identical qualifiers for configuration that should be unified.

## Failure modes

A provider is qualified but the injection parameter is not, causing a missing binding or selection of an available unqualified binding. A matched qualifier can still supply the wrong base URL or interceptor. A test may replace one qualified client but leave another real client in the graph. Compile each relevant variant, verify the actual host and interceptor chain with an appropriate HTTP test server, and keep sensitive headers out of logs.

## Production perspective

For a financial app, use semantic qualifiers for gateway and customer APIs, keep secrets out of build constants, and enforce host allowlists where appropriate. Test both qualified graph paths with fake servers and inspect release variant wiring. On incident, qualifiers make it easier to trace which client produced a request without logging credentials.

## Interview answer — short

A qualifier distinguishes bindings with the same type, such as separate authenticated and public `OkHttpClient`s. `@Named("auth")` is a valid qualifier whose string participates in the compile-time binding key; a custom `@Qualifier` annotation gives the role a named code symbol that is often easier to refactor. Both need matching annotations on provider and request. Scope is a separate decision.

## Interview answer — structured

In Hilt, a binding request is identified by its type and optional qualifier. Suppose I provide one `OkHttpClient` for authenticated traffic and one for public traffic. I annotate both providers and each consumer with matching qualifiers. `@Named("auth")` is perfectly valid for a small graph, but its string is easier to mistype or leave behind during a rename. A custom `@Qualifier` annotation such as `@AuthClient` makes that role a code symbol and can improve navigation and refactoring. A mismatched name or annotation generally fails during graph compilation, while a correctly matched but misconfigured client can still call the wrong host. So I compile the relevant variants and test request routing. Qualifiers choose bindings; `@Singleton` or another scope determines component-level reuse, not which client is chosen.

## Interview answer — deep senior

Dagger describes a key as a type paired with an optional qualifier annotation instance. Thus `OkHttpClient`, `@Named("auth") OkHttpClient`, and `@AuthClient OkHttpClient` are distinct requests. `@Named("auth")` and `@Named("public")` differ because the annotation values differ. Two identical keys in the same graph normally produce a duplicate-binding error; a request without a matching key produces a missing-binding error. Dagger resolves the graph at compile time, so `@Named` does not create a runtime string registry. Multiple qualifiers on one dependency are not supported.

I choose `@Named` when a local distinction is small and legible. If network clients are shared across modules or have security-sensitive roles, a semantic custom annotation can make code ownership and rename operations clearer. This is a maintainability preference, not a universal enterprise ban or a claim that the compiler proves configuration. The type is already part of the key, so two uses of `@Named("api_url")` with *different types* do not collide solely because the names match. An unqualified binding left beside qualified alternatives can still be selected accidentally; Hilt recommends qualifying all ways of providing that type when possible.

Scope is orthogonal: `@Singleton` controls reuse within `SingletonComponent`, and a qualified unscoped binding can create instances according to its binding semantics. Neither scope nor qualifier makes a client thread-safe or persistent across process death. In a payments app I would inspect the generated graph and build variants, test that the gateway client reaches the intended host with the intended interceptors, and ensure a test replacement covers every qualified path. The Android/Hilt snippet here is illustrative and was API-reviewed, not compiled as an Android application in this repository.

## How to answer in the interview

- **Why:** same-type bindings need distinct identity.
- **How:** tag both provider and consumer.
- **Trade-off:** Named brevity versus typed custom annotation.
- **Failure case:** release payments client binds sandbox.
- **Production solution:** variant-specific graph smoke test.

## Deep-dive talking points

Discuss binding key, provider/request symmetry, string fragility, semantic annotations, endpoint security, and variant tests.

## Follow-up questions

- **Interviewer:** "If `@Named` is misspelled, will it silently inject a different client at runtime?"
  **Answer:** "Usually no. A missing matching key is a graph compilation error. The harder bug is a correctly matched qualifier whose provider is configured for the wrong host or interceptors; that needs an integration test."

- **Interviewer:** "Can you use multiple qualifiers on a single injection site?"
  **Answer:** "No. Dagger allows at most one qualifier per binding key. Applying multiple qualifiers causes a compile-time error."

- **Interviewer:** "Does `@Singleton` replace `@AuthClient`?"
  **Answer:** "No. The qualifier selects which `OkHttpClient` binding to request; the scope controls reuse inside the component. Neither proves the client's configuration or thread safety."

Define a binding key, write provider/request qualifiers, compare Named/custom, and identify a misrouted-client risk.
