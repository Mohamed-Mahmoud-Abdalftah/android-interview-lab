# DI-08

## Original interview question

What is a qualifier? Compare @Named and custom qualifiers.

## What the interviewer evaluates

- Explain that type alone is insufficient when multiple bindings of the same type exist.
- Compare string-keyed `@Named` with semantic, type-safe custom qualifier annotations.
- Apply the same qualifier at provider and injection site, including transitive client configuration.

## Explanation in Arabic

ما هو الـ Qualifier في Dagger و Hilt؟ وما الفرق بين `@Named` والـ Custom Qualifiers المخصصة؟

1. المشكلة التي يحلها الـ Qualifier:
   - في Dagger، يتم تمييز التبعيات افتراضياً بناءً على نوع البيانات (Type/Class). لو كان لديك دالتان توفران نفس النوع (مثل `OkHttpClient` موجه لخدمة التحقق من الهوية بتوكنز خاصة، و `OkHttpClient` آخر عام للبيانات العامة):
   - سيفشل Dagger في وقت التجميع مع خطأ: `[Dagger/DuplicateBindings] OkHttpClient is bound multiple times!` لأن Dagger لا يعرف أيهما يحقن.

2. ما هو الـ Qualifier؟
   - هو تعليق توضيحي (Annotation) يُضاف إلى النوع لتمييز التبعية بشكل فريد في شجرة Dagger (`Type + Qualifier = Unique Key`).

3. المقارنة بين `@Named` و Custom Qualifiers:
   - **`@Named("auth")`**: يعتمد على نصوص عادية (String Keys). عيوبه خطيرة في الإنتاج: عرضة للأخطاء الإملائية (Typos)، ولا يدعم إعادة التسمية التلقائية بالـ Refactoring، ولا يكتشف المترجم تعارض النصوص في وقت مبكر.
   - **Custom Qualifiers (`@Qualifier @Retention(RUNTIME) annotation class AuthOkHttp`)**: المعيار الذهبي الموصى به رسمياً من Google. يمنحك Type-Safety كامل، ودعم لإعادة التسمية عبر IDE Refactoring، ومنع الأخطاء الإملائية نهائياً.

## Practical walkthrough

المقارنة العملية بين `@Named` والـ Custom Qualifiers في Hilt:
```kotlin
// ❌ استخدام @Named: نصوص سحرية عرضة لأخطاء الـ Typo والـ Refactoring:
@Provides @Named("auth_client")
fun provideAuthClient(): OkHttpClient = ...

@Inject constructor(@Named("ath_client") val client: OkHttpClient) // Typo يسبب خطأ تجميع غامض!

// ✅ استخدام Custom Type-Safe Qualifiers (أفضل ممارسة معتمدة):
@Qualifier
@Retention(AnnotationRetention.BINARY)
annotation class AuthClient

@Qualifier
@Retention(AnnotationRetention.BINARY)
annotation class PublicClient

@Module
@InstallIn(SingletonComponent::class)
object NetworkModule {
    @Provides @Singleton @AuthClient
    fun provideAuthenticatedOkHttpClient(authInterceptor: AuthInterceptor): OkHttpClient {
        return OkHttpClient.Builder().addInterceptor(authInterceptor).build()
    }
    
    @Provides @Singleton @PublicClient
    fun providePublicOkHttpClient(): OkHttpClient {
        return OkHttpClient.Builder().build()
    }
}

// في الـ Repository: حقن آمن ونظيف بنسبة 100%:
class UserRepository @Inject constructor(
    @AuthClient private val httpClient: OkHttpClient // Type-Safe ومحمي من الـ Typos
)
```

## Why it matters and how it works

Dagger's binding key includes type and qualifier. Two providers returning `OkHttpClient` without distinct keys are ambiguous; a qualified request selects one. `@Named` is a standard qualifier with a String value; a custom annotation marked `@Qualifier` communicates domain meaning and survives refactoring better. A qualifier does not determine scope or safety by itself; each client's configuration and owner still need review.

## Worked example

Define `@Qualifier @Retention(AnnotationRetention.BINARY) annotation class PaymentsClient` and annotate both `@Provides @PaymentsClient fun providePaymentsClient(...): OkHttpClient` and a `@PaymentsClient client: OkHttpClient` constructor parameter. A different `@PublicClient` binding serves catalog traffic. This is an abbreviated Hilt/Dagger example; imports, module installation, and actual TLS/interceptor configuration are intentionally omitted and must be compiled in the app.

### Kotlin / Hilt example

Both the provider and consumer carry the same qualifier. The app should supply the real base URL from its build configuration.

```kotlin
import dagger.Module
import dagger.Provides
import dagger.hilt.InstallIn
import dagger.hilt.components.SingletonComponent
import javax.inject.Inject
import javax.inject.Qualifier
import retrofit2.Retrofit

@Qualifier
@Retention(AnnotationRetention.BINARY)
annotation class PaymentsApi

@Module
@InstallIn(SingletonComponent::class)
object PaymentsNetworkModule {
    @Provides @PaymentsApi
    fun paymentsRetrofit(): Retrofit = Retrofit.Builder()
        .baseUrl("https://payments.example.org/")
        .build()
}

class PaymentGateway @Inject constructor(
    @PaymentsApi private val retrofit: Retrofit
)
```

## Trade-offs and decision criteria

`@Named` is fast for a small number of simple alternatives, but string values can drift and make intent opaque. Custom qualifiers add definitions and imports but support clearer code review for security-sensitive clients. Sometimes distinct wrapper types are even better when two clients have different capabilities rather than merely different endpoints. Avoid proliferating nearly identical qualifiers for configuration that should be unified.

## Failure modes

A provider is qualified but the injection parameter is not, causing a missing or wrong binding. A test substitutes only one of two qualified clients and unintentionally contacts production. A payments Retrofit uses catalog OkHttp interceptors and sends an auth token to the wrong host. Compile each variant, verify base URLs and interceptors, and add integration tests for host routing.

## Production perspective

For a financial app, use semantic qualifiers for gateway and customer APIs, keep secrets out of build constants, and enforce host allowlists where appropriate. Test both qualified graph paths with fake servers and inspect release variant wiring. On incident, qualifiers make it easier to trace which client produced a request without logging credentials.

## Interview answer — short

A Qualifier disambiguates multiple bindings of the identical type in the Dagger graph. While @Named uses raw string keys that are prone to typos and refactoring breakage, custom qualifiers (@Qualifier annotation class) provide compile-time type safety, IDE refactoring support, and semantic clarity.

## Interview answer — structured

In Dagger and Hilt, bindings are keyed by their return type. When you provide multiple instances of the same type—such as an authenticated `OkHttpClient` with tokens versus an unauthenticated client for public CDN assets—Dagger throws a duplicate binding error at compile time.

A **Qualifier** decorates the type to create a compound key (`Qualifier + Type`).

First, @Named is a built-in qualifier parameterized by a string literal (`@Named("auth")`). While convenient for quick prototypes, it is brittle in enterprise codebases: strings are prone to silent typos, cannot be refactored safely across modules, and lack semantic IDE autocompletion. Finally, custom Qualifiers is defined using `@Qualifier` and `@Retention(AnnotationRetention.BINARY)`. They provide full compile-time type safety, enable seamless IDE find-usages and refactoring, and document the architectural intent directly (e.g. `@AuthOkHttp`, `@CacheDirectory`).


## Interview answer — deep senior

Dagger indexes bindings internally in a `Key` structure comprising: `Type`, `Qualifier`, and `MultibindingContributionIdentifier`.

When you define a custom qualifier, you can also include annotation parameters if you need dynamic keys: e.g. `@Qualifier annotation class Backend(val environment: Env)`. However, modern clean architecture strongly favors distinct zero-arg qualifier annotations per responsibility to prevent leaky configuration details.

In Hilt, Google includes standard predefined qualifiers: `@ApplicationContext` and `@ActivityContext`. These allow injecting the exact required Android context variant without accidentally passing an Activity context where a long-lived Application context is expected.


## How to answer in the interview

- **Why:** same-type bindings need distinct identity.
- **How:** tag both provider and consumer.
- **Trade-off:** Named brevity versus typed custom annotation.
- **Failure case:** release payments client binds sandbox.
- **Production solution:** variant-specific graph smoke test.

## Deep-dive talking points

Discuss binding key, provider/request symmetry, string fragility, semantic annotations, endpoint security, and variant tests.

## Follow-up questions

- **Interviewer:** "What retention policy should a custom `@Qualifier` use in Kotlin?"
  **Answer:** "`AnnotationRetention.BINARY` or `RUNTIME`. `BINARY` is preferred because Dagger processes annotations during compilation and does not need runtime reflection overhead."

- **Interviewer:** "Can you use multiple qualifiers on a single injection site?"
  **Answer:** "No. Dagger allows at most one qualifier per binding key. Applying multiple qualifiers causes a compile-time error."
