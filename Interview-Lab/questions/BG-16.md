# BG-16

## Original interview question

A job ran twice after a crash. How do you enforce idempotency?

## What the interviewer evaluates

Handle a Worker running twice after crash with logical operation idempotency.

## Concept and technical explanation

Enforcing idempotency when a background job executes twice following an application crash requires addressing the foundational reality of WorkManager: it is an at-least-once task execution engine, not an exactly-once system. If an operating system crash, low-memory process kill, or unhandled exception occurs after a worker completes its side effect (such as charging a customer or mutating remote state) but before it returns Result.success() to WorkManager's internal database, the platform reschedules the job. Enforcing idempotency requires establishing a resilient two-tier safeguard: client-side deterministic tokenization and server-side duplicate suppression. At the client tier, every discrete domain intent generates a persistent, unique idempotency key (UUID) recorded in a local Room database with a state machine; upon retry, the worker verifies whether local completion was already reached. At the server tier, the remote API requires this idempotency key in an HTTP header, verifying it against an atomic database ledger to return previously cached responses without re-executing transactions.

## Practical walkthrough (English)

Implementing two-tier idempotency guards across app crashes:
```kotlin
// 1. Enforcing idempotency via client state and remote idempotency keys
class ChargeSubscriptionWorker(
    appContext: Context,
    params: WorkerParameters,
    private val billingDao: BillingDao,
    private val billingApi: BillingApi
) : CoroutineWorker(appContext, params) {

    override suspend fun doWork(): Result = withContext(Dispatchers.IO) {
        val invoiceId = inputData.getString("INVOICE_ID") ?: return@withContext Result.failure()
        val invoice = billingDao.getInvoice(invoiceId) ?: return@withContext Result.failure()

        // 1. Local Precondition Check: Skip if already succeeded before the crash
        if (invoice.status == InvoiceStatus.PAID) {
            return@withContext Result.success()
        }

        try {
            // 2. Server Contract: Pass deterministic idempotency key generated at creation
            val response = billingApi.chargeInvoice(
                idempotencyKey = invoice.idempotencyKey, // UUID generated once when invoice was created
                invoiceId = invoice.id,
                amount = invoice.amountCents
            )

            // 3. Atomic local state transition
            billingDao.markAsPaid(invoiceId, response.transactionReceiptId)
            Result.success()
        } catch (e: IOException) {
            // Network failure or timeout: safe to retry because server caches the idempotencyKey
            Result.retry()
        } catch (e: Exception) {
            Result.failure()
        }
    }
}
```

## Explanation in Arabic

المهمة نُفذت مرتين (Ran Twice) بعد حدوث عطل (Crash). كيف تفرض مبدأ الـ Idempotency المعماري لمنع الآثار الجانبية المكررة؟

1. لماذا تُنفذ المهمة مرتين في أنظمة الموبايل؟
   - WorkManager يضمن الوصول على الأقل مرة واحدة (At-Least-Once Delivery).
   - عندما تنفذ المهمة، يحدث الآتي:
     * الخطوة 1: الـ Worker يرسل طلب الخصم أو حجز المقعد للسيرفر بنجاح.
     * الخطوة 2: السيرفر ينفذ العملية في قاعدة بياناته.
     * الخطوة 3: قبل أن يتمكن الـ Worker من حفظ نتيجة النجاح في قاعدة بيانات WorkManager، تنفد بطارية الهاتف أو يقتل النظام الـ Process (Crash / OOM)!
     * الخطوة 4: عند إعادة فتح الهاتف، يرى WorkManager أن المهمة لم تُسجل كـ SUCCEEDED، فيعيد تشغيلها بالكامل!

2. كيفية فرض الـ Idempotency الكامل (Full Idempotency Enforcement):
   - **فصل محاولة الجدولة (Work Attempt) عن هوية العملية التجارية (Logical Operation ID)**:
     * توليد معرف عملية فريد وثابت (`operationId: UUID`) قبل إرسال أول طلب، وحفظه في Room.
   - **سجل الحالة المزدوج (State Machine in Room)**:
     * الحالات: `DRAFT` -> `SUBMITTING` -> `CONFIRMED` -> `FAILED`.
     * عند إعادة تشغيل الـ Worker، يقرأ الحالة من Room: إذا كانت `CONFIRMED`, ينهي بـ `Result.success()` دون استدعاء السيرفر.
   - **السيرفر هو الحصن المنيع (Server-Side Idempotency Cache)**:
     * السيرفر يخزن الـ `Idempotency-Key` ونتيجة العملية في Redis أو SQL لمدة 24 ساعة.
     * إذا استلم السيرفر نفس المفتاح، يعيد نفس الرد السابق برمز `200 OK` فوراً دون تكرار أي خصم أو إنشاء.

## Practical walkthrough

تنفيذ التحقق المزدوج للـ Idempotency على العميل والسيرفر:
```kotlin
class SafeOrderWorker(context: Context, params: WorkerParameters) : CoroutineWorker(context, params) {

    override suspend fun doWork(): Result {
        val orderId = inputData.getString("order_id") ?: return Result.failure()
        val db = EntryPoints.get(applicationContext, DbEntryPoint::class.java).database()
        val api = EntryPoints.get(applicationContext, ApiEntryPoint::class.java).orderApi()

        val order = db.orderDao().getOrder(orderId) ?: return Result.failure()

        // 1. الفحص المحلي: إذا كانت العملية مسجلة بالفعل كـ CONFIRMED:
        if (order.status == OrderStatus.CONFIRMED) {
            return Result.success() // تم تأكيدها مسبقاً قبل الـ Crash! نجاح فوري
        }

        // 2. إرسال الطلب مع استخدام order.id كمفتاح Idempotency ثابت:
        return try {
            val receipt = api.submitOrder(
                idempotencyKey = order.id,
                request = order.toDto()
            )
            // 3. حفظ التأكيد في Room:
            db.orderDao().updateStatus(orderId, OrderStatus.CONFIRMED, receipt.receiptId)
            Result.success()
        } catch (e: IOException) {
            Result.retry()
        }
    }
}
```

## Why it matters and how it works

Local claim in a transaction can prevent overlapping workers in one database, but cannot know whether remote commit happened. Server idempotency must use operation ID plus payload validation and retention. Business outcome is recorded only from authoritative response/status. Keep an audit log of attempts, not sensitive data.

## Worked example

Conceptual Kotlin worker logic; store/gateway are app-owned, and `status` must distinguish unknown from rejected.

```kotlin
suspend fun execute(id: String, store: OpStore, gateway: Gateway): OpStatus {
    val local = store.status(id)
    if (local == OpStatus.Settled) return local
    val remote = gateway.status(id)
    if (remote == OpStatus.Settled) {
        store.markSettled(id); return remote
    }
    return gateway.submitWithSameKey(id)
}
```

## Trade-offs and decision criteria

Client-side deduplication reduces redundant calls but needs server-side contract for crash and multi-device races. For pure idempotent reads, rerun may be harmless; for payments/reversals, ledger-level uniqueness is mandatory. A status endpoint adds complexity but resolves uncertain outcomes.

## Failure modes

A worker may submit, server settle, then app crash before local update. If next run generates a new key, it duplicates effect. If status endpoint temporarily lags, the worker must preserve Pending rather than mislabel failure.

## Production perspective

A finance app records one reversal ID and amount, sends under the same key, reconciles ledger status and stores receipt. Tests execute Worker twice concurrently and crash at server-commit/local-ack window.

## Interview answer — short

Enforce idempotency by separating the WorkManager retry mechanism from the logical domain mutation. Generate a persistent, deterministic UUID when creating the intent and store it in Room. Pass this UUID as an idempotency key in the remote API header so the backend can detect duplicates and return cached results. Inside the worker, verify local entity state before issuing network requests, returning success immediately if already completed.

## Interview answer — structured

Enforcing idempotency requires recognizing why jobs execute twice and addressing the vulnerability across both client and server layers.
When an app crashes or the system kills a process immediately after a remote mutation succeeds but before the worker commits Result.success, WorkManager interprets the interruption as a task failure and reschedules execution.
To prevent duplicate side effects during the subsequent retry, the architecture must implement a two-step defense.
First, maintain an explicit state machine in the local Room database. The domain entity is created with an initial PENDING status and a persistent, client-generated UUID. When the worker resumes, its first action is querying Room: if the entity is already marked COMPLETED or contains a valid transaction receipt, the worker immediately returns Result.success without making network calls.
Second, establish an idempotent server contract. The worker passes the persisted UUID in the request headers (such as Idempotency-Key). The backend stores this key within a unique constraint table. If the server receives a repeated request with an identical key, it returns the cached result without repeating the business transaction.

## Interview answer — deep senior

Under the hood, the post-crash double execution anomaly illustrates the classic fallacies of distributed computing: network latency, partial failures, and lack of atomic distributed transactions across mobile clients and cloud backends. When a client sends a network request, there are three failure domains: the request was lost before reaching the server, the server crashed during execution, or the response was lost after execution.
Because mobile clients cannot differentiate between these three cases upon a sudden crash, WorkManager's at-least-once model guarantees that the request will be re-attempted.
Senior engineers eliminate double processing risks through rigorous distributed coordination patterns. On the client side, Room transactions ensure that the domain entity and its unique idempotency token are committed before any background worker is enqueued.
On the server side, the backend implements an Idempotency Ledger using Redis or a relational database with a short time-to-live or permanent unique constraint. When the worker retries after an app crash, the server intercepts the incoming Idempotency-Key. If an operation with that key is currently processing, the server returns HTTP 409 (Conflict) or an in-flight status, prompting the worker to retry with backoff. If the operation previously succeeded, the server replays the serialized original response payload with HTTP 200 OK.
Additionally, for operations that cannot easily implement server-side idempotency keys, staff engineers implement distributed status probe queries to verify remote status before attempting a re-execution, ensuring zero duplicate operations occur across arbitrary crashes.

## How to answer in the interview

- **Why:** at-least-once execution threatens side effects.
- **How:** persist ID and enforce dedup on server.
- **Trade-off:** retry availability versus dedup complexity.
- **Failure case:** crash between remote commit and local save.
- **Production solution:** status reconciliation and concurrent retry test.

## Follow-up questions

- **Interviewer:** "What is the difference between an Idempotent API and a Safe API?"
  **Answer:** "A Safe API (like GET) does not alter server state at all; an Idempotent API (like PUT or idempotent POST) can alter state on the first call, but subsequent identical calls produce no additional state changes."

- **Interviewer:** "How long should a server retain an Idempotency Key?"
  **Answer:** "Typically 24 to 72 hours, sufficient to cover all possible mobile network retry windows and device reboots."
