# BG-05

## Original interview question

What are constraints, backoff policies, and unique work?

## What the interviewer evaluates

Explain constraints, backoff and unique work without treating them as idempotency.

## Concept and technical explanation

Constraints, backoff policies, and unique work constitute the core policy configuration mechanisms that govern execution eligibility, error recovery, and deduplication in WorkManager. Constraints define prerequisite system conditions—such as network connectivity (Connected, Unmetered, NotRoaming), charging status, battery not low, storage not low, or device idle—that must be concurrently satisfied for work to run; if constraints break mid-execution, WorkManager halts the worker and reschedules it. Backoff policies govern retry intervals when a worker returns Result.retry(), offering Linear or Exponential backoff algorithms starting from a platform-enforced minimum of 10 seconds. Unique work provides name-based deduplication through enqueueUniqueWork, enforcing ExistingWorkPolicy strategies (KEEP, REPLACE, APPEND, APPEND_OR_REPLACE) to prevent redundant concurrent operations.

## Practical walkthrough (English)

Configuring Constraints, Exponential Backoff, and Unique Work:
```kotlin
// 1. Defining environmental constraints
val constraints = Constraints.Builder()
    .setRequiredNetworkType(NetworkType.UNMETERED) // Wi-Fi only
    .setRequiresCharging(true)                     // Plugged in
    .setRequiresBatteryNotLow(true)                // Above 15-20%
    .build()

// 2. Defining OneTimeWorkRequest with Exponential Backoff
val analyticsRequest = OneTimeWorkRequestBuilder<UploadAnalyticsWorker>()
    .setConstraints(constraints)
    .setBackoffCriteria(
        backoffPolicy = BackoffPolicy.EXPONENTIAL, // Delays double: 30s, 60s, 120s...
        backoffDelay = 30,
        timeUnit = TimeUnit.SECONDS
    )
    .build()

// 3. Enqueuing as Unique Work to prevent duplicate background pipelines
WorkManager.getInstance(context).enqueueUniqueWork(
    "upload_analytics_job",
    ExistingWorkPolicy.KEEP, // If job is already pending or running, keep it and ignore the new request
    analyticsRequest
)
```

## Explanation in Arabic

ما هي قيود النظام (Constraints)، وسياسات التراجع (Backoff Policies)، والعمل الفريد (Unique Work) في WorkManager؟

1. قيود النظام (Constraints):
   - شروط بيئية يجب أن تتوفر في الهاتف ليسمح WorkManager بتشغيل المهمة:
     * `setRequiredNetworkType(NetworkType.CONNECTED / UNMETERED)`: الاتصال بالإنترنت عموماً أو Wi-Fi فقط.
     * `setRequiresCharging(true)`: الهاتف موصول بالشاحن.
     * `setRequiresBatteryNotLow(true)`: البطارية ليست منخفضة (أعلى من 15-20%).
     * `setRequiresDeviceIdle(true)`: الهاتف في وضع الخمول وغير مستخدم.
   - إذا فُقد أي شرط أثناء تشغيل المهمة (مثل فصل الشاحن)، يقوم WorkManager بإيقاف الـ Worker فوراً وإعادة جدولته تلقائياً.

2. سياسات التراجع (Backoff Policies):
   - تحدد كيفية حساب وقت الانتظار قبل إعادة تشغيل المهمة عندما تعيد `Result.retry()`:
     * `BackoffPolicy.LINEAR`: زيادة خطية (مثلاً: 10s ثم 20s ثم 30s).
     * `BackoffPolicy.EXPONENTIAL`: زيادة أسية (مثلاً: 10s ثم 20s ثم 40s ثم 80s حتى حد أقصى 5 ساعات).

3. العمل الفريد (Unique Work):
   - يمنع تكرار جدولة نفس المهمة مراراً وتكراراً عبر تعيين اسم فريد ثابت لها (`"sync_orders"`):
     * `ExistingWorkPolicy.KEEP`: إذا كانت هناك مهمة بنفس الاسم مجدولة أو قيد التنفيذ، احتفظ بها وتجاهل الطلب الجديد.
     * `ExistingWorkPolicy.REPLACE`: ألغِ المهمة القديمة فوراً واستبدلها بالطلب الجديد.
     * `ExistingWorkPolicy.APPEND_OR_REPLACE`: ضع الطلب الجديد في طابور بعد انتهاء القديم.

## Practical walkthrough

تطبيق شامل يجمع Constraints و BackoffPolicy و Unique Work:
```kotlin
fun scheduleDailyBackup(context: Context) {
    // 1. قيود صارمة: شاحن + واي فاي + خمول الجهاز ليلاً:
    val constraints = Constraints.Builder()
        .setRequiredNetworkType(NetworkType.UNMETERED) // Wi-Fi فقط
        .setRequiresCharging(true)                     // موصول بالشاحن
        .setRequiresDeviceIdle(true)                   // المستخدم نائم ولا يستخدم الهاتف
        .build()

    // 2. إعداد الطلب مع Exponential Backoff:
    val backupRequest = OneTimeWorkRequestBuilder<DatabaseBackupWorker>()
        .setConstraints(constraints)
        .setBackoffCriteria(
            backoffPolicy = BackoffPolicy.EXPONENTIAL,
            backoffDelay = 30,
            timeUnit = TimeUnit.SECONDS // تكرار أسي يبدأ من 30 ثانية
        )
        .build()

    // 3. جدولة المهمة كعمل فريد يمنع التكرار:
    WorkManager.getInstance(context).enqueueUniqueWork(
        "database_cloud_backup",
        ExistingWorkPolicy.KEEP, // لو كانت مجدولة مسبقاً، لا تنشئ مهمة مكررة!
        backupRequest
    )
}
```

## Why it matters and how it works

Choose constraints from need, not maximum restrictiveness. Backoff is subject to platform minimums and OS scheduling. Unique work policy changes what happens to pending/existing chain; REPLACE cancels prior work but not external effects already committed. Persist operation state and use server idempotency.

## Worked example

Android example enqueues a unique outbox drain when network is connected; SyncWorker is app-defined.

```kotlin
import androidx.work.*
import java.util.concurrent.TimeUnit

fun enqueueOutbox(manager: WorkManager) {
    val request = OneTimeWorkRequestBuilder<SyncWorker>()
        .setConstraints(Constraints.Builder()
            .setRequiredNetworkType(NetworkType.CONNECTED).build())
        .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 30, TimeUnit.SECONDS)
        .build()
    manager.enqueueUniqueWork("outbox", ExistingWorkPolicy.KEEP, request)
}
```

## Trade-offs and decision criteria

Unmetered-only saves data but can starve urgent sync; CONNECTED is broader. KEEP avoids duplicate pending jobs, REPLACE refreshes scheduling but can cancel in-progress local work. Backoff reduces load but increases latency; monitor stuck operations.

## Failure modes

Using unique work as a substitute for server key fails when worker starts twice after crash. REPLACE may cancel a request after the server received it, leaving uncertain status. Retrying 400 validation errors with backoff never resolves them.

## Production perspective

A notes app drains durable edits when connected, retries transient network failures with exponential backoff, and uses unique work to avoid redundant schedulers. Server deduplicates operation IDs; UI shows Pending age and conflict errors.

## Interview answer — short

Constraints specify prerequisite environmental conditions like network connectivity, charging, and battery levels required for work to execute. Backoff policies determine retry delay schedules using linear or exponential algorithms starting from a minimum of ten seconds when workers return Result.retry. Unique work provides named deduplication using ExistingWorkPolicy modes like KEEP, REPLACE, APPEND, and APPEND_OR_REPLACE to prevent concurrent duplicate jobs.

## Interview answer — structured

WorkManager provides fine-grained operational control over background jobs through constraints, backoff policies, and unique work deduplication.
Constraints specify the environmental prerequisites required before a worker is permitted to run. These include network types (such as requiring unmetered Wi-Fi or non-roaming connections), battery thresholds (requiring the battery not to be low), device charging states, and idle status. If any constraint is violated while a task is running, WorkManager halts the worker and returns it to the queue.
Backoff policies dictate how WorkManager reschedules execution when a worker returns Result.retry(). Developers select between Linear backoff, where delays increase by a fixed duration each attempt, and Exponential backoff, where retry delays double progressively. The minimum allowable backoff delay enforced by the platform is ten seconds.
Unique work prevents duplicate tasks from running simultaneously by associating work requests with a unique string identifier. When enqueuing unique work, developers declare an ExistingWorkPolicy: KEEP preserves existing pending or running work while ignoring new requests; REPLACE cancels existing work to start fresh; APPEND chains new tasks after existing ones; and APPEND_OR_REPLACE guarantees sequential chaining while replacing failed precursors.

## Interview answer — deep senior

Under the hood, these three mechanisms work together to guarantee system resource hygiene and prevent thundering herd problems on backend servers.
When evaluating constraints, WorkManager registers system broadcast receivers and network callbacks with the platform ConnectivityManager. Rather than polling device state continuously, WorkManager sleeps until the operating system signals that all designated constraints are satisfied simultaneously.
For backoff policies, Exponential backoff is the mandatory standard for network operations. If a backend service experiences an outage or rate-limiting threshold (HTTP 429 / 503), linear retries or immediate re-executions cause thousands of mobile clients to hammer the server in lockstep. Exponential backoff naturally spreads client retries across widening windows (e.g., 30s, 60s, 120s, up to a maximum cap of 5 hours), allowing backend services to recover safely.
When configuring unique work, selecting the proper ExistingWorkPolicy directly impacts data integrity. For example, with an offline photo upload queue, using ExistingWorkPolicy.APPEND ensures that user photos upload sequentially in the exact order they were taken without racing each other.
Conversely, for user profile updates or telemetry reporting, ExistingWorkPolicy.REPLACE ensures that the latest user edits overwrite stale pending requests, conserving radio data and avoiding redundant updates.
Staff engineers enforce these policies universally, preventing rogue background tasks from depleting device batteries or overwhelming infrastructure.

## Follow-up questions

- **Interviewer:** "What is the minimum backoff delay in WorkManager?"
  **Answer:** "10 seconds (`WorkRequest.MIN_BACKOFF_MILLIS`). Setting anything lower is automatically clamped to 10 seconds."

- **Interviewer:** "Can constraints include checking for available device storage?"
  **Answer:** "Yes, `setRequiresStorageNotLow(true)` ensures the task only runs when the device has sufficient free flash storage."
