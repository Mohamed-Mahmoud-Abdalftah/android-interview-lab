# BG-05

## Original interview question

What are constraints, backoff policies, and unique work?

## What the interviewer evaluates

Explain constraints, backoff and unique work without treating them as idempotency.

## Explanation in Arabic

ما هي قيود النظام (Constraints)، وسياسات التراجع (Backoff Policies)، والعمل الفريد (Unique Work) في WorkManager؟

1. قيود النظام (Constraints):
   - شروط بيئية يجب أن تتوفر في الهاتف ليسمح WorkManager بتشغيل المهمة:
     * `setRequiredNetworkType(NetworkType.CONNECTED / UNMETERED)`: الاتصال بالإنترنت عموماً أو Wi-Fi فقط.
     * `setRequiresCharging(true)`: الهاتف موصول بالشاحن.
     * `setRequiresBatteryNotLow(true)`: البطارية ليست منخفضة (أعلى من 15-20%).
     * `setRequiresDeviceIdle(true)`: الهاتف في وضع الخمول وغير مستخدم.
   - إذا فُقد أي شرط أثناء تشغيل المهمة (مثل فصل الشاحن)، يقوم WorkManager بإيقاف الـ Worker فوراً وإعادة جدولته تلقائياً.

2. سياسات التراجع (Backoff Policies):
   - تحدد كيفية حساب وقت الانتظار قبل إعادة تشغيل المهمة عندما تعيد `Result.retry()`:
     * `BackoffPolicy.LINEAR`: زيادة خطية (مثلاً: 10s ثم 20s ثم 30s).
     * `BackoffPolicy.EXPONENTIAL`: زيادة أسية (مثلاً: 10s ثم 20s ثم 40s ثم 80s حتى حد أقصى 5 ساعات).

3. العمل الفريد (Unique Work):
   - يمنع تكرار جدولة نفس المهمة مراراً وتكراراً عبر تعيين اسم فريد ثابت لها (`"sync_orders"`):
     * `ExistingWorkPolicy.KEEP`: إذا كانت هناك مهمة بنفس الاسم مجدولة أو قيد التنفيذ، احتفظ بها وتجاهل الطلب الجديد.
     * `ExistingWorkPolicy.REPLACE`: ألغِ المهمة القديمة فوراً واستبدلها بالطلب الجديد.
     * `ExistingWorkPolicy.APPEND_OR_REPLACE`: ضع الطلب الجديد في طابور بعد انتهاء القديم.

## Practical walkthrough

تطبيق شامل يجمع Constraints و BackoffPolicy و Unique Work:
```kotlin
fun scheduleDailyBackup(context: Context) {
    // 1. قيود صارمة: شاحن + واي فاي + خمول الجهاز ليلاً:
    val constraints = Constraints.Builder()
        .setRequiredNetworkType(NetworkType.UNMETERED) // Wi-Fi فقط
        .setRequiresCharging(true)                     // موصول بالشاحن
        .setRequiresDeviceIdle(true)                   // المستخدم نائم ولا يستخدم الهاتف
        .build()

    // 2. إعداد الطلب مع Exponential Backoff:
    val backupRequest = OneTimeWorkRequestBuilder<DatabaseBackupWorker>()
        .setConstraints(constraints)
        .setBackoffCriteria(
            backoffPolicy = BackoffPolicy.EXPONENTIAL,
            backoffDelay = 30,
            timeUnit = TimeUnit.SECONDS // تكرار أسي يبدأ من 30 ثانية
        )
        .build()

    // 3. جدولة المهمة كعمل فريد يمنع التكرار:
    WorkManager.getInstance(context).enqueueUniqueWork(
        "database_cloud_backup",
        ExistingWorkPolicy.KEEP, // لو كانت مجدولة مسبقاً، لا تنشئ مهمة مكررة!
        backupRequest
    )
}
```

## Why it matters and how it works

Choose constraints from need, not maximum restrictiveness. Backoff is subject to platform minimums and OS scheduling. Unique work policy changes what happens to pending/existing chain; REPLACE cancels prior work but not external effects already committed. Persist operation state and use server idempotency.

## Worked example

Android example enqueues a unique outbox drain when network is connected; SyncWorker is app-defined.

```kotlin
import androidx.work.*
import java.util.concurrent.TimeUnit

fun enqueueOutbox(manager: WorkManager) {
    val request = OneTimeWorkRequestBuilder<SyncWorker>()
        .setConstraints(Constraints.Builder()
            .setRequiredNetworkType(NetworkType.CONNECTED).build())
        .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 30, TimeUnit.SECONDS)
        .build()
    manager.enqueueUniqueWork("outbox", ExistingWorkPolicy.KEEP, request)
}
```

## Trade-offs and decision criteria

Unmetered-only saves data but can starve urgent sync; CONNECTED is broader. KEEP avoids duplicate pending jobs, REPLACE refreshes scheduling but can cancel in-progress local work. Backoff reduces load but increases latency; monitor stuck operations.

## Failure modes

Using unique work as a substitute for server key fails when worker starts twice after crash. REPLACE may cancel a request after the server received it, leaving uncertain status. Retrying 400 validation errors with backoff never resolves them.

## Production perspective

A notes app drains durable edits when connected, retries transient network failures with exponential backoff, and uses unique work to avoid redundant schedulers. Server deduplicates operation IDs; UI shows Pending age and conflict errors.

## Interview answer — short

Constraints define execution prerequisites (network, charging, idle). Backoff policies (LINEAR or EXPONENTIAL) govern delay intervals between Result.retry() attempts. Unique Work prevents duplicate task accumulation by identifying jobs via unique string keys under policies like KEEP, REPLACE, or APPEND.

## Interview answer — structured

These three mechanisms govern how WorkManager tasks interact with the operating system, network failures, and redundant invocations.

First, **Execution Constraints (`Constraints`)**. Next, environmental prerequisites checked before launch and continuously monitored during execution.
If a constraint breaks while the worker is actively running (e.g., the user disconnects Wi-Fi mid-upload), WorkManager immediately interrupts the worker and reschedules it. **Retry Backoff Policies (`BackoffPolicy`)**.
Dictates how delay intervals scale after a worker returns `Result.retry()`. `BackoffPolicy.EXPONENTIAL` doubles wait times ($15s, 30s, 60s, ...$ up to 5 hours max), shielding backends from aggressive retry loops.
**Unique Work Management (`enqueueUniqueWork`)**. Deduplicates work requests using a persistent string identifier.
`ExistingWorkPolicy.KEEP`: If work with that key is pending or running, retains the existing instance and ignores the new request. `ExistingWorkPolicy.REPLACE`: Cancels and drops the existing instance, immediately substituting the new request.
Finally, `ExistingWorkPolicy.APPEND_OR_REPLACE`: Queues the new work behind the current task.


## Interview answer — deep senior

Senior engineers recognize that **Unique Work is NOT a substitute for Server Idempotency**.

While `ExistingWorkPolicy.KEEP` guarantees that WorkManager will not maintain two duplicate work specifications in its internal SQLite database, it does **NOT** guarantee that a backend API endpoint won't be called twice. If Worker A sends an HTTP request, the server executes it, and the app crashes before Worker A returns `Result.success()`, WorkManager's retry engine will execute Worker A again upon relaunch! Unique Work manages local scheduling deduplication; backend operations must always be secured with client-generated Idempotency Keys.


## How to answer in the interview

- **Why:** scheduler needs conditions and dedup policy.
- **How:** configure constraints, backoff and unique work.
- **Trade-off:** battery efficiency versus latency.
- **Failure case:** REPLACE cancels in-flight business operation.
- **Production solution:** map policy to state machine and server contract.

## Deep-dive talking points

Trace KEEP/REPLACE while a request is in flight and distinguish scheduler duplicate from effect duplicate.

## Follow-up questions

- **Interviewer:** "What is the minimum backoff delay in WorkManager?"
  **Answer:** "10 seconds (`WorkRequest.MIN_BACKOFF_MILLIS`). Setting anything lower is automatically clamped to 10 seconds."

- **Interviewer:** "Can constraints include checking for available device storage?"
  **Answer:** "Yes, `setRequiresStorageNotLow(true)` ensures the task only runs when the device has sufficient free flash storage."
