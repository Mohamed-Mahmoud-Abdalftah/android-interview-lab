# BG-05

## Original interview question

What are constraints, backoff policies, and unique work?

## What the interviewer evaluates

Explain constraints, backoff and unique work without treating them as idempotency.

## Explanation in Arabic

`Constraints` تقول شغّل لما network/charging/battery conditions مناسبة؛ تحققها قد يؤخر التنفيذ. `BackoffPolicy` يحدد linear أو exponential تأخير بعد `Result.retry()`. `unique work` باسم ثابت وpolicy مثل KEEP/REPLACE يمنع تراكم schedules لنفس المهمة داخل WorkManager، لكنه مش ضمان إن server side effect ما تكررتش. الـWorker تقرأ operation ID محفوظة وتكون repeat-safe.

## Why it matters and how it works

Choose constraints from need, not maximum restrictiveness. Backoff is subject to platform minimums and OS scheduling. Unique work policy changes what happens to pending/existing chain; REPLACE cancels prior work but not external effects already committed. Persist operation state and use server idempotency.

## Worked example

Android example enqueues a unique outbox drain when network is connected; SyncWorker is app-defined.

```kotlin
import androidx.work.*
import java.util.concurrent.TimeUnit

fun enqueueOutbox(manager: WorkManager) {
    val request = OneTimeWorkRequestBuilder<SyncWorker>()
        .setConstraints(Constraints.Builder()
            .setRequiredNetworkType(NetworkType.CONNECTED).build())
        .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 30, TimeUnit.SECONDS)
        .build()
    manager.enqueueUniqueWork("outbox", ExistingWorkPolicy.KEEP, request)
}
```

## Trade-offs and decision criteria

Unmetered-only saves data but can starve urgent sync; CONNECTED is broader. KEEP avoids duplicate pending jobs, REPLACE refreshes scheduling but can cancel in-progress local work. Backoff reduces load but increases latency; monitor stuck operations.

## Failure modes

Using unique work as a substitute for server key fails when worker starts twice after crash. REPLACE may cancel a request after the server received it, leaving uncertain status. Retrying 400 validation errors with backoff never resolves them.

## Production perspective

A notes app drains durable edits when connected, retries transient network failures with exponential backoff, and uses unique work to avoid redundant schedulers. Server deduplicates operation IDs; UI shows Pending age and conflict errors.

## Interview answer — short

“Constraints gate eligible execution, backoff delays retries, and unique work controls duplicate schedules. None guarantees exactly-once remote effects; my worker uses durable IDs and a server idempotency contract.”

## Interview answer — structured

“I set constraints that match the task—connected network for sync, perhaps unmetered for a large backup. A worker returns retry on transient failure, and WorkManager applies a backoff policy rather than a busy loop. Unique work lets me KEEP or REPLACE an existing schedule under a stable name. REPLACE can cancel prior local execution but cannot roll back a request already accepted by the server. I therefore persist each logical operation and deduplicate it on the backend.”

## Interview answer — deep senior

“The scheduling layer and business-effect layer must be reviewed separately. Constraints can postpone work for hours under Doze or user network settings, so the UI reports Pending rather than promised completion time. Backoff is bounded by platform behavior and should match server rate limits; permanent validation/auth errors need a different state. Unique work prevents parallel scheduling chains, but workers can still be retried or restarted and a cancelled worker may have committed remotely. I pass an operation ID, check local acknowledgement, submit under a server key, reconcile ambiguous responses, and instrument attempt count, constraint wait and pending age.”

## Deep-dive talking points

Trace KEEP/REPLACE while a request is in flight and distinguish scheduler duplicate from effect duplicate.
