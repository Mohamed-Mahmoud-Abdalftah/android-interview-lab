# DI-09

## Original interview question

How do you provide Retrofit, Room, and an interface implementation with Hilt?

## What the interviewer evaluates

- Combine third-party `@Provides`, DAO binding, and interface `@Binds` in a correctly scoped graph.
- Separate API client configuration and database lifetime from UI ownership.
- Test release endpoints/migrations and avoid storing secrets in build constants.

## Explanation in Arabic

Hilt لا يستطيع وضع `@Inject constructor` داخل Retrofit أو Room classes لأنها من مكتبات خارجية. اعمل `@Module @InstallIn(SingletonComponent::class)` فيه `@Provides` لبناء `OkHttpClient` ثم `Retrofit` مع base URL وconverter، و`Room.databaseBuilder(applicationContext, AppDatabase::class.java, "app.db")`، وDAO من `db.ordersDao()`. لو `OrdersRepositoryImpl` تملكه وله `@Inject constructor(api, dao)`، استخدم `@Binds` abstract function تربط `OrdersRepository` به. شارك client/database حسب الحاجة بـ`@Singleton`، لكن اختبر المigrations والـinterceptors وendpoint في release؛ DI wiring الصحيح وحده لا يضمن صحة البيانات أو الأمان.

## Why it matters and how it works

Provider methods can call factories on library types and receive their own dependencies from the graph. A Hilt module installed in SingletonComponent makes those bindings visible to descendants. A DAO can be provided from one database instance. An injectable repository implementation can then be delegated behind an interface using `@Binds`. Retrofit suspend service behavior, Room query dispatch, and OkHttp configuration remain the libraries' responsibility; Hilt only assembles them.

## Worked example

Conceptual wiring: `@Provides @Singleton fun database(@ApplicationContext context: Context): AppDatabase = Room.databaseBuilder(context, AppDatabase::class.java, "app.db").build()`; `@Provides fun ordersDao(db: AppDatabase): OrdersDao = db.ordersDao()`; `@Provides fun ordersApi(retrofit: Retrofit): OrdersApi = retrofit.create(OrdersApi::class.java)`; `@Binds abstract fun bindRepository(impl: OrdersRepositoryImpl): OrdersRepository`. These lines are illustrative, not a standalone module: imports, converter/client providers, migrations, abstract module layout, and the actual endpoint are omitted.

## Trade-offs and decision criteria

Singleton database/client avoids repeated expensive construction and supports shared cache/connection pools, but retains memory for the process lifetime. Separate Retrofit clients with qualifiers are justified for different hosts/auth policies. A repository binding via `@Binds` is compact; use `@Provides` if construction requires runtime logic. A test graph can replace API or database modules, but integration tests should still exercise real migrations and serialization.

## Failure modes

Two databases with the same file name or multiple client instances cause inconsistent cache/connection behavior. A Room schema change lacks migration and crashes at startup. A release Retrofit uses staging base URL or logs authorization headers. A DAO method runs blocking work on Main through a wrong adapter. Test with fake server and real Room migration database in an integration layer, then validate release variant graph and network security settings.

## Production perspective

Centralize host and TLS configuration, install qualified clients for distinct backends, and avoid hardcoding secrets. Use one database owner and explicit migrations; expose interfaces to features. Run unit tests with fake repository and integration tests with real Room/Retrofit behavior. Measure startup impact and ensure database creation/initial queries do not block Main.

## Interview answer — short

“I provide third-party Retrofit and Room objects with Hilt `@Provides` methods, provide DAOs from the database, and bind my injectable repository implementation to its interface with `@Binds`.”

## Interview answer — structured

“I install an app-level module into SingletonComponent and provide a configured OkHttp/Retrofit client and Room database through factory methods, because those library types do not expose constructors I can annotate. A DAO provider obtains the DAO from the shared database. My owned repository implementation uses constructor injection, and an abstract `@Binds` method maps its interface. I choose Singleton for expensive shared client/database instances, qualify different backends, and keep UI objects out of those providers. Finally I test release endpoint selection, serialization, Room migrations, and main-safe queries; graph compilation alone proves only that objects can be assembled.”

## Interview answer — deep senior

“I build the graph from the infrastructure boundary inward. An application-scoped module provides a configured OkHttp client, Retrofit instance, and Room database using `@ApplicationContext`; DAOs come from that database. I qualify clients or Retrofit instances when hosts or auth policies differ, so a payment token never accidentally rides a public content client. Owned adapters and repositories use injected constructors; `@Binds` maps the repository port to its implementation without handwritten factory logic. I scope the database and connection-pool client for reuse, while leaving cheap stateless bindings unscoped. Hilt does not validate a base URL, migration strategy, TLS policy, or thread usage semantically. I therefore compile every variant, run fake-server integration tests for headers and serialization, Room migration tests, and a release-like startup test to detect synchronous database work. Session credentials are supplied through a controlled runtime source, not embedded in APK constants.”

## Follow-up questions

- Why use `@Provides` for Retrofit? **Answer:** its construction uses a library builder/factory the app cannot annotate with `@Inject`.
- Why use `@Binds` for repository interface? **Answer:** it delegates the interface to an injectable implementation without custom construction code.
- Does successful Hilt compilation prove a Room migration works? **Answer:** no; schema and migration behavior need database integration tests.
