# DI-09

## Original interview question

How do you provide Retrofit, Room, and an interface implementation with Hilt?

## What the interviewer evaluates

- Combine third-party `@Provides`, DAO binding, and interface `@Binds` in a correctly scoped graph.
- Separate API client configuration and database lifetime from UI ownership.
- Test release endpoints/migrations and avoid storing secrets in build constants.

## Concept and technical explanation

Configuring third-party libraries and domain abstractions in Hilt requires establishing structured module boundaries that combine @Provides and @Binds methodologies. Third-party library types like Retrofit and Room cannot be constructor-injected because developers do not own their source code, requiring concrete provider methods annotated with @Provides inside object modules. In these methods, external builder APIs—such as Retrofit.Builder and Room.databaseBuilder—are executed and supplied with dependencies like OkHttpClient or the application Context. Conversely, domain and data layer abstractions mapping an interface to a concrete repository or data source implementation are declared using abstract methods annotated with @Binds inside abstract modules. This separation of concerns enforces architectural cleanliness, reduces boilerplate, and optimizes generated bytecode.

## Practical walkthrough (English)

End-to-end setup providing Retrofit, Room, and Repository bindings in Hilt:
```kotlin
// 1. Network Module: Provides third-party Retrofit and API interfaces
@Module
@InstallIn(SingletonComponent::class)
object NetworkModule {
    @Provides @Singleton
    fun provideRetrofit(): Retrofit =
        Retrofit.Builder()
            .baseUrl("https://api.example.com/")
            .addConverterFactory(GsonConverterFactory.create())
            .build()

    @Provides @Singleton
    fun provideUserApi(retrofit: Retrofit): UserApi =
        retrofit.create(UserApi::class.java)
}

// 2. Database Module: Provides Room Database and DAO
@Module
@InstallIn(SingletonComponent::class)
object DatabaseModule {
    @Provides @Singleton
    fun provideDatabase(@ApplicationContext context: Context): AppDatabase =
        Room.databaseBuilder(context, AppDatabase::class.java, "app.db").build()

    @Provides
    fun provideUserDao(database: AppDatabase): UserDao =
        database.userDao()
}

// 3. Repository Module: Binds domain interface to concrete implementation with @Inject constructor
@Module
@InstallIn(SingletonComponent::class)
abstract class RepositoryModule {
    @Binds @Singleton
    abstract fun bindUserRepository(impl: UserRepositoryImpl): UserRepository
}
```

## Practical walkthrough

النمط المعماري الكامل لتوفير Retrofit و Room وربط الـ Repository في Hilt:
```kotlin
// 1. Network Module: توفير الـ API Client الخارجي:
@Module
@InstallIn(SingletonComponent::class)
object NetworkModule {
    @Provides @Singleton
    fun provideRetrofit(okHttpClient: OkHttpClient): Retrofit = Retrofit.Builder()
        .baseUrl("https://api.example.com/")
        .client(okHttpClient)
        .addConverterFactory(Json.asConverterFactory("application/json".toMediaType()))
        .build()

    @Provides @Singleton
    fun provideUserApi(retrofit: Retrofit): UserApiService = retrofit.create(UserApiService::class.java)
}

// 2. Database Module: توفير Room و الـ DAOs:
@Module
@InstallIn(SingletonComponent::class)
object DatabaseModule {
    @Provides @Singleton
    fun provideDatabase(@ApplicationContext context: Context): AppDatabase = Room.databaseBuilder(
        context,
        AppDatabase::class.java,
        "app.db"
    ).fallbackToDestructiveMigration().build()

    @Provides
    fun provideUserDao(db: AppDatabase): UserDao = db.userDao()
}

// 3. Repository Module: ربط الـ Interface بالتنفيذ الفعلي عبر @Binds:
@Module
@InstallIn(SingletonComponent::class)
abstract class RepositoryModule {
    @Binds @Singleton
    abstract fun bindUserRepository(impl: UserRepositoryImpl): UserRepository
}
```

## Why it matters and how it works

Provider methods can call factories on library types and receive their own dependencies from the graph. A Hilt module installed in SingletonComponent makes those bindings visible to descendants. A DAO can be provided from one database instance. An injectable repository implementation can then be delegated behind an interface using `@Binds`. Retrofit suspend service behavior, Room query dispatch, and OkHttp configuration remain the libraries' responsibility; Hilt only assembles them.

## Worked example

Conceptual wiring: `@Provides @Singleton fun database(@ApplicationContext context: Context): AppDatabase = Room.databaseBuilder(context, AppDatabase::class.java, "app.db").build()`; `@Provides fun ordersDao(db: AppDatabase): OrdersDao = db.ordersDao()`; `@Provides fun ordersApi(retrofit: Retrofit): OrdersApi = retrofit.create(OrdersApi::class.java)`; `@Binds abstract fun bindRepository(impl: OrdersRepositoryImpl): OrdersRepository`. These lines are illustrative, not a standalone module: imports, converter/client providers, migrations, abstract module layout, and the actual endpoint are omitted.

### Kotlin / Hilt example

Assume `AppDb` is the app's Room database and `Store` is an app contract. The snippet focuses on binding construction; real Room entities, DAOs, migrations, and Retrofit converters are configured separately.

```kotlin
import android.content.Context
import androidx.room.Database
import androidx.room.Entity
import androidx.room.PrimaryKey
import androidx.room.Room
import androidx.room.RoomDatabase
import dagger.Binds
import dagger.Module
import dagger.Provides
import dagger.hilt.InstallIn
import dagger.hilt.android.qualifiers.ApplicationContext
import dagger.hilt.components.SingletonComponent
import javax.inject.Inject
import javax.inject.Singleton
import retrofit2.Retrofit

@Entity data class CacheRow(@PrimaryKey val id: String)
@Database(entities = [CacheRow::class], version = 1)
abstract class AppDb : RoomDatabase()
interface Store
class RoomStore @Inject constructor(val db: AppDb) : Store

@Module
@InstallIn(SingletonComponent::class)
abstract class StoreBindings {
    @Binds abstract fun bindStore(impl: RoomStore): Store
}

@Module
@InstallIn(SingletonComponent::class)
object DataProviders {
    @Provides @Singleton
    fun database(@ApplicationContext context: Context): AppDb =
        Room.databaseBuilder(context, AppDb::class.java, "app.db").build()

    @Provides @Singleton
    fun retrofit(): Retrofit = Retrofit.Builder()
        .baseUrl("https://api.example.org/")
        .build()
}
```

## Trade-offs and decision criteria

Singleton database/client avoids repeated expensive construction and supports shared cache/connection pools, but retains memory for the process lifetime. Separate Retrofit clients with qualifiers are justified for different hosts/auth policies. A repository binding via `@Binds` is compact; use `@Provides` if construction requires runtime logic. A test graph can replace API or database modules, but integration tests should still exercise real migrations and serialization.

## Failure modes

Two databases with the same file name or multiple client instances cause inconsistent cache/connection behavior. A Room schema change lacks migration and crashes at startup. A release Retrofit uses staging base URL or logs authorization headers. A DAO method runs blocking work on Main through a wrong adapter. Test with fake server and real Room migration database in an integration layer, then validate release variant graph and network security settings.

## Production perspective

Centralize host and TLS configuration, install qualified clients for distinct backends, and avoid hardcoding secrets. Use one database owner and explicit migrations; expose interfaces to features. Run unit tests with fake repository and integration tests with real Room/Retrofit behavior. Measure startup impact and ensure database creation/initial queries do not block Main.

## Interview answer — short

Provide Retrofit and Room via @Provides methods in SingletonComponent object modules using their respective builder APIs, injecting the ApplicationContext and shared OkHttpClient. Extract DAOs and API interfaces through focused @Provides methods. For domain interfaces, map the interface to its @Inject-annotated concrete implementation using an abstract method annotated with @Binds inside an abstract module for maximum bytecode efficiency.

## Interview answer — structured

Configuring networking, local persistence, and repository bindings in Hilt follows a clean, standardized three-tier module architecture.
For networking, developers declare an object module installed in SingletonComponent. Inside, a @Provides method configures and returns the Retrofit singleton using Retrofit.Builder, attaching serialization converters and HTTP clients. A subsequent @Provides method accepts the Retrofit instance and calls create() to return the API interface.
For local persistence with Room, another SingletonComponent object module uses Room.databaseBuilder. The builder receives Hilt's pre-bound @ApplicationContext and the database class to construct the database singleton. Individual DAOs are exposed through lightweight @Provides methods that invoke the database abstract getter methods.
For domain abstractions, developers construct an abstract module installed in SingletonComponent. Because the concrete repository implementation utilizes @Inject on its constructor, it does not need a builder. Instead, developers declare an abstract @Binds method taking the concrete repository and returning the domain interface. This separation ensures third-party builder logic remains isolated from lightweight interface delegation.

## Interview answer — deep senior

Under the hood, this tripartite module architecture reflects the fundamental design philosophy of Hilt: separating factory instantiation from interface mapping to maximize compile-time efficiency and runtime performance.
When configuring Room, using @ApplicationContext is critical. Passing an Activity context into Room.databaseBuilder leaks the Activity instance for the lifetime of the application process. Hilt's built-in @ApplicationContext qualifier guarantees that only the process-level context is bound.
Furthermore, separating the database module from DAO provider methods allows DAOs to be injected directly into repositories without exposing the entire Room database instance, adhering strictly to the Principle of Least Privilege.
For Retrofit, senior engineers always decouple OkHttpClient configuration into a dedicated provider method. This allows attaching logging interceptors, SSL pinning certificates, and authentication token refresh authenticators independently before injecting the client into Retrofit.
Regarding repository bindings, utilizing an abstract module with @Binds instead of an object module with @Provides eliminates the generation of an unnecessary intermediate Factory class. The concrete repository is instantiated directly by Dagger and bound to the interface symbol inside the internal dependency table, maintaining a slim method count in the final DEX binary and accelerating compilation speed.
Staff engineers structure these bindings across dedicated Gradle library modules so that database drivers and HTTP protocol engines remain completely hidden from UI presentation layers. This separation enforces strict compilation firewalls, improves incremental caching in CI pipelines, and guarantees that unit tests can mock repository interfaces without dragging heavyweight Android database binaries into test execution environments.

## How to answer in the interview

- **How:** Provides Retrofit/Room, Binds repository.

- **Failure case:** Activity Context leak or wrong endpoint.
- **Production solution:** migration and release binding tests.

## Follow-up questions

- **Interviewer:** "Why should you inject the DAO instead of the RoomDatabase into a Repository?"
  **Answer:** "Interface Segregation: Repositories should only know about their specific database operations, not the entire database lifecycle or other unrelated DAOs."

- **Interviewer:** "What is the danger of missing `@Singleton` on the RoomDatabase provider?"
  **Answer:** "Every consumer creates a new RoomDatabase instance, spawning multiple SQLite connection pools, wasting memory and risking database locking errors."
