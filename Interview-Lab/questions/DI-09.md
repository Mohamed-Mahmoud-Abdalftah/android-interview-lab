# DI-09

## Original interview question

How do you provide Retrofit, Room, and an interface implementation with Hilt?

## What the interviewer evaluates

- Combine third-party `@Provides`, DAO binding, and interface `@Binds` in a correctly scoped graph.
- Separate API client configuration and database lifetime from UI ownership.
- Test release endpoints/migrations and avoid storing secrets in build constants.

## Concept and technical explanation

Hilt needs a binding for each requested type. Use an `@Provides` method when construction needs executable code, as with `Retrofit.Builder`, `Room.databaseBuilder`, or `retrofit.create(Api::class.java)`. Use `@Binds` for a one-parameter mapping from an already available implementation binding to an assignable interface. The implementation may come from `@Inject` construction or another binding; `@Inject` is common, not a requirement of `@Binds` itself. Install a module in a component that can see its dependencies. Scope a binding only if consumers need the same instance within that component; `@InstallIn(SingletonComponent::class)` alone does not make all provisions singletons. Use `@ApplicationContext` for a process-level Room database.

## Practical walkthrough (English)

End-to-end setup providing Retrofit, Room, and Repository bindings in Hilt:
```kotlin
// 1. Network Module: Provides third-party Retrofit and API interfaces
@Module
@InstallIn(SingletonComponent::class)
object NetworkModule {
    @Provides @Singleton
    fun provideClient(): OkHttpClient = OkHttpClient.Builder().build()

    @Provides @Singleton
    fun provideRetrofit(client: OkHttpClient): Retrofit =
        Retrofit.Builder()
            .client(client)
            .baseUrl("https://api.example.com/")
            .addConverterFactory(GsonConverterFactory.create())
            .build()

    @Provides @Singleton
    fun provideUserApi(retrofit: Retrofit): UserApi =
        retrofit.create(UserApi::class.java)
}

// 2. Database Module: Provides Room Database and DAO
@Module
@InstallIn(SingletonComponent::class)
object DatabaseModule {
    @Provides @Singleton
    fun provideDatabase(@ApplicationContext context: Context): AppDatabase =
        Room.databaseBuilder(context, AppDatabase::class.java, "app.db").build()

    @Provides
    fun provideUserDao(database: AppDatabase): UserDao =
        database.userDao()
}

// 3. Repository Module: Binds domain interface to concrete implementation with @Inject constructor
@Module
@InstallIn(SingletonComponent::class)
abstract class RepositoryModule {
    @Binds @Singleton
    abstract fun bindUserRepository(impl: UserRepositoryImpl): UserRepository
}
```

## Explanation in Arabic

لو Hilt محتاج `Retrofit` أو `RoomDatabase`، بنكتب `@Provides` لأن الإنشاء محتاج `Builder` أو استدعاء factory من مكتبة مش بنملك constructor بتاعها. `Retrofit` بياخد `OkHttpClient` لو وفرناه في graph، وواجهة API بتيجي من `retrofit.create(...)`. قاعدة Room طويلة العمر تتبني بـ `@ApplicationContext`.

لو عندك `UserRepositoryImpl` وعايزه يظهر للمستهلكين كـ `UserRepository`، `@Binds` مناسبة لو فيه binding متاح للتنفيذ. غالباً التنفيذ عليه `@Inject constructor`، لكن ممكن يتوفر بطريقة تانية. ربط الواجهة نفسه abstract method بمعامل واحد ونوع رجوع قابل للإسناد.

`@InstallIn(SingletonComponent::class)` يحدد مكان إتاحة الـbinding، **مش معناه إن كل binding Singleton**. حط `@Singleton` فقط على اللي لازم يتشارك طول عمر component، زي قاعدة البيانات غالباً. DAO ممكن توفره من `database.userDao()` وتحقنه مباشرة في repository. المثال يوضح شكل الربط؛ نسخة Android الفعلية محتاجة أنواع Room/Retrofit وتعريفات API موجودة.

## Practical walkthrough

في تطبيق مستخدمين، ابني `OkHttpClient` و`Retrofit` في `NetworkModule`، وخلّي provider الـRetrofit ياخد client كمعامل. ابني `AppDatabase` مرة واحدة داخل `SingletonComponent` بـ `@ApplicationContext`، وبعدها وفر `UserDao` من `database.userDao()`. اربط `UserRepositoryImpl` بالواجهة عبر `@Binds` لو التنفيذ متاح للـgraph.

اختبر graph بعد كتابة التعريفات الحقيقية؛ مثال الـMarkdown وحده مش مشروع Android قابل للبناء. لو شلت `@Singleton` من provider قاعدة البيانات، Dagger هيقدر ينشئ قاعدة جديدة مع كل طلب للـbinding غير scoped، وده غالباً غير مرغوب. ولو استخدمت Activity context في بناء مورد طويل العمر بطريقة يدوية، ممكن تحتفظ بالشاشة بعد تدميرها.

## Why it matters and how it works

Provider methods can call factories on library types and receive their own dependencies from the graph. A Hilt module installed in SingletonComponent makes those bindings visible to descendants. A DAO can be provided from one database instance. An injectable repository implementation can then be delegated behind an interface using `@Binds`. Retrofit suspend service behavior, Room query dispatch, and OkHttp configuration remain the libraries' responsibility; Hilt only assembles them.

## Worked example

Conceptual wiring: `@Provides @Singleton fun database(@ApplicationContext context: Context): AppDatabase = Room.databaseBuilder(context, AppDatabase::class.java, "app.db").build()`; `@Provides fun ordersDao(db: AppDatabase): OrdersDao = db.ordersDao()`; `@Provides fun ordersApi(retrofit: Retrofit): OrdersApi = retrofit.create(OrdersApi::class.java)`; `@Binds abstract fun bindRepository(impl: OrdersRepositoryImpl): OrdersRepository`. These lines are illustrative, not a standalone module: imports, converter/client providers, migrations, abstract module layout, and the actual endpoint are omitted.

### Kotlin / Hilt example

Assume `AppDb` is the app's Room database and `Store` is an app contract. The snippet focuses on binding construction; real Room entities, DAOs, migrations, and Retrofit converters are configured separately.

```kotlin
import android.content.Context
import androidx.room.Database
import androidx.room.Entity
import androidx.room.PrimaryKey
import androidx.room.Room
import androidx.room.RoomDatabase
import dagger.Binds
import dagger.Module
import dagger.Provides
import dagger.hilt.InstallIn
import dagger.hilt.android.qualifiers.ApplicationContext
import dagger.hilt.components.SingletonComponent
import javax.inject.Inject
import javax.inject.Singleton
import retrofit2.Retrofit

@Entity data class CacheRow(@PrimaryKey val id: String)
@Database(entities = [CacheRow::class], version = 1)
abstract class AppDb : RoomDatabase()
interface Store
class RoomStore @Inject constructor(val db: AppDb) : Store

@Module
@InstallIn(SingletonComponent::class)
abstract class StoreBindings {
    @Binds abstract fun bindStore(impl: RoomStore): Store
}

@Module
@InstallIn(SingletonComponent::class)
object DataProviders {
    @Provides @Singleton
    fun database(@ApplicationContext context: Context): AppDb =
        Room.databaseBuilder(context, AppDb::class.java, "app.db").build()

    @Provides @Singleton
    fun retrofit(): Retrofit = Retrofit.Builder()
        .baseUrl("https://api.example.org/")
        .build()
}
```

## Trade-offs and decision criteria

Singleton database/client avoids repeated expensive construction and supports shared cache/connection pools, but retains memory for the process lifetime. Separate Retrofit clients with qualifiers are justified for different hosts/auth policies. A repository binding via `@Binds` is compact; use `@Provides` if construction requires runtime logic. A test graph can replace API or database modules, but integration tests should still exercise real migrations and serialization.

## Failure modes

Two databases with the same file name or multiple client instances cause inconsistent cache/connection behavior. A Room schema change lacks migration and crashes at startup. A release Retrofit uses staging base URL or logs authorization headers. A DAO method runs blocking work on Main through a wrong adapter. Test with fake server and real Room migration database in an integration layer, then validate release variant graph and network security settings.

## Production perspective

Centralize host and TLS configuration, install qualified clients for distinct backends, and avoid hardcoding secrets. Use one database owner and explicit migrations; expose interfaces to features. Run unit tests with fake repository and integration tests with real Room/Retrofit behavior. Measure startup impact and ensure database creation/initial queries do not block Main.

## Interview answer — short

Provide Retrofit and Room with `@Provides` methods because their builders need executable code. Build a process-level Room database with `@ApplicationContext`, and expose a DAO or Retrofit API through provider methods. Bind an available repository implementation to its interface with a one-parameter `@Binds` method. `@InstallIn(SingletonComponent)` makes bindings visible to descendants; `@Singleton` on an individual binding controls shared instance identity.

## Interview answer — structured

I create provider methods for third-party construction: an OkHttp client, Retrofit configured with that client, the API proxy from `retrofit.create`, a Room database using `@ApplicationContext`, and its DAO. These methods execute code, so `@Provides` is appropriate. A repository implementation that already has a binding can be exposed as its interface by an abstract `@Binds` method with one assignable parameter.

The module's `@InstallIn` chooses component visibility; it does not scope every binding. I use `@Singleton` only where a shared process-level instance is required, normally for the database and deliberately shared HTTP client. I keep network/database dependencies behind narrower repository APIs and verify the graph with a real Android integration build. The snippets are illustrative until all app-defined types and test setup exist.

## Interview answer — deep senior

Hilt's graph distinguishes constructing a value from mapping one binding key to another. `@Provides` executes a method body, so it fits Retrofit builders, Room database builders, and Retrofit-generated API proxies. `@Binds` is an abstract, single-parameter mapping when the implementation type is already bound and assignable to the return type. Constructor injection is a typical source of that implementation but not a syntactic requirement of `@Binds`.

`@InstallIn` controls component visibility. A binding in `SingletonComponent` is available to descendants, but it is unscoped unless annotated with `@Singleton`; a scoped binding is shared within one component instance. A Room database usually needs one process-level instance, built with `@ApplicationContext`. A DAO provider can expose a narrow dependency without passing the entire database to every repository. Whether the DAO provider itself needs a scope depends on its contract and Room's accessor behavior; do not infer it from the module's installation location.

Use a shared OkHttp client when its configuration and lifecycle should be common, but keep interceptors, authentication, and logging decisions explicit. Avoid claiming a particular generated-factory count or cold-start benefit for `@Binds` without inspecting the actual generated code and build. This is an architectural example; it has not been compiled as a complete Android application and needs concrete API, database, and repository definitions.

## How to answer in the interview

- **Why:** Third-party builders and interface aliases require different binding declarations.
- **How:** Use `@Provides` for executable construction and `@Binds` for a one-parameter alias of an available implementation binding.
- **Scope:** Explain that `@InstallIn` selects visibility while `@Singleton` selects reuse within one SingletonComponent.
- **Failure case:** An unscoped Room provider can construct multiple database instances; a manually passed Activity context can be retained.
- **Evidence:** Android compilation and integration tests are needed for a full app; this source example is not a device result.

## Deep-dive talking points

Discuss library factories, DAO from database, port binding, scope/qualifiers, migrations, variant endpoint, and main safety.

## Follow-up questions

- **Interviewer:** "Does installing a module in SingletonComponent make every binding a singleton?"
  **Answer:** "No. Installation determines where a binding is visible. Only bindings with a matching scope such as `@Singleton` are reused for that component instance."

- **Interviewer:** "Does @Binds require an @Inject constructor?"
  **Answer:** "It requires an available binding for its single implementation parameter. `@Inject constructor` is a common way to provide that binding, but a provider method can supply it too."

- **Interviewer:** "Why inject a DAO rather than the whole RoomDatabase?"
  **Answer:** "It gives the repository the narrower API it uses. The database still owns the DAO; it is a design boundary, not a special performance guarantee."
