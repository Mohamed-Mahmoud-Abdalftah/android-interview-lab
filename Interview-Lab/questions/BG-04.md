# BG-04

## Original interview question

What are Worker, CoroutineWorker, and ListenableWorker?

## What the interviewer evaluates

Choose Worker, CoroutineWorker or ListenableWorker by execution model and cancellation integration.

## Explanation in Arabic

المقارنة الفنية بين أنواع الـ Workers في WorkManager:
`Worker`، و `CoroutineWorker`، و `ListenableWorker`، ومتى تستخدم كلاً منها؟

1. `Worker` (الكلاس الأساسي المتزامن):
   - **كيف يعمل**: يوفر دالة متزامنة `doWork(): Result` تعمل على خيط خلفي (Background Thread) يوفره الـ `Configuration.executor` الخاص بـ WorkManager.
   - **متى يُستخدم**: للمهام المتزامنة القديمة في مشاريع Java، أو لمهام الحسابات الرياضية المباشرة وحجب الخيوط القصير (Blocking IO) دون الحاجة لـ Coroutines.

2. `CoroutineWorker` (المعيار الذهبي في Kotlin):
   - **كيف يعمل**: يوفر دالة تعليق غير متزامنة `suspend fun doWork(): Result`.
   - **المميزات الخارقة**:
     * يدمج مباشرة مع Kotlin Coroutines والـ Structured Concurrency.
     * يعمل افتراضياً على `Dispatchers.Default` (ويمكن تبديله لـ `Dispatchers.IO`).
     * **دعم تلقائي للإلغاء التعاوني (Cooperative Cancellation)**: إذا ألغى النظام المهمة بسبب فقدان شرط الشبكة أو قيود البطارية، يتم إلغاء الـ Coroutine تلقائياً وإطلاق `CancellationException`، مما يتيح إغلاق الملفات والاتصالات فوراً في كتل `finally` أو `invokeOnCancellation`.
   - **متى يُستخدم**: في 99% من تطبيقات Kotlin الحديثة لاستدعاء دوال الـ Repositories والـ Suspending APIs.

3. `ListenableWorker` (الكلاس الأساسي المنخفض المستوى - Base Class):
   - **كيف يعمل**: الكلاس الجذري الذي يرث منه `Worker` و `CoroutineWorker`. يعيد `ListenableFuture<Result>` من مكتبة Guava.
   - **متى يُستخدم**: إذا كنت تبني إطار عمل مخصصاً، أو تدمج مع مكتبات خارجية تعتمد على كائنات الـ Future (مثل RxJava عبر `RxWorker` أو Guava).

## Practical walkthrough

التطبيق المعياري لـ CoroutineWorker مع دعم الإلغاء التعاوني النظيف:
```kotlin
@HiltWorker
class DownloadReportWorker @AssistedInject constructor(
    @Assisted context: Context,
    @Assisted params: WorkerParameters,
    private val reportApi: ReportApiService,
    private val reportStorage: ReportFileStorage
) : CoroutineWorker(context, params) {

    override suspend fun doWork(): Result {
        // تبديل الـ Dispatcher إلى IO لمعالجة الملفات والشبكة:
        return withContext(Dispatchers.IO) {
            try {
                val reportData = reportApi.downloadReport(reportId = inputData.getString("report_id")!!)
                reportStorage.saveReport(reportData)
                Result.success()
            } catch (e: CancellationException) {
                // التعامل مع الإلغاء إذا سحب النظام الصلاحية أو انقطعت الشبكة:
                reportStorage.deletePartialDownload()
                throw e // يجب إعادة إطلاق CancellationException ليعلم WorkManager بالإلغاء
            } catch (e: IOException) {
                Result.retry()
            }
        }
    }
}
```

## Why it matters and how it works

Worker subclasses return Result.success/failure/retry. CoroutineWorker cancellation is cooperative; a blocking SDK may ignore it. ListenableWorker must complete its Future/callback correctly and handle stop. Keep long-running user-visible work and foreground notification requirements separate from subclass choice.

## Worked example

Android illustration assumes `OutboxRepository` is injected via WorkerFactory/Hilt integration and reads durable operations.

```kotlin
import android.content.Context
import androidx.work.CoroutineWorker
import androidx.work.WorkerParameters

class SyncWorker(
    context: Context,
    params: WorkerParameters,
    private val repository: OutboxRepository,
) : CoroutineWorker(context, params) {
    override suspend fun doWork(): Result = repository.syncPending()
}
```

## Trade-offs and decision criteria

CoroutineWorker is natural for suspend APIs but requires DI configuration and cancellation-aware repository code. Worker is simple for synchronous calls but ties up a thread. ListenableWorker supports callbacks yet adds completion/cancellation complexity.

## Failure modes

Calling a blocking SDK inside CoroutineWorker without dispatcher/interrupt handling still blocks its thread. Returning success before an async callback completes loses work. Returning retry for permanent validation failure loops indefinitely.

## Production perspective

An outbox worker uses CoroutineWorker to call suspend Room/network APIs and returns retry only for transient errors. It stores per-operation status and uses stable keys so a repeated worker run is safe. Tests cover stop/retry and 401 refresh.

## Interview answer — short

Worker is a synchronous Java-friendly worker running on a background executor. CoroutineWorker is the modern Kotlin standard providing a suspending doWork() on Dispatchers.Default with cooperative coroutine cancellation. ListenableWorker is the low-level base class returning a ListenableFuture, ideal for custom future or RxJava (RxWorker) integrations.

## Interview answer — structured

WorkManager exposes three worker abstractions tailored to different execution models and language idioms:

1. **`CoroutineWorker` (Modern Kotlin Standard)**:
   - Exposes `suspend fun doWork(): Result` running by default on `Dispatchers.Default`.
   - Native integration with structured concurrency and Kotlin suspension points.
   - **Automatic Cancellation Propagation**: When WorkManager stops work (due to unmet constraints or explicit cancellation), it cancels the underlying `Job`. Suspending functions throw `CancellationException`, enabling immediate resource cleanup.
   - This is the default choice for virtually all modern Android codebases.

2. **`Worker` (Synchronous Worker)**:
   - Exposes synchronous `doWork(): Result` executed on a background thread pool managed by WorkManager's `Configuration.executor`.
   - Intended for synchronous blocking tasks or legacy Java codebases.

3. **`ListenableWorker` (Low-Level Root Primitive)**:
   - The abstract base class that both `Worker` and `CoroutineWorker` extend under the hood. Returns a Guava `ListenableFuture<Result>`.
   - Reserved for custom concurrency adapters or RxJava integration (`RxWorker`).

## Interview answer — deep senior

A critical pitfall in `CoroutineWorker` cancellation is **Swallowing the `CancellationException`**:

```kotlin
// ❌ ANTI-PATTERN:
try {
    repository.uploadLargeFile()
    Result.success()
} catch (e: Exception) { // Catches CancellationException!
    Result.failure() // Reports failure instead of clean cancellation!
}
```
If an unconstrained `catch (e: Exception)` catches Kotlin's `CancellationException`, WorkManager considers the job terminated with `Result.failure()` rather than stopped due to an unmet constraint. Always re-throw `CancellationException` or use `catch (e: IOException)` to ensure WorkManager knows the task was stopped by the system and can re-enqueue it when constraints recover.

## How to answer in the interview

- **Why:** worker type controls async contract.
- **How:** match sync, suspend or callback API.
- **Trade-off:** simplicity versus adapter complexity.
- **Failure case:** cancellation swallowed then side effect repeats.
- **Production solution:** delegate to repository and test stop/retry.

## Deep-dive talking points

Compare execution style, stop behavior, completion signal and business idempotency.

## Follow-up questions

- **Interviewer:** "How do you inspect the reason why a worker was cancelled?"
  **Answer:** "On Android 12+, call `getStopReason()` inside the worker to determine if it stopped due to timeout, constraint loss, or user cancellation."

- **Interviewer:** "Can you inject dependencies into a CoroutineWorker with Hilt?"
  **Answer:** "Yes, using `@HiltWorker` and `@AssistedInject` on the constructor, combined with `HiltWorkerFactory` configured in the Application class."
