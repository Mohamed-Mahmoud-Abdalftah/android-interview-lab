# BG-04

## Original interview question

What are Worker, CoroutineWorker, and ListenableWorker?

## What the interviewer evaluates

Choose Worker, CoroutineWorker or ListenableWorker by execution model and cancellation integration.

## Concept and technical explanation

Worker, CoroutineWorker, and ListenableWorker represent the three fundamental implementation abstractions provided by WorkManager for authoring background operations. ListenableWorker serves as the foundational base class for all background tasks; it defines startWork(), which returns a ListenableFuture<Result> to support arbitrary asynchronous execution, making it the primary choice for Java codebases and RxJava integrations (via RxWorker). Worker is a synchronous subclass of ListenableWorker that executes its doWork() method on a dedicated background thread provided by WorkManager's background executor, blocking that thread until completion. CoroutineWorker is the idiomatic, Kotlin-first subclass of ListenableWorker; it provides a suspending doWork() function that executes within a CoroutineScope on Dispatchers.Default by default, seamlessly propagating WorkManager cancellation to Kotlin coroutine jobs and supporting structured concurrency and cooperative cancellation.

## Practical walkthrough (English)

Implementing synchronous Worker versus suspending CoroutineWorker:
```kotlin
// 1. Worker: Synchronous blocking implementation (Java / legacy compatibility)
class SyncDataWorker(context: Context, params: WorkerParameters) : Worker(context, params) {
    override fun doWork(): Result {
        // Blocks the background executor thread directly
        val response = httpUrlConnectionFetch()
        return if (response.isSuccess) Result.success() else Result.retry()
    }
}

// 2. CoroutineWorker: Idiomatic Kotlin suspending worker with cooperative cancellation
class SuspendingDownloadWorker(
    context: Context,
    params: WorkerParameters,
    private val api: DownloadApi,
    private val ioDispatcher: CoroutineDispatcher = Dispatchers.IO
) : CoroutineWorker(context, params) {

    override suspend fun doWork(): Result = withContext(ioDispatcher) {
        try {
            // Emits progress reactively to WorkInfo observers
            setProgress(workDataOf("percent" to 50))
            api.downloadLargeFile() // Suspending call: automatically cancels if WorkManager stops work!
            Result.success()
        } catch (e: CancellationException) {
            // WorkManager stopped this worker: handle cooperative cleanup
            throw e
        } catch (e: Exception) {
            Result.retry()
        }
    }
}
```

## Explanation in Arabic

المقارنة الفنية بين أنواع الـ Workers في WorkManager:
`Worker`، و `CoroutineWorker`، و `ListenableWorker`، ومتى تستخدم كلاً منها؟

1. `Worker` (الكلاس الأساسي المتزامن):
   - **كيف يعمل**: يوفر دالة متزامنة `doWork(): Result` تعمل على خيط خلفي (Background Thread) يوفره الـ `Configuration.executor` الخاص بـ WorkManager.
   - **متى يُستخدم**: للمهام المتزامنة القديمة في مشاريع Java، أو لمهام الحسابات الرياضية المباشرة وحجب الخيوط القصير (Blocking IO) دون الحاجة لـ Coroutines.

2. `CoroutineWorker` (المعيار الذهبي في Kotlin):
   - **كيف يعمل**: يوفر دالة تعليق غير متزامنة `suspend fun doWork(): Result`.
   - **المميزات الخارقة**:
     * يدمج مباشرة مع Kotlin Coroutines والـ Structured Concurrency.
     * يعمل افتراضياً على `Dispatchers.Default` (ويمكن تبديله لـ `Dispatchers.IO`).
     * **دعم تلقائي للإلغاء التعاوني (Cooperative Cancellation)**: إذا ألغى النظام المهمة بسبب فقدان شرط الشبكة أو قيود البطارية، يتم إلغاء الـ Coroutine تلقائياً وإطلاق `CancellationException`، مما يتيح إغلاق الملفات والاتصالات فوراً في كتل `finally` أو `invokeOnCancellation`.
   - **متى يُستخدم**: في 99% من تطبيقات Kotlin الحديثة لاستدعاء دوال الـ Repositories والـ Suspending APIs.

3. `ListenableWorker` (الكلاس الأساسي المنخفض المستوى - Base Class):
   - **كيف يعمل**: الكلاس الجذري الذي يرث منه `Worker` و `CoroutineWorker`. يعيد `ListenableFuture<Result>` من مكتبة Guava.
   - **متى يُستخدم**: إذا كنت تبني إطار عمل مخصصاً، أو تدمج مع مكتبات خارجية تعتمد على كائنات الـ Future (مثل RxJava عبر `RxWorker` أو Guava).

## Practical walkthrough

التطبيق المعياري لـ CoroutineWorker مع دعم الإلغاء التعاوني النظيف:
```kotlin
@HiltWorker
class DownloadReportWorker @AssistedInject constructor(
    @Assisted context: Context,
    @Assisted params: WorkerParameters,
    private val reportApi: ReportApiService,
    private val reportStorage: ReportFileStorage
) : CoroutineWorker(context, params) {

    override suspend fun doWork(): Result {
        // تبديل الـ Dispatcher إلى IO لمعالجة الملفات والشبكة:
        return withContext(Dispatchers.IO) {
            try {
                val reportData = reportApi.downloadReport(reportId = inputData.getString("report_id")!!)
                reportStorage.saveReport(reportData)
                Result.success()
            } catch (e: CancellationException) {
                // التعامل مع الإلغاء إذا سحب النظام الصلاحية أو انقطعت الشبكة:
                reportStorage.deletePartialDownload()
                throw e // يجب إعادة إطلاق CancellationException ليعلم WorkManager بالإلغاء
            } catch (e: IOException) {
                Result.retry()
            }
        }
    }
}
```

## Why it matters and how it works

Worker subclasses return Result.success/failure/retry. CoroutineWorker cancellation is cooperative; a blocking SDK may ignore it. ListenableWorker must complete its Future/callback correctly and handle stop. Keep long-running user-visible work and foreground notification requirements separate from subclass choice.

## Worked example

Android illustration assumes `OutboxRepository` is injected via WorkerFactory/Hilt integration and reads durable operations.

```kotlin
import android.content.Context
import androidx.work.CoroutineWorker
import androidx.work.WorkerParameters

class SyncWorker(
    context: Context,
    params: WorkerParameters,
    private val repository: OutboxRepository,
) : CoroutineWorker(context, params) {
    override suspend fun doWork(): Result = repository.syncPending()
}
```

## Trade-offs and decision criteria

CoroutineWorker is natural for suspend APIs but requires DI configuration and cancellation-aware repository code. Worker is simple for synchronous calls but ties up a thread. ListenableWorker supports callbacks yet adds completion/cancellation complexity.

## Failure modes

Calling a blocking SDK inside CoroutineWorker without dispatcher/interrupt handling still blocks its thread. Returning success before an async callback completes loses work. Returning retry for permanent validation failure loops indefinitely.

## Production perspective

An outbox worker uses CoroutineWorker to call suspend Room/network APIs and returns retry only for transient errors. It stores per-operation status and uses stable keys so a repeated worker run is safe. Tests cover stop/retry and 401 refresh.

## Interview answer — short

ListenableWorker is the core base class returning a ListenableFuture for custom asynchronous execution. Worker is a synchronous subclass that runs its doWork method on a background thread, blocking until completion. CoroutineWorker is the idiomatic Kotlin-first subclass providing a suspending doWork function with built-in coroutine cancellation propagation, structured concurrency, and reactive progress reporting via setProgress.

## Interview answer — structured

WorkManager provides three core worker classes tailored for different concurrency paradigms and language runtimes.
ListenableWorker is the fundamental base class upon which all WorkManager tasks are built. Instead of blocking a thread, its startWork method returns a Guava ListenableFuture of Result. This architecture provides maximum flexibility, making it the foundation for non-blocking asynchronous implementations, Java CompletableFuture workflows, and RxJava integrations via RxWorker.
Worker is a synchronous subclass designed for straightforward, blocking tasks. When using Worker, you override doWork, which executes on a background thread pool managed by WorkManager's Configuration executor. The thread is held synchronously until doWork returns Result.success(), Result.retry(), or Result.failure().
CoroutineWorker is the recommended, idiomatic standard for modern Kotlin Android development. It replaces blocking threads with a suspending doWork method. By default, it runs on Dispatchers.Default, but developers can switch to Dispatchers.IO inside the coroutine body.
CoroutineWorker bridges WorkManager lifecycle directly with Kotlin structured concurrency: when WorkManager cancels a task, the underlying coroutine job is cancelled cooperatively, immediately halting active network or database operations.

## Interview answer — deep senior

Under the hood, selecting between these three classes impacts resource utilization, thread starvation, and cancellation responsiveness.
When using standard Worker, every running task consumes an entire operating system thread from WorkManager's background executor pool (which defaults to a fixed number of threads based on CPU cores). If several workers perform blocking I/O concurrently, the executor pool becomes starved, delaying other pending background jobs.
CoroutineWorker eliminates thread starvation by leveraging Kotlin suspending functions. Instead of blocking a thread while awaiting network or disk I/O, the coroutine suspends and releases the underlying thread back to the pool, allowing other workers or coroutines to utilize CPU cycles.
Furthermore, cancellation handling in CoroutineWorker is exceptionally elegant. When WorkManager stops a running job—due to constraint violations, timeout, or explicit cancellation—it cancels the CoroutineWorker's CoroutineScope. If your worker invokes suspending functions like delay or Ktor/Retrofit suspending endpoints, the cancellation propagates instantly, throwing a CancellationException.
In contrast, a traditional Worker must imperatively poll isStopped throughout its execution loop; if a blocking call does not check isStopped, the worker continues wasting device battery and memory until the operation eventually returns.
Staff engineers exclusively standardize on CoroutineWorker for all new features, utilizing custom WorkerFactory injection to supply dependencies directly via constructor injection.

## How to answer in the interview

- **Why:** worker type controls async contract.
- **How:** match sync, suspend or callback API.
- **Trade-off:** simplicity versus adapter complexity.
- **Failure case:** cancellation swallowed then side effect repeats.
- **Production solution:** delegate to repository and test stop/retry.

## Follow-up questions

- **Interviewer:** "How do you inspect the reason why a worker was cancelled?"
  **Answer:** "On Android 12+, call `getStopReason()` inside the worker to determine if it stopped due to timeout, constraint loss, or user cancellation."

- **Interviewer:** "Can you inject dependencies into a CoroutineWorker with Hilt?"
  **Answer:** "Yes, using `@HiltWorker` and `@AssistedInject` on the constructor, combined with `HiltWorkerFactory` configured in the Application class."
