# BG-04

## Original interview question

What are Worker, CoroutineWorker, and ListenableWorker?

## What the interviewer evaluates

Choose Worker, CoroutineWorker or ListenableWorker by execution model and cancellation integration.

## Explanation in Arabic

`Worker` API synchronous `doWork()`، ينفع للشغل blocking القصير على executor مناسب. `CoroutineWorker` يدي `suspend doWork()` علشان نستعمل suspend repository APIs بشكل structured. `ListenableWorker` الأساس لasync callback/future integration لما نحتاج adapter خاص. اختيار النوع لا يغير WorkManager scheduling guarantees ولا يجعل server side effect exactly-once.

### Practical walkthrough in Egyptian Arabic

`Worker` مناسب لsync API، `CoroutineWorker` لـsuspend repository في Kotlin، و`ListenableWorker` base لcallback async عند الحاجة. في `CoroutineWorker` راقب cancellation ولا تمسك `CancellationException` كفشل قابل للإعادة؛ النظام ممكن يوقف work ويعيده. حقن repository والـIDs أفضل من وضع network calls مباشرة في worker. اختبر retry والstop مع `TestWorkerBuilder` أو setup مناسب، لكن device integration لازمة للscheduler.

## Why it matters and how it works

Worker subclasses return Result.success/failure/retry. CoroutineWorker cancellation is cooperative; a blocking SDK may ignore it. ListenableWorker must complete its Future/callback correctly and handle stop. Keep long-running user-visible work and foreground notification requirements separate from subclass choice.

## Worked example

Android illustration assumes `OutboxRepository` is injected via WorkerFactory/Hilt integration and reads durable operations.

```kotlin
import android.content.Context
import androidx.work.CoroutineWorker
import androidx.work.WorkerParameters

class SyncWorker(
    context: Context,
    params: WorkerParameters,
    private val repository: OutboxRepository,
) : CoroutineWorker(context, params) {
    override suspend fun doWork(): Result = repository.syncPending()
}
```

## Trade-offs and decision criteria

CoroutineWorker is natural for suspend APIs but requires DI configuration and cancellation-aware repository code. Worker is simple for synchronous calls but ties up a thread. ListenableWorker supports callbacks yet adds completion/cancellation complexity.

## Failure modes

Calling a blocking SDK inside CoroutineWorker without dispatcher/interrupt handling still blocks its thread. Returning success before an async callback completes loses work. Returning retry for permanent validation failure loops indefinitely.

## Production perspective

An outbox worker uses CoroutineWorker to call suspend Room/network APIs and returns retry only for transient errors. It stores per-operation status and uses stable keys so a repeated worker run is safe. Tests cover stop/retry and 401 refresh.

## Interview answer — short

“Worker is synchronous, CoroutineWorker supports suspending doWork, and ListenableWorker is the lower-level async base. I choose by the API I integrate, then still design cancellation, retry classification and idempotent effects.”

## Interview answer — structured

“If my repository already exposes suspend functions, CoroutineWorker gives a straightforward `suspend doWork` path. A traditional Worker runs synchronous work on an executor, while ListenableWorker is useful for integrating callbacks or Future-based APIs. All return success, failure or retry according to outcome. None changes the fact that work may be stopped and attempted again. I keep operation state in Room and classify failures so a permanent error is not retried forever.”

## Interview answer — deep senior

“Subclass choice is about implementation style, not durability level. A CoroutineWorker makes structured suspend calls convenient but cancellation remains cooperative and does not undo a submitted server write. A Worker is fine for bounded synchronous work if its executor and timeout behavior are understood. A custom ListenableWorker must manage callback completion exactly once and respond to stop; it is easy to accidentally signal success before work finishes. In production I inject a repository through the supported WorkerFactory path, pass a stable operation ID, make the endpoint idempotent, and test retries and process death. Foreground execution and notification rules apply independently for eligible long-running work. Tests cover stop/retry and 401 refresh. A `Worker` implementation is useful for synchronous code, whereas `CoroutineWorker` integrates suspending repository calls and cancellation. `ListenableWorker` is the lower-level bridge when an asynchronous callback API cannot be expressed simply through suspend functions. Whichever form I choose, the Worker delegates domain decisions to a repository and reads a stable ID, rather than carrying a serialized object graph in its input. I treat stopping as a cancellation signal, not proof that a remote request did not arrive. Tests inject a fake gateway that can complete late, fail, or never respond; a device test checks the actual scheduler and service restrictions.”

## How to answer in the interview

- **Why:** worker type controls async contract.
- **How:** match sync, suspend or callback API.
- **Trade-off:** simplicity versus adapter complexity.
- **Failure case:** cancellation swallowed then side effect repeats.
- **Production solution:** delegate to repository and test stop/retry.
