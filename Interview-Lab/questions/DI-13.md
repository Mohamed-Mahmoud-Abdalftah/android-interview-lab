# DI-13

## Original interview question

How do you replace dependencies in unit and instrumented tests?

## What the interviewer evaluates

- Separate pure unit tests from Android graph tests.
- Select a Hilt replacement mechanism with the right scope.
- Preserve deterministic setup and verify the replacement is actually injected.

## Concept and technical explanation

For an isolated class with constructor-injected dependencies, a local JVM unit test can instantiate it directly with fakes or mocks; Hilt is unnecessary for that test. This is a useful default, not a prohibition on Hilt in all JVM tests: Hilt also supports Robolectric tests when its test application and processor are configured. To verify integration with the Hilt graph, use `@HiltAndroidTest` with `HiltAndroidRule` and a Hilt test application. `@TestInstallIn` replaces an installed module for all tests in a source set; `@UninstallModules` plus a replacement module or `@BindValue` is useful for one test class. `hiltRule.inject()` populates fields annotated with `@Inject` in the test; a preinitialized `@BindValue` field is supplied by the test itself. Instrumented UI tests additionally require a configured runner and device/emulator.

## Practical walkthrough (English)

Replacing dependencies in Unit and Hilt Instrumented Tests:
```kotlin
// 1. Pure Unit Test: Zero DI framework, pure constructor injection
class GetUserProfileUseCaseTest {
    private val fakeRepository = FakeUserRepository() // Fast in-memory test fake
    private val useCase = GetUserProfileUseCase(fakeRepository)

    @Test
    fun `when user exists returns success state`() = runTest {
        fakeRepository.emitUser(User(id = "1", name = "Alice"))
        val result = useCase("1")
        assertEquals("Alice", result.name)
    }
}

// 2. Instrumented Integration Test with Hilt
@HiltAndroidTest
@UninstallModules(ProductionNetworkModule::class)
@RunWith(AndroidJUnit4::class)
class UserProfileScreenTest {
    @get:Rule(order = 0)
    val hiltRule = HiltAndroidRule(this)

    // This test-owned value replaces the removed UserApi binding
    @BindValue @JvmField
    val fakeApi: UserApi = FakeUserApi()

    @Before
    fun init() {
        hiltRule.inject() // Needed for @Inject test fields; safe setup here
    }

    @Test
    fun verifyUserDisplayedOnScreen() {
        launchActivity<UserProfileActivity>()
        onView(withId(R.id.userName)).check(matches(withText("Alice")))
    }
}
```

## Explanation in Arabic

لو بتختبر `UseCase` أو `ViewModel` constructor بتاعه واضح، أبسط اختبار JVM ينشئه مباشرة بـfake. Hilt **مش ضروري** هنا؛ ده اختيار مفيد للسرعة والعزل، مش منع مطلق. لو عايز تختبر graph مع Android APIs محلياً، Hilt يدعم Robolectric بعد ضبط test application والـprocessor.

لاختبار تكامل شاشة أو graph، استخدم `@HiltAndroidTest` و`HiltAndroidRule` وتطبيق اختبار Hilt. في instrumented test لازم runner يختار `HiltTestApplication` أو custom test application، ويحتاج جهاز/محاكي. `@TestInstallIn` يستبدل module لكل اختبارات source set، بينما `@UninstallModules` في test واحد يزيل module إنتاج مثبت بـ`@InstallIn`، ثم تضيف بديله أو `@BindValue`.

`@BindValue` حقل بتنشئه أنت في الاختبار عشان يقدّم binding للـgraph؛ `hiltRule.inject()` وظيفته حقن حقول الاختبار المكتوب عليها `@Inject`، مش إنشاء قيمة `@BindValue`. جهّز الـfake قبل إطلاق الـActivity، وخلّي الاختبار يوضح مصدر البيانات المتوقع.

## Practical walkthrough

في Unit Test لـ `GetUserProfileUseCase`، أنشئ `FakeUserRepository` ومرّره في constructor، ثم اختبر نتيجة حالة محددة. ده لا يحتاج Hilt، لكنه لا يثبت إن graph الإنتاج صحيح.

في اختبار شاشة بـHilt، اضبط `HiltTestApplication` وrunner، واستخدم `@UninstallModules(ProductionNetworkModule::class)` على test class لو الاستبدال خاص به، و`@BindValue val fakeApi: UserApi = FakeUserApi()` قبل تشغيل الشاشة. لو كل الاختبارات محتاجة نفس البديل، استخدم `@TestInstallIn` في `androidTest` بدلاً من تكرار الإزالة. `hiltRule.inject()` لازم لو عندك حقول `@Inject` في test، لكن الـfake المهيأ كـ`@BindValue` موجود أصلاً. المثال لا يثبت نتيجة UI من غير تعريف FakeUserApi وتهيئة runner.

## Why it matters and how it works

Dependency replacement changes the graph produced for the test rather than patching a global Singleton at runtime. Hilt creates test components and injects the test instance after the rule initializes. Binding identity, qualifiers, and scope still matter: replacing an unqualified repository does not replace a qualified one. A fake should offer deterministic behavior and observable calls; a network or clock left real makes the result flaky.

## Worked example

`LoginViewModel(repo: AuthRepository)` gets `FakeAuthRepository` directly in a JVM test, and the test drives success and failure without an Activity. In an instrumented login-screen test, a test module installed in `SingletonComponent` binds the fake repository, then the test launches the Hilt Activity and asserts rendered state. A test-specific fake exposes controlled responses rather than sleeping for a network call.

### Kotlin / Hilt example

In a JVM unit test, instantiate the consumer with a fake directly. For an Android Hilt test, the replacement module belongs in the test source set; `ProductionApiModule` is the app module it replaces.

```kotlin
import dagger.Module
import dagger.Provides
import dagger.hilt.InstallIn
import dagger.hilt.components.SingletonComponent
import dagger.hilt.testing.TestInstallIn

interface Api { suspend fun status(): String }
class RealApi : Api { override suspend fun status() = "live" }
class FakeApi : Api { override suspend fun status() = "ready" }

// src/main:
@Module
@InstallIn(SingletonComponent::class)
object ProductionApiModule {
    @Provides fun api(): Api = RealApi()
}

// androidTest or test source set, with Hilt test dependencies configured:
@Module
@TestInstallIn(
    components = [SingletonComponent::class],
    replaces = [ProductionApiModule::class]
)
object FakeApiModule {
    @Provides fun api(): Api = FakeApi()
}
```

`ProductionApiModule` is app-defined and must be installed in the same component. Instrumented tests also need the Hilt test application and `HiltAndroidRule`.

## Trade-offs and decision criteria

Constructor injection gives fast, focused tests. A full Hilt test proves wiring and Android integration but costs startup and annotation processing. `@TestInstallIn` suits a shared fake; per-test uninstall/replacement gives isolation when behavior differs. Avoid mutable global test modules that let order affect results.

## Failure modes

A production binding remains because the test replacement has a different qualifier. The Activity launches before the Hilt rule injects the test. A Singleton fake retains state across test cases. A unit test uses a mock for every collaborator and only confirms implementation calls, missing user-visible behavior.

## Production perspective

Keep a small graph smoke suite alongside many pure unit tests. Give fakes explicit reset/constructor state, use an injectable clock and dispatcher, and verify the actual binding through a behavioral assertion. Run instrumented tests on a documented emulator matrix; a passing JVM test cannot establish Android component wiring.

## Interview answer — short

For a constructor-injected unit, instantiate it directly with a fake or mock; Hilt is unnecessary. For graph/UI integration, use `@HiltAndroidTest`, `HiltAndroidRule`, and a Hilt test application. `@TestInstallIn` replaces a module for all tests in a source set; `@UninstallModules` plus a test replacement or `@BindValue` targets one test class. `hiltRule.inject()` populates test `@Inject` fields, not preinitialized `@BindValue` values. Hilt can also run in configured Robolectric tests.

## Interview answer — structured

I first decide what the test must prove. A focused JVM test constructs a use case or ViewModel with a fake repository and checks behavior without a DI container. If it must verify Hilt graph wiring or UI integration, I use `@HiltAndroidTest`, `HiltAndroidRule`, a Hilt test application, and the appropriate Robolectric or instrumented setup. Instrumented tests require a runner and device or emulator.

For a source-set-wide fake I use `@TestInstallIn` replacing an installed production module. For a one-class override I use `@UninstallModules` and either a test module or `@BindValue`. The replacement type and qualifier must match the requested binding. I call `hiltRule.inject()` when the test itself has `@Inject` fields; it does not construct a `@BindValue` field. Fakes versus mocks and test mix are chosen by behavior and risk, not fixed percentages.

## Interview answer — deep senior

For a focused unit test of a constructor-injected type, call the constructor with a fake or mock. Official Hilt guidance says the framework is not necessary for such tests, including directly constructed ViewModels. It does not say Hilt is forbidden in every JVM test: Robolectric integration tests can use a Hilt test application and test processor. Choose the narrowest test that verifies the behavior you care about.

A Hilt integration test uses `@HiltAndroidTest` and `HiltAndroidRule`. For instrumented tests, configure a runner that selects `HiltTestApplication` or a generated custom test application. `@TestInstallIn` replaces an installed production module for all tests in that source set; `@UninstallModules` is per test class and may increase build work because Hilt generates a test-specific component. A test-owned `@BindValue` field can provide one replacement binding after removing the original module, with qualifiers preserved when needed.

`hiltRule.inject()` populates `@Inject` fields on the test; it does not initialize a normal `val` annotated with `@BindValue`. A fake is useful for stateful, deterministic behavior, while a mock can be appropriate for interaction verification. Neither is universally faster or better. Do not state a fixed percentage split between unit and device tests; the mix follows risk, integration boundaries, and CI feedback needs. This source example is illustrative and needs concrete test runner, fake behavior, and Android project setup before it can pass on device.

## How to answer in the interview

- **Unit boundary:** Direct constructor injection with a fake/mock; Hilt not necessary.
- **Graph boundary:** `@HiltAndroidTest`, rule and test application; runner/device for instrumented UI.
- **Replacement scope:** `@TestInstallIn` for a source set, `@UninstallModules` with replacement for one test class.
- **Field roles:** `@BindValue` is test-owned; `hiltRule.inject()` populates `@Inject` test fields.
- **Caveat:** Hilt also supports configured Robolectric tests, so no absolute JVM prohibition.

## Deep-dive talking points

Compare constructor injection, `@TestInstallIn`, `@UninstallModules`, `@BindValue`, qualifier parity, and Hilt rule order.

## Follow-up questions

- **Interviewer:** "Is Hilt forbidden in JVM tests?"
  **Answer:** "No. Constructor-injected units can be tested directly without Hilt, and Hilt can also run with configured Robolectric tests when graph integration matters."

- **Interviewer:** "When use @TestInstallIn instead of @UninstallModules?"
  **Answer:** "Use @TestInstallIn when a replacement should apply to every test in a source set. Use @UninstallModules for one test class, then provide a replacement binding."

- **Interviewer:** "What does hiltRule.inject() initialize?"
  **Answer:** "It populates @Inject fields on the test. A preinitialized @BindValue field is test-owned and is read as a binding; inject() does not create that value."

- **Interviewer:** "Fake or mock?"
  **Answer:** "Use the double that gives a clear assertion. Fakes are useful for stateful flows; mocks can express interaction expectations. Measure test cost rather than claiming one is universally faster."
