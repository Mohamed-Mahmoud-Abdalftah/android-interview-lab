# DI-13

## Original interview question

How do you replace dependencies in unit and instrumented tests?

## What the interviewer evaluates

- Separate pure unit tests from Android graph tests.
- Select a Hilt replacement mechanism with the right scope.
- Preserve deterministic setup and verify the replacement is actually injected.

## Concept and technical explanation

Replacing dependencies in automated tests is essential for isolating business logic, eliminating non-deterministic network interactions, and accelerating test execution. The testing strategy differs fundamentally between local unit tests and instrumented on-device tests. Local unit tests on the JVM should avoid dependency injection frameworks entirely; by relying on constructor injection, tests directly instantiate classes under test and inject lightweight fakes, stubs, or mocks. In contrast, instrumented Android integration tests that boot full Activity and Fragment lifecycles use Hilt's testing infrastructure via @HiltAndroidTest, custom test runners, @UninstallModules, and @BindValue to replace production modules and inject test doubles into the generated test component graph.

## Practical walkthrough (English)

Replacing dependencies in Unit and Hilt Instrumented Tests:
```kotlin
// 1. Pure Unit Test: Zero DI framework, pure constructor injection
class GetUserProfileUseCaseTest {
    private val fakeRepository = FakeUserRepository() // Fast in-memory test fake
    private val useCase = GetUserProfileUseCase(fakeRepository)

    @Test
    fun `when user exists returns success state`() = runTest {
        fakeRepository.emitUser(User(id = "1", name = "Alice"))
        val result = useCase("1")
        assertEquals("Alice", result.name)
    }
}

// 2. Instrumented Integration Test with Hilt
@HiltAndroidTest
@UninstallModules(ProductionNetworkModule::class)
@RunWith(AndroidJUnit4::class)
class UserProfileScreenTest {
    @get:Rule(order = 0)
    val hiltRule = HiltAndroidRule(this)

    // Automatically replaces the UserApi binding in the test graph
    @BindValue @JvmField
    val fakeApi: UserApi = FakeUserApi()

    @Before
    fun init() {
        hiltRule.inject()
    }

    @Test
    fun verifyUserDisplayedOnScreen() {
        launchActivity<UserProfileActivity>()
        onView(withId(R.id.userName)).check(matches(withText("Alice")))
    }
}
```

   - **لا تستخدم Hilt على الإطلاق!**

2. في الـ Instrumented Tests (اختبارات الشاشات و Espresso/Compose UI):

## Practical walkthrough

المقارنة بين استبدال التبعيات في Unit Test مقابل Instrumented Test مع Hilt:
```kotlin
// 1. في JVM Unit Test: اختبار سريع ومباشر بدون Hilt وبدون أي أطر عمل:
class OrderViewModelTest {
    @Test
    fun testOrderPlacement() = runTest {
        val fakeRepo = FakeOrderRepository()
        val viewModel = OrderViewModel(fakeRepo) // تمرير الـ Fake مباشرة في المشيد!
        viewModel.placeOrder("item_1")
        assertTrue(fakeRepo.hasOrder("item_1"))
    }
}

// 2. في Android Instrumented Test: استبدال موديول الإنتاج بـ Test Double:
@UninstallModules(AnalyticsModule::class)
@HiltAndroidTest
class CheckoutScreenUiTest {
    @get:Rule(order = 0)
    var hiltRule = HiltAndroidRule(this)

    // استبدال التبعية بقيمة مزيفة داخل الاختبار مباشرة:
    @BindValue
    val fakeAnalytics: AnalyticsTracker = FakeAnalyticsTracker()

    @Before
    fun init() {
        hiltRule.inject()
    }

    @Test
    fun verifyCheckoutTriggersAnalytics() {
        // اختبار الـ UI مع التأكد من أن fakeAnalytics تم حقنه في الـ Graph الحقيقي!
    }
}
```

## Why it matters and how it works

Dependency replacement changes the graph produced for the test rather than patching a global Singleton at runtime. Hilt creates test components and injects the test instance after the rule initializes. Binding identity, qualifiers, and scope still matter: replacing an unqualified repository does not replace a qualified one. A fake should offer deterministic behavior and observable calls; a network or clock left real makes the result flaky.

## Worked example

`LoginViewModel(repo: AuthRepository)` gets `FakeAuthRepository` directly in a JVM test, and the test drives success and failure without an Activity. In an instrumented login-screen test, a test module installed in `SingletonComponent` binds the fake repository, then the test launches the Hilt Activity and asserts rendered state. A test-specific fake exposes controlled responses rather than sleeping for a network call.

### Kotlin / Hilt example

In a JVM unit test, instantiate the consumer with a fake directly. For an Android Hilt test, the replacement module belongs in the test source set; `ProductionApiModule` is the app module it replaces.

```kotlin
import dagger.Module
import dagger.Provides
import dagger.hilt.InstallIn
import dagger.hilt.components.SingletonComponent
import dagger.hilt.testing.TestInstallIn

interface Api { suspend fun status(): String }
class RealApi : Api { override suspend fun status() = "live" }
class FakeApi : Api { override suspend fun status() = "ready" }

// src/main:
@Module
@InstallIn(SingletonComponent::class)
object ProductionApiModule {
    @Provides fun api(): Api = RealApi()
}

// androidTest or test source set, with Hilt test dependencies configured:
@Module
@TestInstallIn(
    components = [SingletonComponent::class],
    replaces = [ProductionApiModule::class]
)
object FakeApiModule {
    @Provides fun api(): Api = FakeApi()
}
```

`ProductionApiModule` is app-defined and must be installed in the same component. Instrumented tests also need the Hilt test application and `HiltAndroidRule`.

## Trade-offs and decision criteria

Constructor injection gives fast, focused tests. A full Hilt test proves wiring and Android integration but costs startup and annotation processing. `@TestInstallIn` suits a shared fake; per-test uninstall/replacement gives isolation when behavior differs. Avoid mutable global test modules that let order affect results.

## Failure modes

A production binding remains because the test replacement has a different qualifier. The Activity launches before the Hilt rule injects the test. A Singleton fake retains state across test cases. A unit test uses a mock for every collaborator and only confirms implementation calls, missing user-visible behavior.

## Production perspective

Keep a small graph smoke suite alongside many pure unit tests. Give fakes explicit reset/constructor state, use an injectable clock and dispatcher, and verify the actual binding through a behavioral assertion. Run instrumented tests on a documented emulator matrix; a passing JVM test cannot establish Android component wiring.

## Interview answer — short

In unit tests on the JVM, do not use DI frameworks; instantiate the class under test directly via constructor injection, passing fakes or mocks. In instrumented UI tests, annotate the test with @HiltAndroidTest, use HiltAndroidRule, and swap production bindings using @UninstallModules to replace production modules with test modules, or use @BindValue to bind test doubles directly into the test component graph.

## Interview answer — structured

Testing dependency-injected architectures requires a disciplined separation between local unit testing and instrumented integration testing.
For local unit tests running on the JVM, invoking Dagger or Hilt is an anti-pattern. Because well-architected classes declare their operational requirements through constructor parameters, test suites should instantiate classes directly using standard Kotlin constructors. This approach enables sub-second test execution and complete isolation from Android framework dependencies by supplying clean fakes or mock objects.
For instrumented integration tests and end-to-end UI tests that require launching Activities or Fragments, Hilt provides first-class testing tooling. Engineers configure a custom test runner extending HiltTestApplication and annotate test classes with @HiltAndroidTest and HiltAndroidRule.
To replace production networking, analytics, or database engines with test doubles, developers use @UninstallModules to disable specific production modules, replacing them with test-specific modules. Alternatively, @BindValue allows developers to declare test doubles as fields directly inside the test class, automatically rebinding them into Hilt's test graph before launching the UI.

## Interview answer — deep senior

Under the hood, Hilt's testing architecture generates a custom application class and a dedicated test component subclass for each instrumented test execution.
When @UninstallModules is declared, Hilt's annotation processor excludes the designated production modules from the test component assembly. When paired with @BindValue, Hilt inspects the test class fields and synthesizes an internal test module that provides those specific instances, overriding corresponding bindings in the test DAG without requiring handwritten test module boilerplate.
Senior engineers prioritize in-memory fakes over mocking frameworks like Mockito or MockK, particularly for repositories and local databases. Fakes maintain state deterministically across sequential operations, catch architectural concurrency issues, and run orders of magnitude faster without byte-buddy reflection overhead.
Staff engineers enforce a strict testing boundary in CI pipelines: 90 percent of business logic, ViewModels, and UseCases are verified through pure JVM unit tests with manual constructor instantiation. Instrumented Hilt tests are reserved exclusively for critical integration smoke tests, navigation flows, and UI contract verification, optimizing developer feedback loops and CI execution times. This two-tier testing methodology prevents flakiness, slashes emulator execution costs, and provides deterministic assertions across all production features and user checkout flows, ensuring continuous delivery confidence and architectural integrity for the entire engineering organization.

## How to answer in the interview

- **Why:** tests need controlled dependencies at the right boundary.
- **How:** direct fakes for JVM, Hilt replacement for Android integration.
- **Trade-off:** graph tests cost setup and runtime.
- **Failure case:** fake tests pass while release graph binds wrong endpoint.
- **Production solution:** deterministic fakes plus production graph smoke test.

## Deep-dive talking points

Compare constructor injection, `@TestInstallIn`, `@UninstallModules`, `@BindValue`, qualifier parity, and Hilt rule order.

## Follow-up questions

- **Interviewer:** "What happens if you forget `hiltRule.inject()` in a Hilt test?"
  **Answer:** "Any `@Inject lateinit var` fields or `@BindValue` configurations declared in the test class will remain uninitialized, throwing NullPointerException."

- **Interviewer:** "Can you use MockK or Mockito with `@BindValue`?"
  **Answer:** "Yes. `@BindValue val mockRepo: Repository = mockk()` works seamlessly and binds the mock into Hilt's test component."
