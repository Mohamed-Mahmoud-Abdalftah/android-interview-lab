# DI-13

## Original interview question

How do you replace dependencies in unit and instrumented tests?

## What the interviewer evaluates

- Separate pure unit tests from Android graph tests.
- Select a Hilt replacement mechanism with the right scope.
- Preserve deterministic setup and verify the replacement is actually injected.

## Explanation in Arabic

في unit test لكلاس عادي، أنشئه يدويًا ومرّر fake أو mock عبر constructor؛ تشغيل Hilt هنا غالبًا تكلفة غير لازمة. في instrumented test يحتاج Android graph استخدم `@HiltAndroidTest` مع `HiltAndroidRule` و`HiltTestApplication` المناسب للتشغيل. `@TestInstallIn` يستبدل module للـtest source set كله؛ `@UninstallModules` مع test module يناسب حالة اختبار بعينها لكنه يزيد وقت compilation. `@BindValue` مفيد لقيمة test-local، بشرط الانتباه لتوقيت التهيئة. اختبر أن الـfake وصل فعلًا إلى الشاشة بدل الاكتفاء بأن الاختبار اشتغل.

## Practical walkthrough

Unit test للـViewModel تقدر تبنيها مباشرة بـfake repository؛ ما تحتاجش Hilt container. instrumented UI test اللي بتبني Activity حقيقية تحتاج `HiltAndroidRule` وtest Application مناسب، وتقدر تستبدل module بـ`@TestInstallIn` لكل test source set أو `@UninstallModules` لاختبار محدد، و`@BindValue` لحالة بسيطة. خلي fake deterministic وماتعتمدش على شبكة أو DB مشتركة؛ واختبر graph الإنتاج نفسها في smoke test منفصل.

## Why it matters and how it works

Dependency replacement changes the graph produced for the test rather than patching a global Singleton at runtime. Hilt creates test components and injects the test instance after the rule initializes. Binding identity, qualifiers, and scope still matter: replacing an unqualified repository does not replace a qualified one. A fake should offer deterministic behavior and observable calls; a network or clock left real makes the result flaky.

## Worked example

`LoginViewModel(repo: AuthRepository)` gets `FakeAuthRepository` directly in a JVM test, and the test drives success and failure without an Activity. In an instrumented login-screen test, a test module installed in `SingletonComponent` binds the fake repository, then the test launches the Hilt Activity and asserts rendered state. A test-specific fake exposes controlled responses rather than sleeping for a network call.

### Kotlin / Hilt example

In a JVM unit test, instantiate the consumer with a fake directly. For an Android Hilt test, the replacement module belongs in the test source set; `ProductionApiModule` is the app module it replaces.

```kotlin
import dagger.Module
import dagger.Provides
import dagger.hilt.InstallIn
import dagger.hilt.components.SingletonComponent
import dagger.hilt.testing.TestInstallIn

interface Api { suspend fun status(): String }
class RealApi : Api { override suspend fun status() = "live" }
class FakeApi : Api { override suspend fun status() = "ready" }

// src/main:
@Module
@InstallIn(SingletonComponent::class)
object ProductionApiModule {
    @Provides fun api(): Api = RealApi()
}

// androidTest or test source set, with Hilt test dependencies configured:
@Module
@TestInstallIn(
    components = [SingletonComponent::class],
    replaces = [ProductionApiModule::class]
)
object FakeApiModule {
    @Provides fun api(): Api = FakeApi()
}
```

`ProductionApiModule` is app-defined and must be installed in the same component. Instrumented tests also need the Hilt test application and `HiltAndroidRule`.

## Trade-offs and decision criteria

Constructor injection gives fast, focused tests. A full Hilt test proves wiring and Android integration but costs startup and annotation processing. `@TestInstallIn` suits a shared fake; per-test uninstall/replacement gives isolation when behavior differs. Avoid mutable global test modules that let order affect results.

## Failure modes

A production binding remains because the test replacement has a different qualifier. The Activity launches before the Hilt rule injects the test. A Singleton fake retains state across test cases. A unit test uses a mock for every collaborator and only confirms implementation calls, missing user-visible behavior.

## Production perspective

Keep a small graph smoke suite alongside many pure unit tests. Give fakes explicit reset/constructor state, use an injectable clock and dispatcher, and verify the actual binding through a behavioral assertion. Run instrumented tests on a documented emulator matrix; a passing JVM test cannot establish Android component wiring.

## Interview answer — short

“For plain unit tests I pass fakes through constructors. For Android graph tests I use Hilt's test components and replace bindings with `@TestInstallIn`, a local test module, or `@BindValue` as appropriate.”

## Interview answer — structured

“I choose the smallest test that proves the claim. A ViewModel's decision logic is tested on the JVM with a fake repository and controlled dispatcher. When I need to prove that the Activity receives the intended implementation, I use `@HiltAndroidTest`, its rule, and a test application, then replace the module binding. I match qualifiers and component scopes, launch after injection, and assert behavior that could only occur through the fake. This also catches an accidentally live backend.”

## Interview answer — deep senior

“My starting point is the seam, not the annotation. A constructor-injected class can be instantiated directly, which keeps most tests fast and tells me whether its behavior is correct. Hilt's instrumented test support is valuable for a different claim: the Android entry point, generated graph, and replacement binding work together. I usually install a common fake with `@TestInstallIn`; a one-off graph can use `@UninstallModules` and a nested module, or `@BindValue` when that fits the binding. I check qualifier and scope parity so that the test cannot silently use the real implementation. The fake starts with explicit state and injectable time, and the assertion observes UI or repository behavior rather than merely checking injection did not crash. I avoid starting the Activity before the rule has prepared injection, and I isolate mutable fake state between tests. Finally, I distinguish the evidence: a JVM test validates logic, a Hilt emulator test validates graph and Android integration, and neither by itself proves a production server contract. A concrete test pair makes the distinction clear: a JVM test passes a fake API that times out and checks the ViewModel error state; an instrumented Hilt test launches the Activity with a test replacement and checks the visible error message. I would then run a small test against production bindings in a release-like variant. Replacement tests alone can pass while the real graph still targets an incorrect host.”

## How to answer in the interview

- **Why:** tests need controlled dependencies at the right boundary.
- **How:** direct fakes for JVM, Hilt replacement for Android integration.
- **Trade-off:** graph tests cost setup and runtime.
- **Failure case:** fake tests pass while release graph binds wrong endpoint.
- **Production solution:** deterministic fakes plus production graph smoke test.

## Deep-dive talking points

Compare constructor injection, `@TestInstallIn`, `@UninstallModules`, `@BindValue`, qualifier parity, and Hilt rule order.

## Follow-up questions

- When should you avoid Hilt in a test? **Answer:** when a constructor-injected unit can be tested directly and Android graph behavior is irrelevant.
- Why can a test replacement silently fail? **Answer:** an unmatched qualifier or component means the target still resolves another binding.
- What does an instrumented graph test add? **Answer:** evidence that the Android entry point and generated Hilt component inject the intended binding.

## Self-check rubric

Choose a replacement method, show a deterministic fake, verify rule order and qualifier, and state what each test proves.
