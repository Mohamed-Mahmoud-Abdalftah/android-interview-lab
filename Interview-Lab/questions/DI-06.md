# DI-06

## Original interview question

What is a DI graph? What is a component hierarchy?

## What the interviewer evaluates

- Model bindings as a directed graph and identify missing/ambiguous/cyclic dependencies.
- Describe Hilt parent/child component visibility and lifetime.
- Explain why a short-lived dependency cannot safely be captured by a longer-lived binding.

## Concept and technical explanation

A dependency injection graph is a directed acyclic graph where nodes represent injectable types and edges represent dependency relationships required to construct those types. In Dagger and Hilt, this graph is constructed and validated entirely at compile time to guarantee that every requested dependency can be resolved without cyclic dependencies or missing bindings. A component hierarchy is an ordered, parent-child tree of dependency containers that mirrors the architectural and lifecycle structure of the host platform. In Hilt, components form a strict hierarchy rooted at SingletonComponent (process lifetime), branching to ActivityRetainedComponent (configuration change lifetime), ActivityComponent (UI instance lifetime), FragmentComponent, and ViewComponent. In this hierarchy, child components inherit all bindings and scopes from their ancestors, while parents remain completely decoupled from and unaware of child bindings.

## Practical walkthrough (English)

Understanding Hilt's component hierarchy and binding inheritance:
```kotlin
// 1. SingletonComponent: Root component, lives for the entire application process
@Module
@InstallIn(SingletonComponent::class)
object AppModule {
    @Provides @Singleton
    fun provideAppDatabase(@ApplicationContext context: Context): AppDatabase =
        Room.databaseBuilder(context, AppDatabase::class.java, "app.db").build()
}

// 2. ActivityComponent: Subcomponent, inherits from SingletonComponent
// Can inject AppDatabase (from parent) AND Activity Context (from self)
@Module
@InstallIn(ActivityComponent::class)
object ActivityModule {
    @Provides @ActivityScoped
    fun provideNavigator(activity: Activity): AppNavigator =
        AppNavigatorImpl(activity)
}

// Child component can inject dependencies from parent, but parent CANNOT access child bindings!
```

## Explanation in Arabic

ما هو الـ Dependency Graph (شجرة التبعيات) وما هو الـ Component Hierarchy (تسلسل المكونات الهرمي) في Hilt؟

1. الـ Dependency Graph (رسم بياني موجه للتبعيات):
   - هو رسم بياني موجه بدون حلقات (Directed Acyclic Graph - DAG) يربط كل كائن بالتبعيات التي يحتاجها لإنشائه.
   - يقوم Dagger في وقت التجميع (Compile-time) بفحص هذا الرسم البياني بالكامل للتحقق من:
     * عدم وجود تبعيات مفقودة (Missing Bindings).
     * عدم وجود تعارض أو غموض (Ambiguous Bindings).
     * عدم وجود حلقات دائرية مستحيلة (Cyclic Dependencies، مثل A يحتاج B و B يحتاج A).

2. الـ Component Hierarchy في Hilt:
   - يقسم Hilt شجرة التبعيات إلى مكونات هرمية مرتبطة بدورة حياة أندرويد:
     `SingletonComponent` (طوال عمر التطبيق)
       └── `ActivityRetainedComponent` (يعبر الـ Configuration Changes)
             └── `ViewModelComponent` (مرتبط بعمر الـ ViewModel)
       └── `ActivityComponent` (مرتبط بدورة حياة الـ Activity الواحدة)
             └── `FragmentComponent` (مرتبط بدورة حياة الـ Fragment)
                   └── `ViewComponent`

3. قواعد الرؤية والـ Scoping في التسلسل الهرمي:
   - **الرؤية باتجاه واحد للأسفل**: المكون الابن (Child) يرى جميع كائنات المكون الأب (Parent) وأجداده، ولكن المكون الأب لا يستطيع رؤية كائنات المكون الابن!
   - **قاعدة منع التسريب**: لا يمكن لكائن في `SingletonComponent` أن يعتمد على كائن في `ActivityComponent` لأن عمر الـ Singleton أطول بكثير وسيؤدي ذلك إلى تسريب الـ Activity في الذاكرة (Memory Leak).

## Practical walkthrough

توضيح التسلسل الهرمي وقواعد الرؤية ومنع التبعيات الدائرية:
```kotlin
// 1. كائن في SingletonComponent: متاح للجميع طوال عمر التطبيق:
@Module
@InstallIn(SingletonComponent::class)
object AppModule {
    @Provides @Singleton
    fun provideDatabase(@ApplicationContext context: Context): AppDatabase = ...
}

// 2. كائن في ActivityComponent: يرى الـ Database، ولكن الـ Database لا تراه:
@Module
@InstallIn(ActivityComponent::class)
object ActivityModule {
    @Provides @ActivityScoped
    fun provideNavigator(activity: Activity): AppNavigator {
        return AppNavigator(activity) // مسموح: ActivityComponent لديه مرجع للـ Activity
    }
}

// ❌ خطأ تجميعي فادح يمنعه Dagger:
// لو حاول كائن في SingletonComponent طلب AppNavigator:
// [Dagger/MissingBinding] AppNavigator cannot be provided without an @Provides-annotated method in SingletonComponent!
```

## Why it matters and how it works

Dagger resolves requested types by following binding edges at compile time and generates construction code. Hilt installs modules into generated components. A binding installed in a parent can be consumed by child components, with scoped instances shared according to the owning component. Sibling components do not automatically share child-scoped state. The hierarchy encodes lifecycle and visibility, not module names; a Gradle module can contribute bindings to different components if configured correctly.

## Worked example

An app-wide `OkHttpClient` lives in `SingletonComponent`; each `CheckoutViewModel` gets a `CheckoutDraftController` in `ViewModelComponent`. Two checkout ViewModels should not share a mutable draft merely because both use the same repository interface. A binding graph review traces `CheckoutViewModel -> CheckoutRepository -> OrdersApi -> OkHttpClient` and identifies the component that owns each instance. This is a conceptual graph, not a generated Hilt report.

## Trade-offs and decision criteria

Parent-scoped sharing saves construction cost but retains memory and state longer. Unscoped bindings are simpler for stateless cheap objects. A ViewModel-scoped mutable collaborator supports screen-local sharing; an Activity-retained collaborator may need sharing across ViewModels during rotation. Avoid choosing `@Singleton` solely to solve a missing binding error; install and scope according to true ownership.

## Failure modes

A cycle such as `Repository -> AuthManager -> Repository` cannot be constructed directly. Two unqualified API clients create ambiguity. A provider installed in ViewModelComponent is unavailable to an application-level worker. A singleton captures an Activity reference through a transitive dependency and leaks it. Check generated-graph compile errors, inspect component scopes, and test identity/lifecycle behavior.

## Production perspective

Document a small dependency diagram for critical flows, especially session and payment boundaries. Compile each variant and run tests that verify one shared network client, per-screen controllers, and teardown on logout. Review new bindings in code review for scope and qualifier semantics, not just annotation correctness.

## Interview answer — short

A DI graph is a directed acyclic graph mapping all injectable types and their dependency relationships, verified at compile time to ensure no cycles or missing bindings exist. A component hierarchy is a structured tree of dependency containers aligned with Android lifecycles. In Hilt, child components like ActivityComponent inherit bindings from ancestor components like SingletonComponent, while isolating short-lived dependencies from leaking into longer-lived scopes.

## Interview answer — structured

The dependency injection graph and component hierarchy form the structural backbone of Dagger and Hilt architectures.
A dependency injection graph is mathematically defined as a Directed Acyclic Graph (DAG). Each node in the graph represents a providable object or class, while the directed edges represent dependencies required to satisfy constructor or provider parameters. Dagger validates this graph during compilation; if an edge forms a loop (a circular dependency) or if a required node cannot be supplied, compilation halts immediately with a clear error.
A component hierarchy organizes the dependency graph into distinct lifecycle-bound containers arranged as a parent-child tree.
In Hilt, the hierarchy begins at the root with SingletonComponent, which lives for the entire application process. Beneath it sits ActivityRetainedComponent, which survives screen rotations and configuration changes. This in turn parents ActivityComponent and ViewModelComponent. ActivityComponent further parents FragmentComponent and ViewComponent.
The fundamental rule governing the component hierarchy is directional inheritance: any child component can access and inject all bindings provided by its parent and ancestor components. However, parent components cannot access bindings declared inside child components, preventing short-lived dependencies from leaking into application-wide singletons.

## Interview answer — deep senior

Under the hood, Dagger compiles the dependency injection graph into standard Java classes that instantiate and connect factories without reflection. When evaluating the DAG, Dagger traverses from requested injection roots (such as an Activity field or ViewModel constructor) down to leaf provider nodes.
The component hierarchy mirrors Android's underlying runtime process and component lifecycles. For example, injecting an Activity into an Application-scoped singleton is prohibited because the SingletonComponent resides higher in the hierarchy and cannot see child bindings. If Dagger permitted this, retaining the child binding would cause catastrophic Activity Context memory leaks.
Furthermore, Hilt's predefined hierarchy strictly enforces separation of concerns:
SingletonComponent provides application-wide, state-free or thread-safe shared resources such as Retrofit clients, Room databases, SharedPreferences, and CoroutineDispatchers.
ActivityRetainedComponent and ViewModelComponent manage state that must survive Activity recreation across screen rotations, such as ViewModels and navigation state holders.
ActivityComponent and FragmentComponent handle UI-bound instances, including custom layout managers, dialog formatters, and Activity-specific navigation delegates.
Staff engineers leverage this hierarchical scoping to prevent memory leaks and optimize memory allocation across diverse device tiers. Dependencies allocated in FragmentComponent or ViewComponent are automatically garbage collected when the corresponding UI component is destroyed, ensuring that mobile memory footprints remain lean and strictly bound to active user journeys without accumulating unnecessary background overhead.

## How to answer in the interview

- **Why:** a binding graph also encodes lifetime.
- **How:** draw nodes, edges, parent/child visibility.
- **Trade-off:** shared objects save construction but retain state longer.
- **Failure case:** parent depends on Activity-scoped object.
- **Production solution:** identity tests across rotation and navigation.

## Deep-dive talking points

Discuss graph edges, compile-time missing/ambiguous/cycle errors, parent visibility, scoped reuse, and transitive lifetime leaks.

## Follow-up questions

- **Interviewer:** "How do you break a cyclic dependency between two services in Dagger?"
  **Answer:** "Inject `dagger.Lazy<T>` or `Provider<T>` into one of the services to defer resolution until runtime, or extract the shared dependency into a third service."

- **Interviewer:** "Can a ViewModelScoped dependency be injected into an Activity?"
  **Answer:** "No. `ActivityComponent` is not a child of `ViewModelComponent`. They branch separately under `ActivityRetainedComponent`."
