# DI-06

## Original interview question

What is a DI graph? What is a component hierarchy?

## What the interviewer evaluates

- Trace requested binding keys and their dependency edges.
- Place Activity and ViewModel components on sibling branches of the Hilt hierarchy.
- Separate installation, scope, component instance and runtime state ownership.

## Concept and technical explanation

A DI graph is the set of requested binding keys and dependency edges needed to satisfy component entry points. A key includes a type and optional qualifier. Dagger validates requested bindings for missing, conflicting and unconstructable cyclic paths at build time; it does not inspect unrelated classes or verify backend behavior. Hilt components determine binding visibility and lifetime. Children can request ancestor bindings, but ancestors and sibling branches cannot request child-only bindings. `ActivityComponent` and `ViewModelComponent` are siblings below `ActivityRetainedComponent`. `@InstallIn` selects visibility; only a scope annotation makes a binding shared within one component instance.

## Practical walkthrough (English)

Trace `CheckoutViewModel -> CheckoutRepository -> OrdersApi -> OkHttpClient` and label each binding’s component. An app-wide network client may live in `SingletonComponent`. A mutable `DraftController` can be `@ViewModelScoped` when each ViewModel needs its own draft. Another ViewModel gets another component instance and another controller. An Activity cannot directly request a binding exclusive to `ViewModelComponent`. This is a conceptual graph, not a compiled Hilt example.

## Explanation in Arabic

Dagger تفحص الـ Graph التي تُطلب من Component وقت البناء وتبلّغ عن Missing أو Duplicate Bindings وعن دورات إنشاء غير قابلة للحل؛ ده مش معناه إنها تحلل كل كلاس غير مستخدمة في الريبو أو تختبر Backend.

Component Hierarchy في Hilt تحدد أين الـ Binding مرئية ومَن يملك الـ Instance. `SingletonComponent` فوق، ومنه `ActivityRetainedComponent`؛ تحت الأخيرة فرعان مهمان: `ActivityComponent` و`ViewModelComponent`. `FragmentComponent` تحت Activity، وViewComponent حسب الـ Host. Child تقدر تستخدم Binding من Ancestor، لكن Parent لا ترى Binding خاصة بالـ Child، والفرعان الشقيقان لا يشاركان Binding خاصة بأحدهما.

`@InstallIn` تحدد Component الإتاحة، لكنها لا تجعل الـ Binding Scoped تلقائيًا. Scope مثل `@ViewModelScoped` تعيد نفس Instance داخل ViewModelComponent واحدة؛ ViewModel ثانية لها Component ثانية. لو `@Singleton` طلبت Activity Context من Child، الـ Graph العادية ترفض المسار لعدم الرؤية. ده يمنع شكلًا من الخطأ، لكن لا يثبت غياب كل Memory Leak، لأن Provider أو State ممكن تحتفظ بمراجع Runtime بطريقة أخرى.

## Practical walkthrough

ارسم مسار Checkout:
```text
CheckoutViewModel [ViewModelComponent]
  -> CheckoutRepository [SingletonComponent أو unscoped حسب الملكية]
  -> OrdersApi [SingletonComponent]
  -> OkHttpClient [SingletonComponent]
```
لو `DraftController` لها `@ViewModelScoped`، الـ ViewModel الواحدة تشاركها بين Dependencies بتاعتها، لكن ViewModel ثانية تحصل على Instance أخرى. لو عايز مشاركة عبر أكثر من ViewModel في نفس Activity retention boundary، افحص `ActivityRetainedComponent` بدل `ViewModelComponent`. ما تحطش Activity Context في Singleton؛ استخدم `@ApplicationContext` للكائنات التي تحتاج Context بعمر التطبيق.

## Why it matters and how it works

The hierarchy is about generated-component visibility and lifecycle, not Gradle module names. Installation makes a binding available in a component; scoping controls identity within one component instance. A parent cannot request a child-only binding, and siblings do not share child-scoped state. Build validation does not prove business ownership or the absence of all runtime leaks.

## Worked example

Two checkout ViewModels share a repository binding in an ancestor component but each requests a `@ViewModelScoped` draft controller. Verify same-instance use within one ViewModel and distinct instances across ViewModels. A missing-binding error for Activity requesting that controller is a hierarchy issue, not a reason to make the controller a singleton.

## Trade-offs and decision criteria

Broader scopes share identity but retain state longer. Unscoped bindings avoid retained state when identity is unnecessary. `@ViewModelScoped` is appropriate for one ViewModel’s mutable collaborator; `@ActivityRetainedScoped` can share across ViewModels under one retained Activity owner. Choose from the intended state owner and test identity rather than applying `@Singleton` to silence a graph error.

## Failure modes

An Activity requests a binding installed only in its sibling ViewModel component. Two reachable unqualified bindings conflict. A direct repository/auth-manager cycle blocks construction. A `Provider` may defer a cycle yet still recurse at runtime if both sides request each other. A singleton captures an Activity through a callback outside the DI graph despite graph visibility rules.

## Production perspective

Record the key, installed component, scope and consumers for critical bindings. Build supported variants, then test instance identity across rotation, separate screens and logout on Android. Review references retained by long-lived objects. Component destruction bounds Hilt-scoped caching but does not guarantee immediate garbage collection when other references exist.

## Interview answer — short

A DI graph is the requested binding keys and the dependency edges needed to construct them. Dagger checks the requested graph for missing, duplicate and unconstructable cyclic bindings at build time. A component hierarchy controls visibility and lifetime: Hilt children can use ancestor bindings, but parents and siblings cannot use child-only bindings. `@InstallIn` chooses a component, while a scope shares an instance only within one instance of that component. `ActivityComponent` and `ViewModelComponent` are sibling branches below `ActivityRetainedComponent`.

## Interview answer — structured

I draw a request path such as `CheckoutViewModel -> CheckoutRepository -> OrdersApi -> OkHttpClient`. Each binding key is a type with an optional qualifier. Dagger checks requested graph paths for missing, conflicting or cyclic construction, but not runtime endpoint behavior. Hilt’s component hierarchy gives each binding a visibility boundary. `SingletonComponent` is an ancestor of `ActivityRetainedComponent`; the retained component parents sibling `ActivityComponent` and `ViewModelComponent` branches. A child can use ancestor bindings, while an Activity cannot use a binding installed only in the ViewModel branch. `@InstallIn` makes the binding visible but does not scope it automatically. A scoped binding is shared per component instance, so separate ViewModels receive separate `@ViewModelScoped` collaborators. I choose scope from state ownership and verify instance identity on Android.

## Interview answer — deep senior

The useful mental model has three parts: binding key, dependency edge and component owner. A key consists of a type and optional qualifier. A request from `CheckoutViewModel` can pull in `CheckoutRepository`, `OrdersApi` and `OkHttpClient`; Dagger validates the relevant requested graph at build time. Missing or conflicting bindings and direct cycles are reported, but the compiler does not check server behavior or whether a scope matches product state. Inserting `Provider` can defer one edge, but it is not a universal cycle fix: mutually requested values can still recurse at runtime, so I first revisit responsibilities.

Hilt’s hierarchy is separate from Gradle modularization. `SingletonComponent` is an ancestor of `ActivityRetainedComponent`. The retained component has sibling Activity and ViewModel branches; a ViewModel-only binding is invisible to the Activity component. A Fragment component is below an Activity component. Children see ancestor bindings, but parents and siblings do not see child-only bindings. `@InstallIn` places a binding; it does not make that binding scoped. An unscoped binding may be created for each request, whereas `@ViewModelScoped` yields one shared instance within one ViewModelComponent. A second ViewModel has a second component and a different scoped instance.

For checkout, I might share a repository broadly but keep mutable draft state inside each ViewModel. I would not put it in `SingletonComponent` merely to silence a missing binding. Hierarchy rules can prevent direct application-scope requests for Activity bindings, but they do not prove that a callback or global cache cannot retain an Activity outside the DI graph. Component destruction ends its own scoped caching guarantee; it does not promise immediate garbage collection if other references remain. I build the real variants and test identity through rotation, opening another checkout and logout on Android.

## How to answer in the interview

- Draw a request path and identify each binding key.
- Place Activity and ViewModel on sibling branches below ActivityRetained.
- Separate `@InstallIn` visibility from scope-based reuse.
- Explain a missing binding and an identity test.

## Deep-dive talking points

Requested graph; type-plus-qualifier keys; missing/conflicting/cyclic paths; parent-child visibility; sibling isolation; per-component-instance scopes; runtime references outside DI.

## Follow-up questions

- **Interviewer:** "Can an Activity inject a ViewModel-scoped binding?"
  **Answer:** "Not directly from its Activity component; Activity and ViewModel components are sibling branches. Choose an appropriate common owner if sharing is intended."

- **Interviewer:** "Does `Provider<T>` always resolve a cycle?"
  **Answer:** "It can defer a request, but runtime mutual requests may still recurse. Revisit responsibilities first."

- **Interviewer:** "Does installing a module in SingletonComponent make its bindings singletons?"
  **Answer:** "No. A binding needs the matching scope annotation for per-component shared identity."

## Self-check rubric

Trace a requested graph, name a missing or duplicate key, draw the Activity/ViewModel sibling branches, distinguish installation from scope, and avoid a blanket leak or garbage-collection guarantee.
