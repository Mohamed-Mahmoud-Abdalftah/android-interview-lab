# DI-06

## Original interview question

What is a DI graph? What is a component hierarchy?

## What the interviewer evaluates

- Model bindings as a directed graph and identify missing/ambiguous/cyclic dependencies.
- Describe Hilt parent/child component visibility and lifetime.
- Explain why a short-lived dependency cannot safely be captured by a longer-lived binding.

## Explanation in Arabic

الـDI graph شبكة عقدها object bindings وحوافها متطلبات constructor أو provider. لو `OrdersViewModel` يحتاج `OrdersRepository` والـrepository يحتاج `OrdersApi`، graph لازم تعرف بناء الثلاثة. نقص binding أو وجود اثنين من نفس النوع بلا qualifier يظهر وقت compilation. `Component hierarchy` في Hilt تقسم graph حسب العمر: `SingletonComponent` فوق Activity/Service، ثم scopes أقصر مثل Activity وViewModel. binding في parent متاحة للـchildren، لكن parent لا تعتمد على child لأن حياتها أطول. لذلك Singleton لا يجوز عمليًا أن تحتفظ بـActivity Context أو ViewModel-specific object.

## Practical walkthrough

Graph فيها nodes للـobjects وedges للـdependencies: ViewModel→Repository→API/DAO. Hilt component hierarchy تخلي child تشوف parent bindings، لكن parent ما تشوفش child binding. `ActivityScoped` ما تنفعش تتطلبها من Singleton لأن عمرها أقصر. ارسم graph صغيرة قبل annotations، وحدد مين يعيش rotation ومين ينتهي مع Activity instance.

## Why it matters and how it works

Dagger resolves requested types by following binding edges at compile time and generates construction code. Hilt installs modules into generated components. A binding installed in a parent can be consumed by child components, with scoped instances shared according to the owning component. Sibling components do not automatically share child-scoped state. The hierarchy encodes lifecycle and visibility, not module names; a Gradle module can contribute bindings to different components if configured correctly.

## Worked example

An app-wide `OkHttpClient` lives in `SingletonComponent`; each `CheckoutViewModel` gets a `CheckoutDraftController` in `ViewModelComponent`. Two checkout ViewModels should not share a mutable draft merely because both use the same repository interface. A binding graph review traces `CheckoutViewModel -> CheckoutRepository -> OrdersApi -> OkHttpClient` and identifies the component that owns each instance. This is a conceptual graph, not a generated Hilt report.

## Trade-offs and decision criteria

Parent-scoped sharing saves construction cost but retains memory and state longer. Unscoped bindings are simpler for stateless cheap objects. A ViewModel-scoped mutable collaborator supports screen-local sharing; an Activity-retained collaborator may need sharing across ViewModels during rotation. Avoid choosing `@Singleton` solely to solve a missing binding error; install and scope according to true ownership.

## Failure modes

A cycle such as `Repository -> AuthManager -> Repository` cannot be constructed directly. Two unqualified API clients create ambiguity. A provider installed in ViewModelComponent is unavailable to an application-level worker. A singleton captures an Activity reference through a transitive dependency and leaks it. Check generated-graph compile errors, inspect component scopes, and test identity/lifecycle behavior.

## Production perspective

Document a small dependency diagram for critical flows, especially session and payment boundaries. Compile each variant and run tests that verify one shared network client, per-screen controllers, and teardown on logout. Review new bindings in code review for scope and qualifier semantics, not just annotation correctness.

## Interview answer — short

“A DI graph maps how requested types are constructed from other bindings. A component hierarchy partitions that graph by visibility and lifetime, so app-wide bindings can serve shorter-lived owners without the reverse lifetime leak.”

## Interview answer — structured

“I picture the graph as types and their dependency edges: a ViewModel needs a repository, which needs an API client. Dagger resolves those edges at compile time, detecting missing or ambiguous bindings. Hilt groups bindings into lifecycle components. A parent binding can be used by child components, while child-only state should not be retained by a parent. Scope controls whether a component reuses one instance or creates another. This matters because making everything singleton can accidentally share mutable screen state or retain Activity Context. I assign each binding an owner and test expected instance identity across screens and rotation.”

## Interview answer — deep senior

“The graph is both a construction map and a lifetime design. Each constructor parameter or provider method adds an edge; code generation follows those edges to build requested objects. Missing bindings, competing unqualified bindings, and cycles are construction defects that the compiler can catch. Hilt's component hierarchy adds ownership: SingletonComponent sits above lifecycle-bound Activity, ViewModel, and Service components, and a binding installed in a parent is visible to descendants. A longer-lived object cannot safely capture a shorter-lived Activity or View through that path, even if the type system allows it. I scope only bindings needing identity, shared mutable state, or costly creation, because scoping retains objects. For checkout, I keep a shared network client at app scope and a draft controller at ViewModel scope, while durable payment state lives in a repository. I verify variant graph compilation and run identity/recreation tests, then inspect transitive dependencies when a memory leak appears. Suppose two ViewModels share an API client but keep independent draft caches. The API client can live in SingletonComponent, while each cache belongs in ViewModelComponent. I would verify one client identity across both owners and two cache identities. A binding graph that compiles with a singleton cache would still be wrong because one screen could show another screen’s draft.”

## How to answer in the interview

- **Why:** a binding graph also encodes lifetime.
- **How:** draw nodes, edges, parent/child visibility.
- **Trade-off:** shared objects save construction but retain state longer.
- **Failure case:** parent depends on Activity-scoped object.
- **Production solution:** identity tests across rotation and navigation.

## Deep-dive talking points

Discuss graph edges, compile-time missing/ambiguous/cycle errors, parent visibility, scoped reuse, and transitive lifetime leaks.

## Follow-up questions

- Can an Application binding request an Activity-scoped object? **Answer:** it should not; the parent outlives and cannot depend on a child-owned instance.
- Does a Gradle module equal a Hilt component? **Answer:** no; build modules organize code, while Hilt components define runtime injection ownership and visibility.
- Why can a graph compile yet still leak? **Answer:** a valid binding may be scoped too broadly or transitively capture a short-lived Context.

## Self-check rubric

Draw three binding edges, identify a missing binding, explain parent visibility, and choose a safe scope for mutable screen state.
