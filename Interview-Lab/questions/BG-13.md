# BG-13

## Original interview question

When should an exact alarm be used instead of periodic work?

## What the interviewer evaluates

Choose exact alarms only for precise user-facing events under permissions and power policy.

## Explanation in Arabic

`Exact alarm` مناسبة لو المستخدم محتاج event في وقت محدد فعلًا، مثل منبه أو calendar reminder، وممكن تحتاج special access حسب API/نوع التطبيق. WorkManager periodic مناسب sync مرنة لكنه مش موعد دقيق. AlarmManager wakeup لا يدي حرية تنفيذ network طويل؛ عند الحدث نعرض notification أو نبدأ مسار مسموح به وفق قيود النظام. نراجع أذونات `SCHEDULE_EXACT_ALARM`/`USE_EXACT_ALARM` الحالية قبل التصميم.

## Practical walkthrough

Exact alarm لا تصلح بديلًا عامًا للـperiodic sync. استخدمها فقط لحدث user-facing يتطلب توقيتًا فعليًا مثل منبه، مع permission/eligibility حسب API والسياسة. WorkManager periodic للrefresh المرن وقد يتأخر بسبب Doze. لو requirement “كل ثانية” لserver polling، غيّر التصميم إلى push أو foreground user-visible session أو server-side schedule؛ لا تعد بدقة لا يوفرها OS.

## Why it matters and how it works

Exact-alarm eligibility, permission and Doze behavior vary by Android version and use case. Use `canScheduleExactAlarms` where applicable, handle permission revocation and reschedule after reboot if required. A receiver should perform brief work and delegate longer durable operations to the supported scheduler. Avoid exact alarms for periodic polling.

## Trade-offs and decision criteria

Exact timing can meet a user promise but costs battery and has permission/restriction complexity. Inexact alarm or WorkManager is preferable when a window is acceptable. Even exact alarm delivery is subject to device state and API behavior; do not promise second-perfect repeated background computation.

## Failure modes

Using an exact alarm for every one-minute sync can drain battery and violate policy. Failing to handle denied/revoked permission silently drops reminders. A BroadcastReceiver that performs long network work can be killed before completion.

## Production perspective

A medication reminder app checks eligibility, asks for special access only when the core feature needs it, schedules a one-time reminder and handles reboot/reschedule. Data sync remains in WorkManager with flexible timing.

## Interview answer — short

“I use exact alarms for genuinely precise user-facing reminders, subject to platform eligibility and permission. Periodic sync belongs in WorkManager. The alarm receiver stays brief and longer work uses a suitable durable mechanism.”

## Interview answer — structured

“WorkManager periodic work cannot promise an exact wall-clock moment. If a product feature truly requires a calendar or alarm notification at a specified time, I evaluate AlarmManager exact alarms and current Android permission rules. I check whether exact scheduling is allowed, handle denial and reboot, and keep the receiver’s work short. If the event triggers network synchronization, I schedule that separately; an exact alarm is not a license for long background execution.”

## Interview answer — deep senior

“I start from the user guarantee: is a precise reminder essential, or is a flexible maintenance window acceptable? Exact alarms are a special-case API with power cost and evolving eligibility; I verify target SDK requirements, canScheduleExactAlarms behavior, revocation and permission UX. WorkManager handles deferrable periodic tasks and respects Doze, so it is not an exact reminder mechanism. On alarm delivery I do the minimum needed to notify the user and schedule longer work through an allowed path. I test idle mode, reboot, timezone changes and denied access, and phrase product timing promises according to what the platform actually guarantees. Avoid exact alarms for periodic polling. An exact alarm is for a genuinely time-sensitive user-visible event, not a loophole for polling. It may require special eligibility or permission depending on platform and app use case, and it still does not mean the app can keep an arbitrary network task running forever afterward. WorkManager periodic requests are inexact and subject to constraints and power policy. If product wants a data refresh every second while the app is closed, I renegotiate the requirement: use server-side scheduling, push notification, or an active foreground session when appropriate. I document the timing guarantee we can actually test on supported devices and what happens when the device is off.”
