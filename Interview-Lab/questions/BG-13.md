# BG-13

## Original interview question

When should an exact alarm be used instead of periodic work?

## What the interviewer evaluates

Choose exact alarms only for precise user-facing events under permissions and power policy.

## Concept and technical explanation

Choosing between AlarmManager exact alarms and WorkManager periodic work requires understanding the architectural trade-off between clock precision and battery conservation. Exact alarms via AlarmManager setExactAndAllowWhileIdle are reserved exclusively for clock-precise, user-facing events where failure to trigger at the precise designated minute or second causes direct real-world harm or invalidates the core functionality—such as a personal alarm clock, a calendar appointment alert, or a scheduled medication reminder. Exact alarms require the SCHEDULE_EXACT_ALARM or USE_EXACT_ALARM permission, both subject to strict Google Play review policies and automatic platform revocation on Android 13+. In contrast, WorkManager PeriodicWorkRequest is the mandatory platform standard for deferrable background execution, enforcing an API-level minimum interval of 15 minutes, flexible execution windows, and full harmonization with Doze mode and App Standby buckets to optimize battery life.

## Practical walkthrough (English)

Contrasting exact alarms with periodic work:
```kotlin
// 1. Clock-exact user alarm: Wakes CPU at precise second for user-facing event
fun scheduleClockExactAlarm(context: Context, triggerEpochMs: Long, pendingIntent: PendingIntent) {
    val alarmManager = context.getSystemService(AlarmManager::class.java)

    // Check if app has permission on Android 12+ (SCHEDULE_EXACT_ALARM)
    if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.S && !alarmManager.canScheduleExactAlarms()) {
        // Guide user to system settings to grant permission
        return
    }

    alarmManager.setExactAndAllowWhileIdle(
        AlarmManager.RTC_WAKEUP,
        triggerEpochMs,
        pendingIntent
    )
}

// 2. Periodic background maintenance: Battery-friendly, deferrable, persists across reboots
fun schedulePeriodicDataSync(context: Context) {
    val syncRequest = PeriodicWorkRequestBuilder<SyncWorker>(
        repeatInterval = 1, repeatIntervalTimeUnit = TimeUnit.HOURS,
        flexTimeInterval = 15, flexTimeIntervalUnit = TimeUnit.MINUTES
    ).setConstraints(
        Constraints.Builder()
            .setRequiredNetworkType(NetworkType.UNMETERED)
            .setRequiresBatteryNotLow(true)
            .build()
    ).build()

    WorkManager.getInstance(context).enqueueUniquePeriodicWork(
        "periodic_data_sync",
        ExistingPeriodicWorkPolicy.KEEP,
        syncRequest
    )
}
```

## Practical walkthrough

فحص الصلاحية وبرمجة Exact Alarm مع الإيقاظ في وضع Doze Mode:
```kotlin
class AlarmScheduler(private val context: Context) {
    private val alarmManager = context.getSystemService(AlarmManager::class.java)

    fun scheduleMedicationReminder(reminderId: Int, triggerTimeMillis: Long) {
        // 1. التحقق من صلاحية الجدولة الدقيقة على Android 12+ (API 31+):
        if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.S) {
            if (!alarmManager.canScheduleExactAlarms()) {
                // توجيه المستخدم لصفحة الإعدادات لتفعيل الصلاحية:
                val intent = Intent(Settings.ACTION_REQUEST_SCHEDULE_EXACT_ALARM)
                intent.flags = Intent.FLAG_ACTIVITY_NEW_TASK
                context.startActivity(intent)
                return
            }
        }

        val intent = Intent(context, AlarmReceiver::class.java).apply {
            putExtra("reminder_id", reminderId)
        }
        val pendingIntent = PendingIntent.getBroadcast(
            context,
            reminderId,
            intent,
            PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_IMMUTABLE
        )

        // 2. إيقاظ الجهاز بالثانية حتى لو كان في وضع الخمول العميق (Doze Mode):
        alarmManager.setExactAndAllowWhileIdle(
            AlarmManager.RTC_WAKEUP,
            triggerTimeMillis,
            pendingIntent
        )
    }
}
```

## Why it matters and how it works

Exact-alarm eligibility, permission and Doze behavior vary by Android version and use case. Use `canScheduleExactAlarms` where applicable, handle permission revocation and reschedule after reboot if required. A receiver should perform brief work and delegate longer durable operations to the supported scheduler. Avoid exact alarms for periodic polling.

## Worked example

Conceptual Android code assumes a valid immutable PendingIntent and permission/eligibility check; API details depend on target SDK.

```kotlin
import android.app.AlarmManager
import android.app.PendingIntent

fun scheduleReminder(
    manager: AlarmManager, triggerAtMillis: Long, intent: PendingIntent,
) {
    // Check exact-alarm eligibility before calling on applicable API levels.
    manager.setExact(AlarmManager.RTC_WAKEUP, triggerAtMillis, intent)
}
```

## Trade-offs and decision criteria

Exact timing can meet a user promise but costs battery and has permission/restriction complexity. Inexact alarm or WorkManager is preferable when a window is acceptable. Even exact alarm delivery is subject to device state and API behavior; do not promise second-perfect repeated background computation.

## Failure modes

Using an exact alarm for every one-minute sync can drain battery and violate policy. Failing to handle denied/revoked permission silently drops reminders. A BroadcastReceiver that performs long network work can be killed before completion.

## Production perspective

A medication reminder app checks eligibility, asks for special access only when the core feature needs it, schedules a one-time reminder and handles reboot/reschedule. Data sync remains in WorkManager with flexible timing.

## Interview answer — short

Use exact alarms with AlarmManager setExactAndAllowWhileIdle strictly for clock-precise, user-facing events where triggering at the exact minute is mandatory, such as alarm clocks, calendar reminders, and medical alerts. Use WorkManager PeriodicWorkRequest for all background data syncing, cleanup, and maintenance, which enforces a 15-minute minimum interval and aligns with Doze mode to preserve device battery.

## Interview answer — structured

The decision between an exact alarm and periodic work centers on clock precision versus power efficiency.
Exact alarms via AlarmManager are built for time-critical, user-perceived events. If a user sets an alarm to wake up at 07:00 AM or a medical reminder to take medication at noon, triggering even five minutes late represents a product failure. In these scenarios, developers use setExactAndAllowWhileIdle, which wakes the CPU from low-power states to trigger a PendingIntent. However, this precision comes with significant regulatory overhead: starting in Android 12, apps must secure SCHEDULE_EXACT_ALARM, and Google Play rejects applications using exact alarms for routine background operations.
WorkManager PeriodicWorkRequest is designed for deferrable, recurring operations like syncing catalog data, uploading analytics, or pruning database caches. The platform enforces a hardcoded minimum interval of 15 minutes. WorkManager intentionally defers execution until environmental constraints like network availability and charging status are met, batching work into Doze mode maintenance windows.
Under no circumstances should AlarmManager be used as a polling mechanism for background data synchronization.

## Interview answer — deep senior

Under the hood, AlarmManager and WorkManager interact with Android power management infrastructure in fundamentally divergent ways. When an exact alarm fires via setExactAndAllowWhileIdle, the system PowerManagerService acquires a transient kernel wake lock, spinning up CPU cores and piercing through Doze mode restrictions to deliver the broadcast or start a foreground activity.
Because frequent CPU wakeups severely impact battery longevity, Android restricts exact alarms aggressively. On Android 13+ (API 33+), the SCHEDULE_EXACT_ALARM permission is revoked by default for newly installed applications unless the app is classified as an alarm, timer, or calendar app. If an app attempts to call setExact without permission, the system throws a SecurityException.
Furthermore, repeating exact alarms do not exist natively on modern Android: the platform converts repeating alarms into inexact alarms. To simulate repetition with exact alarms, an app must manually calculate the next target timestamp and reschedule a new one-shot exact alarm inside its broadcast receiver upon every trigger.
In contrast, WorkManager delegates periodic tasks to JobScheduler. JobScheduler batches jobs from multiple applications into synchronized execution windows, minimizing radio activations and maximizing CPU deep sleep states. It also dynamically manages App Standby Buckets, adjusting execution quotas based on how frequently the user interacts with the app.
Staff engineers establish architectural boundaries: AlarmManager is quarantined within specialized reminder modules with explicit user settings fallbacks, while all background data retrieval, cache invalidation, and server synchronization are strictly assigned to WorkManager.

## Follow-up questions

- **Interviewer:** "What is `AlarmManager.canScheduleExactAlarms()`?"
  **Answer:** "A method introduced in Android 12 to check whether the user has granted the app permission to schedule exact alarms before attempting to set one."

- **Interviewer:** "Why shouldn't you use `setRepeating()` for exact alarms?"
  **Answer:** "Since Android 4.4 (KitKat), all repeating alarms are inexact and batched by the OS; to achieve recurring exact alarms, reschedule an exact alarm inside the receiver."
