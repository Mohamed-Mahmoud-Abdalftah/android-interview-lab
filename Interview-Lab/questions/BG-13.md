# BG-13

## Original interview question

When should an exact alarm be used instead of periodic work?

## What the interviewer evaluates

Choose exact alarms only for precise user-facing events under permissions and power policy.

## Explanation in Arabic

متى يجب استخدام التنبيه الدقيق (Exact Alarm عبر AlarmManager) بدلاً من العمل الدوري (Periodic WorkManager)؟

1. متى يكون الـ Exact Alarm إلزامياً ومبرراً (When Exact Alarm is Mandatory):
   - **التطبيقات التي تتطلب الدقة بالثانية في لحظة زمنية معينة يدركها المستخدم (Clock-Exact User-Facing Events)**:
     * تطبيق المنبه (Alarm Clock) للاستيقاظ في تمام 07:00:00 صباحاً.
     * منبه مواعيد تناول الدواء لمرضى السكري والقلب (Medical/Medication Reminders).
     * تذكير تقويم بالتقاء أو مكالمة فيديو يبدأ في وقت محدد.
   - في هذه الحالات، لا يمكن الاعتماد على WorkManager لأن WorkManager يجمع المهام ويؤخرها لدقائق وساعات أثناء وضع الـ Doze Mode والبطارية.

2. متى يُحظر استخدام الـ Exact Alarm (When to Avoid):
   - مزامنة البيانات من السيرفر (Data Sync).
   - جلب أحدث المقالات الإخبارية.
   - فحص وجود إشعارات جديدة (Polling).
   - في هذه الحالات، يجب استخدام WorkManager أو FCM Push Notifications.

3. القيود والصلاحيات الصارمة في Android الحديث (Android 12 إلى 14):
   - **صلاحية `SCHEDULE_EXACT_ALARM`**: تم تقييدها بشدة. في Android 13/14، لا تمنح تلقائياً إلا لتطبيقات من فئتي: المنبهات (Clock/Alarms) والتقويم (Calendar). باقي التطبيقات تتطلب توجيهاً صريحاً للمستخدم إلى شاشة إعدادات النظام للموافقة اليدوية.
   - **صلاحية `USE_EXACT_ALARM`**: متاحة فقط للتطبيقات المتخصصة رسمياً في المنبهات على متجر Google Play.

## Practical walkthrough

فحص الصلاحية وبرمجة Exact Alarm مع الإيقاظ في وضع Doze Mode:
```kotlin
class AlarmScheduler(private val context: Context) {
    private val alarmManager = context.getSystemService(AlarmManager::class.java)

    fun scheduleMedicationReminder(reminderId: Int, triggerTimeMillis: Long) {
        // 1. التحقق من صلاحية الجدولة الدقيقة على Android 12+ (API 31+):
        if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.S) {
            if (!alarmManager.canScheduleExactAlarms()) {
                // توجيه المستخدم لصفحة الإعدادات لتفعيل الصلاحية:
                val intent = Intent(Settings.ACTION_REQUEST_SCHEDULE_EXACT_ALARM)
                intent.flags = Intent.FLAG_ACTIVITY_NEW_TASK
                context.startActivity(intent)
                return
            }
        }

        val intent = Intent(context, AlarmReceiver::class.java).apply {
            putExtra("reminder_id", reminderId)
        }
        val pendingIntent = PendingIntent.getBroadcast(
            context,
            reminderId,
            intent,
            PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_IMMUTABLE
        )

        // 2. إيقاظ الجهاز بالثانية حتى لو كان في وضع الخمول العميق (Doze Mode):
        alarmManager.setExactAndAllowWhileIdle(
            AlarmManager.RTC_WAKEUP,
            triggerTimeMillis,
            pendingIntent
        )
    }
}
```

## Why it matters and how it works

Exact-alarm eligibility, permission and Doze behavior vary by Android version and use case. Use `canScheduleExactAlarms` where applicable, handle permission revocation and reschedule after reboot if required. A receiver should perform brief work and delegate longer durable operations to the supported scheduler. Avoid exact alarms for periodic polling.

## Worked example

Conceptual Android code assumes a valid immutable PendingIntent and permission/eligibility check; API details depend on target SDK.

```kotlin
import android.app.AlarmManager
import android.app.PendingIntent

fun scheduleReminder(
    manager: AlarmManager, triggerAtMillis: Long, intent: PendingIntent,
) {
    // Check exact-alarm eligibility before calling on applicable API levels.
    manager.setExact(AlarmManager.RTC_WAKEUP, triggerAtMillis, intent)
}
```

## Trade-offs and decision criteria

Exact timing can meet a user promise but costs battery and has permission/restriction complexity. Inexact alarm or WorkManager is preferable when a window is acceptable. Even exact alarm delivery is subject to device state and API behavior; do not promise second-perfect repeated background computation.

## Failure modes

Using an exact alarm for every one-minute sync can drain battery and violate policy. Failing to handle denied/revoked permission silently drops reminders. A BroadcastReceiver that performs long network work can be killed before completion.

## Production perspective

A medication reminder app checks eligibility, asks for special access only when the core feature needs it, schedules a one-time reminder and handles reboot/reschedule. Data sync remains in WorkManager with flexible timing.

## Interview answer — short

Use exact alarms (AlarmManager.setExactAndAllowWhileIdle) only for clock-precise, user-facing events like wakeup alarms, medical alerts, and calendar reminders. Use WorkManager for all deferrable data sync and background maintenance. Exact alarms require special permissions (SCHEDULE_EXACT_ALARM) and must not be abused for network polling.

## Interview answer — structured

The choice between AlarmManager and WorkManager centers on **Temporal Precision versus Resource Optimization**:

1. **When to Choose Exact Alarms (`AlarmManager`)**:
   - Mandatory only when missing the trigger time by 30 seconds ruins the core user experience: wakeup alarms, medication dosage reminders, and scheduled video-call notifications.
   - Invoked via `setExactAndAllowWhileIdle(AlarmManager.RTC_WAKEUP, time, pendingIntent)`. This guarantees the device will wake from deep sleep and fire the broadcast receiver within a second of the target wall-clock time.

2. **When Exact Alarms are an Anti-Pattern**:
   - Polling an API for updates, fetching new feed posts, or cleaning local caches. Using exact alarms for data sync burns excessive battery and violates Google Play policies.
   - For all data operations, use **WorkManager**; it batches tasks into Doze maintenance windows and respects network conditions.

3. **Platform Policy & Permissions (Android 12/14+)**:
   - Applications targeting API 31+ must hold the `SCHEDULE_EXACT_ALARM` or `USE_EXACT_ALARM` permission. In Android 14, `SCHEDULE_EXACT_ALARM` is revoked by default for newly installed apps unless explicitly categorized as an Alarm or Calendar app by Google Play.

## Interview answer — deep senior

What happens after an Exact Alarm fires?

When `AlarmReceiver.onReceive()` triggers, the device is briefly awake holding a temporary partial wake-lock granted by the OS (lasting approximately 10–15 seconds).

- **The Trap**: If the receiver initiates a long-running coroutine or network request inside `onReceive()`, the method returns immediately, the OS releases the temporary wake-lock, and the device goes back to sleep, freezing the coroutine midway!

- **The Production Protocol**: Keep `onReceive()` lightweight. Post a high-priority heads-up notification with sound immediately. If the alarm requires heavy data processing, enqueue an **Expedited WorkRequest** via WorkManager or transition to a dedicated typed Foreground Service.

## How to answer in the interview

- **Why:** precision has permission and battery cost.
- **How:** use exact alarm only for qualifying event.
- **Trade-off:** precision versus energy and policy.
- **Failure case:** periodic worker promised as alarm.
- **Production solution:** redesign timing contract with product.

## Deep-dive talking points

Trace permission denial, reboot, timezone and short receiver execution.

## Follow-up questions

- **Interviewer:** "What is `AlarmManager.canScheduleExactAlarms()`?"
  **Answer:** "A method introduced in Android 12 to check whether the user has granted the app permission to schedule exact alarms before attempting to set one."

- **Interviewer:** "Why shouldn't you use `setRepeating()` for exact alarms?"
  **Answer:** "Since Android 4.4 (KitKat), all repeating alarms are inexact and batched by the OS; to achieve recurring exact alarms, reschedule an exact alarm inside the receiver."
