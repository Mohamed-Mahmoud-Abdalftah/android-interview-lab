# DI-15

## Original interview question

How do you handle assisted injection or runtime parameters?

## What the interviewer evaluates

- Separate graph-known dependencies from values known only at creation time.
- Explain an assisted factory and Android owner-specific alternatives.
- Avoid treating runtime parameters as mutable global bindings.

## Explanation in Arabic

الـDI graph يعرف repository وlogger وقت البناء، لكن `documentId` يأتي من navigation وقت تشغيل الشاشة. Assisted injection تجمع الاثنين: constructor عليه `@AssistedInject`، parameter متغير عليه `@Assisted`، وfactory عليها `@AssistedFactory` تنشئ instance بالقيمة المحددة. ليس كل runtime argument يحتاج assisted injection؛ `SavedStateHandle` مناسب غالبًا لمعرّفات ViewModel القادمة من navigation، مع validation وفهم الاستعادة بعد process death. المهم ألا تخزن آخر ID في Singleton متغير فتختلط طلبات متعددة.

## Practical walkthrough

في navigation ViewModel، `SavedStateHandle` غالبًا يكفي لـargument زي `orderId` ويدعم restore، فلا تستخدم assisted injection لمجرد وجود argument. لكن لو `ReportProcessor` يحتاج runtime value لا يملكه graph ومش state persisted، Dagger `@AssistedInject` مع `@AssistedFactory` تخلي factory تستقبل القيمة وقت الإنشاء وباقي deps من graph. assisted type نفسها مش scoped؛ حدد owner للـfactory والنتيجة، واختبر invalid ID.

## Why it matters and how it works

The generated factory receives graph-provided dependencies while the caller supplies assisted arguments. Assisted types are constructed through that factory rather than injected as an ordinary cached binding. A runtime parameter may affect object identity, so scope and reuse need deliberate design. For Android ViewModels, framework creation and saved state integration impose additional rules; use the supported Hilt ViewModel creation path where applicable.

## Worked example

A `ReportExporter` needs an injected `StorageGateway` and a user-selected `reportId`. Its factory `create(reportId)` builds an exporter for that request. If a screen's ViewModel only needs a route's document ID, read the ID from `SavedStateHandle`, reject missing IDs, and load via the injected repository. The choice follows the owner and restoration requirement.

### Kotlin / Hilt example

The graph supplies `Repository`; the caller supplies `reportId`. A Hilt ViewModel with a navigation ID usually reads it from `SavedStateHandle` instead.

```kotlin
import dagger.assisted.Assisted
import dagger.assisted.AssistedFactory
import dagger.assisted.AssistedInject

interface Repository { suspend fun load(id: String): String }

class ReportProcessor @AssistedInject constructor(
    private val repository: Repository,
    @Assisted private val reportId: String
) {
    suspend fun run(): String = repository.load(reportId)

    @AssistedFactory
    interface Factory {
        fun create(reportId: String): ReportProcessor
    }
}
```

The app supplies a binding for `Repository`; `ReportProcessor` itself is not scoped.

## Trade-offs and decision criteria

Assisted factories provide typed construction and clear call sites, at the cost of another interface and compiler configuration. A plain factory function is enough for small manual-DI code. `SavedStateHandle` fits navigation state and restoration but should not carry large domain objects. A per-request object need not be process-scoped.

## Failure modes

The caller forgets to provide an argument or injects an assisted type directly. A mutable Singleton stores `currentReportId`, so concurrent exports pick up the wrong ID. A ViewModel relies on an in-memory-only argument and cannot restore after process death. Runtime input is trusted without validation.

## Production perspective

Document parameter source, validation, identity, and restoration behavior. Test two simultaneous IDs and recreated owner state. Keep sensitive values out of route strings where exposure is possible; pass durable identifiers and reload authorized data.

## Interview answer — short

“I inject stable collaborators from the graph and supply runtime values through an assisted factory, or use `SavedStateHandle` for supported ViewModel navigation state.”

## Interview answer — structured

“The key distinction is when the value exists. A repository is graph-known; a selected report ID appears only when the user starts an export. An assisted factory takes the ID at `create` time while Hilt supplies stable dependencies. For a destination ViewModel I first consider `SavedStateHandle`, because navigation arguments and process recreation matter. I validate the ID and avoid a shared mutable ‘current ID’ binding, which would race across requests.”

## Interview answer — deep senior

“I model runtime input as part of creation, not as a global switch inside the graph. For a request-owned service, assisted injection gives a generated factory: the graph resolves the storage client and telemetry, and the caller passes a report identifier to create one exporter. That makes concurrent exports independent. If the object is an Android ViewModel, I consider the framework's supported creation and saved-state path before adding a custom factory; a route identifier in `SavedStateHandle` can be restored and used to reload data after process death. I would not place an entire mutable document in saved state, and I validate and authorize the identifier before use. The test matrix covers missing input, two distinct IDs in parallel, owner recreation, and any sensitive route exposure. The decision is about ownership and restoration as much as dependency construction: an assisted object has the lifetime of its caller unless I explicitly design a longer-lived store. For an order detail ViewModel, a route ID in `SavedStateHandle` can be restored after process recreation. A report export object created after the user chooses a format may need a runtime value; an assisted factory makes that value explicit. I would reject an invalid ID at creation and ensure two export requests do not accidentally reuse one processor. The factory’s own lifetime does not make its products scoped.”

## How to answer in the interview

- **Why:** graph-time and runtime values have different owners.
- **How:** SavedStateHandle for restorable nav state; assisted factory for runtime construction.
- **Trade-off:** factory flexibility versus explicit restoration work.
- **Failure case:** assisted instance reused for wrong ID.
- **Production solution:** argument and recreation tests.

## Deep-dive talking points

Explain `@AssistedInject`, `@Assisted`, `@AssistedFactory`, state restoration, and per-request identity.

## Follow-up questions

- Why not bind a mutable current ID as Singleton? **Answer:** concurrent owners can overwrite it and receive each other's state.
- Is `SavedStateHandle` a universal DI factory? **Answer:** no; it is owner-linked saved state, useful for small restorable ViewModel arguments.
- What does the factory supply? **Answer:** the caller supplies assisted values while the graph provides injected collaborators.

## Self-check rubric

Choose a runtime parameter path, show where it comes from, validate it, and test restoration and concurrency.
