# DI-15

## Original interview question

How do you handle assisted injection or runtime parameters?

## What the interviewer evaluates

- Separate graph-known dependencies from values known only at creation time.
- Explain an assisted factory and Android owner-specific alternatives.
- Avoid treating runtime parameters as mutable global bindings.

## Explanation in Arabic

كيف تتعامل مع الحقن المساعد (Assisted Injection) أو المعاملات التي تُعرف فقط في وقت التشغيل (Runtime Parameters) في Dagger و Hilt؟

1. ما هي المشكلة التي يحلها الـ Assisted Injection؟
   - في الوضع الطبيعي، يعرف Dagger جميع التبعيات في وقت التجميع عبر شجرة الـ DI (مثل `UserRepository`, `Analytics`).
   - ولكن في أحيان كثيرة، يحتاج الكائن إلى معامل لا يُعرف إلا في وقت التشغيل أو من الـ UI (مثل `orderId: String` يتم استلامه من intent أو ضغطة زر المستخدم، أو `productId`).
   - قبل Assisted Injection، كان المطورون يضطرون لعمل حيل سيئة مثل إنشاء كائن بـ `lateinit var orderId` وتعيينها بعد الإنشاء، مما يفتح الباب لحالات `UninitializedPropertyAccessException`.

2. كيف يعمل الـ Assisted Injection الرسمي؟
   - نستخدم تعليقة `@AssistedInject` على الـ Constructor بدلاً من `@Inject`.
   - نضع تعليقة `@Assisted` على المعاملات التي تأتي في وقت التشغيل.
   - ننشئ واجهة مصنع (Factory Interface) معلّمة بـ `@AssistedFactory` تحتوي على دالة إنشاء تأخذ فقط المعاملات المؤقتة (`@Assisted`).
   - يتولى Dagger توليد كود المصنع تلقائياً، بحيث يحقن التبعيات المعروفة من الـ Graph، ويطلب منك فقط تمرير الـ `orderId` عند الاستدعاء.

## Practical walkthrough

التطبيق العملي لـ Assisted Injection لبناء كائن يحتاج لمعامل في وقت التشغيل:
```kotlin
// 1. الكائن يطلب تبعيات من الـ Graph وتبعية من وقت التشغيل (@Assisted):
class OrderReceiptGenerator @AssistedInject constructor(
    private val repository: OrderRepository, // محقون تلقائياً من Dagger Graph
    private val formatter: CurrencyFormatter, // محقون تلقائياً من Dagger Graph
    @Assisted private val orderId: String // معامل يأتي في وقت التشغيل فقط!
) {
    fun generateReceipt(): Receipt = repository.getOrder(orderId).formatWith(formatter)
}

// 2. واجهة المصنع المساعد (Assisted Factory):
@AssistedFactory
interface OrderReceiptFactory {
    fun create(orderId: String): OrderReceiptGenerator
}

// 3. الاستخدام في الـ ViewModel أو الـ Presenter:
@HiltViewModel
class OrderDetailsViewModel @Inject constructor(
    private val receiptFactory: OrderReceiptFactory // حقن المصنع المساعد
) : ViewModel() {
    fun printReceipt(selectedOrderId: String) {
        // استدعاء دالة الإنشاء وتمرير المعامل الحي:
        val generator = receiptFactory.create(selectedOrderId)
        val receipt = generator.generateReceipt()
    }
}
```

## Why it matters and how it works

The generated factory receives graph-provided dependencies while the caller supplies assisted arguments. Assisted types are constructed through that factory rather than injected as an ordinary cached binding. A runtime parameter may affect object identity, so scope and reuse need deliberate design. For Android ViewModels, framework creation and saved state integration impose additional rules; use the supported Hilt ViewModel creation path where applicable.

## Worked example

A `ReportExporter` needs an injected `StorageGateway` and a user-selected `reportId`. Its factory `create(reportId)` builds an exporter for that request. If a screen's ViewModel only needs a route's document ID, read the ID from `SavedStateHandle`, reject missing IDs, and load via the injected repository. The choice follows the owner and restoration requirement.

### Kotlin / Hilt example

The graph supplies `Repository`; the caller supplies `reportId`. A Hilt ViewModel with a navigation ID usually reads it from `SavedStateHandle` instead.

```kotlin
import dagger.assisted.Assisted
import dagger.assisted.AssistedFactory
import dagger.assisted.AssistedInject

interface Repository { suspend fun load(id: String): String }

class ReportProcessor @AssistedInject constructor(
    private val repository: Repository,
    @Assisted private val reportId: String
) {
    suspend fun run(): String = repository.load(reportId)

    @AssistedFactory
    interface Factory {
        fun create(reportId: String): ReportProcessor
    }
}
```

The app supplies a binding for `Repository`; `ReportProcessor` itself is not scoped.

## Trade-offs and decision criteria

Assisted factories provide typed construction and clear call sites, at the cost of another interface and compiler configuration. A plain factory function is enough for small manual-DI code. `SavedStateHandle` fits navigation state and restoration but should not carry large domain objects. A per-request object need not be process-scoped.

## Failure modes

The caller forgets to provide an argument or injects an assisted type directly. A mutable Singleton stores `currentReportId`, so concurrent exports pick up the wrong ID. A ViewModel relies on an in-memory-only argument and cannot restore after process death. Runtime input is trusted without validation.

## Production perspective

Document parameter source, validation, identity, and restoration behavior. Test two simultaneous IDs and recreated owner state. Keep sensitive values out of route strings where exposure is possible; pass durable identifiers and reload authorized data.

## Interview answer — short

Assisted injection combines graph dependencies known at compile time with runtime parameters known only at creation time. Annotate the target constructor with @AssistedInject, mark runtime parameters with @Assisted, and declare a factory interface annotated with @AssistedFactory. Dagger generates the factory implementation automatically.

## Interview answer — structured

Assisted Injection solves the problem of instantiating an object that requires both graph dependencies (managed by Dagger) and runtime parameters (known only dynamically at user interaction time, such as an `orderId` or `userId`).

The pattern works in three steps:
1. **`@AssistedInject`**: Annotate the target class constructor with `@AssistedInject` instead of `@Inject`. Mark the runtime parameters with `@Assisted`.
2. **`@AssistedFactory`**: Define an interface with a single `create(...)` method matching the exact types and names of the `@Assisted` parameters.
3. **Automatic Assembly**: Dagger implements the factory at compile time. Consumers simply inject the factory via standard constructor injection and invoke `factory.create(runtimeParam)` whenever the runtime parameter becomes available.

For ViewModels specifically, Hilt provides built-in assisted injection for `SavedStateHandle`, eliminating the need to write custom assisted factories just to read navigation route arguments.

## Interview answer — deep senior

Prior to Dagger's native `@AssistedInject` (introduced in Dagger 2.31), developers relied on third-party libraries (Square's AssistedInject) or resorted to mutable state setters, which broke immutability and risked runtime null pointer exceptions.

Under the hood, Dagger generates an implementation of your factory interface (e.g. `OrderReceiptFactory_Impl`). The generated class injects `Provider<OrderRepository>` and `Provider<CurrencyFormatter>` from the parent component, and in its `create(orderId)` method, it calls `new OrderReceiptGenerator(repositoryProvider.get(), formatterProvider.get(), orderId)`.

This preserves the Inversion of Control principle: the consumer never touches or manages the compile-time dependencies, only supplying the dynamic payload, while the created object remains completely immutable (`val`).

## How to answer in the interview

- **Why:** graph-time and runtime values have different owners.
- **How:** SavedStateHandle for restorable nav state; assisted factory for runtime construction.
- **Trade-off:** factory flexibility versus explicit restoration work.
- **Failure case:** assisted instance reused for wrong ID.
- **Production solution:** argument and recreation tests.

## Deep-dive talking points

Explain `@AssistedInject`, `@Assisted`, `@AssistedFactory`, state restoration, and per-request identity.

## Follow-up questions

- **Interviewer:** "Can you have multiple `@Assisted` parameters of the same type in the constructor?"
  **Answer:** "Yes, but you must disambiguate them using identifier names: `@Assisted("sourceId")` and `@Assisted("targetId")` on both the constructor and the factory interface."

- **Interviewer:** "How does Assisted Injection compare to passing arguments to a method?"
  **Answer:** "If the object needs the runtime parameter across its entire lifecycle to configure internal state, Assisted Injection is superior because fields remain constructor-initialized and immutable."

## Self-check rubric

Choose a runtime parameter path, show where it comes from, validate it, and test restoration and concurrency.
