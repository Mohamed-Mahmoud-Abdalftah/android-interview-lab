# BG-01

## Original interview question

When should you use a coroutine, WorkManager, foreground service, or AlarmManager?

## What the interviewer evaluates

Select lifecycle coroutine, persistent work, foreground service or exact alarm by lifetime and user visibility.

## Concept and technical explanation

Choose the mechanism from task lifetime, deferrability, user visibility, and exact timing. A coroutine is an execution model inside a scope, not persistent scheduling; a coroutine can also run inside a Worker or Service. WorkManager persists a request for deferrable work across process death and reboot subject to system constraints, but does not guarantee immediate execution or business success. A foreground service supports eligible ongoing user-visible work under version-dependent start, type, permission, and notification rules; it is not a worker thread or process-survival guarantee. AlarmManager is for genuinely time-sensitive triggers, particularly user-facing exact alarms, with permission and policy limits. Routine network synchronization should use suitable deferrable scheduling.

## Practical walkthrough (English)

A product preview request runs under a UI-owned coroutine scope. A photo upload that must continue after the screen is gone persists an upload intent and is scheduled with WorkManager under network constraints; its worker handles retries and reports progress. Eligible continuous media playback may use a foreground service under current platform rules. A user-facing medication reminder that truly needs exact time may use an exact alarm after checking the required access. This is a design walkthrough; it does not claim that scheduling guarantees completion or exact execution time.

## Why it matters and how it works

Coroutines give structured in-process work. WorkManager persists scheduling with constraints and may delay execution. Foreground services require an ongoing user-visible notification and are restricted when starting from background. Exact alarms are for genuinely time-critical alarm/calendar use cases, not routine sync.

## Trade-offs and decision criteria

WorkManager improves durability but trades away exact timing. Foreground service offers ongoing execution subject to platform rules and notification cost. Exact alarm may require special access and harms battery. Choose the narrowest mechanism that satisfies user need.

## Failure modes

Putting upload only in viewModelScope loses it on navigation/process death. Scheduling ordinary polling with exact alarms fights power policy and may be disallowed. Starting foreground service from background can throw on newer Android versions.

## Production perspective

A media app persists an upload and schedules WorkManager; UI observes progress. A user-started live navigation session may use an eligible foreground service. A calendar alarm uses exact alarm only when precise delivery is core to the feature.

## Interview answer — short

Use a UI-owned coroutine for immediate in-process work. Use WorkManager for deferrable work whose scheduling must persist beyond the app process, while handling constraints, retries, and failure. Use an eligible foreground service for ongoing work the user is aware of, subject to platform rules. Use AlarmManager when precise trigger time is part of the feature, not for routine polling. Coroutines can run inside the other mechanisms too.

## Interview answer — structured

I classify the task by lifetime, allowable delay, user visibility, and timing precision. A coroutine in viewModelScope suits screen work such as fetching a preview; it ends with its owner and cannot survive process death. A photo upload that must continue after navigation should persist its intent and be scheduled with WorkManager. WorkManager respects constraints and can retry, but it does not promise immediate execution or a successful server response.

Eligible ongoing media playback may need a foreground service with the right type, permission, and notification behavior for the target Android version. A genuinely time-critical user reminder may need an exact AlarmManager alarm and appropriate access. Routine periodic sync does not justify exact alarms.

These mechanisms are not mutually exclusive: a Worker or Service may use coroutines internally. I also design the backend operation for retries, because a restarted Worker can repeat a request. The choice is about ownership and operational guarantees, not just which API has an asynchronous callback.

## Interview answer — deep senior

A coroutine is in-process execution with cooperative cancellation tied to a chosen scope. viewModelScope is cancelled when its ViewModel is cleared, which depends on the owner and navigation behavior; it is not a general guarantee that pressing Back cancels every job immediately. Process death ends in-memory coroutines. Work that must outlive the process needs persisted intent and a scheduler.

WorkManager persists work requests and cooperates with platform scheduling. Its constraints, battery policy, and quotas can delay work. A Worker can be stopped and retried, so success of a business operation is not guaranteed by enqueueing it. Expedited work has quota and an OutOfQuotaPolicy; it is higher priority, not an exact-time promise. Design network writes so retries preserve a stable operation identity when duplicate effects matter.

A foreground service is for eligible ongoing user-visible work. Android 12+ limits background starts for apps targeting those versions, with documented exemptions. Newer versions add service-type and while-in-use-permission constraints. A Service runs on the main thread by default and its process can still terminate. Test the actual start path and recovery behavior on target versions.

An exact alarm fits a feature whose trigger time is essential, subject to permission or special access rules and user revocation. It should not become a polling loop for routine server sync. In production I persist state, show pending and failure honestly, and test process death, reboot, network loss, quota behavior, and denied alarm access before claiming reliability.

## How to answer in the interview

- **Why:** ownership and timing determine API.
- **How:** classify lifetime, deferrability and user visibility.
- **Trade-off:** durability versus immediacy.
- **Failure case:** ViewModel coroutine treated as persistent upload.
- **Production solution:** persist intent and choose compliant scheduler.

## Deep-dive talking points

Draw lifetime versus timing matrix and explain process death and retry semantics.

## Follow-up questions

- **Interviewer:** "Does WorkManager guarantee that an upload succeeds?"
  **Answer:** "No. It persists scheduling under constraints, but execution can be delayed and the server call can fail. Observe work state and plan retries or recovery."

- **Interviewer:** "Should periodic sync use exact alarms?"
  **Answer:** "No. It is deferrable and should use appropriate background scheduling; exact time and access are reserved for genuine timing needs."

- **Interviewer:** "Is a foreground service a worker thread?"
  **Answer:** "No. Its callbacks run on the main thread by default. It also has launch and permission rules and does not make the process immortal."
