# BG-01

## Original interview question

When should you use a coroutine, WorkManager, foreground service, or AlarmManager?

## What the interviewer evaluates

Select lifecycle coroutine, persistent work, foreground service or exact alarm by lifetime and user visibility.

## Explanation in Arabic

متى تختار Coroutines، أو WorkManager، أو Foreground Service، أو AlarmManager في Android؟

1. شجرة اتخاذ القرار المعماري (Decision Tree Matrix):
   - **Kotlin Coroutines (`viewModelScope` / `lifecycleScope`)**:
     * **طبيعة العمل**: عمل غير متزامن فوري مرتبط بدورة حياة الشاشة (Immediate In-Process Work).
     * **أمثلة**: جلب بيانات لعرضها في الشاشة، تصفية قائمة محلياً، أو استجابة لضغطة زر أثناء تواجد المستخدم في الشاشة.
     * **مصيره عند خروج المستخدم**: يُلغى فوراً مع انتهاء الـ Scope (لا يعيش بعد تدمير الشاشة أو موت الـ Process).
   - **WorkManager (العمل المستمر الموثوق - Persistent / Deferrable Work)**:
     * **طبيعة العمل**: عمل يجب تنفيذه حتماً حتى لو أغلق المستخدم التطبيق، أو مات الـ Process، أو أعيد تشغيل الهاتف (Survives Process Death & Device Reboot).
     * **أمثلة**: مزامنة التعديلات غير المتصلة (Offline Sync)، رفع سجلات الأخطاء (Log Upload)، ضغط وتصدير تقرير، أو تنزيل تحديث بيانات دوري.
     * **شروطه**: يقبل التأجيل (Deferrable)، ويخضع لقيود النظام (مثل توفر الإنترنت أو الشاحن).
   - **Foreground Service (الخدمة الأمامية - User-Perceived Long-Running Work)**:
     * **طبيعة العمل**: مهمة مستمرة طويلة الأمد يدركها المستخدم بنشاط وتتطلب إشعاراً دائماً لا يمكن إزالته.
     * **أمثلة**: تشغيل الموسيقى في الخلفية، الملاحة بـ GPS خطوة بخطوة (Turn-by-turn Navigation)، مكالمة فيديو، أو تسجيل الصوت.
   - **AlarmManager (التنبيهات اللحظية الدقيقة - Exact Time-Sensitive Triggers)**:
     * **طبيعة العمل**: إيقاظ الجهاز عند ثانية محددة في المستقبل.
     * **أمثلة**: منبه الاستيقاظ، تنبيه موعد الدواء، أو تذكير التقويم.
     * **تحذير**: لا يُستخدم للـ Network Polling أو المزامنة الدورية؛ بل لتنبيه المستخدم فقط ويتطلب صلاحية `SCHEDULE_EXACT_ALARM`.

## Practical walkthrough

المقارنة العملية بالكود لاختيار الأداة المناسبة حسب طبيعة المهمة:
```kotlin
// 1. Coroutines: عمل فوري مرتبط بالشاشة فقط:
class SearchViewModel : ViewModel() {
    fun onSearchQuery(query: String) {
        viewModelScope.launch { // يُلغى تلقائياً لو خرج المستخدم من الشاشة
            val results = searchApi.query(query)
            _uiState.value = results
        }
    }
}

// 2. WorkManager: عمل دائم يجب أن يكتمل حتماً حتى لو أُغلق التطبيق:
fun scheduleLogUpload(context: Context) {
    val uploadRequest = OneTimeWorkRequestBuilder<UploadLogsWorker>()
        .setConstraints(Constraints.Builder().setRequiredNetworkType(NetworkType.CONNECTED).build())
        .build()
    WorkManager.getInstance(context).enqueueUniqueWork("upload_logs", ExistingWorkPolicy.KEEP, uploadRequest)
}

// 3. AlarmManager: إيقاظ الهاتف في وقت محدد بالثانية لمنبه حقيقي:
fun setExactAlarm(context: Context, triggerAtMillis: Long, pendingIntent: PendingIntent) {
    val alarmManager = context.getSystemService(AlarmManager::class.java)
    alarmManager.setExactAndAllowWhileIdle(AlarmManager.RTC_WAKEUP, triggerAtMillis, pendingIntent)
}
```

## Why it matters and how it works

Coroutines give structured in-process work. WorkManager persists scheduling with constraints and may delay execution. Foreground services require an ongoing user-visible notification and are restricted when starting from background. Exact alarms are for genuinely time-critical alarm/calendar use cases, not routine sync.

## Trade-offs and decision criteria

WorkManager improves durability but trades away exact timing. Foreground service offers ongoing execution subject to platform rules and notification cost. Exact alarm may require special access and harms battery. Choose the narrowest mechanism that satisfies user need.

## Failure modes

Putting upload only in viewModelScope loses it on navigation/process death. Scheduling ordinary polling with exact alarms fights power policy and may be disallowed. Starting foreground service from background can throw on newer Android versions.

## Production perspective

A media app persists an upload and schedules WorkManager; UI observes progress. A user-started live navigation session may use an eligible foreground service. A calendar alarm uses exact alarm only when precise delivery is core to the feature.

## Interview answer — short

Use coroutines (viewModelScope) for immediate UI-bound work that dies with the screen. Use WorkManager for persistent, deferrable background tasks that must survive app exit and reboots. Use Foreground Services for long-running tasks the user is actively aware of with a persistent notification (audio, navigation). Use AlarmManager only for exact, second-precise user alarms.

## Interview answer — structured

Selecting the correct background mechanism in Android hinges on two questions: **Is the work tied to the UI lifecycle?** and **Is the timing second-exact or deferrable?**

First, coroutines (`viewModelScope` / `lifecycleScope`) is designed for immediate, ephemeral in-process execution. If the user navigates away or the app process is reclaimed, the coroutine is cancelled. Perfect for UI data fetching, query debouncing, and local calculations. Next, a WorkManager is the default engine for persistent, deferrable background execution. Guarantees execution even if the app exits, the process dies, or the device reboots. Work requests are persisted in an internal SQLite database and executed via system `JobScheduler` respecting Doze mode and OS power constraints. Essential for offline sync, analytics uploading, and background database pruning.
Additionally, with Foreground Service, reserved exclusively for long-running operations the user is actively conscious of, mandated by a persistent status bar notification. Strictly categorized by `foregroundServiceType` in modern Android (e.g. `mediaPlayback`, `location`, `phoneCall`). Finally, with AlarmManager, intended exclusively for clock-exact calendar reminders and wake-up alarms (`setExactAndAllowWhileIdle`). Never use AlarmManager for periodic data sync or network polling.


## Interview answer — deep senior

Modern Android OS restrictions (Android 12+ / 14+) enforce strict limitations on these APIs.

First, with Foreground Service Background-Start Restrictions, starting a Foreground Service from the background is heavily blocked on Android 12+ (throws `ForegroundServiceStartNotAllowedException`), except for narrow exemptions (FCM high-priority push, user click on a widget, or companion device pairing). Finally, with WorkManager Expedited Jobs, for tasks that cannot wait for idle windows (e.g. Sending a critical chat message or processing a payment receipt), WorkManager provides **Expedited Work** (`setExpedited(OutOfQuotaPolicy.RUN_AS_NON_EXPEDITED_WORK_REQUEST)`). On older APIs it runs as a foreground service, while on Android 12+ it leverages platform JobScheduler expedited quotas without user-visible notification boilerplate.

- **Trade-off:** durability versus immediacy.
- **Failure case:** ViewModel coroutine treated as persistent upload.
- **Production solution:** persist intent and choose compliant scheduler.

## Follow-up questions

- **Interviewer:** "Can WorkManager execute a task every 5 seconds?"
  **Answer:** "No. PeriodicWorkRequest enforces a hard platform minimum interval of 15 minutes to preserve device battery."

- **Interviewer:** "What happens to a coroutine launched in `GlobalScope` when the process dies?"
  **Answer:** "It dies immediately. `GlobalScope` does not survive Android process death; it only outlives the active Activity while the process is warm."
