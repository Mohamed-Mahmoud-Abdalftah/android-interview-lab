# BG-01

## Original interview question

When should you use a coroutine, WorkManager, foreground service, or AlarmManager?

## What the interviewer evaluates

Select lifecycle coroutine, persistent work, foreground service or exact alarm by lifetime and user visibility.

## Concept and technical explanation

Selecting the appropriate background execution mechanism in Android hinges on two primary architectural criteria: whether the work is ephemeral or durable, and whether execution requires user-perceived ongoing operations or exact clock timing. Kotlin coroutines running in viewModelScope or lifecycleScope manage immediate in-process tasks that cancel naturally when the user navigates away or the process terminates. WorkManager is the platform standard for persistent, deferrable background execution, persisting job metadata in an internal SQLite database to guarantee execution across process death and device reboots under system constraints. Foreground Services are strictly reserved for operations the user actively perceives and expects to continue uninterrupted, mandating an ongoing system notification and explicit runtime types (such as mediaPlayback or location). AlarmManager is intended exclusively for clock-exact, user-facing triggers like alarms and calendar reminders.

## Practical walkthrough (English)

Selecting the right background execution tool in practice:
```kotlin
// 1. Coroutine: Ephemeral in-process work tied to screen lifecycle
class ProductDetailsViewModel(private val api: ProductApi) : ViewModel() {
    fun loadDetails(productId: String) {
        viewModelScope.launch { // Cancels automatically when screen is popped
            _uiState.value = api.fetchDetails(productId)
        }
    }
}

// 2. WorkManager: Durable background work surviving process death and reboots
fun schedulePhotoUpload(context: Context, photoUri: Uri) {
    val request = OneTimeWorkRequestBuilder<UploadPhotoWorker>()
        .setConstraints(Constraints.Builder().setRequiredNetworkType(NetworkType.CONNECTED).build())
        .setInputData(workDataOf("uri" to photoUri.toString()))
        .build()
    WorkManager.getInstance(context).enqueueUniqueWork("upload_photo", ExistingWorkPolicy.KEEP, request)
}

// 3. AlarmManager: Clock-exact user reminder waking the device from idle
fun scheduleMorningAlarm(context: Context, triggerEpochMs: Long, pendingIntent: PendingIntent) {
    val alarmManager = context.getSystemService(AlarmManager::class.java)
    alarmManager.setExactAndAllowWhileIdle(AlarmManager.RTC_WAKEUP, triggerEpochMs, pendingIntent)
}
```

## Explanation in Arabic

متى تختار Coroutines، أو WorkManager، أو Foreground Service، أو AlarmManager في Android؟

1. شجرة اتخاذ القرار المعماري (Decision Tree Matrix):
   - **Kotlin Coroutines (`viewModelScope` / `lifecycleScope`)**:
     * **طبيعة العمل**: عمل غير متزامن فوري مرتبط بدورة حياة الشاشة (Immediate In-Process Work).
     * **أمثلة**: جلب بيانات لعرضها في الشاشة، تصفية قائمة محلياً، أو استجابة لضغطة زر أثناء تواجد المستخدم في الشاشة.
     * **مصيره عند خروج المستخدم**: يُلغى فوراً مع انتهاء الـ Scope (لا يعيش بعد تدمير الشاشة أو موت الـ Process).
   - **WorkManager (العمل المستمر الموثوق - Persistent / Deferrable Work)**:
     * **طبيعة العمل**: عمل يجب تنفيذه حتماً حتى لو أغلق المستخدم التطبيق، أو مات الـ Process، أو أعيد تشغيل الهاتف (Survives Process Death & Device Reboot).
     * **أمثلة**: مزامنة التعديلات غير المتصلة (Offline Sync)، رفع سجلات الأخطاء (Log Upload)، ضغط وتصدير تقرير، أو تنزيل تحديث بيانات دوري.
     * **شروطه**: يقبل التأجيل (Deferrable)، ويخضع لقيود النظام (مثل توفر الإنترنت أو الشاحن).
   - **Foreground Service (الخدمة الأمامية - User-Perceived Long-Running Work)**:
     * **طبيعة العمل**: مهمة مستمرة طويلة الأمد يدركها المستخدم بنشاط وتتطلب إشعاراً دائماً لا يمكن إزالته.
     * **أمثلة**: تشغيل الموسيقى في الخلفية، الملاحة بـ GPS خطوة بخطوة (Turn-by-turn Navigation)، مكالمة فيديو، أو تسجيل الصوت.
   - **AlarmManager (التنبيهات اللحظية الدقيقة - Exact Time-Sensitive Triggers)**:
     * **طبيعة العمل**: إيقاظ الجهاز عند ثانية محددة في المستقبل.
     * **أمثلة**: منبه الاستيقاظ، تنبيه موعد الدواء، أو تذكير التقويم.
     * **تحذير**: لا يُستخدم للـ Network Polling أو المزامنة الدورية؛ بل لتنبيه المستخدم فقط ويتطلب صلاحية `SCHEDULE_EXACT_ALARM`.

## Practical walkthrough

المقارنة العملية بالكود لاختيار الأداة المناسبة حسب طبيعة المهمة:
```kotlin
// 1. Coroutines: عمل فوري مرتبط بالشاشة فقط:
class SearchViewModel : ViewModel() {
    fun onSearchQuery(query: String) {
        viewModelScope.launch { // يُلغى تلقائياً لو خرج المستخدم من الشاشة
            val results = searchApi.query(query)
            _uiState.value = results
        }
    }
}

// 2. WorkManager: عمل دائم يجب أن يكتمل حتماً حتى لو أُغلق التطبيق:
fun scheduleLogUpload(context: Context) {
    val uploadRequest = OneTimeWorkRequestBuilder<UploadLogsWorker>()
        .setConstraints(Constraints.Builder().setRequiredNetworkType(NetworkType.CONNECTED).build())
        .build()
    WorkManager.getInstance(context).enqueueUniqueWork("upload_logs", ExistingWorkPolicy.KEEP, uploadRequest)
}

// 3. AlarmManager: إيقاظ الهاتف في وقت محدد بالثانية لمنبه حقيقي:
fun setExactAlarm(context: Context, triggerAtMillis: Long, pendingIntent: PendingIntent) {
    val alarmManager = context.getSystemService(AlarmManager::class.java)
    alarmManager.setExactAndAllowWhileIdle(AlarmManager.RTC_WAKEUP, triggerAtMillis, pendingIntent)
}
```

## Why it matters and how it works

Coroutines give structured in-process work. WorkManager persists scheduling with constraints and may delay execution. Foreground services require an ongoing user-visible notification and are restricted when starting from background. Exact alarms are for genuinely time-critical alarm/calendar use cases, not routine sync.

## Trade-offs and decision criteria

WorkManager improves durability but trades away exact timing. Foreground service offers ongoing execution subject to platform rules and notification cost. Exact alarm may require special access and harms battery. Choose the narrowest mechanism that satisfies user need.

## Failure modes

Putting upload only in viewModelScope loses it on navigation/process death. Scheduling ordinary polling with exact alarms fights power policy and may be disallowed. Starting foreground service from background can throw on newer Android versions.

## Production perspective

A media app persists an upload and schedules WorkManager; UI observes progress. A user-started live navigation session may use an eligible foreground service. A calendar alarm uses exact alarm only when precise delivery is core to the feature.

## Interview answer — short

Use coroutines in viewModelScope for immediate in-process tasks tied directly to screen lifecycles. Use WorkManager for persistent, deferrable background execution that must survive process death and device reboots, such as offline syncing and analytics uploads. Use Foreground Services only for long-running operations the user actively perceives with a persistent notification like audio playback or navigation. Use AlarmManager strictly for clock-exact, time-critical user alarms, never for routine background data polling.

## Interview answer — structured

Selecting the appropriate background execution mechanism in Android requires evaluating task durability, user awareness, and execution timing precision.
Kotlin coroutines operating within viewModelScope or lifecycleScope manage immediate, in-process asynchronous tasks. When the user leaves the screen or the operating system reclaims the host process, these coroutines cancel cooperatively. This makes them ideal for fetching screen data, debouncing queries, and running presentation animations.
WorkManager serves as the official platform standard for persistent, deferrable background work. It guarantees completion even if the application process dies or the device reboots by persisting job metadata inside an internal SQLite database and delegating execution to the platform JobScheduler. WorkManager is essential for offline outbox synchronization, batch uploads, and database housekeeping under network and battery constraints.
Foreground Services are reserved strictly for long-running tasks that users actively observe and expect to persist while navigating away, such as turn-by-turn GPS navigation, VoIP calls, or music playback. They mandate a persistent system notification and require declaring explicit runtime foregroundServiceType permissions under modern Android platform constraints.
Finally, AlarmManager is intended exclusively for clock-exact, user-facing events such as morning wake-up alarms and medication reminders using exact alarm permissions. It wakes the device CPU from low-power states and should never be used for periodic polling or general background data processing.

## Interview answer — deep senior

Under the hood, modern Android operating system releases—specifically Android 12 through 15—have systematically restricted background execution to maximize battery life and system health.
In earlier Android eras, developers routinely launched background services or scheduled inexact alarms for periodic synchronization. Today, background services face severe restrictions: starting a foreground service from the background throws ForegroundServiceStartNotAllowedException on Android 12 and later, unless the application meets narrow platform exemptions such as handling a high-priority Firebase Cloud Messaging push or user interaction with a home screen widget.
Furthermore, AlarmManager now requires user-granted exact alarm permissions like SCHEDULE_EXACT_ALARM or USE_EXACT_ALARM, which Google Play strictly regulates under policy enforcement. Using exact alarms to poll backend servers wastes radio power and will result in store rejection.
To bridge the gap between deferrable jobs and immediate execution without relying on fragile foreground services, WorkManager provides Expedited Work. Expedited work grants a high-priority execution quota managed by the platform JobScheduler. It executes within seconds of being enqueued, operates without requiring a user-visible notification on Android 12+, and falls back to a temporary foreground service on older API levels.
Staff engineers enforce this operational hierarchy by establishing lint rules: viewModels handle transient in-memory operations, repositories register durable synchronization jobs via WorkManager with exponential backoff, and foreground services remain strictly quarantined behind specialized media or location modules.

## Follow-up questions

- **Interviewer:** "Can WorkManager execute a task every 5 seconds?"
  **Answer:** "No. PeriodicWorkRequest enforces a hard platform minimum interval of 15 minutes to preserve device battery."

- **Interviewer:** "What happens to a coroutine launched in `GlobalScope` when the process dies?"
  **Answer:** "It dies immediately. `GlobalScope` does not survive Android process death; it only outlives the active Activity while the process is warm."
