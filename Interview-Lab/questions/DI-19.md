# DI-19

## Original interview question

A dynamic-feature module needs dependencies supplied by the base app. What are the options?

## What the interviewer evaluates

- Explain the reversed dependency edge of dynamic features.
- Name a supported Hilt entry-point/component-dependency bridge.
- Consider installation, lifecycle, testing, and API boundaries.

## Explanation in Arabic

في dynamic feature، الـbase app لا يعتمد على كود feature بالطريقة العادية؛ feature يعتمد على app. لذلك Hilt لا يجمع annotations في dynamic feature تلقائيًا مثل library module عادي. الحل الموثق: base app يعلن `@EntryPoint` للعقود التي ستحتاجها feature، وfeature يعمل Dagger component بـ`dependencies` على ذلك entry point، ثم يحقن objects الخاصة به. بديل أبسط عند نطاق صغير أن تمرر base-owned interface/factory من مدخل feature، لكن لا تنقل implementation كاملة ولا تفتح graph كلها. لازم تتأكد من وقت install، component lifetime، وإعادة البناء بعد process death.

## Why it matters and how it works

Hilt generates its application components while compiling the base app, which cannot see source symbols located only in an on-demand feature. An entry point exposes a deliberate subset of base bindings. A Dagger component in the feature can depend on that exposed contract and own feature-specific bindings. The feature still must request/install before instantiating its entry point, and it must not retain Activity dependencies beyond their component lifetime.

## Worked example

The base app owns `AccountRepository` and `Telemetry`. It exposes both through a `FeatureDependencies` entry point installed in `SingletonComponent`. An on-demand `receipt` feature defines `ReceiptComponent(dependencies = [FeatureDependencies])` and injects its screen coordinator after installation. The coordinator receives interfaces; it does not reach into the base app's internal database types.

## Trade-offs and decision criteria

Entry point plus component dependency is explicit and scales across several injected types, but adds Dagger setup and requires version-compatible boundaries. Passing a small factory through navigation can be easier for one feature. A broad service locator hides the dependency contract and makes feature tests harder. Choose the component based on actual lifetime, not convenience.

## Failure modes

The feature assumes Hilt can aggregate its bindings into base-generated code. The entry point leaks internal app implementations. Feature code resolves an Activity binding from a process component. An install is canceled while code tries to navigate to an unloaded class. Tests compile only the base module and never exercise feature injection.

## Production perspective

Keep the exported contract stable and small, add an installed-feature integration test for each supported variant, and test canceled/failed installation and process recreation. Monitor module API compatibility and dependency cycles as the feature evolves.

## Interview answer — short

“Because the base app cannot compile against a dynamic feature's classes, I expose a narrow base Hilt entry point and use a feature Dagger component dependency, or pass a small factory explicitly.”

## Interview answer — structured

“I first account for Gradle's dependency direction: the on-demand module sees the base app, while the base app cannot aggregate its feature-only bindings. The documented Hilt approach is a base `@EntryPoint` that exposes needed interfaces and a Dagger component in the feature depending on that entry point. For a very small seam, an explicit factory passed at navigation can be simpler. I keep implementation details behind contracts and test actual feature installation and injection.”

## Interview answer — deep senior

“A dynamic feature changes the composition problem. The base app's Hilt component is generated without knowing the feature's source types, so I cannot assume the normal multi-module Hilt pattern will discover a module declared only there. I put stable interfaces in a contract both sides can compile against and expose the base-owned bindings through a narrow Hilt entry point. The feature defines its own Dagger component with that entry point as a dependency and injects feature-owned classes after installation. If the seam is tiny, passing a base-created factory explicitly may lower complexity. I evaluate the required lifecycle carefully: process-safe repositories can be exposed from the Singleton component, but a screen owner should be supplied from a live Activity boundary rather than smuggled through an application entry point. I test split install success, failure or cancellation, navigation after installation, and recreation when the process has been killed. The public contract stays small so changing base internals does not force feature churn. I also build the actual delivery variant, because compiling a feature in isolation cannot prove the integrated graph works.”

## Deep-dive talking points

Explain reversed Gradle edges, base visibility, entry points, component dependencies, install timing, and exported API size.

## Follow-up questions

- Why does ordinary Hilt aggregation fail here? **Answer:** base compilation cannot see classes declared only in the dynamic feature.
- What should the entry point expose? **Answer:** the minimal stable base-owned interfaces needed by the feature.
- What extra test is essential? **Answer:** an integrated installed-feature path that proves component creation and injection.
