# DI-19

## Original interview question

A dynamic-feature module needs dependencies supplied by the base app. What are the options?

## What the interviewer evaluates

- Explain the reversed dependency edge of dynamic features.
- Name a supported Hilt entry-point/component-dependency bridge.
- Consider installation, lifecycle, testing, and API boundaries.

## Concept and technical explanation

Injecting dependencies into Dynamic Feature Modules (DFMs) presents an architectural challenge due to inverted Gradle module dependencies. In Android App Bundles, dynamic feature modules depend on the base :app module, but the base module cannot depend on the dynamic feature module. Consequently, Hilt's standard top-down monolithic component generation cannot incorporate DFM-specific classes into the root SingletonComponent. To resolve this dependency inversion and share base app resources (such as repositories, network engines, and storage clients) with on-demand dynamic features, engineers utilize Dagger component dependencies or Hilt EntryPoints combined with interface extraction in core library modules.

## Practical walkthrough (English)

Supplying dependencies to Dynamic Feature Modules:
```
Module Topology:
:core:di (Base interfaces) <--- :app (Implements bindings)
         ^                         ^
         |                         | (Gradle dependency)
:feature:dynamic_checkout --------+
```
Implementation using Hilt EntryPoint and Component Dependencies:
```kotlin
// In :core:di (Accessible to both :app and :dynamic_checkout)
@EntryPoint
@InstallIn(SingletonComponent::class)
interface DynamicFeatureDependencies {
    fun networkClient(): OkHttpClient
    fun userRepository(): UserRepository
}

// In :feature:dynamic_checkout (Downloaded on demand, cannot use standard Hilt annotations)
class DynamicCheckoutActivity : AppCompatActivity() {

    private val dependencies: DynamicFeatureDependencies by lazy {
        EntryPointAccessors.fromApplication(
            applicationContext,
            DynamicFeatureDependencies::class.java
        )
    }

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        // Access base app singletons seamlessly inside dynamic feature
        val userRepo = dependencies.userRepository()
    }
}
```

## Explanation in Arabic

موديول ميزة ديناميكية (Dynamic-Feature Module) يحتاج إلى تبعيات موفرة من تطبيق الأساس (Base App Module). ما هي الحلول والخيارات المعمارية في Hilt؟

1. التحدي المعماري للـ Dynamic Feature Modules (DFMs):
   - في موديولات أندرويد العادية، يعتمد موديول الـ `:app` على الموديولات الفرعية (`:app -> :feature`).
   - في الـ Dynamic Features (التي يتم تنزيلها عند الطلب عبر Play Feature Delivery)، **تنعكس العلاقة**: موديول الـ DFM هو الذي يعتمد على `:app` (`:dynamic_feature -> :app`)، ولا يعرف `:app` أي كود داخل الـ DFM في وقت التجميع!
   - بسبب هذا الانعكاس، يعجز Hilt عن تجميع الـ Modules الخاصة بالـ DFM داخل الـ `SingletonComponent` الرئيسي في `:app`.

2. الخيارات والحلول المعمارية المعتمدة:
   - **الحل الرسمي الأقوى (Hilt `@EntryPoint`)**:
     * يحدد الـ Base App واجهات التبعيات العامة في `:app` أو `:core`.
     * داخل الـ Dynamic Feature، ينشئ المطور `@EntryPoint` لاستخراج التبعيات من الـ `applicationContext` عبر `EntryPoints.get()`.
   - **الحل الثاني: Dagger Component Dependencies**:
     * إنشاء Dagger Component مستقل داخل الـ DFM يعلن عن اعتماده على الـ Base Component: `@Component(dependencies = [BaseAppComponent::class])`.
   - **الحل الثالث: Pure Manual DI / Interfaces Boundary**:
     * تمرير واجهات التبعيات عبر Navigation Intents أو Factory Provider مسجل في طبقة الأساس.

## Practical walkthrough

استخدام @EntryPoint لتمرير التبعيات من الـ Base App إلى الـ Dynamic Feature Module:
```kotlin
// 📁 في موديول ':core' (مرئي لكل من :app و :dynamic_feature):
@EntryPoint
@InstallIn(SingletonComponent::class)
interface DynamicFeatureDependencies {
    fun getAuthRepository(): AuthRepository
    fun getNetworkClient(): OkHttpClient
}

// 📁 داخل موديول ':feature_on_demand' (Dynamic Feature Module):
// يتم استخراج التبعيات داخل الـ Activity أو Fragment الخاص بالميزة عند تنزيلها:
class DynamicFeatureActivity : ComponentActivity() {
    private lateinit var authRepository: AuthRepository

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        
        // سحب التبعيات من Base App Graph عبر الـ EntryPoint:
        val dependencies = EntryPoints.get(
            applicationContext,
            DynamicFeatureDependencies::class.java
        )
        
        authRepository = dependencies.getAuthRepository()
    }
}
```

## Why it matters and how it works

Hilt generates its application components while compiling the base app, which cannot see source symbols located only in an on-demand feature. An entry point exposes a deliberate subset of base bindings. A Dagger component in the feature can depend on that exposed contract and own feature-specific bindings. The feature still must request/install before instantiating its entry point, and it must not retain Activity dependencies beyond their component lifetime.

## Worked example

The base app owns `AccountRepository` and `Telemetry`. It exposes both through a `FeatureDependencies` entry point installed in `SingletonComponent`. An on-demand `receipt` feature defines `ReceiptComponent(dependencies = [FeatureDependencies])` and injects its screen coordinator after installation. The coordinator receives interfaces; it does not reach into the base app's internal database types.

### Kotlin / Hilt example

The entry point is declared in the base app; the Dagger component and Activity are compiled in the installed feature. `AccountRepository` is a base-owned interface visible to the feature.

```kotlin
import android.os.Bundle
import androidx.appcompat.app.AppCompatActivity
import dagger.Component
import dagger.hilt.EntryPoint
import dagger.hilt.InstallIn
import dagger.hilt.android.EntryPointAccessors
import dagger.hilt.components.SingletonComponent
import javax.inject.Inject

interface AccountRepository

// Base app module:
@EntryPoint
@InstallIn(SingletonComponent::class)
interface ReceiptDeps {
    fun accountRepository(): AccountRepository
}

// Dynamic feature module:
@Component(dependencies = [ReceiptDeps::class])
interface ReceiptComponent {
    fun inject(activity: ReceiptActivity)

    @Component.Factory
    interface Factory {
        fun create(deps: ReceiptDeps): ReceiptComponent
    }
}

class ReceiptActivity : AppCompatActivity() {
    @Inject lateinit var repository: AccountRepository

    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        val deps = EntryPointAccessors.fromApplication(
            applicationContext, ReceiptDeps::class.java
        )
        DaggerReceiptComponent.factory().create(deps).inject(this)
    }
}
```

In a real project these declarations live in their respective modules, and feature navigation happens only after split installation succeeds.

## Trade-offs and decision criteria

Entry point plus component dependency is explicit and scales across several injected types, but adds Dagger setup and requires version-compatible boundaries. Passing a small factory through navigation can be easier for one feature. A broad service locator hides the dependency contract and makes feature tests harder. Choose the component based on actual lifetime, not convenience.

## Failure modes

The feature assumes Hilt can aggregate its bindings into base-generated code. The entry point leaks internal app implementations. Feature code resolves an Activity binding from a process component. An install is canceled while code tries to navigate to an unloaded class. Tests compile only the base module and never exercise feature injection.

## Production perspective

Keep the exported contract stable and small, add an installed-feature integration test for each supported variant, and test canceled/failed installation and process recreation. Monitor module API compatibility and dependency cycles as the feature evolves.

## Interview answer — short

Because dynamic feature modules depend on the base app while the base app cannot depend on dynamic modules, standard Hilt @AndroidEntryPoint cannot be fully assembled from the base. The primary options are using Hilt Entry Points defined in shared core modules accessed via EntryPointAccessors, or building a custom Dagger component inside the dynamic feature module that declares the base app component as a component dependency.

## Interview answer — structured

Supplying dependencies from the base application to a Dynamic Feature Module requires overcoming an architectural dependency inversion.
In standard multi-module architectures, the :app module depends on all feature modules and serves as the unified assembly root. In Android dynamic delivery, this relationship is inverted: the dynamic feature module depends on :app, while :app has no compile-time knowledge of the dynamic feature. Because Hilt's standard code generator requires the base application to scan all contributing modules, standard monolithic Hilt injection cannot natively construct dynamic feature components.
There are two established architectural solutions.
The first and most modern approach is using Hilt Entry Points. Developers define an @EntryPoint interface in a shared core module that exposes required singletons such as repositories and network clients. When the dynamic module is loaded at runtime via SplitCompat, its Activities and Fragments use EntryPointAccessors.fromApplication() to retrieve these dependencies on demand.
The second approach is using Dagger Component Dependencies. The dynamic module defines its own internal Dagger component that explicitly declares the base app's dependency interface in its dependencies attribute, allowing the dynamic feature to bridge dependencies into its own localized Dagger sub-graph.

## Interview answer — deep senior

Under the hood, Android dynamic feature modules are compiled into separate split APKs and installed on-demand by the Play Core library or SplitCompat runtime. Because the base APK is compiled before the dynamic feature module exists, the base app's SingletonComponent generated by Hilt cannot contain factory providers for classes located inside the dynamic split.
When using the EntryPoint pattern, the dynamic module bypasses the need for base app awareness. By extracting the dependency contract into a shared core library module that both :app and the DFM depend upon, the base app's Hilt component automatically implements the @EntryPoint interface. When the dynamic activity calls EntryPointAccessors.fromApplication(), Hilt casts the application instance to the entry point interface and hands over the required singleton bindings without reflection.
If the dynamic feature requires its own internal dependency injection graph with custom scopes, engineers combine EntryPoints with a local Dagger component. The dynamic component defines a factory taking the extracted base dependencies interface, instantiating an isolated graph that lives only while the dynamic feature is in memory.
Staff engineers favor the EntryPoint approach because it avoids the complexity of manual Dagger subcomponents while maintaining strict binary firewalls between on-demand splits and the base application binary. This guarantees that base APK downloads remain as small as possible while ensuring full type-safe dependency access when dynamic splits are installed.

## How to answer in the interview

- **Why:** dynamic feature reverses the compile-time visibility.
- **How:** base Hilt entry point plus feature Dagger component.
- **Trade-off:** component setup versus small explicit factory.
- **Failure case:** injection attempted before split install.
- **Production solution:** installed-feature and process-recreation tests.

## Follow-up questions

- **Interviewer:** "Can a dynamic feature module use `@AndroidEntryPoint`?"
  **Answer:** "Starting with newer Hilt versions, limited DFM support exists, but standard practice still relies on `@EntryPoint` because DFMs cannot contribute bindings back into the base app's SingletonComponent."

- **Interviewer:** "Why can't `:app` depend on a dynamic feature module?"
  **Answer:** "Because dynamic feature modules are packaged as separate APK splits delivered on-demand by Google Play; a compile-time dependency from `:app` would bundle it into the base APK, defeating dynamic delivery."
