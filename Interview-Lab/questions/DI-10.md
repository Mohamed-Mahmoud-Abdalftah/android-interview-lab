# DI-10

## Original interview question

When do you choose @Binds over @Provides?

## What the interviewer evaluates

- Choose a declarative interface-to-implementation binding when implementation is injectable.
- Choose provider code for third-party builders or computation needed to create a value.
- Keep scopes and qualifiers aligned with the binding rather than claiming one annotation changes lifetime.

## Explanation in Arabic

لو عندك `PaymentsRepositoryImpl @Inject constructor(...) : PaymentsRepository`، فقط محتاج تقول للـgraph إن طلب interface يروح للimplementation؛ `@Binds` abstract function مناسبة ولا تحتاج تنشئ object يدويًا. لو بتبني Retrofit من builder أو Room database أو SDK يحتاج factory/config، استخدم `@Provides` لأن فيه كود لازم يتنفذ. `@Binds` لا تعمل construction logic ولا تختار من runtime config. الاتنين يقدروا يكون عليهم qualifier وscope مناسب، ومكان `@InstallIn` هو اللي يحدد visibility. اختيار annotation مش علاج لسوء lifetime أو اختبار ناقص.

### Practical walkthrough in Egyptian Arabic

لو `RealStore @Inject constructor(...) : Store` جاهزة، `@Binds abstract fun bind(impl: RealStore): Store` أقل code وHilt تستخدم constructor graph. لو محتاج `Retrofit.Builder()` أو conditional config، `@Provides` فيها body. متحاولش `@Binds` على class محتاجة runtime parameter مش في graph، ولا تجعل provider ينشئ object كل مرة بالخطأ لو identity مهمة.

## Why it matters and how it works

Dagger's `@Binds` defines a relationship between one parameter type and a return contract; the implementation must already be constructible in the graph. `@Provides` defines a method whose body constructs or obtains the requested value. Both contribute bindings at compile time, but provider code is more flexible and can hide work. Hilt modules place those rules in a component; scoping is independent from the method kind.

## Worked example

An abstract Hilt module may declare `@Binds abstract fun bindLogger(impl: StructuredLogger): Logger` when `StructuredLogger` has an injected constructor. A separate object module declares `@Provides fun provideApi(retrofit: Retrofit): OrdersApi = retrofit.create(OrdersApi::class.java)`. Both require `@Module` and correct `@InstallIn`; the excerpt omits imports and complete module declarations rather than pretending it compiles alone.

### Kotlin / Hilt example

`@Binds` aliases an injectable implementation; `@Provides` executes construction code. The app supplies its real endpoint through build configuration.

```kotlin
import dagger.Binds
import dagger.Module
import dagger.Provides
import dagger.hilt.InstallIn
import dagger.hilt.components.SingletonComponent
import javax.inject.Inject
import retrofit2.Retrofit

interface CatalogStore
class RealCatalogStore @Inject constructor() : CatalogStore

@Module
@InstallIn(SingletonComponent::class)
abstract class CatalogBindings {
    @Binds abstract fun bind(impl: RealCatalogStore): CatalogStore
}

@Module
@InstallIn(SingletonComponent::class)
object CatalogProviders {
    @Provides fun retrofit(): Retrofit = Retrofit.Builder()
        .baseUrl("https://catalog.example.org/")
        .build()
}
```

## Trade-offs and decision criteria

`@Binds` communicates a simple delegation with less construction boilerplate and often less generated work. `@Provides` handles libraries, dynamic configuration, and values needing validation, at the cost of an imperative body to review. If two implementations exist, a qualifier or distinct contract is needed regardless of annotation. For runtime user data, a factory/assisted mechanism may be more appropriate than a global provider.

## Failure modes

Using `@Binds` when the implementation cannot be constructed produces a missing binding error. A `@Provides` function creates a fresh expensive client per request unintentionally. A provider chooses sandbox or production at runtime using an unsafe flag. A scope is placed on the wrong component. Compile all variants and test endpoint and object-identity behavior.

## Production perspective

Bind owned interfaces declaratively, provide third-party infrastructure in dedicated modules, and keep provider side effects small. Review provider code for credentials, file I/O, and startup cost. Add graph integration tests and release variant assertions beyond consumer unit tests.

## Interview answer — short

“I choose `@Binds` for a simple interface-to-injectable-implementation mapping. I choose `@Provides` when construction needs code, such as a Retrofit factory or third-party builder.”

## Interview answer — structured

“`@Binds` is an abstract declaration: given an injectable implementation, the graph may satisfy a request for its interface with that implementation. It cannot run custom construction logic. `@Provides` is a method that executes to create or retrieve a value, so it fits Retrofit, Room, and SDK factories. Both still need the correct Hilt component installation, qualifiers when same-type bindings exist, and a deliberate scope if sharing is required. I prefer `@Binds` for a pure port-to-adapter mapping because it makes intent clear, and I inspect any `@Provides` body for hidden I/O, wrong endpoints, or accidental repeated expensive creation.”

## Interview answer — deep senior

“The deciding question is whether the binding is a type relationship or a creation algorithm. If `OrdersRepositoryImpl` has an injected constructor and implements `OrdersRepository`, an abstract `@Binds` method expresses exactly that mapping. If I need `Retrofit.Builder` calls, `Room.databaseBuilder`, a third-party SDK factory, or a validated runtime configuration, `@Provides` is the correct tool because the body must execute. The provider parameters themselves come from the graph, so I keep its side effects and startup cost visible. Neither method grants a lifetime automatically; I install into the owning component and scope only when one instance should be reused. Multiple clients need qualifiers or distinct wrapper contracts. I compile production and test variants and run integration checks for endpoint, credentials policy, migration, and instance identity. A graph that compiles can still be wired to the wrong service, so annotation choice is only one part of the design. If the implementation later gains constructor dependencies, a `@Binds` mapping still works as long as those dependencies have bindings. If creation instead requires a runtime builder or environment selection, I move that logic to `@Provides` and test the resulting instance. Neither annotation implies reuse: I would add a scope only when multiple consumers must observe the same object, then verify that identity.”

## How to answer in the interview

- **Why:** aliasing and construction are different binding tasks.
- **How:** Binds for injectable implementation, Provides for builder logic.
- **Trade-off:** concise mapping versus flexible body.
- **Failure case:** unscoped provider creates duplicate resource.
- **Production solution:** scope and variant graph tests.

## Deep-dive talking points

Discuss relationship versus construction, graph-resolvable implementation, provider side effects, qualifiers, scope, and variant tests.

## Follow-up questions

- Can `@Binds` call `Retrofit.create()`? **Answer:** no; it declares a binding relationship, while executable factory code belongs in `@Provides`.
- Does `@Provides` imply Singleton? **Answer:** no; a scope annotation and matching component determine sharing.
- Why test variants if graph compilation passes? **Answer:** a valid provider can still use an incorrect release host, key source, or database migration.

## Self-check rubric

Choose annotation for an interface and an SDK factory, place scope/qualifier correctly, and identify a semantic graph failure.
