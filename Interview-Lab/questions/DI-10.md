# DI-10

## Original interview question

When do you choose @Binds over @Provides?

## What the interviewer evaluates

- Choose a declarative interface-to-implementation binding when implementation is injectable.
- Choose provider code for third-party builders or computation needed to create a value.
- Keep scopes and qualifiers aligned with the binding rather than claiming one annotation changes lifetime.

## Concept and technical explanation

Choosing between @Binds and @Provides is an essential architectural decision regarding code generation efficiency, boilerplate reduction, and design intent in Dagger and Hilt. @Binds is designed specifically for delegating an interface or abstract supertype to a concrete implementation that already possesses an @Inject-annotated constructor. It is declared as an abstract method inside an abstract module or interface, generating zero runtime factory classes and resolving the binding purely within Dagger's compile-time symbol tables. Conversely, @Provides is designed for constructing instances requiring executable imperative code—such as invoking third-party builders, configuring libraries (like Retrofit or Room), resolving complex conditional initialization logic, or passing parameters not managed by the dependency injection graph. @Binds should always be preferred over @Provides whenever mapping an interface to an injectable implementation.

## Practical walkthrough (English)

Contrasting @Binds efficiency with @Provides execution:
```kotlin
// Scenario 1: Interface mapping where you own the implementation class (ALWAYS USE @Binds)
interface UserRepository
class UserRepositoryImpl @Inject constructor(private val api: UserApi) : UserRepository

@Module
@InstallIn(SingletonComponent::class)
abstract class EfficientRepositoryModule {
    // Generates NO Factory class: pure compile-time symbol delegation!
    @Binds
    abstract fun bindUserRepository(impl: UserRepositoryImpl): UserRepository
}

// Scenario 2: Third-party library where you DO NOT own the constructor (MUST USE @Provides)
@Module
@InstallIn(SingletonComponent::class)
object ThirdPartyModule {
    // Generates ThirdPartyModule_ProvideOkHttpClientFactory.class
    @Provides
    @Singleton
    fun provideOkHttpClient(): OkHttpClient = OkHttpClient.Builder().build()
}
```

   - **استخدم `@Binds`**: عندما تريد ربط واجهة (Interface) بتنفيذ ملموس (Concrete Implementation) تملك أنت كوده ولديه بالفعل مشيد معلّم بـ `@Inject` (`@Inject constructor`).
   - **استخدم `@Provides`**: في جميع الحالات الأخرى التي تتطلب كوداً تنفيذياً لإنشاء الكائن:
     * كلاسات من مكتبات خارجية (Retrofit, OkHttp, Room, Gson, Firebase).

2. الفروق الجوهرية تحت الغطاء (Performance & Bytecode):
   - **`@Provides`**: دالة عادية ملموسة تولد كلاس Java منفصل (`Module_ProvideMethodFactory`). يتطلب استدعاؤها تحميل كلاسات إضافية وتمرير مراجع.

المقارنة البرمجية بين الطريقتين والأثر على الكود المولد:

```kotlin
    abstract fun bindRepo(impl: UserRepositoryImpl): UserRepository

```

## Why it matters and how it works

Dagger's `@Binds` defines a relationship between one parameter type and a return contract; the implementation must already be constructible in the graph. `@Provides` defines a method whose body constructs or obtains the requested value. Both contribute bindings at compile time, but provider code is more flexible and can hide work. Hilt modules place those rules in a component; scoping is independent from the method kind.

## Worked example

An abstract Hilt module may declare `@Binds abstract fun bindLogger(impl: StructuredLogger): Logger` when `StructuredLogger` has an injected constructor. A separate object module declares `@Provides fun provideApi(retrofit: Retrofit): OrdersApi = retrofit.create(OrdersApi::class.java)`. Both require `@Module` and correct `@InstallIn`; the excerpt omits imports and complete module declarations rather than pretending it compiles alone.

### Kotlin / Hilt example

`@Binds` aliases an injectable implementation; `@Provides` executes construction code. The app supplies its real endpoint through build configuration.

```kotlin
import dagger.Binds
import dagger.Module
import dagger.Provides
import dagger.hilt.InstallIn
import dagger.hilt.components.SingletonComponent
import javax.inject.Inject
import retrofit2.Retrofit

interface CatalogStore
class RealCatalogStore @Inject constructor() : CatalogStore

@Module
@InstallIn(SingletonComponent::class)
abstract class CatalogBindings {
    @Binds abstract fun bind(impl: RealCatalogStore): CatalogStore
}

@Module
@InstallIn(SingletonComponent::class)
object CatalogProviders {
    @Provides fun retrofit(): Retrofit = Retrofit.Builder()
        .baseUrl("https://catalog.example.org/")
        .build()
}
```

## Trade-offs and decision criteria

`@Binds` communicates a simple delegation with less construction boilerplate and often less generated work. `@Provides` handles libraries, dynamic configuration, and values needing validation, at the cost of an imperative body to review. If two implementations exist, a qualifier or distinct contract is needed regardless of annotation. For runtime user data, a factory/assisted mechanism may be more appropriate than a global provider.

## Failure modes

Using `@Binds` when the implementation cannot be constructed produces a missing binding error. A `@Provides` function creates a fresh expensive client per request unintentionally. A provider chooses sandbox or production at runtime using an unsafe flag. A scope is placed on the wrong component. Compile all variants and test endpoint and object-identity behavior.

## Production perspective

Bind owned interfaces declaratively, provide third-party infrastructure in dedicated modules, and keep provider side effects small. Review provider code for credentials, file I/O, and startup cost. Add graph integration tests and release variant assertions beyond consumer unit tests.

## Interview answer — short

Choose @Binds when mapping an interface to a concrete implementation whose constructor has an @Inject annotation. Declared as an abstract method inside an abstract module, @Binds generates no factory class, reducing DEX size and compilation time. Choose @Provides only when executing imperative setup code, configuring third-party libraries like Retrofit or Room, or handling dynamic initialization logic.

## Interview answer — structured

The choice between @Binds and @Provides centers on whether a dependency requires executable instantiation logic or simple interface delegation.
Developers should choose @Binds whenever they need to bind an interface contract to a concrete class that they own and have annotated with an @Inject constructor. Because the DI framework already knows how to construct the concrete class through its constructor signature, no instantiation code is required. The developer simply writes an abstract method inside an abstract module that takes the implementation as a parameter and returns the interface. Dagger links the two types directly at compile time without generating an intermediate factory class.
Developers must choose @Provides when instantiating classes that cannot use constructor injection. This includes third-party library classes where the source code cannot be modified, instances requiring multi-step builder patterns like Room and Retrofit, or objects configured through conditional runtime logic. Because @Provides methods contain real, executable code, Dagger generates a dedicated Factory class to manage their invocation.
Whenever both annotations could theoretically be used, @Binds is always the superior architectural choice due to its zero-overhead code generation.

## Interview answer — deep senior

Under the hood, the architectural superiority of @Binds over @Provides is directly measurable in build metrics, DEX method counts, and runtime class-loading performance.
When an engineer writes a @Provides method to return an interface from an implementation (e.g., provideRepo(impl: RepoImpl): Repo = impl), Dagger views this as an imperative provider. Consequently, the annotation processor generates a full factory class: RepositoryModule_ProvideRepoFactory. This generated class contains static create() methods, instance provider mechanisms, and proxy method invocations. In a large enterprise codebase with hundreds of interfaces, using @Provides instead of @Binds generates thousands of redundant classes and methods, inflating the APK size and degrading class-loader warm-up speed during app cold start.
In contrast, when using @Binds, Dagger's annotation processor generates zero byte-level classes. Dagger parses the abstract method signature, verifies that RepoImpl satisfies the Repo contract, and immediately updates its internal BindingGraph. In the generated component code, any consumer requesting Repo is handed the factory of RepoImpl directly.
Staff engineers enforce the usage of @Binds through static analysis and custom architecture rules. The presence of a @Provides method whose only purpose is casting a concrete parameter to an interface is treated as a code smell, ensuring that the codebase maximizes compile-time performance and minimizes application binary bloat.

## How to answer in the interview

- **Why:** aliasing and construction are different binding tasks.
- **How:** Binds for injectable implementation, Provides for builder logic.
- **Trade-off:** concise mapping versus flexible body.
- **Failure case:** unscoped provider creates duplicate resource.
- **Production solution:** scope and variant graph tests.

## Deep-dive talking points

Discuss relationship versus construction, graph-resolvable implementation, provider side effects, qualifiers, scope, and variant tests.

## Follow-up questions

- **Interviewer:** "Can `@Binds` take multiple arguments?"
  **Answer:** "No. A `@Binds` method must have exactly one parameter whose type is assignable to the return type."

- **Interviewer:** "Does `@Binds` change the scope of a dependency?"
  **Answer:** "No. If you want the bound interface to be a Singleton, you must apply `@Singleton` to either the `@Binds` declaration or the implementation class."
