# DI-10

## Original interview question

When do you choose @Binds over @Provides?

## What the interviewer evaluates

- Choose a declarative interface-to-implementation binding when implementation is injectable.
- Choose provider code for third-party builders or computation needed to create a value.
- Keep scopes and qualifiers aligned with the binding rather than claiming one annotation changes lifetime.

## Concept and technical explanation

Use `@Binds` for an abstract method that maps one already-bound, assignable implementation type to an interface or supertype. The method has exactly one parameter and no body. The implementation is commonly constructor-injected, but any valid binding can supply it. Use `@Provides` when creation requires executable code: third-party builders, factory calls, configuration, or values the graph cannot construct automatically. Dagger's official API says `@Binds` is likely more efficient than an equivalent pass-through `@Provides`; it does not promise zero generated code, zero runtime overhead, or a measurable APK or startup improvement. Scope and qualifier can apply to either binding method as appropriate.

## Practical walkthrough (English)

Contrasting @Binds efficiency with @Provides execution:
```kotlin
// Scenario 1: A simple interface mapping; @Binds is concise
interface UserRepository
class UserRepositoryImpl @Inject constructor(private val api: UserApi) : UserRepository

@Module
@InstallIn(SingletonComponent::class)
abstract class EfficientRepositoryModule {
    // Abstract alias for an available implementation binding
    @Binds
    abstract fun bindUserRepository(impl: UserRepositoryImpl): UserRepository
}

// Scenario 2: Builder construction needs a method body
@Module
@InstallIn(SingletonComponent::class)
object ThirdPartyModule {
    // Generated implementation details vary by Dagger version and processor
    @Provides
    @Singleton
    fun provideOkHttpClient(): OkHttpClient = OkHttpClient.Builder().build()
}
```

## Explanation in Arabic

`@Binds` تستخدمها لما المسألة مجرد ربط نوع بنوع آخر متوافق: `RepoImpl` موجود له binding والـ method abstract بياخده كمعامل واحد ويرجع `Repo`. `@Inject constructor` طريقة شائعة عشان توفر التنفيذ، لكنه مش شرط على annotation نفسها.

`@Provides` تستخدمها لما لازم تنفذ كود بناء، زي `OkHttpClient.Builder()` أو `Retrofit.Builder()` أو `roomDatabase.userDao()`. ينفع كمان توفر بها interface لو الإنشاء محتاج قراراً أو factory خاصاً. الاتنين ممكن يكون لهم qualifier أو scope صحيح بحسب مكانهم في graph.

وثائق Dagger بتقول إن `@Binds` **غالباً** أكفأ من `@Provides` اللي بترجع نفس المعامل فقط. ما ينفعش أحوّل ده لوعد إن مفيش Factory classes مطلقاً، أو إن حجم APK والـcold start اتحسنوا من غير قياس. الأفضل أختار الأسلوب حسب معنى الـbinding وأراجع generated code لو الأداء فعلاً مشكلة.

## Practical walkthrough

لو `UserRepositoryImpl` له `@Inject constructor`، وعايز تحقنه كـ `UserRepository`، اكتب abstract `@Binds fun bind(impl: UserRepositoryImpl): UserRepository`. لو تنفيذ المستودع جاي من `@Provides` تانية، برضه ممكن `@Binds` تربطه بالواجهة طالما binding التنفيذ متاح.

أما `OkHttpClient` من مكتبة خارجية وبيحتاج `Builder`، فاستخدم `@Provides` بجسم يكوّنه. لو محتاج نفس الـclient بين عدة مستهلكين داخل `SingletonComponent`، ضيف `@Singleton` للـbinding. المثال توضيحي؛ لا يحسب عدد الـFactory classes ولا زمن الإقلاع.

## Why it matters and how it works

Dagger's `@Binds` defines a relationship between one parameter type and a return contract; the implementation must already be constructible in the graph. `@Provides` defines a method whose body constructs or obtains the requested value. Both contribute bindings at compile time, but provider code is more flexible and can hide work. Hilt modules place those rules in a component; scoping is independent from the method kind.

## Worked example

An abstract Hilt module may declare `@Binds abstract fun bindLogger(impl: StructuredLogger): Logger` when `StructuredLogger` has an injected constructor. A separate object module declares `@Provides fun provideApi(retrofit: Retrofit): OrdersApi = retrofit.create(OrdersApi::class.java)`. Both require `@Module` and correct `@InstallIn`; the excerpt omits imports and complete module declarations rather than pretending it compiles alone.

### Kotlin / Hilt example

`@Binds` aliases an injectable implementation; `@Provides` executes construction code. The app supplies its real endpoint through build configuration.

```kotlin
import dagger.Binds
import dagger.Module
import dagger.Provides
import dagger.hilt.InstallIn
import dagger.hilt.components.SingletonComponent
import javax.inject.Inject
import retrofit2.Retrofit

interface CatalogStore
class RealCatalogStore @Inject constructor() : CatalogStore

@Module
@InstallIn(SingletonComponent::class)
abstract class CatalogBindings {
    @Binds abstract fun bind(impl: RealCatalogStore): CatalogStore
}

@Module
@InstallIn(SingletonComponent::class)
object CatalogProviders {
    @Provides fun retrofit(): Retrofit = Retrofit.Builder()
        .baseUrl("https://catalog.example.org/")
        .build()
}
```

## Trade-offs and decision criteria

`@Binds` communicates a simple delegation with less construction boilerplate and often less generated work. `@Provides` handles libraries, dynamic configuration, and values needing validation, at the cost of an imperative body to review. If two implementations exist, a qualifier or distinct contract is needed regardless of annotation. For runtime user data, a factory/assisted mechanism may be more appropriate than a global provider.

## Failure modes

Using `@Binds` when the implementation cannot be constructed produces a missing binding error. A `@Provides` function creates a fresh expensive client per request unintentionally. A provider chooses sandbox or production at runtime using an unsafe flag. A scope is placed on the wrong component. Compile all variants and test endpoint and object-identity behavior.

## Production perspective

Bind owned interfaces declaratively, provide third-party infrastructure in dedicated modules, and keep provider side effects small. Review provider code for credentials, file I/O, and startup cost. Add graph integration tests and release variant assertions beyond consumer unit tests.

## Interview answer — short

Choose `@Binds` for an abstract, single-parameter mapping from an already available implementation binding to an assignable interface. Choose `@Provides` when a body must construct or configure a value. The implementation need not specifically have an `@Inject` constructor if another binding provides it. Dagger says `@Binds` is likely more efficient than pass-through `@Provides`, but exact generated code and startup impact must be measured.

## Interview answer — structured

A `@Binds` method states that one bound type satisfies another contract. It is abstract and accepts exactly one parameter assignable to its return type. Constructor injection is a common way to make that parameter available; a separate provider can also do so. A `@Provides` method contains executable code, so it fits builder construction, third-party factory calls, and configuration logic.

For a trivial pass-through interface binding, I prefer `@Binds` because its intent is clearer and Dagger documents likely efficiency. I do not promise no generated factory or a particular DEX/cold-start gain. Scope and qualifier rules apply independently to either method. I inspect the generated graph and benchmark the app before making performance claims.

## Interview answer — deep senior

The choice is about binding semantics. A `@Binds` method is abstract, has exactly one parameter assignable to its return type, and aliases an already available implementation binding. Dagger documents it as likely more efficient than a pass-through `@Provides` method. A `@Provides` method has a body and can perform construction, call a builder or factory, or adapt parameters into a value. Either method may carry a qualifier or a scope consistent with its component.

An `@Inject` constructor is common for the `@Binds` parameter, but a provider binding may also make that parameter available. Conversely, owning a class does not force `@Binds`: if initialization needs code, `@Provides` may be clearer. Avoid calling the choice an absolute runtime optimization. Generated implementation details can change across Dagger versions and processors, and one binding annotation does not by itself prove a change in DEX size or startup. Inspect generated sources and profile a representative build before making such a claim.

In review, I prefer `@Binds` for a simple interface alias because it states intent, removes a trivial method body, and aligns with official guidance. I prefer `@Provides` for Retrofit, Room, and other construction logic. Scoping is a separate decision: `@Singleton` on a binding installed in `SingletonComponent` means one instance per component instance, while unscoped requests can create new instances.

## How to answer in the interview

- **Rule:** `@Binds` aliases an available assignable binding with an abstract one-parameter method.
- **When code is needed:** `@Provides` runs a body for builders and factories.
- **Nuance:** `@Inject constructor` is common for the parameter, not mandatory.
- **Performance:** Official guidance says likely more efficient; do not promise zero factories or a measurable startup win.
- **Scope:** Component installation and scope are separate decisions.

## Deep-dive talking points

Discuss relationship versus construction, graph-resolvable implementation, provider side effects, qualifiers, scope, and variant tests.

## Follow-up questions

- **Interviewer:** "Can @Binds take more than one parameter?"
  **Answer:** "No. It is an abstract method with exactly one parameter assignable to the return type."

- **Interviewer:** "Must the implementation have @Inject constructor?"
  **Answer:** "No. The parameter type needs an available binding. Constructor injection is common, but another provider can supply it."

- **Interviewer:** "Is @Binds guaranteed to remove factories and improve startup?"
  **Answer:** "Dagger says it is likely more efficient than a pass-through @Provides. Exact generated code and runtime impact depend on the build; I would inspect and measure before claiming a gain."

- **Interviewer:** "Can @Binds be scoped?"
  **Answer:** "Yes. Scope the binding consistently with the component when shared identity is required; scoping is not automatic."
