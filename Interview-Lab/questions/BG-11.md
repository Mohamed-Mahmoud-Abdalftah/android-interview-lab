# BG-11

## Original interview question

How do you avoid duplicate processing when a Worker is retried?

## What the interviewer evaluates

Avoid duplicate processing under Worker retries using stable IDs and state transitions.

## Concept and technical explanation

WorkManager enforces an at-least-once execution guarantee, meaning that transient interruptions, unhandled exceptions, constraint breaks, or process termination before a successful result is committed will cause the system to reschedule and re-execute the worker. To prevent duplicate processing—such as double billing, redundant database writes, or duplicate network mutations—background tasks must be architected with strict idempotency across both client and server boundaries. This entails three core engineering strategies: attaching unique, deterministic client-generated idempotency keys (such as UUIDs) to network requests so the backend can recognize and de-duplicate repeated operations; maintaining transactional local state machines in Room to verify whether an action was already completed prior to invoking remote services; and recording resumable progress checkpoints so retried workers resume from the last committed step rather than restarting from the beginning.

## Practical walkthrough (English)

Enforcing idempotency under worker retries:
```kotlin
// 1. Worker implementing idempotency via local state and remote idempotency keys
class SubmitPaymentWorker(
    appContext: Context,
    params: WorkerParameters,
    private val paymentDao: PaymentDao,
    private val paymentApi: PaymentApi
) : CoroutineWorker(appContext, params) {

    override suspend fun doWork(): Result = withContext(Dispatchers.IO) {
        val paymentId = inputData.getString("PAYMENT_ID") ?: return@withContext Result.failure()
        val localRecord = paymentDao.getPayment(paymentId) ?: return@withContext Result.failure()

        // Local idempotency guard: skip if already executed prior to interruption
        if (localRecord.status == PaymentStatus.COMPLETED) {
            return@withContext Result.success()
        }

        try {
            // Pass deterministic idempotency key to remote server
            val response = paymentApi.chargeCard(
                idempotencyKey = localRecord.clientRequestId,
                amount = localRecord.amount
            )

            // Commit completed state atomically in Room
            paymentDao.updateStatus(paymentId, PaymentStatus.COMPLETED, response.transactionId)
            Result.success()
        } catch (e: IOException) {
            Result.retry() // Rescheduled with exponential backoff; safe because server de-duplicates key
        } catch (e: Exception) {
            Result.failure()
        }
    }
}
```

## Practical walkthrough

كتابة Worker محمي ضد التكرار عند إعادة التشغيل:
```kotlin
class SafePaymentWorker(context: Context, params: WorkerParameters) : CoroutineWorker(context, params) {
    override suspend fun doWork(): Result {
        val operationId = inputData.getString("op_id") ?: return Result.failure()
        val db = EntryPoints.get(applicationContext, DbEntryPoint::class.java).database()
        val api = EntryPoints.get(applicationContext, ApiEntryPoint::class.java).api()

        // 1. فحص محلي: هل تم تأكيد هذه العملية مسبقاً قبل الـ Crash؟
        val record = db.transactionDao().getTransaction(operationId)
        if (record == null) return Result.failure()
        if (record.isConfirmed) {
            // العملية تمت بالفعل في تشغيل سابق! ننهي بنجاح فوري دون تكرار:
            return Result.success()
        }

        return try {
            // 2. إرسال مع Idempotency Key:
            val response = api.submitPayment(idempotencyKey = operationId, record.toRequest())
            
            // 3. تأكيد الحالة محلياً في Room:
            db.transactionDao().markConfirmed(operationId, response.receiptId)
            Result.success()
        } catch (e: IOException) {
            Result.retry() // إعادة المحاولة بأمان
        }
    }
}
```

## Why it matters and how it works

A worker should be reentrant: repeated run from Pending reaches same final state. Local compare-and-set/transaction can prevent two local workers claiming the same row, but only server idempotency protects cross-process/device/unknown commit windows. Classify permanent versus transient failure and keep an audit trail of operation IDs.

## Worked example

Conceptual worker-facing repository API; server contracts are app-specific and must be tested.

## Trade-offs and decision criteria

Local lock/claim reduces redundant concurrent calls but cannot prove server did not commit. Stable server key plus reconciliation costs backend design work but is required for money and other non-idempotent effects. Some read-only workers can simply rerun safely.

## Failure modes

A Worker may send payment then crash before local acknowledgement. Retry with new key charges twice. A non-atomic local check-and-set lets two workers both send. Assuming WorkManager unique name prevents all of this is false.

## Production perspective

A reversal worker persists one operation ID, claims it transactionally, submits under a server key, and records authoritative receipt. On retry it queries status; telemetry flags Pending older than SLA for support.

## Interview answer — short

Avoid duplicate processing under Worker retries by treating WorkManager as an at-least-once execution engine and enforcing strict idempotency. Generate a deterministic client-side UUID or idempotency key and pass it with mutating network calls, allowing the backend to de-duplicate repeated requests. Simultaneously, maintain a local state machine in Room to verify completion before dispatching network calls and resume multi-step workflows from saved checkpoints.

## Interview answer — structured

Preventing duplicate processing during Worker retries requires recognizing that WorkManager provides at-least-once execution rather than exactly-once execution. If a process crash, network timeout, or constraint violation interrupts a worker before it records success, WorkManager automatically reschedules the job.
The primary defense is client-driven idempotency tokens. Before enqueuing work, generate a unique deterministic UUID representing the transaction and store it locally. When the worker invokes backend mutation endpoints, it passes this token in the request headers. If the worker crashes after the server processes the charge but before receiving the acknowledgment, the subsequent retry submits the identical token. The backend detects the existing token and returns the cached success response without repeating the charge.
Locally, the worker must inspect its Room database entity state before making network calls. If a previous attempt succeeded in updating local status or if the transaction identifier is already populated, the worker immediately returns Result.success without executing remote side effects.
For multi-step batch operations, saving incremental progress checkpoints enables retried workers to skip completed units and process only pending items.

## Interview answer — deep senior

Under the hood, the root cause of duplicate background processing is the distributed commit problem between remote servers and local persistence engines. When a Worker issues an HTTP POST request to submit a payment or place an order, the server may process the database transaction and commit the record. However, if the cellular connection drops before the TCP response arrives, or if the Android low-memory killer terminates the app process at that exact millisecond, WorkManager never receives Result.success.
Because WorkManager relies on JobScheduler to reschedule unacknowledged tasks, the worker executes again upon device reboot or network restoration. Without idempotency safeguards, the worker will submit a second charge.
Senior engineers address this vulnerability by designing atomic local-remote state machines. In Room, the business entity starts in a PENDING state with a persistent client-generated UUID. When the worker retries, it first queries the local database: if the status is already marked COMMITTED, it exits immediately.
If the status remains PENDING, the worker issues an idempotent request containing the UUID. The server enforces a unique database index on the idempotency key, transforming potential duplicate inserts into safe read-only queries returning the original transaction payload.
Furthermore, for long-running batch synchronization, staff engineers avoid coarse all-or-nothing retry loops. By persisting granular item-level statuses, the worker queries only items where status equals UNPROCESSED, preventing redundant network payloads and guaranteeing system-wide consistency across arbitrary process interruptions.
