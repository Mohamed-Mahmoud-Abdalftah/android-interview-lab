# BG-11

## Original interview question

How do you avoid duplicate processing when a Worker is retried?

## What the interviewer evaluates

Avoid duplicate processing under Worker retries using stable IDs and state transitions.

## Explanation in Arabic

كيف تتجنب المعالجة المكررة (Duplicate Processing) عندما يُعاد تشغيل الـ Worker بعد عطل أو فشل؟

1. حتمية التكرار في WorkManager (At-Least-Once Execution):
   - يجب أن يدرك كل مهندس أن WorkManager **لا يضمن التنفيذ مرة واحدة فقط (Does NOT guarantee exactly-once)**.
   - إذا أرسل الـ Worker طلباً بنجاح، ومات التطبيق (Process Crash أو Out of Memory) قبل أن يتمكن من كتابة `Result.success()` في قاعدة بيانات WorkManager، سيعتبر WorkManager المهمة فاشلة ويعيد تشغيلها بالكامل عند الإقلاع التالي!

2. استراتيجية الحماية المعمارية ضد التكرار (Idempotent Execution Pipeline):
   - **المعرف الفريد الثابت (Durable Operation ID)**: يجب أن يمرر للمهمة معرف ثابت للعملية (`operationId: UUID`) محفوظ في Room مسبقاً، ولا يجوز توليد معرف جديد داخل الـ Worker.
   - **فحص الحالة المحلية قبل الإرسال (Pre-Flight Local State Check)**:
     * عند بدء تشغيل الـ Worker، يفحص قاعدة بيانات Room أولاً:
     * إذا وجد أن المعاملة مسجلة بالفعل كـ `COMPLETED` أو `ACKNOWLEDGED`، يعيد `Result.success()` فوراً دون لمس السيرفر!
   - **إرسال الـ Idempotency Key للسيرفر**:
     * في طلب الشبكة، يرسل `Idempotency-Key: operationId` لضمان أن السيرفر لن يكرر الخصم أو الإنشاء لو وصله الطلب سابقاً.

## Practical walkthrough

كتابة Worker محمي ضد التكرار عند إعادة التشغيل:
```kotlin
class SafePaymentWorker(context: Context, params: WorkerParameters) : CoroutineWorker(context, params) {
    override suspend fun doWork(): Result {
        val operationId = inputData.getString("op_id") ?: return Result.failure()
        val db = EntryPoints.get(applicationContext, DbEntryPoint::class.java).database()
        val api = EntryPoints.get(applicationContext, ApiEntryPoint::class.java).api()

        // 1. فحص محلي: هل تم تأكيد هذه العملية مسبقاً قبل الـ Crash؟
        val record = db.transactionDao().getTransaction(operationId)
        if (record == null) return Result.failure()
        if (record.isConfirmed) {
            // العملية تمت بالفعل في تشغيل سابق! ننهي بنجاح فوري دون تكرار:
            return Result.success()
        }

        return try {
            // 2. إرسال مع Idempotency Key:
            val response = api.submitPayment(idempotencyKey = operationId, record.toRequest())
            
            // 3. تأكيد الحالة محلياً في Room:
            db.transactionDao().markConfirmed(operationId, response.receiptId)
            Result.success()
        } catch (e: IOException) {
            Result.retry() // إعادة المحاولة بأمان
        }
    }
}
```

## Why it matters and how it works

A worker should be reentrant: repeated run from Pending reaches same final state. Local compare-and-set/transaction can prevent two local workers claiming the same row, but only server idempotency protects cross-process/device/unknown commit windows. Classify permanent versus transient failure and keep an audit trail of operation IDs.

## Worked example

Conceptual worker-facing repository API; server contracts are app-specific and must be tested.

```kotlin
interface PendingOperationStore {
    suspend fun claim(id: String): Boolean
    suspend fun markAcknowledged(id: String, serverReceipt: String)
    suspend fun state(id: String): OperationState
}
// Worker checks state, sends idempotency key=id, then records receipt.
// On timeout it queries server status before repeating.
```

## Trade-offs and decision criteria

Local lock/claim reduces redundant concurrent calls but cannot prove server did not commit. Stable server key plus reconciliation costs backend design work but is required for money and other non-idempotent effects. Some read-only workers can simply rerun safely.

## Failure modes

A Worker may send payment then crash before local acknowledgement. Retry with new key charges twice. A non-atomic local check-and-set lets two workers both send. Assuming WorkManager unique name prevents all of this is false.

## Production perspective

A reversal worker persists one operation ID, claims it transactionally, submits under a server key, and records authoritative receipt. On retry it queries status; telemetry flags Pending older than SLA for support.

## Interview answer — short

Prevent duplicate processing under Worker retries by treating WorkManager as at-least-once. Pass a persistent operation ID into the worker, check local database state before executing to return success if already completed, and attach client-generated Idempotency Keys to all network requests.

## Interview answer — structured

Because WorkManager enforces **At-Least-Once delivery semantics**, workers will occasionally run multiple times for the same logical operation (e.g. if the process is killed after network transmission but before WorkManager marks the task succeeded in SQLite).

To guarantee idempotent processing without duplicate side-effects:

1. **Durable Operation Identity**: Never generate operation UUIDs dynamically inside `doWork()`. The business operation ID must be generated upstream, saved to Room, and passed into the worker via `Data.Builder().putString("operation_id", id)`.

2. **Pre-Flight State Validation**: The first action inside `doWork()` is checking local SQLite state: `if (repository.isOperationAcknowledged(opId)) return Result.success()`. If a previous run already completed the work before a crash, exit immediately.

3. **Wire-Level Idempotency**: Transmit `Idempotency-Key: <operationId>` on the network call. If the previous attempt succeeded on the backend, the server returns the cached response rather than duplicating the write.

4. **Atomic Local Commitment**: Persist the server acknowledgment in Room before returning `Result.success()`.

## Interview answer — deep senior

A subtle failure mode is the **Crash-After-Commit Window**:

```kotlin
api.chargeCard(idempotencyKey, payload) // 1. Server commits card charge
// <-- PROCESS KILLED BY OS HERE!
db.markConfirmed(id)                   // 2. Never executes
return Result.success()                 // 3. Never executes
```
When WorkManager re-runs the worker, the local database still shows `status = PENDING`. Because the worker uses the *identical* `idempotencyKey`, the payment API returns the previously generated charge receipt (`HTTP 200` with `Idempotent-Replayed: true`). The worker parses the receipt, updates SQLite to `status = CONFIRMED`, and returns `Result.success()`. The customer is charged exactly once.

## How to answer in the interview

- **Why:** scheduler retries can replay effects.
- **How:** stable identity and server dedup.
- **Trade-off:** availability versus duplicate risk.
- **Failure case:** local flag says unsent after remote commit.
- **Production solution:** contract test lost response and status lookup.

## Deep-dive talking points

Draw attempts versus one logical operation and the server-commit/client-ack gap.

## Follow-up questions

- **Interviewer:** "Can `runAttemptCount` help detect retries in WorkManager?"
  **Answer:** "Yes. `runAttemptCount` exposes how many times this specific worker has been retried, allowing you to trigger reconciliation on repeated retries."

- **Interviewer:** "What happens if a worker never returns a Result?"
  **Answer:** "If a worker hangs or blocks its thread without completing, the OS eventually terminates the worker when timeouts or constraints expire, scheduling a retry."
