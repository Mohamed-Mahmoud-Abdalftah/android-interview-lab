# BG-11

## Original interview question

How do you avoid duplicate processing when a Worker is retried?

## What the interviewer evaluates

Avoid duplicate processing under Worker retries using stable IDs and state transitions.

## Explanation in Arabic

WorkManager ممكن تشغّل نفس logical work مرة تانية بعد crash/retry. لازم worker تقرأ durable operation ID، تشوف هل acknowledged، وتبعته بنفس idempotency key للسيرفر. backend يعمل deduplication ويتحقق من payload؛ بعد lost response نستعلم عن status. `unique work` تقلل duplicate schedules لكنها مش exactly-once processing.

### Practical walkthrough in Egyptian Arabic

WorkManager قد يعيد Worker بعد crash أو نتيجة غير مؤكدة، لذلك `doWork()` لازم يتحمل at-least-once execution. استخدم stable operation ID محفوظ في DB، وسجل step status محليًا، والbackend يفرض idempotency. لا تعمل “check then send” في client وحده؛ جهاز آخر أو crash بين الخطوتين يكسرها. اختبر lost response ثم retry بنفس ID، وراقب attempts والunknown outcomes.

## Why it matters and how it works

A worker should be reentrant: repeated run from Pending reaches same final state. Local compare-and-set/transaction can prevent two local workers claiming the same row, but only server idempotency protects cross-process/device/unknown commit windows. Classify permanent versus transient failure and keep an audit trail of operation IDs.

## Worked example

Conceptual worker-facing repository API; server contracts are app-specific and must be tested.

```kotlin
interface PendingOperationStore {

// Worker checks state, sends idempotency key=id, then records receipt.
// On timeout it queries server status before repeating.
```

## Trade-offs and decision criteria

Local lock/claim reduces redundant concurrent calls but cannot prove server did not commit. Stable server key plus reconciliation costs backend design work but is required for money and other non-idempotent effects. Some read-only workers can simply rerun safely.

## Failure modes

A Worker may send payment then crash before local acknowledgement. Retry with new key charges twice. A non-atomic local check-and-set lets two workers both send. Assuming WorkManager unique name prevents all of this is false.

## Production perspective

A reversal worker persists one operation ID, claims it transactionally, submits under a server key, and records authoritative receipt. On retry it queries status; telemetry flags Pending older than SLA for support.

## Interview answer — short

“Workers may retry, so I make the logical operation idempotent. I store a stable ID, check durable state, use the same server key, and reconcile unknown outcomes. Unique work alone does not prevent duplicate effects.”

## Interview answer — structured

“A worker is an attempt, not the business operation itself. I persist a logical operation with a stable ID before scheduling. Each run checks whether it is already acknowledged, claims it if needed, and calls a server endpoint that deduplicates the ID. If a response is lost, the next run asks for authoritative status rather than inventing a new operation. Local transactions reduce overlapping attempts, but server idempotency covers the crash window after remote commit. Tests deliberately run the Worker twice.”

## Interview answer — deep senior

“I enumerate the failure windows: crash before send, after send but before server commit, after commit but before response, and after response but before local acknowledgement. A stable operation ID and server status endpoint let each retry converge to the same logical outcome. Local claim/CAS prevents concurrent workers in one database from duplicating requests, but cannot coordinate all clients or undo remote side effects. WorkManager unique scheduling and backoff are operational tools, not exactly-once guarantees. I preserve an audit trail and use business-specific conflict handling. Tests force duplicate workers and each crash window, checking one ledger effect and eventual local acknowledgement. Retry with new key charges twice. The classic failure is server success followed by client crash before writing local success. The next run cannot infer failure from the local pending row. It queries status or retries with the same server-enforced operation key and identical parameters. Unique work prevents some duplicate scheduling in one app installation but not replay across crashes, restored backups, multiple devices or concurrent backend handlers. I keep retry attempts and the logical operation separate in logs so operators can reconcile. I test a server that commits then drops the connection, duplicate workers racing, a changed payload under the same ID, and retention expiry, because deduplication has a bounded provider contract.”

## How to answer in the interview

- **Why:** scheduler retries can replay effects.
- **How:** stable identity and server dedup.
- **Trade-off:** availability versus duplicate risk.
- **Failure case:** local flag says unsent after remote commit.
- **Production solution:** contract test lost response and status lookup.
