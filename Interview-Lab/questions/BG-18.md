# BG-18

## Original interview question

A payment reversal must eventually reach backend after app exits. What durable mechanism and server contract do you need?

## What the interviewer evaluates

Make payment reversal durable after app exit with server idempotency and reconciliation.

## Concept and technical explanation

Executing a mission-critical payment reversal that must survive application termination, process reclamation, and network failure requires combining an offline-first transactional durable mechanism with an idempotent, auditable backend server contract. Relying on transient coroutines in viewModelScope or lifecycleScope is unacceptable because the host process may be destroyed before network delivery. The client-side mechanism relies on the Transactional Outbox pattern: within an atomic Room database transaction, the application records a persistent reversal intent (with unique client-generated reversal UUID, parent payment reference, timestamp, and payload) before enqueuing a durable WorkManager OneTimeWorkRequest configured with network constraints and exponential backoff. The server contract mandates an idempotent endpoint (accepting an Idempotency-Key header with strict deduplication), a state-query reconciliation probe endpoint, and strict HTTP status semantics distinguishing retryable server/transport errors (HTTP 5xx, network drops) from non-retryable domain rejections (HTTP 4xx).

## Practical walkthrough (English)

Implementing durable payment reversal and server contract:
```kotlin
// 1. Transactional Outbox commit in Room + WorkManager durable enqueue
class PaymentRepository(
    private val db: AppDatabase,
    private val paymentDao: PaymentDao,
    private val workManager: WorkManager
) {
    suspend fun schedulePaymentReversal(paymentId: String, reason: String) = withContext(Dispatchers.IO) {
        val reversalId = UUID.randomUUID().toString()
        val reversalEntity = PaymentReversalEntity(
            reversalId = reversalId,
            paymentId = paymentId,
            reason = reason,
            status = ReversalStatus.PENDING,
            createdAtEpoch = System.currentTimeMillis()
        )

        // Step A: Atomic local commit to Room (Survives immediate app kill)
        db.withTransaction {
            paymentDao.insertReversal(reversalEntity)
        }

        // Step B: Enqueue durable WorkManager task with Exponential Backoff
        val request = OneTimeWorkRequestBuilder<PaymentReversalWorker>()
            .setInputData(workDataOf("REVERSAL_ID" to reversalId))
            .setConstraints(Constraints.Builder().setRequiredNetworkType(NetworkType.CONNECTED).build())
            .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 15, TimeUnit.SECONDS)
            .build()

        workManager.enqueueUniqueWork("reversal_$reversalId", ExistingWorkPolicy.KEEP, request)
    }
}

// 2. Durable Worker executing with server contract
class PaymentReversalWorker(
    appContext: Context,
    params: WorkerParameters,
    private val paymentDao: PaymentDao,
    private val paymentApi: PaymentApi
) : CoroutineWorker(appContext, params) {

    override suspend fun doWork(): Result = withContext(Dispatchers.IO) {
        val reversalId = inputData.getString("REVERSAL_ID") ?: return@withContext Result.failure()
        val reversal = paymentDao.getReversal(reversalId) ?: return@withContext Result.failure()

        if (reversal.status == ReversalStatus.COMPLETED) return@withContext Result.success()

        try {
            // Idempotent Server Contract: Idempotency-Key header guarantees single execution
            val response = paymentApi.reversePayment(
                idempotencyKey = reversal.reversalId,
                paymentId = reversal.paymentId,
                reason = reversal.reason
            )
            paymentDao.updateReversalStatus(reversalId, ReversalStatus.COMPLETED, response.reversalReceiptId)
            Result.success()
        } catch (e: HttpException) {
            when (e.code()) {
                in 500..599 -> Result.retry() // Server transient outage: retry with exponential backoff
                else -> {
                    paymentDao.updateReversalStatus(reversalId, ReversalStatus.FAILED, null)
                    Result.failure() // 4xx: unrecoverable domain failure, stop retry loop
                }
            }
        } catch (e: IOException) {
            Result.retry() // Network drop: retry when connectivity returns
        }
    }
}
```

## Explanation in Arabic

عملية عكس/استرداد مالي (Payment Reversal) يجب أن تصل إلى السيرفر حتماً حتى بعد خروج التطبيق. ما هي الآلية المتينة (Durable Mechanism) وعقد السيرفر المطلوب؟

1. خطورة المعاملة المالية عند خروج التطبيق:
   - المستخدم ضغط على 'إلغاء الطلب واسترداد المبلغ'.
   - خرج المستخدم من التطبيق أو أغلق الهاتف في نفس اللحظة.
   - إذا اعتمد التطبيق على Coroutine في الـ ViewModel، ستُلغى العملية فوراً، وسيظل طلب المستخدم معلقاً ولن يسترد أمواله!

2. الآلية المتينة المحلية (Durable Client Mechanism):
   - **تسجيل نية الاسترداد في Room أولاً (Transactional Outbox)**:
     * قبل إظهار أي رد للـ UI، يتم حفظ المعاملة في جدول `payment_reversals` في Room: `reversalId: UUID`, `originalTransactionId`, `amount`, `status = PENDING_DISPATCH`.
     * الـ UI تعرض للمستخدم: 'تم طلب الإلغاء، جارِ المعالجة'.
   - **جدولة المهمة عبر WorkManager**:
     * إطلاق `OneTimeWorkRequestBuilder<PaymentReversalWorker>()` كـ Unique Work بسياسة `APPEND_OR_REPLACE` مع شرط `NetworkType.CONNECTED`.
     * سيقوم WorkManager بتنفيذ العملية حتماً حتى لو أُغلق التطبيق أو أعيد تشغيل الهاتف.

3. عقد السيرفر الإلزامي (The Mandatory Server Contract):
   - **Idempotency Key**: يرسل العميل `Idempotency-Key: reversalId`. يمنع السيرفر تكرار الاسترداد إذا أُعيد تشغيل الـ Worker.
   - **State Reconciliation Endpoint**: توفير endpoint استقصائي (`GET /payments/{id}/reversal-status`) يتيح للـ Worker التحقق من حالة الاسترداد لو انقطعت الشبكة بعد إرسال الطلب وقبل استلام الرد.

## Practical walkthrough

التطبيق المعماري المتكامل لنظام استرداد المدفوعات المتين:
```kotlin
// 1. تسجيل نية الاسترداد محلياً في Room أولاً:
class PaymentReversalRepositoryImpl @Inject constructor(
    private val db: AppDatabase,
    private val workManager: WorkManager
) : PaymentReversalRepository {

    override suspend fun requestPaymentReversal(transactionId: String, amountCents: Long): ReversalResult {
        val reversalId = "rev_${transactionId}_$amountCents"
        
        db.withTransaction {
            db.reversalDao().insertIntent(
                ReversalEntity(
                    id = reversalId,
                    transactionId = transactionId,
                    amountCents = amountCents,
                    status = ReversalStatus.PENDING
                )
            )
        }

        // جدولة موثوقة في WorkManager:
        val workRequest = OneTimeWorkRequestBuilder<PaymentReversalWorker>()
            .setInputData(workDataOf("reversal_id" to reversalId))
            .setConstraints(Constraints.Builder().setRequiredNetworkType(NetworkType.CONNECTED).build())
            .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 15, TimeUnit.SECONDS)
            .build()

        workManager.enqueueUniqueWork("reversal_$reversalId", ExistingWorkPolicy.KEEP, workRequest)
        return ReversalResult.Submitted(reversalId)
    }
}

// 2. الـ Worker المتين المحمي ضد التكرار وانقطاع الشبكة:
class PaymentReversalWorker(context: Context, params: WorkerParameters) : CoroutineWorker(context, params) {
    override suspend fun doWork(): Result {
        val revId = inputData.getString("reversal_id") ?: return Result.failure()
        val db = EntryPoints.get(applicationContext, DbEntryPoint::class.java).database()
        val api = EntryPoints.get(applicationContext, PaymentApiEntryPoint::class.java).api()

        val entity = db.reversalDao().getReversal(revId) ?: return Result.failure()
        if (entity.status == ReversalStatus.CONFIRMED) return Result.success()

        return try {
            val response = api.executeReversal(idempotencyKey = entity.id, transactionId = entity.transactionId)
            db.reversalDao().markConfirmed(revId, response.settlementId)
            Result.success()
        } catch (e: IOException) {
            Result.retry()
        }
    }
}
```

## Why it matters and how it works

Reversal is an authoritative server state transition, potentially subject to settlement windows and partial/duplicate constraints. Persist operation ID, original payment ID, amount and reason securely. Worker uses stable key, queries status before retry, and records receipt. Backend ledger enforces uniqueness and valid state transitions.

## Trade-offs and decision criteria

WorkManager improves eventual attempts but cannot guarantee immediate execution or final financial outcome. Server idempotency and status lookup add backend complexity but protect money. Support escalation is needed for unresolved Pending beyond SLA.

## Failure modes

A retry with a new reversal ID can credit twice. A worker may stop after server acceptance; treating cancellation as failed can prompt a duplicate user action. A reversal may be rejected because original payment already settled or was reversed; local code cannot override ledger rules.

## Production perspective

A wallet app stores reversal Pending, queues network-constrained unique work and shows progress from Room. Worker reconciles server status, submits with stable key when safe, and records receipt. Alerts monitor pending age and support has correlation IDs without sensitive data.

## Interview answer — short

Execute a durable payment reversal by committing the reversal intent with a unique UUID to a Room database in an atomic transaction before enqueuing a WorkManager OneTimeWorkRequest with connected network constraints. Pair this with an idempotent backend contract that enforces an Idempotency-Key header, supports status reconciliation queries, and returns clear HTTP status codes distinguishing transient 5xx retries from non-retryable 4xx client errors.

## Interview answer — structured

Guaranteeing that a payment reversal reaches the backend after application exit requires coupling a resilient local persistence mechanism with an idempotent server contract.
The client mechanism relies on the Transactional Outbox pattern implemented through Room and WorkManager. When a reversal is triggered, the repository generates a persistent UUID and commits the reversal record into the Room database with a PENDING status inside an atomic transaction. Only after this commit succeeds does the repository enqueue a OneTimeWorkRequest with connected network constraints and exponential backoff. Because WorkManager serializes the job to disk, execution is guaranteed even if the user swipes away the application or the device reboots.
The server contract requires an idempotent API endpoint that accepts the client-generated UUID via an Idempotency-Key header. The backend logs this key in a transactional database ledger; repeated calls with the same key return the original cached receipt without executing duplicate reversals.
The contract must also provide a query endpoint to verify reversal state if network timeouts occur, and enforce strict status semantics where transient 5xx errors trigger retries while permanent 4xx failures terminate cleanly.

## Interview answer — deep senior

Under the hood, financial reversals in mobile systems present the most acute distributed consensus challenges due to asynchronous network partitions and process teardowns. If a reversal is dispatched through standard in-memory scopes, the user pressing the home button followed by the OS reclaiming memory halts the network socket midway, leaving the transaction in an ambiguous state where money may remain deducted or improperly credited.
Senior engineers construct a fault-tolerant multi-layered safety net. In the client layer, the Room database guarantees durable local write-ahead logging before network dispatch.
In the WorkManager layer, exponential backoff (e.g., 15s, 30s, 60s, up to platform caps) ensures that temporary payment gateway outages do not create a denial-of-service avalanche.
The server contract must support distributed two-phase reconciliation. When the backend receives the reversal request, it validates the Idempotency-Key against an atomic database table with a unique constraint. If the worker encounters a network timeout after the server committed the reversal, the retried worker resends the identical key; the backend detects the prior commit and returns HTTP 200 with the original reversal receipt.
Furthermore, staff engineers establish a dead-letter queue and dual-trigger reconciliation: if a reversal encounters repeated 5xx errors exceeding a max retry threshold, the record transitions to REQUIRES_MANUAL_AUDIT in Room, alerting internal analytics.
Simultaneously, a low-frequency periodic reconciliation worker scans the outbox table for unconfirmed reversals, ensuring that every financial transaction reaches eventual consistency regardless of edge-case operating system crashes.

## Follow-up questions

- **Interviewer:** "What is the difference between a Payment Void and a Payment Refund?"
  **Answer:** "A Void cancels an unsettled transaction before funds transfer; a Refund returns settled funds after the transaction has closed."

- **Interviewer:** "Why shouldn't a payment reversal rely on push notifications to trigger?"
  **Answer:** "Push notifications require device connectivity to receive; an offline client cannot receive a push to initiate work."
