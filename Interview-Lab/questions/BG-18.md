# BG-18

## Original interview question

A payment reversal must eventually reach backend after app exits. What durable mechanism and server contract do you need?

## What the interviewer evaluates

## Why it matters and how it works

Reversal is an authoritative server state transition, potentially subject to settlement windows and partial/duplicate constraints. Persist operation ID, original payment ID, amount and reason securely. Worker uses stable key, queries status before retry, and records receipt. Backend ledger enforces uniqueness and valid state transitions.

## Trade-offs and decision criteria

WorkManager improves eventual attempts but cannot guarantee immediate execution or final financial outcome. Server idempotency and status lookup add backend complexity but protect money. Support escalation is needed for unresolved Pending beyond SLA.

## Failure modes

A retry with a new reversal ID can credit twice. A worker may stop after server acceptance; treating cancellation as failed can prompt a duplicate user action. A reversal may be rejected because original payment already settled or was reversed; local code cannot override ledger rules.

## Production perspective

A wallet app stores reversal Pending, queues network-constrained unique work and shows progress from Room. Worker reconciles server status, submits with stable key when safe, and records receipt. Alerts monitor pending age and support has correlation IDs without sensitive data.

## Interview answer — short

“I persist one reversal operation, schedule WorkManager, and make retries use a stable server-enforced key. The backend ledger validates the original payment and exposes status. The UI shows Pending until reconciliation confirms the outcome.”

## Interview answer — structured

“A reversal must not depend on the screen remaining open. I commit an operation record with a stable ID before enqueueing a Worker. The Worker checks server status, submits under that same ID if appropriate, and stores the authoritative receipt. WorkManager may retry or run later, so the server must deduplicate and enforce valid reversal state transitions. If the response is lost, I keep Pending and reconcile rather than displaying failure or issuing a fresh reversal.”

## Interview answer — deep senior

“I model the reversal as a durable financial state machine. The Android database stores operation ID, original payment reference, amount and Pending status; a startup scan repairs any enqueue gap. WorkManager executes under network constraints and may restart. Each attempt queries ledger status and uses the same idempotency key; the backend prevents duplicate reversals and rejects invalid settlement transitions. A timeout does not imply rejection, so UI remains Pending until an authoritative status/receipt arrives. I monitor oldest Pending age and offer support escalation for unresolved cases. Tests crash after server commit but before local acknowledgement, run the Worker twice and verify only one ledger reversal. The local outbox transaction creates an obligation that survives screen exit and ordinary process death, and WorkManager can retry its delivery when constraints allow. But the phone may remain offline forever, be uninstalled or lose its data; therefore an unconditional “guaranteed eventual delivery” claim would be false. The backend or acquirer must own a matching reconciliation process and an escalation threshold for aging reversals. Each attempt carries the original transaction reference and stable reversal identity under the provider’s contract. I test the server committing then dropping its reply, two workers racing, and a device restart, and I alert on unresolved status rather than silently deleting the row.”

## How to answer in the interview

- **Trade-off:** delayed delivery versus battery/network limits.
- **Failure case:** retry with new ID reverses twice.
- **Production solution:** backend reconciliation and escalation.
