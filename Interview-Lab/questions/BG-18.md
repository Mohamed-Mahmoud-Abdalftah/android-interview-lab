# BG-18

## Original interview question

A payment reversal must eventually reach backend after app exits. What durable mechanism and server contract do you need?

## What the interviewer evaluates

Make payment reversal durable after app exit with server idempotency and reconciliation.

## Concept and technical explanation

The client should persist a reversal intent with a stable ID before the screen exits. A WorkManager worker can retry delivery across ordinary app restarts and device reboots, but a crash between the local commit and enqueue must be repaired by scanning pending records later. The backend must deduplicate the operation ID, expose a status lookup, and keep its own durable record of unresolved reversals. Interpret HTTP and provider responses according to the actual contract; 4xx is not a universal permanent failure rule. A client cannot guarantee eventual delivery while offline indefinitely, force-stopped, or uninstalled. The final `Reversed` state requires provider confirmation, and unresolved cases need reconciliation or an operator path.

## Practical walkthrough (English)

Implementing durable payment reversal and server contract:
```kotlin
// 1. Transactional Outbox commit in Room + WorkManager durable enqueue
class PaymentRepository(
    private val db: AppDatabase,
    private val paymentDao: PaymentDao,
    private val workManager: WorkManager
) {
    suspend fun schedulePaymentReversal(paymentId: String, reason: String) = withContext(Dispatchers.IO) {
        val reversalId = UUID.randomUUID().toString()
        val reversalEntity = PaymentReversalEntity(
            reversalId = reversalId,
            paymentId = paymentId,
            reason = reason,
            status = ReversalStatus.PENDING,
            createdAtEpoch = System.currentTimeMillis()
        )

        // Step A: Commit local intent; scan pending rows if enqueue is interrupted
        db.withTransaction {
            paymentDao.insertReversal(reversalEntity)
        }

        // Step B: Enqueue durable WorkManager task with Exponential Backoff
        val request = OneTimeWorkRequestBuilder<PaymentReversalWorker>()
            .setInputData(workDataOf("REVERSAL_ID" to reversalId))
            .setConstraints(Constraints.Builder().setRequiredNetworkType(NetworkType.CONNECTED).build())
            .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 15, TimeUnit.SECONDS)
            .build()

        workManager.enqueueUniqueWork("reversal_$reversalId", ExistingWorkPolicy.KEEP, request)
    }
}

// 2. Durable Worker executing with server contract
class PaymentReversalWorker(
    appContext: Context,
    params: WorkerParameters,
    private val paymentDao: PaymentDao,
    private val paymentApi: PaymentApi
) : CoroutineWorker(appContext, params) {

    override suspend fun doWork(): Result = withContext(Dispatchers.IO) {
        val reversalId = inputData.getString("REVERSAL_ID") ?: return@withContext Result.failure()
        val reversal = paymentDao.getReversal(reversalId) ?: return@withContext Result.failure()

        if (reversal.status == ReversalStatus.COMPLETED) return@withContext Result.success()

        try {
            // Backend must enforce this key atomically under the provider contract
            val response = paymentApi.reversePayment(
                idempotencyKey = reversal.reversalId,
                paymentId = reversal.paymentId,
                reason = reversal.reason
            )
            paymentDao.updateReversalStatus(reversalId, ReversalStatus.COMPLETED, response.reversalReceiptId)
            Result.success()
        } catch (e: HttpException) {
            when (e.code()) {
                in 500..599 -> Result.retry() // retry under documented API rules
                else -> {
                    paymentDao.updateReversalStatus(reversalId, ReversalStatus.REQUIRES_RECONCILIATION, null)
                    Result.failure() // stop this worker; backend/operator must resolve the record
                }
            }
        } catch (e: IOException) {
            Result.retry() // Network drop: retry when connectivity returns
        }
    }
}
```

class PaymentReversalRepositoryImpl @Inject constructor(
    private val db: AppDatabase,
    private val workManager: WorkManager
) : PaymentReversalRepository {

    override suspend fun requestPaymentReversal(transactionId: String, amountCents: Long): ReversalResult {
        val reversalId = "rev_${transactionId}_$amountCents"
        
        db.withTransaction {
            db.reversalDao().insertIntent(
                ReversalEntity(
                    id = reversalId,
                    transactionId = transactionId,
                    amountCents = amountCents,
                    status = ReversalStatus.PENDING
                )
            )

        val workRequest = OneTimeWorkRequestBuilder<PaymentReversalWorker>()
            .setInputData(workDataOf("reversal_id" to reversalId))

            .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 15, TimeUnit.SECONDS)
            .build()

        workManager.enqueueUniqueWork("reversal_$reversalId", ExistingWorkPolicy.KEEP, workRequest)
        return ReversalResult.Submitted(reversalId)
    }

// 2. الـ Worker المتين المحمي ضد التكرار وانقطاع الشبكة:
class PaymentReversalWorker(context: Context, params: WorkerParameters) : CoroutineWorker(context, params) {
    override suspend fun doWork(): Result {
        val revId = inputData.getString("reversal_id") ?: return Result.failure()
        val db = EntryPoints.get(applicationContext, DbEntryPoint::class.java).database()
        val api = EntryPoints.get(applicationContext, PaymentApiEntryPoint::class.java).api()

        val entity = db.reversalDao().getReversal(revId) ?: return Result.failure()
        if (entity.status == ReversalStatus.CONFIRMED) return Result.success()

        return try {
            val response = api.executeReversal(idempotencyKey = entity.id, transactionId = entity.transactionId)
            db.reversalDao().markConfirmed(revId, response.settlementId)
            Result.success()
        } catch (e: IOException) {
            Result.retry()
        }
    }
}

## Why it matters and how it works

Reversal is an authoritative server state transition, potentially subject to settlement windows and partial/duplicate constraints. Persist operation ID, original payment ID, amount and reason securely. Worker uses stable key, queries status before retry, and records receipt. Backend ledger enforces uniqueness and valid state transitions.

## Trade-offs and decision criteria

WorkManager improves eventual attempts but cannot guarantee immediate execution or final financial outcome. Server idempotency and status lookup add backend complexity but protect money. Support escalation is needed for unresolved Pending beyond SLA.

## Failure modes

A retry with a new reversal ID can credit twice. A worker may stop after server acceptance; treating cancellation as failed can prompt a duplicate user action. A reversal may be rejected because original payment already settled or was reversed; local code cannot override ledger rules.

## Production perspective

A wallet app stores reversal Pending, queues network-constrained unique work and shows progress from Room. Worker reconciles server status, submits with stable key when safe, and records receipt. Alerts monitor pending age and support has correlation IDs without sensitive data.

## Interview answer — short

I would persist the reversal intent with a stable ID before the UI closes, then use WorkManager to attempt delivery when the device can run. The backend must deduplicate that ID and let us query the outcome when a reply is lost. This makes recovery possible across app restarts, but a phone cannot guarantee delivery through indefinite offline time or force-stop. Unresolved reversals need backend reconciliation or an operator path under the payment provider's contract.

## Interview answer — structured

The reversal cannot live only in a screen coroutine. I would write a pending reversal record, tied to the original payment and a stable operation ID, into local storage before treating the action as queued. A WorkManager worker can then read that record and attempt delivery under suitable network constraints, even after a normal app restart or device reboot.

The server side is just as important. It must treat repeated requests with the same operation ID as one logical reversal and provide a status lookup. If the client times out after the server accepted the request, the worker can query the same ID rather than invent a new reversal. The provider may have its own reversal semantics, so I would not mark the payment `Reversed` until the authoritative side confirms that state.

I would also plan for the limits: WorkManager is a reliable scheduler, not a promise of immediate execution or of network availability. A force-stopped or uninstalled app cannot be the only recovery owner. The backend should know which reversals remain unresolved, retry or reconcile them under its contract, and alert an operator when automatic resolution fails.

## Interview answer — deep senior

I would begin with the financial contract: what event creates a reversal obligation, what reference identifies the original authorization, and which response means the provider actually accepted the reversal? That determines the state machine. On the client, saving the pending record and the local payment transition in one transaction avoids a gap where the UI says “queued” but no durable intent exists. Enqueuing WorkManager happens after that commit. If enqueue itself fails or is interrupted, a later scan of pending records can restore scheduling.

The worker sends the stable ID and provider reference, then handles three outcomes: confirmed, definitely rejected with an actionable reason, or unknown because the response was lost. A generic 4xx-versus-5xx rule is too crude; a 409 might mean a duplicate or state conflict, and some 4xx responses may need reconciliation rather than deletion. An idempotency key has to be enforced atomically by the backend for the relevant operation and retention window. If the backend calls another payment system, it still has to reconcile that downstream result; returning a cached HTTP 200 alone does not prove funds were released.

For long outages, I would not claim a periodic phone worker guarantees eventual delivery. Android scheduling, user actions, battery state, connectivity, and uninstall can all intervene. The backend needs its own durable recovery record, alerts for aging unknown states, and an operator process where automation cannot establish truth. I would test a crash between local commit and enqueue, a lost response after server acceptance, repeated work execution, and a provider reversal that stays pending. The UI should say “reversal requested” until confirmation, not “money returned.”

## How to answer in the interview

- **Why:** financial obligation outlives the app.
- **How:** durable outbox plus worker and server contract.
- **Trade-off:** delayed delivery versus battery/network limits.
- **Failure case:** retry with new ID reverses twice.
- **Production solution:** backend reconciliation and escalation.

## Follow-up questions

- **Interviewer:** "What if the app crashes after saving the outbox row but before enqueueing WorkManager?"
  **Answer:** "On the next app start or scheduled reconciliation pass, I would scan pending rows and enqueue missing work. The durable row is the recovery source, not the enqueue call alone."

- **Interviewer:** "Can WorkManager guarantee the reversal reaches the backend after uninstall?"
  **Answer:** "No. That is why the backend must own unresolved obligations and have reconciliation and alerting. The phone can help while it exists and is allowed to run."

- **Interviewer:** "Is every HTTP 4xx a permanent reversal failure?"
  **Answer:** "No. I would interpret each status under the API contract. A duplicate or state conflict might require a status query; a malformed request may need operator action. I would not discard the record based only on the status class."
