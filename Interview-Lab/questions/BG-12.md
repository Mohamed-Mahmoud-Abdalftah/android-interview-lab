# BG-12

## Original interview question

What are foreground-service restrictions and notification requirements?

## What the interviewer evaluates

Describe current foreground-service eligibility, types, notifications and background-start limits.

## Explanation in Arabic

ما هي قيود الخدمات الأمامية (Foreground Service Restrictions) ومتطلبات الإشعارات في إصدارات Android الحديثة؟

1. التحول الصارم في Android الحديث (Android 12 إلى 15):
   - تاريخياً، كان المطورون يسيئون استخدام الخدمات الأمامية (Foreground Services) كحيلة لتشغيل كود في الخلفية إلى ما لا نهاية وتفادي قيود النظام.
   - **Android 12+ (حظر البدء من الخلفية - FGS Background Launch Restrictions)**: حظر النظام تماماً تشغيل أي Foreground Service أثناء وجود التطبيق في الخلفية! محاولة تشغيلها تؤدي إلى انهيار فوري بـ `ForegroundServiceStartNotAllowedException`، باستثناء حالات نادرة (مثل FCM High-Priority Push أو أجهزة بلوتوث متصلة).
   - **Android 14+ (إلزامية تحديد النوع - Mandatory FGS Types)**: يجب تحديد `android:foregroundServiceType` صريح في الـ Manifest وفي كود التشغيل (مثل `mediaPlayback`, `location`, `connectedDevice`, `health`). إذا شغلت خدمة بنوع غير معلن أو بدون تبرير، ينهار التطبيق فوراً ويرفضه متجر Google Play.

2. متطلبات الإشعارات (Notification Requirements):
   - **إشعار دائم وظاهر (Ongoing Notification)**: يجب إرفاق إشعار فوري عبر `startForeground(id, notification)` في غضون 5 إلى 10 ثوانٍ كحد أقصى من بدء الخدمة (وإلا يحدث ANR).
   - **صلاحية الإشعارات (`POST_NOTIFICATIONS` في Android 13+)**: يجب الحصول على موافقة المستخدم الصريحة لإظهار الإشعارات.
   - **مركز أمان Android 13 (FGS Task Manager)**: يوفر النظام للمستخدم زراً في شريط الإشعارات يتيح له إيقاف أي Foreground Service قيد التشغيل بضغطة زر واحدة (Stop button).

## Practical walkthrough

إعداد Foreground Service متوافق مع Android 14 مع تحديد النوع والصلاحيات:
```xml
<!-- 1. في AndroidManifest.xml: إعلان الصلاحيات ونوع الخدمة المحدد: -->
<uses-permission android:name="android.permission.FOREGROUND_SERVICE" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE_LOCATION" />
<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />

<service
    android:name=".tracking.LocationTrackingService"
    android:foregroundServiceType="location"
    android:exported="false" />
```

```kotlin
// 2. في كود الخدمة: ربط الإشعار وتحديد نوع الخدمة في startForeground:
class LocationTrackingService : Service() {
    override fun onStartCommand(intent: Intent?, flags: Int, startId: Int): Int {
        val notification = createTrackingNotification()
        
        if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.Q) {
            // تحديد النوع البرمجي الإلزامي في Android 14+:
            startForeground(NOTIFICATION_ID, notification, ServiceInfo.FOREGROUND_SERVICE_TYPE_LOCATION)
        } else {
            startForeground(NOTIFICATION_ID, notification)
        }
        
        startLocationUpdates()
        return START_STICKY
    }
}
```

## Why it matters and how it works

Foreground service rules vary by API level and declared service type. Start promptly from an eligible context, call startForeground within platform deadline, supply appropriate notification channel and stop when work ends. Background-start and while-in-use permission restrictions must be checked against current official docs for target SDK.

## Trade-offs and decision criteria

FGS provides user-visible ongoing execution but consumes battery and notification space and is restricted. WorkManager fits deferrable durable sync. Exact alarms fit precise reminder delivery, not continuous work. Choose only when the product justifies persistent user-visible operation.

## Failure modes

Starting an FGS from an ineligible background state may throw ForegroundServiceStartNotAllowedException. Missing type/permission or failing timely notification can crash. Continuing an FGS after user stops tracking wastes battery and violates user expectation.

## Production perspective

A navigation app starts location tracking from an eligible user action, shows an accurate ongoing notification, persists route state and stops promptly. It tests target SDK permission/type behavior and background transitions on devices; ordinary map prefetch stays in WorkManager.

## Interview answer — short

Android 12+ strictly blocks starting Foreground Services from the background, throwing ForegroundServiceStartNotAllowedException. Android 14+ mandates declaring specific foregroundServiceTypes in Manifest and code (e.g. location, mediaPlayback). A persistent ongoing notification must be attached within seconds, and users can terminate FGS tasks via the Android 13 Task Manager.

## Interview answer — structured

Foreground Services in modern Android are subjected to severe architectural restrictions to protect user privacy and battery life:

1. **Background Start Restrictions (Android 12+)**: Applications cannot launch a Foreground Service while running in the background. Doing so throws a runtime `ForegroundServiceStartNotAllowedException`. Allowed exceptions are narrowly restricted: high-priority FCM notifications, user interaction via widgets or pending intents, or Companion Device Manager exemptions.

2. **Mandatory Typed Services (Android 14+)**: Android 14 requires specifying an explicit `foregroundServiceType` in `AndroidManifest.xml` and passing it to `startForeground(id, notification, type)`. Permitted types include `camera`, `location`, `mediaPlayback`, `microphone`, `phoneCall`, and `dataSync`. Google Play requires policy justifications for each declared type.

3. **Notification Governance**: Services must call `startForeground()` within milliseconds of creation with an ongoing notification. Starting in Android 13, the `POST_NOTIFICATIONS` runtime permission is required, and the Android OS Task Manager allows users to stop running Foreground Services directly from the notification shade.

## Interview answer — deep senior

What should you use instead of Foreground Services for background work?

Google's official architecture guidance recommends migrating **90% of data-sync Foreground Services to WorkManager**:

- For background syncing, backups, or offline uploads, use **WorkManager with Constraints**.
- If the task is urgent and user-initiated (e.g. sending an instant chat image), use **WorkManager Expedited Work** (`setExpedited()`). On Android 12+, expedited work runs via platform JobScheduler quotas without launching an FGS or requiring background start exemptions.

Reserve Foreground Services strictly for active, ongoing, user-perceived multimedia, navigation, and live call sessions.

## Follow-up questions

- **Interviewer:** "What is the timeout limit for `dataSync` Foreground Services in Android 14?"
  **Answer:** "Android 14 enforces a cumulative runtime cap of approximately 6 hours within a 24-hour window for `dataSync` services, after which the OS terminates the service."

- **Interviewer:** "What exception is thrown if `startForeground()` is not called within 5 seconds of `startForegroundService()`?"
  **Answer:** "`ForegroundServiceDidNotStartInTimeException` (a specialized fatal ANR exception)."
