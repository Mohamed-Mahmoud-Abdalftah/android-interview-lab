# DI-20

## Original interview question

How would you migrate manual DI to Hilt while keeping tests stable?

## What the interviewer evaluates

- Propose an incremental migration with one composition boundary.
- Preserve behavior and test seams while swapping construction.
- Handle scopes, qualifiers, build variants, and rollout evidence.

## Explanation in Arabic

ابدأ بحصر constructors الحالية وملكية كل dependency، ثم حدد graph boundaries قبل إضافة annotations. انقل feature واحدة أو vertical slice مع إبقاء interfaces وفakes التي تستخدمها الاختبارات. فعّل `@HiltAndroidApp` وentry points المطلوبة، ثم استبدل manual factories تدريجيًا بــ`@Inject` أو `@Provides` عند objects لا تملك constructor لها. لا تشغّل مسارين يكوّنان Singleton مختلفين لنفس state بدون خطة؛ سيظهر cache أو session غير متسق. ثبت سلوك الاختبارات أولًا، ثم graph smoke test، ثم راقب startup وmemory مع rollout.

## Why it matters and how it works

Manual DI and Hilt both construct object graphs; a migration changes wiring and lifetime even when business classes remain unchanged. `@Inject` suits owned constructors, while modules provide third-party or configured instances. Scope annotations must reproduce intended identity without accidentally promoting screen state to process state. Tests that instantiate core classes directly need not change when constructors and interfaces remain stable.

## Worked example

A manual `AppContainer` creates `ApiClient`, `CatalogRepository`, and `CatalogViewModelFactory`. First move repository and use case to constructor injection while JVM tests keep `FakeCatalogRepository`. Then Hilt binds the real repository for Android screens and the ViewModel uses supported Hilt creation. Remove the corresponding manual factory only after an instrumented graph test proves the same screen behavior.

## Trade-offs and decision criteria

Vertical migration limits blast radius and allows a clear rollback, but temporarily carries two wiring paths. A big-bang migration removes duplicate infrastructure sooner but magnifies binding and scope regressions. Prefer stable interfaces and explicit ownership over annotating every class at once. Keep factory seams for objects with runtime arguments.

## Failure modes

Both containers create separate session stores. A binding changes from per-screen to Singleton and leaks UI state. Tests are rewritten to depend on Hilt unnecessarily, slowing feedback. A debug variant passes while release lacks a module. A manual provider is removed before all callers migrate.

## Production perspective

Create a graph inventory with scope, qualifier, owner, and test replacement. Migrate feature by feature, run JVM behavioral tests and Android injection smoke tests, and compare startup, crashes, and memory in rollout. Delete obsolete container code once there is no caller and verify every build variant.

## Interview answer — short

“I migrate one vertical slice at a time, preserve constructor and fake seams, match existing scopes, prove Hilt graph wiring, and remove each manual factory only after its last caller moves.”

## Interview answer — structured

“I inventory the manual graph first because migration can change identity and lifetime. I keep domain interfaces and direct JVM tests, then introduce Hilt at the Android composition root. Owned classes move to constructor injection; external clients get modules. One feature at a time, I compare its UI behavior under the new graph, replace test bindings in Android graph tests, and remove old factories only when no caller remains. I watch for duplicate session stores and variant-specific missing bindings.”

## Interview answer — deep senior

“I treat this as a wiring migration with behavioral and lifecycle risk, not an annotation exercise. I document every manually created object, its qualifier-equivalent configuration, scope, and test seam. The app gets a Hilt composition root, but I keep ordinary constructors on business classes so their JVM tests still pass with fakes. I choose a vertical slice, bind its real implementation through `@Inject` or a module when I cannot own the constructor, and move the Android entry point to Hilt-supported creation. During transition, I define one source of truth for shared resources: a session store created by both containers would split state even if each is locally correct. I run focused behavior tests, a graph smoke test for each relevant variant, and screen lifecycle tests before deleting the old factory. Then I compare startup and memory metrics in rollout and retain a clear rollback boundary. Runtime-parameter factories may remain explicit, and tests need not adopt Hilt unless they assert graph behavior. The migration is done when old paths have no callers and the intended scope/qualifier relationships are verified.”

## Deep-dive talking points

Cover graph inventory, vertical slices, duplicate state, scope parity, test seams, variant builds, and rollout metrics.

## Follow-up questions

- Why preserve direct constructor tests? **Answer:** they validate behavior quickly without coupling every unit test to Android graph setup.
- What is the most dangerous dual-container bug? **Answer:** separate instances of state intended to be shared, such as a session store.
- When should a manual factory remain? **Answer:** when it is the clear creation seam for runtime parameters or external ownership.

## Self-check rubric

Present an incremental sequence, name a scope regression, define test evidence, and specify deletion criteria.
