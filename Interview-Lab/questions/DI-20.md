# DI-20

## Original interview question

How would you migrate manual DI to Hilt while keeping tests stable?

## What the interviewer evaluates

- Propose an incremental migration with one composition boundary.
- Preserve behavior and test seams while swapping construction.
- Handle scopes, qualifiers, build variants, and rollout evidence.

## Concept and technical explanation

Migrating a large-scale Android codebase from manual dependency injection (such as custom AppContainer singletons, factory registries, or service locators) to Hilt is a strategic architectural refactoring that must be executed incrementally without breaking production stability or automated CI pipelines. The golden rule of migration is coexistence: Hilt and manual DI containers must run concurrently during the transition. By treating the manual container as a bridge provider in Hilt modules, teams can migrate classes bottom-up (from data sources and repositories up to ViewModels and Activities) while preserving existing unit test suites completely untouched through constructor injection purity.

## Practical walkthrough (English)

Step-by-step phased migration strategy from manual container to Hilt:
```kotlin
// Phase 1: Existing legacy manual container
class LegacyAppContainer(context: Context) {
    val api: UserApi = Retrofit.Builder().baseUrl("https://api.com").build().create(UserApi::class.java)
    val database: AppDatabase = Room.databaseBuilder(context, AppDatabase::class.java, "db").build()
}

// Phase 2: Bridge manual container into Hilt so newly migrated classes can consume legacy dependencies
@Module
@InstallIn(SingletonComponent::class)
object ContainerBridgeModule {
    @Provides
    @Singleton
    fun provideUserApi(@ApplicationContext context: Context): UserApi {
        return (context as MyApplication).appContainer.api
    }
}

// Phase 3: Migrate leaf classes first (Repositories & ViewModels) using standard constructor injection
// Unit tests remain 100% UNTOUCHED because constructor parameters did not change!
@HiltViewModel
class MigratedUserViewModel @Inject constructor(
    private val repository: UserRepository // Injected cleanly by Hilt
) : ViewModel()

// Phase 4: Annotate Activities/Fragments with @AndroidEntryPoint
@AndroidEntryPoint
class UserActivity : AppCompatActivity() {
    private val viewModel: MigratedUserViewModel by viewModels()
}
// Phase 5: Once all consumers are migrated, decommission LegacyAppContainer completely.
```

## Explanation in Arabic

كيف تهاجر تطبيقاً ضخماً من حقن التبعيات اليدوي (Manual DI) إلى Hilt مع الحفاظ على استقرار الاختبارات وسير العمل؟

1. استراتيجية الهجرة المتدرجة (Strangler Fig Pattern):
   - محاولة تحويل التطبيق كاملاً إلى Hilt في PR واحد هي وصفة مضمونة للكوارث والتوقف عن الإنتاج.
   - الهجرة الناجحة تتم عبر خطوات تدريجية مرحلية، مع استمرار التطبيق في البناء والعمل بنسبة 100% في كل خطوة.

2. خطة العمل خطوة بخطوة:
   - **المرحلة 1: التأسيس والبنية التحتية**: إضافة Hilt Gradle Plugin و KSP، وإعداد `@HiltAndroidApp` على كلاس الـ `Application`، وبناء Hilt Module يوفر الـ Singletons الأساسية القائمة (مثل `RoomDatabase`, `Retrofit`).
   - **المرحلة 2: جسر الربط المؤقت (Bridge / Adapter)**: ربط الـ `AppContainer` اليدوي بـ Hilt عبر `@EntryPoint`، بحيث تستطيع الكودات القديمة سحب تبعياتها من Hilt، والعكس.
   - **المرحلة 3: هجرة الشاشات من القمة للقاع (Top-Down by Screen)**: تحويل شاشة كاملة بمفردها (Activity/Fragment إلى `@AndroidEntryPoint` و ViewModel إلى `@HiltViewModel`)، مع الإبقاء على باقي الشاشات تعمل بالـ Manual DI.
   - **المرحلة 4: استقرار الاختبارات**: التأكد من أن جميع Unit Tests لا تزال تعمل على الـ JVM بدون Hilt، وتحديث اختبارات الـ UI تدريجياً باستخدام `@HiltAndroidTest`.

## Practical walkthrough

خطة الهجرة التدريجية وجسر الربط المؤقت بين Manual DI و Hilt:
```kotlin
// 1. التطبيق الأساسي مع تفعيل Hilt:
@HiltAndroidApp
class App : Application() {
    // الاحتفاظ بالـ AppContainer القديم كجسر مؤقت أثناء الهجرة:
    lateinit var legacyContainer: LegacyAppContainer
    
    override fun onCreate() {
        super.onCreate()
        legacyContainer = LegacyAppContainer(this)
    }
}

// 2. توفير الـ Legacy Container داخل Hilt Graph لخدمة الكود المهاجر حديثاً:
@Module
@InstallIn(SingletonComponent::class)
object LegacyBridgeModule {
    @Provides @Singleton
    fun provideLegacyContainer(@ApplicationContext context: Context): LegacyAppContainer {
        return (context as App).legacyContainer
    }
}

// 3. تحويل الشاشات تدريجياً: شاشة شاشة دون كسر أي اختبار!
@HiltViewModel
class MigratedFeatureViewModel @Inject constructor(
    private val repository: ModernRepository // محقون بنظافة عبر Hilt
) : ViewModel()
```

## Why it matters and how it works

Manual DI and Hilt both construct object graphs; a migration changes wiring and lifetime even when business classes remain unchanged. `@Inject` suits owned constructors, while modules provide third-party or configured instances. Scope annotations must reproduce intended identity without accidentally promoting screen state to process state. Tests that instantiate core classes directly need not change when constructors and interfaces remain stable.

## Worked example

A manual `AppContainer` creates `ApiClient`, `CatalogRepository`, and `CatalogViewModelFactory`. First move repository and use case to constructor injection while JVM tests keep `FakeCatalogRepository`. Then Hilt binds the real repository for Android screens and the ViewModel uses supported Hilt creation. Remove the corresponding manual factory only after an instrumented graph test proves the same screen behavior.

## Trade-offs and decision criteria

Vertical migration limits blast radius and allows a clear rollback, but temporarily carries two wiring paths. A big-bang migration removes duplicate infrastructure sooner but magnifies binding and scope regressions. Prefer stable interfaces and explicit ownership over annotating every class at once. Keep factory seams for objects with runtime arguments.

## Failure modes

Both containers create separate session stores. A binding changes from per-screen to Singleton and leaks UI state. Tests are rewritten to depend on Hilt unnecessarily, slowing feedback. A debug variant passes while release lacks a module. A manual provider is removed before all callers migrate.

## Production perspective

Create a graph inventory with scope, qualifier, owner, and test replacement. Migrate feature by feature, run JVM behavioral tests and Android injection smoke tests, and compare startup, crashes, and memory in rollout. Delete obsolete container code once there is no caller and verify every build variant.

## Interview answer — short

To migrate from manual DI to Hilt without breaking tests, run both systems concurrently. First, setup Hilt and annotate the Application class. Second, bridge existing container instances into Hilt using @Provides modules so migrated classes can consume legacy dependencies. Third, migrate leaf data layers and ViewModels to @Inject constructors, leaving unit tests completely untouched. Finally, annotate UI components with @AndroidEntryPoint and decommission the legacy container once migration is complete.

## Interview answer — structured

Migrating an enterprise Android application from manual dependency injection to Hilt requires an incremental, risk-mitigated strategy that ensures uninterrupted team velocity and test stability.
Attempting a big-bang rewrite of dependency injection across a production app inevitably causes merge conflicts, regression bugs, and broken CI pipelines. Instead, senior engineers employ a phased coexistence strategy.
The migration begins by adding Hilt dependencies and annotating the Application class with @HiltAndroidApp. The legacy AppContainer remains fully operational.
In the second phase, developers build a bridge Hilt module that exposes shared dependencies from the legacy container using @Provides methods. This allows newly refactored classes to resolve dependencies from the existing container without waiting for the entire application to be converted.
In the third phase, engineering teams migrate dependencies bottom-up, starting with leaf repositories and UseCases, annotating their constructors with @Inject. Because well-architected classes rely on constructor injection, existing unit tests require zero modifications and continue passing seamlessly.
In the final phase, ViewModels are annotated with @HiltViewModel and Activities with @AndroidEntryPoint. Once all consumers are wired through Hilt, the legacy container is deleted cleanly.

## Interview answer — deep senior

Under the hood, the architectural feasibility of migrating to Hilt while preserving test stability rests upon constructor injection purity. Unit tests instantiate target classes directly on the JVM, passing mock or fake collaborators into constructors without executing any DI framework code. Consequently, introducing @Inject annotations on constructors causes zero behavioral or bytecode disruption to existing JUnit test suites.
The technical challenge arises in instrumented tests where the legacy application class previously injected fake containers. To keep instrumented tests stable, teams implement a custom test runner extending HiltTestApplication. During the migration phase, the test runner instantiates the fake legacy container while allowing Hilt's @UninstallModules and @BindValue to progressively take over component testing seams.
Senior engineers execute the migration in vertical slices by feature, rather than horizontal slices by layer. Migrating an entire feature vertically—from its database tables and repositories up to its ViewModel and Activity—allows the team to verify and ship complete functional units to production incrementally.
Staff engineers monitor APK size, DEX method counts, and cold startup times throughout the migration. Once the final legacy container class is deleted and reflection service locators are purged, class-loading overhead drops and build times stabilize through incremental KSP code generation. This systematic transition transforms the codebase into a modern, standardized foundation without risking regressions or slowing product delivery.

## How to answer in the interview

- **Why:** migration must preserve instance identity and tests.
- **How:** inventory, constructors, modules, Android entry points, one slice at a time.
- **Trade-off:** temporary dual wiring raises complexity.
- **Failure case:** two session managers split state.
- **Production solution:** scope regression and release graph tests.

## Deep-dive talking points

Cover graph inventory, vertical slices, duplicate state, scope parity, test seams, variant builds, and rollout metrics.

## Follow-up questions

- **Interviewer:** "How do you prevent duplicate instances of singletons during migration?"
  **Answer:** "Designate a single source of truth: have Hilt provide the instance from the legacy container, or have the legacy container delegate to Hilt via an EntryPoint."

- **Interviewer:** "Do JVM unit tests need to be rewritten when adopting Hilt?"
  **Answer:** "No. Because classes rely on constructor injection, pure unit tests continue to pass test doubles directly into constructors without touching Hilt."
