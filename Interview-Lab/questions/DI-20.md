# DI-20

## Original interview question

How would you migrate manual DI to Hilt while keeping tests stable?

## What the interviewer evaluates

Can the candidate migrate a composition root incrementally, keep one owner for stateful dependencies, preserve direct JVM test construction, and verify Android graphs and build variants without claiming automatic stability?

## Concept and technical explanation

Manual DI and Hilt both assemble dependencies; the migration changes who creates each instance and which component owns its lifetime. Start with an inventory of bindings, scopes, qualifiers, runtime parameters, consumers, and tests. Enable Hilt at the application boundary, then move one coherent feature slice at a time. During coexistence, assign each stateful dependency exactly one owner. A temporary Hilt `@Provides` binding can return an object from the legacy container, or legacy code can access a Hilt-owned dependency through a documented `@EntryPoint` where needed. Choose a direction per dependency; creating both copies can split session, database, or cache state.

Constructor-injected policy classes can still be instantiated directly in JVM tests if their constructor contracts remain stable. `@Inject` does not require Hilt to run in those tests. Android entry-point tests may need the documented Hilt test application, rule, and replacement binding mechanisms. Scope or qualifier changes can alter behavior even when unit tests compile, so test graph identity and feature behavior in supported variants. Delete a legacy factory only after its callers and test overrides have migrated.

## Practical walkthrough (English)

A catalog feature currently receives one `CatalogRepository` from `LegacyAppContainer`. First record which screens and workers use it and whether it owns a cache. Introduce Hilt app setup and a temporary binding that returns that exact repository instance; do not construct a second repository. Move the catalog screen and its ViewModel to supported Hilt entry points while keeping the repository's plain constructor seam for JVM tests. Add an Android injection smoke test and a release-variant build check. Once every consumer uses the new path, move ownership to Hilt and remove the bridge.

## Why it matters and how it works

A binding can compile while its scope is wrong. If the old container shared one session store but Hilt creates another, migrated and unmigrated screens disagree. If a per-screen object becomes application-scoped, UI state can outlive its owner. A vertical slice gives a testable behavior boundary and a rollback path. JVM tests often remain direct-construction tests, while Android graph tests verify entry points and replacement modules. There is no guarantee that tests remain unchanged or performance improves.

## Worked example

Runnable Kotlin/JVM illustration of single ownership during a temporary bridge. The Android Hilt `@Provides` method would return `bridge.repository()`; this snippet tests object identity, not Hilt compilation:

```kotlin
class CatalogRepository {
    private val items = mutableListOf<String>()
    fun add(item: String) { items += item }
    fun all(): List<String> = items.toList()
}

class LegacyCatalogContainer(val repository: CatalogRepository = CatalogRepository())

class CatalogBridge(private val legacy: LegacyCatalogContainer) {
    fun repository(): CatalogRepository = legacy.repository
}
```

When Hilt takes ownership later, remove the bridge and confirm every consumer resolves the same intended scope.

## Trade-offs and decision criteria

Incremental migration limits the affected feature surface but temporarily maintains two construction paths. The bridge should have an owner and deletion criterion. `@Inject` constructors work for owned classes; `@Provides` can adapt an existing instance or third-party construction; `@EntryPoint` is an escape hatch for code Hilt does not create. Choose scopes and qualifiers from behavior, not from a blanket singleton policy. Keep runtime arguments in factories or supported assisted mechanisms.

## Failure modes

Two graphs create two session stores. A release variant misses a binding that debug has. A ViewModel's constructor signature changes and pure JVM tests are assumed to remain untouched. A legacy factory is removed while a worker still calls it. A Hilt test replaces a module but the target test does not use the Hilt test application and rule. Performance claims based on removing a service locator are unmeasured.

## Production perspective

Track each binding's owner, scope, qualifier, variant, consumers, and migration state. For every feature slice, run direct JVM policy tests, an Android graph smoke path where available, variant builds, and behavior checks for identity and lifecycle. During rollout compare startup, crashes, and memory rather than promising improvement. Remove bridges and old container code only when no production or test caller remains.

## Interview answer — short

I inventory bindings and lifetimes, enable Hilt at the app boundary, and migrate one feature slice at a time. During coexistence, each stateful dependency has one owner; a temporary bridge returns the existing instance instead of creating a duplicate. JVM tests can still construct policy classes directly if their constructors stay stable. I test Android graph wiring and variants, then delete the old factory after its last caller moves.

## Interview answer — structured

I treat this as a change of composition root and lifetime ownership. First I list dependencies, scopes, qualifiers, runtime arguments, all consumers, and current test overrides. I set up Hilt for the Application, then choose a feature slice. During coexistence, I make the bridge direction explicit: if the legacy container owns a stateful repository, Hilt's binding returns that exact instance. If a legacy caller must reach a Hilt-owned object, I use a documented entry point only at that boundary.

I preserve plain constructors for policy classes, so direct JVM tests can still pass fakes when signatures have not changed. Android entry-point tests need their own Hilt test setup and replacement bindings. I verify scope identity, screen behavior, and debug and release variants; a compiling graph alone does not prove matching behavior. Once no caller or test depends on the legacy factory, I remove the bridge and factory. I do not promise zero test edits or a startup improvement.

## Interview answer — deep senior

The risk is not the annotation count; it is silently changing object identity and lifetime. Before editing, I map each binding to its owner, scope, qualifier, variant, runtime data, and consumer. A stateful session or cache should have one authority during the transition. If Hilt and the legacy container each construct their own copy, two screens can observe different states even though both graphs compile. A temporary bridge can return the existing instance from a Hilt `@Provides` method; if ownership is reversed, a documented `@EntryPoint` can let an unmigrated boundary obtain a Hilt-owned object. I choose one direction per dependency and plan when the bridge disappears.

I migrate a coherent vertical feature slice because it has behavior I can verify. Plain policy classes keep explicit constructors; their JVM tests can still instantiate them with fakes. That does not mean every test is unchanged: constructor contracts may evolve, and Android tests using Hilt need the Hilt test application, rule, and module or value replacements appropriate to the test. Scope and qualifier mismatches need graph-level verification, especially across debug, release, and test variants.

For rollout, I compare actual startup, memory, and crash data if these are concerns. I do not claim that removing a service locator automatically improves them. A bridge is temporary debt with an owner, a list of remaining callers, and a deletion gate. Once all consumers and test seams are migrated, I move final ownership to the intended Hilt component and remove the old factory. I also check workers and other non-UI callers before deleting any manual provider.

## How to answer in the interview

- Start with binding, scope, qualifier, variant, and consumer inventory.
- Explain a one-owner bridge and a vertical feature slice.
- Separate direct JVM construction from Android graph tests.
- State the deletion gate and avoid unmeasured performance claims.

## Deep-dive talking points

Duplicate session identity, bridge direction, `@Provides` versus `@EntryPoint`, scope and qualifier parity, runtime arguments, variant builds, Android test replacements, rollout metrics.

## Follow-up questions

- **Interviewer:** “How do you prevent two copies of a session store?” **Answer:** “Give it one owner during coexistence. The other graph receives that exact instance through a temporary bridge.”
- **Interviewer:** “Will all JVM tests stay unchanged?” **Answer:** “Only tests whose constructor contracts remain stable can keep direct construction. Android Hilt tests may require setup and replacement bindings.”
- **Interviewer:** “When do you delete the legacy container?” **Answer:** “After every production and test caller has moved and graph and behavior checks pass for supported variants.”

Can I explain one-owner coexistence, a feature-slice sequence, scope regression, test evidence, and a safe bridge deletion gate?
