# DI-14

## Original interview question

What problems occur if every dependency is a Singleton?

## What the interviewer evaluates

- Connect scope choice to mutable state, lifecycle, and memory.
- Recognize concurrency and test isolation effects.
- Offer a narrower ownership model with exceptions for real process-wide resources.

## Concept and technical explanation

Defaulting every dependency to @Singleton is a pervasive architectural anti-pattern that undermines the principles of scoped lifecycles and modern resource management. While Singletons guarantee a single instance throughout the application process, indiscriminate singleton scoping introduces four severe failure modes: permanent heap retention preventing garbage collection, concurrency race conditions from shared mutable state, hidden state bleeding across user journeys and test suites, and violation of the Principle of Least Privilege. In mobile applications operating under strict OS memory limits, hoarding unnecessary long-lived instances in memory degrades performance, elevates Low Memory Killer (LMK) eviction rates, and causes hard-to-reproduce state pollution bugs.

## Practical walkthrough (English)

Contrasting unscoped transient dependencies with dangerous global singletons:
```kotlin
// Dangerous Anti-Pattern: Scoping mutable feature state as @Singleton
@Singleton
class ShoppingCartManager @Inject constructor() {
    private val items = mutableListOf<CartItem>() // Shared global mutable state!
    fun addItem(item: CartItem) = items.add(item)
    // Problem: State bleeds across user logout/login sessions, causing data leaks!
}

// Correct Architectural Design: Unscoped or narrowly scoped state holders
class FormatDateUseCase @Inject constructor() {
    // Zero state: Unscoped, instantiated lightweight on demand, collected immediately
    fun format(timestamp: Long): String = DateFormatter.format(timestamp)
}

@ActivityRetainedScoped // Bound strictly to active user checkout journey
class CheckoutSessionHolder @Inject constructor() {
    val checkoutState = MutableStateFlow<CheckoutState>(CheckoutState.Idle)
    // Automatically destroyed and cleared when checkout activity finishes
}
```

## Practical walkthrough

المقارنة بين كائن متورط بـ Singleton غير مبرر وكائن Unscoped نقي:
```kotlin
// ❌ Singleton غير مبرر: يحتفظ ببيانات ملوثة في الذاكرة حتى بعد مغادرة الشاشة:
@Singleton
class BadInvoiceFilterHelper @Inject constructor() {
    // كاش داخلي يظل محبوساً في الذاكرة طوال حياة التطبيق!
    private val temporaryCache = mutableListOf<Invoice>()
    fun filter(...) { /* ... */ }
}

// ✅ Unscoped (بدون أي Scope): كائن خفيف الوزن ينشأ ويتحرر فور انتهاء الحاجة إليه:
class GoodInvoiceFilterHelper @Inject constructor() {
    // دالة نقية بدون الاحتفاظ بأي حالة في الذاكرة:
    fun filter(invoices: List<Invoice>, query: String): List<Invoice> {
        return invoices.filter { it.matches(query) }
    }
}
// مجمع القمامة في ART (Android Runtime) يجمع الكائنات الخفيفة بسرعة فائقة في الـ Young Generation!
```

## Why it matters and how it works

Hilt caches a scoped binding in its owning component. Process-wide retention makes all dependent mutable fields and reachable objects survive until process termination. More sharing can reduce creation cost but expands synchronization requirements and makes reset semantics obscure. Scoping an object does not make its methods thread safe, nor does it persist state after process death.

## Worked example

Two account sessions use one `CheckoutState` Singleton. A background refresh for account A writes an address after the user signs in as B, so B sees A's data. A repository backed by durable per-account storage can still be shared if calls take explicit account identity and all caches are partitioned and cleared on logout; the editable checkout draft belongs to a screen or flow owner.

## Trade-offs and decision criteria

Share expensive stateless clients or deliberately bounded caches where their process lifetime is justified. Use `ViewModelScoped`, `ActivityRetainedScoped`, or unscoped factories for transient work based on the actual owner. More instances cost some allocation and setup; shared mutable instances cost synchronization, reset logic, and isolation checks.

## Failure modes

An Activity callback is registered in a Singleton and never removed. Tests pass individually but leak fake state when run together. A mutable token field changes during concurrent requests. A developer assumes Singleton survives process recreation and loses an unsaved workflow.

## Production perspective

Classify each binding as stateless shared resource, bounded cache, or owner-specific state. Document clear/reset events, add account-switch and rotation tests, and inspect heap paths for UI owners. Measure creation cost before promoting short-lived objects to Singleton.

## Interview answer — short

Making every dependency a Singleton causes permanent memory overhead because instances are never garbage collected during the process lifetime. It introduces severe concurrency race conditions through shared mutable state, causes state bleeding where data from one user session pollutes another after logout, and complicates automated testing by leaking state across test runs. Bindings should remain unscoped by default.

## Interview answer — structured

Overusing the @Singleton annotation transforms a dependency injection graph into a repository of permanent memory overhead and hidden global state.
The primary problem is memory bloat. A singleton instance cannot be reclaimed by the garbage collector as long as the application process lives. When developers mark transient helper classes, parsers, formatters, and feature state holders as singletons, the application's resident heap footprint expands permanently, increasing the frequency of Garbage Collection pauses and triggering Low Memory Killer kills when the app enters the background.
The second major hazard is state pollution and concurrency vulnerabilities. Singletons that encapsulate mutable state become shared points of contention across background threads and coroutines, requiring defensive locking mechanisms to prevent race conditions. Furthermore, singletons do not clear their internal state when a user logs out, leading to critical privacy bugs where previous user data leaks into subsequent sessions.
The third drawback is test suite fragility. When singletons hold mutable state, test cases execute against polluted environments, causing unpredictable failures that depend on test execution ordering.

## Interview answer — deep senior

Under the hood, Dagger implements @Singleton using a DoubleCheck memoization holder inside the generated SingletonComponent implementation class. Every singleton binding permanently occupies a reference slot in the component's internal array of provider instances.
When an unscoped binding is requested (a class with @Inject constructor without a scope annotation), Dagger's generated factory executes a lightweight constructor call. Because modern JVMs and Android ART runtimes excel at allocating and garbage collecting short-lived, transient generational nursery objects in microseconds, unscoped objects impose near-zero memory footprint and zero synchronization overhead.
In contrast, scoping an object with @Singleton incurs synchronized volatile reads on every lookup to guarantee thread-safe memoization. If that singleton retains references to bitmaps, large collections, or listeners, it exerts continuous memory pressure on low-RAM Android devices, precipitating OutOfMemoryError crashes.
Staff engineers enforce a strict default-unscoped policy: an object should only be scoped if maintaining instance identity is fundamentally required for correctness (such as an in-memory token cache or database connection pool) or if object construction involves massive I/O overhead. Everything else, including UseCases, mappers, formatters, and presenters, must remain unscoped. This discipline maximizes generational garbage collection efficiency, eliminates hidden state leakage, and keeps heap footprints minimal throughout extended app sessions across diverse device tiers.

## How to answer in the interview

- **Why:** broad lifetime can leak state across owners.
- **How:** choose the narrowest identity that satisfies use.
- **Trade-off:** reuse versus isolation.
- **Failure case:** old-user cart survives logout.
- **Production solution:** scope table and multi-owner tests.

## Deep-dive talking points

Discuss component caching, thread safety, account isolation, process death, and measured construction costs.

## Follow-up questions

- **Interviewer:** "What is the memory cost of an unscoped object in Android?"
  **Answer:** "Negligible. Allocating a standard Kotlin object in ART takes single-digit nanoseconds, and young generation garbage collection is highly optimized."

- **Interviewer:** "How should user-specific repositories be cleared on logout if they are `@Singleton`?"
  **Answer:** "Either encapsulate them within a clearable session state holder that invalidates caches on logout, or create a custom UserComponent that is destroyed upon session termination."
