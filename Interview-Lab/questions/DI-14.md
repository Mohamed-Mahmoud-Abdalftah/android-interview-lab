# DI-14

## Original interview question

What problems occur if every dependency is a Singleton?

## What the interviewer evaluates

- Connect scope choice to mutable state, lifecycle, and memory.
- Recognize concurrency and test isolation effects.
- Offer a narrower ownership model with exceptions for real process-wide resources.

## Explanation in Arabic

لو كل dependency Singleton، الحالة المؤقتة تبقى process-wide بدون سبب: session قديمة، listener لشاشة مغلقة، cache بلا حد، وسباق بين شاشتين أو حسابين. Singleton في DI يعني instance داخل `SingletonComponent` طوال حياة component، وليس وعدًا ببقاء بيانات بعد قتل process. أشياء مثل عميل HTTP المهيأ وdatabase handle قد تستفيد من المشاركة، لكن `CheckoutDraft` و`PermissionCoordinator` لازم lifetime أقصر أو immutable input. اختبار الذاكرة والتزامن أهم من قاعدة “Singleton أسرع”.

## Practical walkthrough

لو كل حاجة `@Singleton`، cart الخاص بمستخدم ممكن يفضل بعد logout، وscreen cache تبقى مشتركة بين شاشتين. بعض objects زي DB أو configured HTTP client فعلاً process-wide؛ لكن screen selection أو temporary form state لها owner أقصر. اعمل scope table فيها owner، reset trigger، وidentity المطلوبة، واختبر two screens/logout/process recreation. `@Singleton` لا يعني durable storage.

## Why it matters and how it works

Hilt caches a scoped binding in its owning component. Process-wide retention makes all dependent mutable fields and reachable objects survive until process termination. More sharing can reduce creation cost but expands synchronization requirements and makes reset semantics obscure. Scoping an object does not make its methods thread safe, nor does it persist state after process death.

## Worked example

Two account sessions use one `CheckoutState` Singleton. A background refresh for account A writes an address after the user signs in as B, so B sees A's data. A repository backed by durable per-account storage can still be shared if calls take explicit account identity and all caches are partitioned and cleared on logout; the editable checkout draft belongs to a screen or flow owner.

## Trade-offs and decision criteria

Share expensive stateless clients or deliberately bounded caches where their process lifetime is justified. Use `ViewModelScoped`, `ActivityRetainedScoped`, or unscoped factories for transient work based on the actual owner. More instances cost some allocation and setup; shared mutable instances cost synchronization, reset logic, and isolation checks.

## Failure modes

An Activity callback is registered in a Singleton and never removed. Tests pass individually but leak fake state when run together. A mutable token field changes during concurrent requests. A developer assumes Singleton survives process recreation and loses an unsaved workflow.

## Production perspective

Classify each binding as stateless shared resource, bounded cache, or owner-specific state. Document clear/reset events, add account-switch and rotation tests, and inspect heap paths for UI owners. Measure creation cost before promoting short-lived objects to Singleton.

## Interview answer — short

“Making everything a Singleton broadens state ownership and creates leak, concurrency, and test-isolation risks. I scope each dependency to the shortest owner that needs its identity.”

## Interview answer — structured

“Singleton is useful for a genuinely shared client, not as a default performance switch. If an object stores a screen callback or per-user draft, process ownership outlives the intended state. It can leak an Activity, mix accounts, and force concurrency control. I keep transient state in a ViewModel or flow-owned object, pass identity explicitly to shared services, and bound and invalidate shared caches. I also remember Hilt's Singleton lasts only as long as that process component.”

## Interview answer — deep senior

“I ask what identity the object represents and when that identity should end. An HTTP client may reasonably be built once because its configuration and connection pool are shared; an editable checkout is tied to one flow and should disappear or be persisted deliberately. Applying Singleton everywhere turns a graph into a global state store. That makes tests order-dependent, raises races when independent callers mutate fields, and can retain destroyed Activities through indirect listeners. It also creates a false persistence assumption: the operating system may kill the process, after which Hilt builds a new component. I would map scopes from owners, make shared services mostly stateless, give caches limits and logout invalidation, and make per-account data keyed explicitly. Then I test account switching, concurrent requests, navigation and rotation, and process recreation where the product needs recovery. If a narrower scope causes meaningful setup cost, I measure it and share the expensive resource separately from the short-lived state. Scope is an ownership contract, not an optimization annotation. Imagine user A logs out while a singleton cart cache still holds account A’s items; user B then opens checkout and sees stale data. I would move the cache to a narrower owner or implement an explicit session reset, then test the two-user transition. For a database or configured client, process reuse may still be correct. The scope table should record both owner and reset trigger.”

## How to answer in the interview

- **Why:** broad lifetime can leak state across owners.
- **How:** choose the narrowest identity that satisfies use.
- **Trade-off:** reuse versus isolation.
- **Failure case:** old-user cart survives logout.
- **Production solution:** scope table and multi-owner tests.

## Deep-dive talking points

Discuss component caching, thread safety, account isolation, process death, and measured construction costs.

## Follow-up questions

- Does `@Singleton` survive process death? **Answer:** no; a new process creates a new Hilt application component.
- Can a stateless shared service be Singleton? **Answer:** yes, if its lifetime and dependencies are process compatible.
- What would you test after narrowing a scope? **Answer:** state isolation, setup cost, and lifecycle recreation behavior.

## Self-check rubric

Name a valid Singleton, a harmful one, a concrete leak or race, and a narrower replacement scope.
