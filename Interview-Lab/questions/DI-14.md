# DI-14

## Original interview question

What problems occur if every dependency is a Singleton?

## What the interviewer evaluates

- Connect scope choice to mutable state, lifecycle, and memory.
- Recognize concurrency and test isolation effects.
- Offer a narrower ownership model with exceptions for real process-wide resources.

## Explanation in Arabic

ما هي الكوارث والمشاكل التي تحدث إذا جعلت كل كائن في التطبيق `@Singleton`؟

1. ظاهرة الـ Scope Inflation (تضخم الـ Singleton):
   - يميل المطور المبتدئ إلى وضع `@Singleton` فوق كل Repository و UseCase و Helper ظناً منه أن هذا 'يوفر الذاكرة' بمنع تكرار الإنشاء.

2. المشاكل الناتجة عن جعل كل شيء Singleton:
   - **تضخم استهلاك الذاكرة (Memory Bloat)**: كائنات الـ Singleton لا يتم جمعها بواسطة مجمع القمامة (GC) أبداً طوال فترة عمل التطبيق. الكائنات التي كان ينبغي أن تعيش لمدة ثانيتين فقط أثناء تصفح شاشة معينة تظل محبوسة في الـ Heap للأبد.
   - **تلوث الحالة والبيانات القديمة (Stale State & Memory Pollution)**: لو كان الـ Singleton يحتوي على كاش أو قائمة أو متغيرات داخلية، فإن تسجيل خروج المستخدم (Logout) لن يفرغ هذه البيانات، مما قد يعرض بيانات مستخدم سابق لمستخدم جديد!
   - **اختبارات فاشلة وغير معزولة (Flaky & Order-Dependent Tests)**: في اختبارات الـ JVM، تتشارك الاختبارات نفس الـ Singletons، مما يجعل نجاح اختبار معتمداً على نتيجة اختبار آخر قبله.
   - **مخاطر التزامن والـ Concurrency**: إذا طلبت عدة Threads الوصول إلى كائن Singleton في نفس اللحظة بدون مزامنة دقيقة (Thread Synchronization)، تحدث أخطاء الـ Race Conditions وتلف البيانات.

## Practical walkthrough

المقارنة بين كائن متورط بـ Singleton غير مبرر وكائن Unscoped نقي:
```kotlin
// ❌ Singleton غير مبرر: يحتفظ ببيانات ملوثة في الذاكرة حتى بعد مغادرة الشاشة:
@Singleton
class BadInvoiceFilterHelper @Inject constructor() {
    // كاش داخلي يظل محبوساً في الذاكرة طوال حياة التطبيق!
    private val temporaryCache = mutableListOf<Invoice>()
    fun filter(...) { /* ... */ }
}

// ✅ Unscoped (بدون أي Scope): كائن خفيف الوزن ينشأ ويتحرر فور انتهاء الحاجة إليه:
class GoodInvoiceFilterHelper @Inject constructor() {
    // دالة نقية بدون الاحتفاظ بأي حالة في الذاكرة:
    fun filter(invoices: List<Invoice>, query: String): List<Invoice> {
        return invoices.filter { it.matches(query) }
    }
}
// مجمع القمامة في ART (Android Runtime) يجمع الكائنات الخفيفة بسرعة فائقة في الـ Young Generation!
```

## Why it matters and how it works

Hilt caches a scoped binding in its owning component. Process-wide retention makes all dependent mutable fields and reachable objects survive until process termination. More sharing can reduce creation cost but expands synchronization requirements and makes reset semantics obscure. Scoping an object does not make its methods thread safe, nor does it persist state after process death.

## Worked example

Two account sessions use one `CheckoutState` Singleton. A background refresh for account A writes an address after the user signs in as B, so B sees A's data. A repository backed by durable per-account storage can still be shared if calls take explicit account identity and all caches are partitioned and cleared on logout; the editable checkout draft belongs to a screen or flow owner.

## Trade-offs and decision criteria

Share expensive stateless clients or deliberately bounded caches where their process lifetime is justified. Use `ViewModelScoped`, `ActivityRetainedScoped`, or unscoped factories for transient work based on the actual owner. More instances cost some allocation and setup; shared mutable instances cost synchronization, reset logic, and isolation checks.

## Failure modes

An Activity callback is registered in a Singleton and never removed. Tests pass individually but leak fake state when run together. A mutable token field changes during concurrent requests. A developer assumes Singleton survives process recreation and loses an unsaved workflow.

## Production perspective

Classify each binding as stateless shared resource, bounded cache, or owner-specific state. Document clear/reset events, add account-switch and rotation tests, and inspect heap paths for UI owners. Measure creation cost before promoting short-lived objects to Singleton.

## Interview answer — short

Making every dependency a Singleton causes permanent memory bloat, prevents garbage collection of transient objects, leads to stale state across user sessions, creates concurrency bugs across threads, and couples unit tests into order-dependent flakiness. Scopes should be applied strictly to expensive, truly process-wide shared resources.

## Interview answer — structured

Dogmatically annotating every class with `@Singleton` is a dangerous architectural anti-pattern known as 'Scope Inflation'.

It introduces four critical production failures:
1. **Unreclaimable Memory Retention**: Objects scoped to `@Singleton` can never be collected by the ART garbage collector while the app process lives. Transient helpers, formatters, and screen-specific caches occupy permanent RAM in the Old Generation heap.
2. **State Leakage Across User Sessions**: If a singleton repository or manager holds user-specific data in memory, logging out and logging in with another account risks serving stale, unpurged data from the previous user, creating serious data privacy breaches.
3. **Concurrency & Thread Safety Hazards**: Singletons are accessed concurrently by multiple background threads and coroutines. Unless internally synchronized with thread-safe primitives (like `Mutex` or atomic references), they produce subtle race conditions and data corruption.

Default to **unscoped bindings**. The ART runtime allocates and garbage-collects short-lived, transient objects with virtually zero overhead. Reserve `@Singleton` exclusively for expensive, process-wide resources (Room database, HTTP connection pools, and core event buses).

## Interview answer — deep senior

From an ART memory management standpoint, scoping an object changes its GC lifetime tier.

Unscoped objects are allocated in ART's **Young Generation (Eden space)**. When their consumer leaves scope, ART collects them during minor GC cycles in sub-millisecond pauses. When an object is `@Singleton`, it quickly gets promoted to the **Old/Tenured Generation**. Collecting objects from the Old Gen requires full concurrent mark-sweep or compacting GC cycles, which cause frame drops (jank) and UI freezes.

Furthermore, for user session data, the correct architectural approach is not `@Singleton`, but a custom user-scoped component or an explicit session repository that clears all in-memory flows upon receiving an `AuthEvent.LoggedOut` notification.

## How to answer in the interview

- **Why:** broad lifetime can leak state across owners.
- **How:** choose the narrowest identity that satisfies use.
- **Trade-off:** reuse versus isolation.
- **Failure case:** old-user cart survives logout.
- **Production solution:** scope table and multi-owner tests.

## Deep-dive talking points

Discuss component caching, thread safety, account isolation, process death, and measured construction costs.

## Follow-up questions

- **Interviewer:** "What is the memory cost of an unscoped object in Android?"
  **Answer:** "Negligible. Allocating a standard Kotlin object in ART takes single-digit nanoseconds, and young generation garbage collection is highly optimized."

- **Interviewer:** "How should user-specific repositories be cleared on logout if they are `@Singleton`?"
  **Answer:** "Either encapsulate them within a clearable session state holder that invalidates caches on logout, or create a custom UserComponent that is destroyed upon session termination."
