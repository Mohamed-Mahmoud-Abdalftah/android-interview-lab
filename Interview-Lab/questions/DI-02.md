# DI-02

## Original interview question

Compare constructor injection, field injection, and manual DI.

## What the interviewer evaluates

- Prefer explicit constructor requirements for ordinary classes while explaining Android-owned instantiation constraints.
- Distinguish injection site from manual versus framework-driven graph assembly.
- Discuss initialization, testability, and invalid partially constructed states.

## Explanation in Arabic

مقارنة متعمقة بين Constructor Injection، و Field Injection، و Manual DI في Android:

1. Constructor Injection (الحقن عبر المشيد):
   - **كيف يعمل**: تمرير التبعيات مباشرة كـ `val` في الـ Constructor للكلاس.
   - **المميزات**: هو المعيار الذهبي (Gold Standard). يجعل التبعيات صريحة وغير قابلة للتغيير (Immutable)، ويمنع الكائن من التواجد في حالة غير مكتملة (Partially Constructed State). يتيح الـ Unit Testing على الـ JVM بسهولة فائقة دون أي أطر عمل.
   - **العيوب في Android**: لا يمكن استخدامه مباشرة مع الكلاسات التي ينشئها نظام أندرويد عبر الـ Reflection (مثل Activity, Fragment, Service, BroadcastReceiver).

2. Field Injection (الحقن عبر الحقول `@Inject lateinit var`):
   - **كيف يعمل**: يتم إنشاء الكائن بواسطة الـ Android OS، ثم يقوم المجمع (Dagger/Hilt) بحقن الحقول بعد الإنشاء مباشرة عبر `@AndroidEntryPoint`.
   - **المميزات**: الحل الإجباري للأصناف التي يتحكم النظام في إنشائها (Activities, Services).
   - **العيوب**: المتغيرات تكون `lateinit var` وقابلة للتعديل (Mutable). احتمالية حدوث `UninitializedPropertyAccessException` إذا تم استدعاء الحقل قبل إتمام الحقن، وصعوبة إجراء Unit Testing بدون استدعاء دوال حقن مخصصة.

3. Manual DI (حقن التبعيات اليدوي):
   - **كيف يعمل**: بناء شجرة التبعيات يدوياً باستخدام كلاسات Kotlin عادية (`AppContainer`) بدون استخدام Dagger أو Hilt.
   - **المميزات**: وقت تجميع سريع جداً (صفر كود مولد أو Annotation Processing)، سهولة قراءة الـ Stack Trace بدون ألغاز، ومثالي للمشاريع والمكتبات الصغيرة.
   - **العيوب**: يتطلب كتابة كميات ضخمة من كود المصانع (Factory Boilerplate) يدوياً، وصعوبة إدارة الـ Scoping ودورات حياة أندرويد المعقدة يدوياً في المشاريع الضخمة.

## Practical walkthrough

المقارنة العملية بالكود بين الأنماط الثلاثة:
```kotlin
// 1. Constructor Injection: الأفضل والأكثر أماناً للكلاسات العادية والـ ViewModels:
class FetchUserDataUseCase @Inject constructor(
    private val repository: UserRepository // Immutable, non-null, explicit
) {
    suspend operator fun invoke() = repository.getUser()
}

// 2. Field Injection: إجباري لمكونات أندرويد التي ينشئها النظام (Activities/Services):
@AndroidEntryPoint
class MainActivity : ComponentActivity() {
    @Inject lateinit var analytics: AnalyticsTracker // يتم حقنه بعد onCreate وقبل استخدامه
    
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        // آمن للاستخدام بعد استدعاء super.onCreate()
        analytics.trackScreen("Main")
    }
}

// 3. Manual DI: إدارة الحاوية يدوياً بدون مكتبات خارجية:
class AppContainer(private val context: Context) {
    val database: AppDatabase by lazy { Room.databaseBuilder(context, AppDatabase::class.java, "db").build() }
    val userRepository: UserRepository by lazy { UserRepositoryImpl(database.userDao()) }
}
```

## Why it matters and how it works

Constructor injection transfers every required dependency as the object is built, allowing immutability and straightforward JVM tests. Field injection mutates an instance after its constructor; Android framework components often need this because the platform creates them. Manual DI controls the composition root directly without code generation, but can accumulate factories and lifecycle bookkeeping. Hilt can use constructor injection for owned classes and field injection at supported Android entry points.

## Worked example

An owned `OrdersRepository` can declare `@Inject constructor(api: OrdersApi, dao: OrdersDao)`, making both needs explicit. An `@AndroidEntryPoint` Activity can receive `@Inject lateinit var analytics: Analytics` because Android instantiates the Activity, while its ViewModel should receive a constructor-injected repository. For a small app, an `AppContainer` can construct the same repository manually and pass it to a ViewModel factory. These are integration patterns, not complete standalone snippets.

## Trade-offs and decision criteria

Constructor injection is clear and testable, but runtime parameters may require assisted creation or a factory. Field injection works at framework-owned boundaries yet hides requirements from the constructor and can be accessed too early. Manual DI has little build-tool overhead but requires developers to maintain graph construction and scope. A framework earns its cost when graph complexity and Android entry points make manual wiring error-prone.

## Failure modes

An Activity accesses a `lateinit` field before Hilt injects it. A business object exposes public mutable injected fields and is used partially initialized. A manual container accidentally creates one database per screen or retains Activity Context. A factory omits a runtime account ID. Test construction paths, verify scope and entry-point configuration, and keep runtime data distinct from injectable services.

## Production perspective

Use constructor injection throughout repositories/use cases/ViewModels where possible; keep field injection restricted to supported framework entry points. Centralize manual graph wiring if not using Hilt, and test every variant's app container. For session-bound dependencies, define teardown at logout rather than promoting all objects to process singletons.

## Interview answer — short

Constructor injection passes immutable dependencies explicitly via constructor parameters and is the gold standard for testability and immutability. Field injection is required for Android-instantiated components (Activities, Services) where Hilt injects lateinit vars after creation. Manual DI wires graphs using pure Kotlin containers without frameworks, avoiding build overhead but requiring extensive factory boilerplate.

## Interview answer — structured

Choosing between constructor injection, field injection, and manual DI depends on class ownership and framework integration.

First, with Constructor Injection, always the default choice for repositories, use cases, and ViewModels. It ensures dependencies are explicit, immutable (`val`), non-null, and fully satisfied before the object can exist. It allows pure JVM unit testing by passing mocks or fakes into the constructor without any DI framework. Next, with Field Injection, Android creates Activities, Services, and BroadcastReceivers via reflection through their default no-arg constructors. Because we cannot alter their constructor signatures, Hilt/Dagger uses field injection (`@Inject lateinit var`). The container populates these fields immediately after creation. The trade-off is mutability and the risk of accessing uninitialized fields before injection.
Finally, with Manual DI, building the object graph by hand using an `AppContainer`. It provides lightning-fast compile times, zero annotation processing, and crystal-clear stack traces. However, on large multi-module teams, manually maintaining factories and matching Android component scopes becomes an overwhelming maintenance burden.


## Interview answer — deep senior

Under the hood, Dagger and Hilt bridge the gap between Constructor and Field injection via generated code:

For Constructor Injection, Dagger generates a `Factory<T>` (e.g. `UserRepository_Factory`), implementing `get(): T { return new UserRepository(provider.get()); }`. It is clean, direct instantiation with zero reflection.

For Field Injection in `@AndroidEntryPoint Activity`, Hilt generates a base class (or uses bytecode transformation via the Hilt Gradle Plugin) that intercepts `onCreate()` before `super.onCreate()`. It retrieves the `ActivityComponent` from the Application's generated entry point and invokes a `MembersInjector<MainActivity>` (e.g. `MainActivity_MembersInjector.injectAnalytics(instance, provider.get())`). If you attempt to access an `@Inject lateinit var` inside an initializer block (`init { ... }`) or before `super.onCreate()`, the app crashes with an `UninitializedPropertyAccessException` because field injection has not executed yet.


## How to answer in the interview

- **Why:** required collaborators should be explicit.
- **How:** constructors for owned classes, fields at framework entry points.
- **Trade-off:** manual clarity versus generated wiring.
- **Failure case:** reading injected field before injection.
- **Production solution:** direct JVM tests and Android entry-point smoke tests.

## Deep-dive talking points

Discuss injection site versus composition mechanism, framework instantiation, partial initialization, runtime parameter factory, and scope tests.

## Follow-up questions

- **Interviewer:** "Can we use constructor injection in Fragments?"
  **Answer:** "Yes, using FragmentFactory with Hilt or Dagger. However, with Jetpack Compose, Activities host Composables directly, largely rendering FragmentFactory unnecessary."

- **Interviewer:** "Why is method injection rarely used in Android?"
  **Answer:** "Method injection executes after constructor injection but before field usage. In modern Android, passing dependencies directly as method parameters (`useCase.execute(param)`) or via the constructor is cleaner and less ambiguous."
