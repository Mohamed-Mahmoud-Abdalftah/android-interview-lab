# DI-02

## Original interview question

Compare constructor injection, field injection, and manual DI.

## What the interviewer evaluates

Can the candidate distinguish where a dependency enters an object from who assembles the graph, choose the right boundary for Android-owned components, and avoid treating constructor injection as a thread-safety guarantee?

## Concept and technical explanation

Constructor and field injection describe injection sites. Manual DI describes how the object graph is assembled; a manual container can use constructor injection. For an ordinary class you construct, a required collaborator in its constructor is explicit and available when construction completes. A `val` prevents reassignment of that reference, but does not make the collaborator immutable or thread-safe. Direct JVM tests can supply a fake without starting Hilt.

Field injection fills a property after construction. Hilt supports it on Android entry points that the framework creates, such as an `@AndroidEntryPoint` Activity using `@Inject lateinit var analytics`. The property must not be used before injection, and a `lateinit` property can be read too early. Field injection is not the universal requirement for all Android-related types: a Hilt ViewModel uses `@HiltViewModel` with constructor injection, and factories can construct other owned classes. Hilt graph validation checks available bindings and cycles, not the semantics of scope or policy.

Manual DI uses Kotlin code to create and pass dependencies. It avoids Hilt's generated graph setup and keeps construction visible, but requires someone to maintain scopes, factories, and Android lifecycle handoff. The Kotlin compiler still checks ordinary types and constructor calls; manual DI is not devoid of compile-time checking. Hilt adds graph-level checks for its bindings.

## Practical walkthrough (English)

An `OrdersUseCase` takes `OrdersRepository` in its constructor. A handwritten `AppContainer` or Hilt can create that class. An Activity created by Android may receive a Hilt-injected analytics field; it should use it only after the documented injection point, while a Hilt ViewModel can receive the repository in its constructor. For a small app, a manual container and ViewModel factory may be sufficient. With many bindings and entry points, generated graph validation may justify Hilt's configuration.

## Why it matters and how it works

A required constructor parameter is visible to callers and tests. A field is not necessarily ready during initialization, so lifecycle timing matters. Android's ownership of an Activity's construction explains Hilt field injection there; it does not justify mutable injected fields throughout policy classes. Manual DI can keep the graph understandable but makes the team responsible for component lifetime and replacement. No injection style guarantees runtime synchronization or architectural quality.

## Worked example

Runnable Kotlin/JVM example: both manual construction and a generated container could call the same constructor. The Hilt Activity field-injection path is Android-specific and is not claimed to be tested by this JVM snippet.

```kotlin
interface OrdersRepository {
    fun countOpen(): Int
}

class OpenOrderCount(private val repository: OrdersRepository) {
    fun load(): Int = repository.countOpen()
}

class ManualGraph(private val repository: OrdersRepository) {
    fun openOrderCount(): OpenOrderCount = OpenOrderCount(repository)
}
```

For a real `@AndroidEntryPoint` Activity, an `@Inject lateinit var` field is supplied by Hilt after Android constructs the component; use it only at a supported lifecycle point.

## Trade-offs and decision criteria

Constructor injection expresses required collaborators and supports direct tests, but runtime values may need a factory or supported assisted creation. Field injection works at framework-owned Hilt entry points but introduces post-construction timing and a mutable property. Manual DI reduces generated-tool setup but can grow complex with many lifetimes and variants. Hilt's graph checks help when binding complexity grows; it also adds build configuration. Measure build cost rather than assuming one approach is always faster.

## Failure modes

An Activity reads `lateinit analytics` during property initialization before injection. A business class uses public injected fields and permits partially initialized use. A manual container accidentally creates one database per screen or retains an Activity context. A constructor uses a `val` reference to a mutable repository and the team assumes it is thread-safe. A runtime account ID is treated as a process-scoped service instead of a factory input.

## Production perspective

Use constructors for required dependencies in ordinary classes and Hilt ViewModels. Use Hilt field injection only where its supported Android entry-point lifecycle calls for it. If wiring manually, keep a clear composition root and test graph identity and teardown. Verify Hilt entry-point behavior on Android separately from JVM policy tests. Review scopes and runtime parameters independently from injection syntax.

## Interview answer — short

Constructor injection names required dependencies when an object is created, so direct tests can pass fakes. Field injection sets a property after construction; Hilt uses it at supported Android entry points, so access timing matters. Manual DI means writing the graph yourself and can still use constructors. Hilt adds generated binding checks, while Kotlin still type-checks manual wiring. None of these choices alone guarantees thread safety or a good architecture.

## Interview answer — structured

I separate injection site from graph assembly. Constructor injection puts required collaborators in the signature of a class I construct, such as a use case or Hilt ViewModel. Tests can instantiate it with a fake. A `val` keeps the reference stable, though the dependency may still be mutable. Field injection fills a property after construction; Hilt supports that on an Android-owned Activity or Service, so I avoid reading the field before the supported injection point.

Manual DI is handwritten composition using constructors, factories, and containers. It has ordinary Kotlin type checking, but the team owns graph assembly, scope, and lifecycle rules. Hilt generates components and validates its binding graph, at the cost of configuration and code generation. In a small graph manual wiring may be clear; a complex app with many entry points can benefit from Hilt. I verify Android injection separately and never infer thread safety from `@Inject` or `val`.

## Interview answer — deep senior

Constructor injection, field injection, and manual DI are not three mutually exclusive containers. The first two tell us where the dependency enters an object; manual DI tells us that application code assembles the graph. A manual composition root can call every constructor explicitly. Hilt can also constructor-inject ordinary classes and Hilt ViewModels, while using field injection at supported Android entry points whose construction the framework controls.

For a required collaborator in an owned class, the constructor makes the requirement visible and lets a plain JVM test pass a fake. The constructor finishing does not make the whole object graph immutable or safely published across threads by magic. A Kotlin `val` prevents reassignment of one reference; the referenced repository can still mutate. With field injection, the object exists before the field is set, so using a `lateinit` field in property initialization or too early in the lifecycle is an error. I keep that timing issue at a narrow Android boundary rather than spreading fields into policy classes.

Manual DI is often easy to inspect in a small app, and the Kotlin compiler catches incorrect constructor calls and types. It does not automatically provide Hilt's generated graph checks for missing or cyclic bindings, and developers must manage lifetimes, variants, and Android entry points. Hilt can validate bindings, but a valid graph can still use a poor scope or leak a transport detail into business policy. I choose by graph complexity and ownership needs, test pure behavior through constructors, and run Android injection tests where field timing or generated components matter. Runtime arguments such as account IDs stay separate from long-lived service bindings.

## How to answer in the interview

- Distinguish injection site from graph assembly.
- Give an ordinary constructor example, an Android field example, and a manual container.
- State field timing, runtime arguments, scope, and test boundaries.
- Reject claims that `val` means immutable collaborator or that manual DI has no compiler checks.

## Deep-dive talking points

Hilt ViewModel constructor injection; Activity field timing; `lateinit`; manual composition root; graph validation; runtime parameters; scope and thread-safety review.

## Follow-up questions

- **Interviewer:** “Is field injection mandatory for all Android classes?” **Answer:** “No. Hilt uses it on supported framework-created entry points, while Hilt ViewModels and ordinary owned classes can use constructor injection.”
- **Interviewer:** “Does manual DI lose all compile-time checking?” **Answer:** “No. Kotlin checks constructor calls and types; Hilt additionally validates its generated binding graph.”
- **Interviewer:** “Does a `val` injected dependency make a class thread-safe?” **Answer:** “No. The reference cannot be reassigned, but the collaborator and its operations can still be mutable or unsynchronized.”
