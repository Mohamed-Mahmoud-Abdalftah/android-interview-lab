# BG-08

## Original interview question

How do you queue offline synchronization and retry with WorkManager?

## What the interviewer evaluates

Queue offline synchronization with durable outbox, constraints and safe retry.

## Concept and technical explanation

Queueing offline synchronization and retry with WorkManager relies on the Outbox architectural pattern, establishing a reliable transactional bridge between local persistent storage and remote servers. When a user creates or modifies data while offline, the repository immediately commits the mutation to the local Room database within a transaction, assigning the record a pending sync state and a client-generated UUID. The repository then enqueues a unique OneTimeWorkRequest configured with network constraints and exponential backoff retry criteria. When execution conditions are satisfied, the CoroutineWorker retrieves pending mutations, transmits them to the backend with idempotency headers, marks local records as synced upon success, and triggers exponential retries via Result.retry() if network interruptions occur.

## Practical walkthrough (English)

Implementing the Outbox Pattern with WorkManager and Room:
```kotlin
// 1. Room Entity with local sync status tracking
@Entity(tableName = "posts")
data class PostEntity(
    @PrimaryKey val id: String = UUID.randomUUID().toString(),
    val content: String,
    val syncStatus: SyncStatus = SyncStatus.PENDING // PENDING, SYNCED, FAILED
)

// 2. Repository commits locally and schedules unique WorkManager task
class PostRepositoryImpl(
    private val postDao: PostDao,
    private val workManager: WorkManager
) : PostRepository {
    override suspend fun createPost(content: String) {
        val post = PostEntity(content = content, syncStatus = SyncStatus.PENDING)
        postDao.insertPost(post) // 1. Immediate local persistence (SSOT)

        // 2. Enqueue unique durable worker
        val syncRequest = OneTimeWorkRequestBuilder<SyncPostsWorker>()
            .setConstraints(Constraints.Builder().setRequiredNetworkType(NetworkType.CONNECTED).build())
            .setBackoffCriteria(BackoffPolicy.EXPONENTIAL, 15, TimeUnit.SECONDS)
            .build()

        workManager.enqueueUniqueWork("sync_posts_work", ExistingWorkPolicy.KEEP, syncRequest)
    }
}

// 3. CoroutineWorker batches pending items and commits status atomically
class SyncPostsWorker(context: Context, params: WorkerParameters) : CoroutineWorker(context, params) {
    override suspend fun doWork(): Result = withContext(Dispatchers.IO) {
        val dao = AppDatabase.getInstance(applicationContext).postDao()
        val api = NetworkClient.api
        val pendingPosts = dao.getPendingPosts()

        if (pendingPosts.isEmpty()) return@withContext Result.success()

        runCatching {
            pendingPosts.forEach { post ->
                api.uploadPost(PostDto(id = post.id, content = post.content)) // Idempotent by UUID!
                dao.updateSyncStatus(post.id, SyncStatus.SYNCED)
            }
            Result.success()
        }.getOrElse { Result.retry() } // Triggers exponential backoff on network failure
    }
}
```

كيف تدير طابور المزامنة في وضع عدم الاتصال (Offline Sync Queue) وإعادة المحاولة عبر WorkManager؟

1. معمارية طابور الـ Outbox:
   - **جدول الـ Outbox في Room**: جدول محلي يحتوي على العمليات المعلقة: `id`, `entity_type`, `action (INSERT/UPDATE/DELETE)`, `payload_json`, `created_at`, `status`.

2. جدولة وتفعيل المزامنة:
   - يتم إطلاق `SyncOutboxWorker` كـ Unique Work بسياسة `KEEP` مع شرط `NetworkType.CONNECTED`.
   - إذا كان الهاتف متصلاً، يبدأ العمل فوراً؛ وإذا كان غير متصل، ينتظر في صمت دون استهلاك أي موارد حتى تتوفر الشبكة.

3. معالجة الأخطاء وإعادة المحاولة بذكاء:
   - أخطاء الشبكة المؤقتة والـ Timeouts: يُرجع الـ Worker تعليمة `Result.retry()`، ويطبق WorkManager سياسة الـ Exponential Backoff.

## Practical walkthrough

تنفيذ طابور المزامنة التتابعي المتكامل في CoroutineWorker:
```kotlin
@HiltWorker
class OutboxDrainWorker @AssistedInject constructor(
    @Assisted context: Context,
    @Assisted params: WorkerParameters,
    private val db: AppDatabase,
    private val api: SyncApiService
) : CoroutineWorker(context, params) {

    override suspend fun doWork(): Result {
        // 1. قراءة أقدم العمليات المعلقة بالترتيب الزمني (FIFO):
        val pendingActions = db.outboxDao().getPendingActions(limit = 10)
        if (pendingActions.isEmpty()) return Result.success()

        for (action in pendingActions) {
            try {
                // 2. إرسال العملية مع مفتاح تكرار فريد وثابت:
                api.syncAction(action.id, action.actionType, action.payloadJson)
                
                // 3. حذف العملية من الطابور بعد تأكيد السيرفر:
                db.withTransaction {
                    db.outboxDao().deleteAction(action.id)
                    db.itemsDao().markSynced(action.targetEntityId)
                }
            } catch (e: IOException) {
                // انقطاع شبكة عابر: نطلب إعادة المحاولة تلقائياً بـ Exponential Backoff:
                return Result.retry()
            } catch (e: HttpException) {
                if (e.code() in 400..499 && e.code() != 409) {
                    // خطأ دائم في العميل: نحذف من الطابور لمنع تعليق باقي العمليات:
                    db.outboxDao().markPermanentFailure(action.id, e.message())
                } else {
                    return Result.retry()
                }
            }
        }
        return Result.success()
    }
}
```

## Why it matters and how it works

WorkManager scheduling and business outbox must be coordinated despite no atomic transaction across their databases. A startup/foreground scan should enqueue if pending rows exist. Worker processes stable IDs, marks acknowledged only after authoritative response and respects server rate limits.

## Worked example

Conceptual Android enqueue; `SyncWorker` reads durable outbox, so WorkRequest Data contains no sensitive payload.

```kotlin
import androidx.work.*

fun scheduleOutbox(manager: WorkManager) {
    val request = OneTimeWorkRequestBuilder<SyncWorker>()
        .setConstraints(Constraints.Builder()
            .setRequiredNetworkType(NetworkType.CONNECTED).build())
        .build()
    manager.enqueueUniqueWork("outbox-sync", ExistingWorkPolicy.KEEP, request)
}
```

## Trade-offs and decision criteria

Network constraint avoids futile attempts but delays work until connectivity. Unique scheduling reduces duplicate queues but not duplicate server execution. Backoff limits retry load; user-visible pending state handles delay.

## Failure modes

If app crashes after outbox commit and before enqueue, work is stranded unless recovery scans pending rows. If worker crashes after server commit and before local acknowledgement, retry must reuse ID and reconcile. A blanket retry on conflict can loop forever.

## Production perspective

A field app stores edits and pending IDs, shows them immediately offline, schedules a network-constrained worker and syncs on reconnect. Backend checks versions and idempotency. Tests cut connectivity and kill process at every transition.

## Interview answer — short

Queue offline synchronization using the Outbox pattern: save the mutation to the local Room database immediately with a PENDING state and unique UUID, then enqueue a unique WorkManager request with a connected network constraint and exponential backoff. The worker reads pending items, posts them to the API idempotently, marks them as SYNCED upon success, and returns Result.retry on network errors.

## Interview answer — structured

Implementing robust offline synchronization requires combining local persistence with durable WorkManager background execution through the Outbox pattern.
The workflow begins at the data layer. When a user performs an action—such as submitting an order or creating a comment—the repository writes the record directly to the local Room database inside an atomic transaction. The record is flagged with a sync status of PENDING and stamped with a client-generated UUID. This delivers immediate, zero-latency feedback to the UI.
Next, the repository enqueues a OneTimeWorkRequest using unique work scheduling with ExistingWorkPolicy.KEEP. The request configures a network constraint requiring NetworkType.CONNECTED and sets an exponential backoff policy starting at fifteen seconds.
When network connectivity becomes available, WorkManager executes the worker on a background dispatcher. The worker queries Room for all PENDING mutations, batches them to the backend API, and attaches each record's UUID as an idempotency key.
Upon receiving a successful HTTP response, the worker updates the local Room entities to SYNCED. If the network call throws an IOException or the server returns a temporary error, the worker returns Result.retry(), prompting WorkManager to back off exponentially before re-attempting.

## Interview answer — deep senior

Under the hood, executing offline synchronization across distributed mobile networks requires solving synchronization race conditions, payload batching, and server idempotency.
A critical architectural trap is attempting to pass large mutation payloads directly inside WorkManager's Data object via setInputData(). The WorkManager Data container is constrained by Android Binder transaction buffer limits (strictly capped at 10KB total). Passing large JSON strings or image byte arrays triggers an IllegalStateException or fatal TransactionTooLargeException.
Instead, the Outbox pattern uses WorkManager purely as an execution trigger. The actual data payload resides safely inside the persistent Room SQLite database. The worker simply wakes up, queries the database for pending records, processes the batch, and updates local rows transactionally.
Furthermore, because mobile network connections frequently drop mid-transmission, a worker might successfully send data to the backend but crash or disconnect before receiving the HTTP 200 response. When WorkManager retries, the worker will submit the exact same mutation again.
Staff engineers guarantee transactional safety by designing idempotent backend APIs. The client-generated UUID assigned during the initial Room insert acts as an Idempotency-Key header in the HTTP request. When the server encounters a duplicate UUID, it returns the cached success response rather than creating a duplicate database record, ensuring flawless data integrity under erratic network conditions.

## Follow-up questions

- **Interviewer:** "What happens if the phone reboots while the outbox queue has 20 pending items?"
  **Answer:** "WorkManager reconstructs the worker from SQLite upon device reboot and executes it as soon as the network connected constraint is satisfied."

- **Interviewer:** "Why shouldn't you send all 20 outbox items concurrently in parallel coroutines?"
  **Answer:** "Parallel dispatch risks out-of-order execution on the server (e.g. executing an item update before its creation has processed)."
