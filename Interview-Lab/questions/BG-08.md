# BG-08

## Original interview question

How do you queue offline synchronization and retry with WorkManager?

## What the interviewer evaluates

Queue offline synchronization with durable outbox, constraints and safe retry.

## Explanation in Arabic

الـoffline edit تتسجل مع outbox row وoperation ID في Room transaction. نعمل unique WorkManager work بـnetwork constraint علشان يقرأ pending rows، يرسلها بمفاتيح idempotency ثابتة، ويرجع `Result.retry()` للأخطاء المؤقتة. `409` conflict يحتاج state خاصة؛ `400` validation مش retry. لو response ضاعت نعمل status reconciliation بدل duplicate logical write.

## Why it matters and how it works

WorkManager scheduling and business outbox must be coordinated despite no atomic transaction across their databases. A startup/foreground scan should enqueue if pending rows exist. Worker processes stable IDs, marks acknowledged only after authoritative response and respects server rate limits.

## Worked example

Conceptual Android enqueue; `SyncWorker` reads durable outbox, so WorkRequest Data contains no sensitive payload.

```kotlin
import androidx.work.*

fun scheduleOutbox(manager: WorkManager) {
    val request = OneTimeWorkRequestBuilder<SyncWorker>()
        .setConstraints(Constraints.Builder()
            .setRequiredNetworkType(NetworkType.CONNECTED).build())
        .build()
    manager.enqueueUniqueWork("outbox-sync", ExistingWorkPolicy.KEEP, request)
}
```

## Trade-offs and decision criteria

Network constraint avoids futile attempts but delays work until connectivity. Unique scheduling reduces duplicate queues but not duplicate server execution. Backoff limits retry load; user-visible pending state handles delay.

## Failure modes

If app crashes after outbox commit and before enqueue, work is stranded unless recovery scans pending rows. If worker crashes after server commit and before local acknowledgement, retry must reuse ID and reconcile. A blanket retry on conflict can loop forever.

## Production perspective

A field app stores edits and pending IDs, shows them immediately offline, schedules a network-constrained worker and syncs on reconnect. Backend checks versions and idempotency. Tests cut connectivity and kill process at every transition.

## Interview answer — short

“I use a transactional local outbox, schedule unique network-constrained WorkManager sync, and make each operation repeat-safe with a stable server key. I recover the gap between local commit and enqueue by scanning pending rows.”

## Interview answer — structured

“An offline edit is accepted only after Room commits both the content and its pending operation. A Worker reads pending IDs when network is available, submits them with stable idempotency keys and marks them acknowledged after a trustworthy server response. Transient failures retry with backoff; validation and conflict errors become explicit states. Because Room and WorkManager have separate stores, startup or foreground recovery must find pending rows that were committed before enqueue completed. The UI observes local status.”

## Interview answer — deep senior

“I design the outbox as the durable source, not the WorkRequest payload. Each row has operation ID, base version, attempt metadata and state. Worker runs can repeat after crash, so it checks acknowledgement, sends the same key and reconciles ambiguous timeout via server status. WorkManager’s network constraint and backoff handle scheduling, but do not imply exactly-once effects. A scan repairs the gap between Room commit and WorkManager enqueue. I partition by account, stop old-session work on logout without discarding unresolved server truth, and monitor oldest pending age. Tests simulate offline edits, conflict, rate limit, duplicate worker, server-commit/client-crash and reboot. Backend checks versions and idempotency.”
