# BG-14

## Original interview question

How do you coordinate WorkManager with repository and database transactions?

## What the interviewer evaluates

Coordinate WorkManager scheduling with repository and Room transactions despite separate databases.

## Explanation in Arabic

Room transaction تقدر تحفظ domain row وoutbox row معًا، لكن ما تقدرش تعمل atomic commit مع WorkManager database. لذلك نخلي outbox هي الحقيقة: بعد commit نعمل enqueue unique work، ولو process مات بين الاتنين، startup/foreground scan يلاقي pending rows ويعيد enqueue. worker تقرأ ID فقط، وتعمل claim/check وتكتب acknowledgement transactionally بعد server confirmation.

## Why it matters and how it works

At-least-once scheduling is acceptable when the worker is idempotent. The repository owns the outbox and business states; WorkManager owns eligible execution. Keep `WorkRequest` input small and non-sensitive. A unique drain worker can process many pending rows; use stable server keys and retry classification.

## Worked example

Conceptual Android coordinator; Dao and SyncWorker are application types with a Room transaction for `saveWithPending`.

```kotlin
import androidx.work.ExistingWorkPolicy
import androidx.work.OneTimeWorkRequestBuilder
import androidx.work.WorkManager

suspend fun acceptAndSchedule(dao: EditDao, manager: WorkManager, edit: Edit) {
    dao.saveWithPending(edit) // one Room transaction
    manager.enqueueUniqueWork(
        "outbox", ExistingWorkPolicy.KEEP,
        OneTimeWorkRequestBuilder<SyncWorker>().build(),
    )
}
```

## Trade-offs and decision criteria

One drain worker simplifies scheduling and retries but can delay a high-priority item behind others; partition by priority if needed. Direct enqueue per item is simpler for few operations but grows scheduler rows. Either way, database/WorkManager atomicity gap needs a recovery scan.

## Failure modes

If enqueue fails after local commit, the UI must not forget pending work. If worker runs twice, it must not send two logical writes. Holding a Room transaction open around WorkManager enqueue does not create a distributed transaction and can block the DB.

## Production perspective

A form repository stores edit plus outbox row, then schedules one unique drain. App startup scans pending rows and ensures the drain is queued. Worker submits under stable keys, marks receipts and tracks stuck pending age.

## Interview answer — short

“Room and WorkManager do not share one transaction. I commit the business row and outbox row together, enqueue afterward, and repair the commit-to-enqueue gap by scanning pending work. The worker is repeat-safe.”

## Interview answer — deep senior

“This is a two-system coordination problem. A Room transaction can atomically accept user data and its outbox intent, but cannot atomically commit a WorkManager request or a remote server write. I choose a recoverable order: local commit first, enqueue second, and a periodic/startup repair scan for pending rows lacking effective scheduling. Repeated enqueues or worker attempts are safe because a shared operation ID and backend deduplication converge on one logical result. Worker state transitions use Room transactions and version checks so two workers cannot both claim a row blindly.
