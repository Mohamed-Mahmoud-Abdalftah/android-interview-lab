# SEC-31

## Original interview question

A team puts a private API key in BuildConfig from local.properties. Why is this not sufficient?

## What the interviewer evaluates

- BuildConfig/local.properties extraction path.
- Incident response and server-side privilege design.

## Concept and technical explanation

Storing secrets in local.properties and exposing them via BuildConfig field generation is effective for source control hygiene—it prevents sensitive tokens from being committed to Git repositories—but it provides zero security against extraction from compiled application binaries. During the build process, Gradle translates buildConfigField declarations into static string constants inside the generated BuildConfig.java class. When compiled into classes.dex within the final APK or AAB, these strings reside as plaintext literals in the DEX string pool. Any adversary can download the APK, execute a single command like strings classes.dex or open the binary in decompilers like JADX, and extract the secret within seconds. Consequently, private secrets (such as payment gateway secret keys, cloud master credentials, and backend service keys) must never reside inside a mobile client.

## Practical walkthrough (English)

Architecture migration replacing client-side secret with Backend-For-Frontend (BFF) gateway:
```kotlin
// 1. VULNERABLE APPROACH: Private secret baked into BuildConfig
// val stripeClient = Stripe(BuildConfig.STRIPE_SECRET_KEY) // Trivially decompiled from DEX!

// 2. SECURE BFF ARCHITECTURE: Ephemeral intent token generated by secure server
class PaymentRepository(private val backendApi: BackendPaymentApi) {
    suspend fun initiateCheckout(cartId: String): ClientSecretToken {
        // Backend creates payment intent using its own private master key in the cloud
        // Mobile client receives ONLY an ephemeral, scoped client secret
        val response = backendApi.createPaymentIntent(cartId)
        return response.clientSecret
    }
}
```

## Explanation in Arabic

فريق برمجي يضع مفتاح الـ API الخاص (Private API Key) في ملف `local.properties` ويقرأه داخل `BuildConfig`. لماذا يُعد هذا غير كافٍ وثغرة أمنية فادحة؟

1. ما الذي يفعله `local.properties` وما الذي لا يفعله؟
   - وضع المفتاح في `local.properties` يمنع رفعه إلى مستودع الـ Git (GitHub/GitLab) إذا كان الملف مستثنى في `.gitignore`. هذا إجراء تنظيمي جيد لحماية الـ Git History فقط.
   - **لكن**: عند قراءة المفتاح وتمريره إلى `buildConfigField`, يقوم Gradle بتوليد كلاس جافا اسمه `BuildConfig.java` يحتوي على سطر صريح:
     `public static final String STRIPE_SECRET = "sk_live_1234567890";`.

2. كيف يتم استخراج هذا المفتاح من الـ APK في 5 ثوانٍ؟
   - عند تجميع الـ APK، يُترجم كلاس `BuildConfig` إلى Dalvik Bytecode داخل `classes.dex`.
   - يستطيع أي شخص تنزيل الـ APK من المتجر وتنفيذ أمر سطر واحد في الـ Terminal:
     `strings classes.dex | grep sk_live`
     أو فتح الـ APK في `JADX-GUI` وقراءة المفتاح بنصه الصريح فوراً!

3. الفرق بين المفاتيح العامة (Public Keys) والمفاتيح الخاصة (Private Secrets):
   - **المفاتيح العامة (Allowed on Client)**: مفاتيح مثل Google Maps API Key أو Firebase Public Key. هذه المفاتيح مخصصة لتعريف التطبيق ومحمية من جهة Google Console بقيود الباكدج والبصمة الرقمية (Package Name + SHA-1 Restriction).
   - **المفاتيح الخاصة (Strictly Forbidden on Client)**: مفاتيح مثل OpenAI Secret Key, Stripe Secret Key, AWS S3 Master Credentials. هذه المفاتيح **ممنوع تماماً وضعها في أي تطبيق موبايل**! يجب أن تظل حصرياً على خادم الـ Backend (BFF - Backend for Frontend)، ويقوم الموبايل بالاتصال بالسيرفر الخاص بك والسيرفر هو من يتصل بتلك الخدمات.

## Practical walkthrough

المقارنة بين الطريقة الساذجة المكشوفة في الـ APK والمعمارية الصحيحة باستخدام Backend for Frontend:

```groovy
android {
    defaultConfig {
        // يتم تضمين هذا المفتاح كنص صريح في ملف DEX ويمكن استخراجه في ثوانٍ!
        buildConfigField "String", "OPENAI_SECRET_KEY", "\"sk-proj-998877665544332211\""
    }
}
```

```kotlin
// ✅ المعمارية الصحيحة: العميل لا يملك المفتاح السري، بل يتصل بـ Backend Proxy:
class AiAssistantRepository(
    private val companyBackendApi: CompanyBackendApi

    suspend fun generateSummary(userPrompt: String): String {
```

## Why it matters and how it works

BuildConfig values are compiled into the distributed client. R8 name changes and JNI relocation cannot create a server-controlled secret. Provider package/signature restrictions and quotas may help for public mobile identifiers, but private operations require server custody and authorization.

## Worked example

A team stores `ACQUIRER_PRIVATE_KEY` in local.properties and writes it to BuildConfigField. The remediation is to revoke/rotate the key, inspect provider activity, remove it from APK artifacts, and have the backend create scoped payment intents after validating user and order state.

## Trade-offs and decision criteria

Keeping config out of Git remains useful hygiene. A backend proxy costs latency and maintenance but is the proper trust boundary for privileged keys. Public SDK keys can stay in APK only under the provider’s documented restrictions.

## Failure modes

Rotating only the local.properties file leaves already released APKs with the old key. Removing the source line without revoking the provider credential leaves the incident active. Inspect all release versions and use provider-side revocation.

## Production perspective

CI scans source and packaged artifacts, while secret-management controls restrict backend access. Backend logs key identifiers and operation IDs rather than raw credentials.

## Interview answer — short

Storing secrets in local.properties and exposing them via BuildConfig prevents pushing keys to Git, but provides zero security against extraction from the APK. During compilation, Gradle embeds the key as a plaintext string in classes.dex. Anyone can decompile the APK with JADX or run strings to extract the secret within seconds.

## Interview answer — structured

Putting API keys in local.properties and injecting them into BuildConfig is good source control hygiene, but it is completely ineffective as a binary protection mechanism.
The local.properties file successfully prevents developers from accidentally committing sensitive credentials to public or private Git repositories.
However, when Gradle builds the application, it generates a BuildConfig.java class containing the key as a static final string constant.
When compiled into the final APK or App Bundle, this string literal sits in the constant pool of classes.dex in plaintext.
An adversary does not even need to root a device or decompile source code; running a single strings command on classes.dex or opening the APK in tools like JADX reveals the secret in seconds.
Mobile clients must never hold private administrative secrets such as payment gateway secret keys or backend master credentials.
Private credentials must remain on a secure backend gateway, while public third-party keys must be restricted on vendor consoles using package names and SHA-256 signing certificate fingerprints.

## Interview answer — deep senior

This common security misunderstanding stems from confusing source control privacy with compiled binary confidentiality.
Excluding secrets from git commits via local.properties protects against repository leaks, but an Android application is fundamentally a public binary distributed to untrusted hardware.
The build system translates buildConfigField declarations directly into Dalvik bytecode.
Once an APK is released, anyone can download it from the Play Store, unpack classes.dex, and extract strings using basic reverse engineering utilities like strings, apktool, or JADX.
Even if a team attempts to obscure the secret using NDK C++ shared libraries, XOR masking, or string encryption, reverse engineers can hook runtime decryption methods with Frida or dump memory to extract the plaintext key effortlessly.
In robust security architecture, a mobile application is considered an untrusted client that should never possess private master secrets.
If an app requires interaction with a sensitive service like Stripe or AWS, calls must route through our own Backend-for-Frontend gateway.
The mobile app authenticates to our backend using short-lived user session tokens, and our secure server uses its own securely managed private keys to interact with the third-party service.
For unavoidable client-side API keys such as Google Maps or Firebase, we enforce strict vendor-side restrictions, binding the key exclusively to our Android package name and release SHA-256 signing certificate fingerprint.

## How to answer in the interview

- **Why:** compilation copies the credential into an attacker-owned binary.
- **How:** inspect build artifacts and runtime use, then classify the key's privilege.
- **Trade-off:** backend proxy adds an integration step.
- **Failure case:** leaked key can authorize calls outside user context.
- **Production solution:** revoke, investigate, rotate, and remove private credentials from mobile builds.

## Deep-dive talking points

Prompt for APK artifact inspection, provider rotation, backend authority and distinction between public identifier and private key.

## Follow-up questions

- **Interviewer:** "Why is Google Maps API key safe to keep in AndroidManifest.xml?"
  **Answer:** "Because Google Maps APIs restrict usage by verifying the calling app's package name and SHA-1 signing certificate fingerprint on Google servers."

- **Interviewer:** "Can R8 obfuscation hide BuildConfig strings?"
  **Answer:** "No; R8 renames class and variable identifiers, but literal string constants remain completely unencrypted in the DEX string pool."
