# DI-05

## Original interview question

What are @HiltAndroidApp, @AndroidEntryPoint, and @HiltViewModel?

## What the interviewer evaluates

- Place each annotation on the proper Application, supported Android entry point or ViewModel.
- Explain object creation and ViewModelStore ownership.
- Handle fragment hosts, receiver injection and saved-state limits accurately.

## Concept and technical explanation

`@HiltAndroidApp` belongs on the actual Application class and triggers Hilt root code generation. `@AndroidEntryPoint` marks supported Android owners for Hilt injection. An annotated Fragment needs an Hilt-enabled host Activity. A BroadcastReceiver can be injected but has no dedicated Hilt component; its dependencies come from `SingletonComponent`. A composable is not itself an Android entry point. `@HiltViewModel` works with an `@Inject` constructor and the ViewModelProvider/Navigation integration, so the chosen ViewModelStoreOwner determines instance lifetime and sharing. `SavedStateHandle` supports small restorable state, not durable storage for confirmed business operations.

## Practical walkthrough (English)

An illustrative Android setup connects each owner:
```kotlin
@HiltAndroidApp
class ShopApp : Application()

@AndroidEntryPoint
class CatalogActivity : ComponentActivity() {
    @Inject lateinit var analytics: AnalyticsTracker
    private val viewModel: CatalogViewModel by viewModels()
}

@HiltViewModel
class CatalogViewModel @Inject constructor(
    private val repository: CatalogRepository,
    private val state: SavedStateHandle
) : ViewModel()
```
Register `ShopApp` in the manifest and provide the analytics and repository bindings. Here `by viewModels()` uses the Activity owner. A navigation destination needs its appropriate owner. This repository does not compile an Android Hilt graph.

## Explanation in Arabic

`@HiltAndroidApp` توضع على كلاس `Application` المسجل للتطبيق، وبتبدأ توليد Hilt Graph الجذرية وتجهيز الـ Application-level container. ده إعداد للتطبيق؛ مش معناه إن كل Object بتنشأ فورًا وقت التشغيل.

`@AndroidEntryPoint` توضع على Android classes المدعومة مثل Activity وFragment وService وView؛ Hilt توصلها بالـ Component المناسبة وتسمح بحقن الـ Fields. Fragment عليها الـ Annotation لازم تكون مستضافة في Activity تستخدم Hilt. BroadcastReceiver مدعومة للحقن، لكن ما لهاش Component مستقلة؛ Hilt تحقنها من `SingletonComponent`. الـ Composable نفسها مش Android Entry Point؛ عادة الـ Activity المضيفة هي المدخل.

`@HiltViewModel` على ViewModel ذات `@Inject constructor` بتخلي Hilt Factory توفر Dependencies لما تطلب الـ ViewModel من `ViewModelProvider` أو `by viewModels()` أو `hiltViewModel()` في مسار Navigation المناسب. الـ ViewModelStoreOwner، مش الـ Annotation وحدها، يحدد مشاركة الـ Instance وعمرها. `SavedStateHandle` متاحة في التكامل المدعوم، لكنها مش بديل دائم لتخزين بيانات عملية مالية أو كبيرة بعد Process Death.

## Why it matters and how it works

Android constructs framework owners, while ViewModelProvider owns ViewModel identity. Hilt connects its graph to these creation points. The annotation does not replace ViewModelStore ownership or durable persistence. Receivers do not have a dedicated Hilt component even though they can be injected.

## Worked example

A Catalog Activity uses field-injected analytics and obtains `CatalogViewModel` through `by viewModels()`. Rotation should preserve the ViewModel for that Activity owner; a separate navigation entry may own a different instance. Test process recreation for small SavedStateHandle values, and keep confirmed order data in repository storage. The snippet omits Gradle, manifest and actual bindings.

## Trade-offs and decision criteria

Hilt reduces wiring on supported Android paths but requires plugin/compiler, manifest and host setup. A manual factory remains valid without Hilt. Choose a ViewModelStoreOwner that matches the screen boundary; an Activity owner may share state more broadly than a destination owner. SavedStateHandle is not durable business storage.

## Failure modes

The annotated Application is not the one registered in the manifest. An annotated Fragment is hosted in a non-Hilt Activity. A Hilt ViewModel is directly constructed and therefore bypasses the ViewModelProvider factory and store. A receiver is assumed to have its own scope. Important order state exists only in a ViewModel and is lost after process death.

## Production perspective

Document the owner of each ViewModel, then exercise cold start, rotation, navigation and process recreation on Android. Use `@HiltWorker` and the documented factory integration for WorkManager workers. Keep confirmed payment or order records in durable repository storage. JVM logic tests do not establish Android graph wiring.

## Interview answer — short

`@HiltAndroidApp` marks the application class and triggers root graph generation. `@AndroidEntryPoint` marks supported Android classes so Hilt can inject them; an annotated Fragment needs an Hilt-enabled host Activity. `@HiltViewModel` enables constructor-injected ViewModels obtained through ViewModelProvider or the appropriate Navigation owner. That owner determines ViewModel identity and retention. BroadcastReceivers are injected from `SingletonComponent`, without a dedicated receiver component.

## Interview answer — structured

I map each annotation to the framework owner. `@HiltAndroidApp` belongs on the Application registered in the manifest and establishes Hilt code generation for the root graph. `@AndroidEntryPoint` belongs on supported Android classes such as Activity and Fragment to allow member injection; the Fragment host must also participate in Hilt. BroadcastReceiver injection is special because it uses `SingletonComponent` rather than a receiver-specific component. `@HiltViewModel` works with an `@Inject` constructor, but the ViewModel should be obtained through ViewModelProvider, `by viewModels()` or the correct Navigation/Compose owner. The ViewModelStoreOwner controls sharing across rotation and route boundaries. SavedStateHandle can restore small UI state but does not replace durable storage. I verify startup, navigation, rotation and process recreation on Android.

## Interview answer — deep senior

I start with construction ownership. Android creates Application and Activity instances; Jetpack ViewModelProvider manages ViewModel identity. `@HiltAndroidApp` on the actual manifest Application triggers root Hilt graph generation. It does not mean every dependency is eagerly instantiated at startup. Hilt setup, reachable bindings and scoping still determine graph behavior.

`@AndroidEntryPoint` attaches supported Android entry points to Hilt. An Activity can receive field-injected dependencies, and a Fragment can do so when its host Activity is Hilt-enabled. I would avoid saying every annotated type receives a separate component: BroadcastReceiver injection uses `SingletonComponent` and has no dedicated receiver component. Composables are not Android entry points themselves; a supported host and the correct ViewModel owner supply their state. WorkManager has a separate `@HiltWorker` and factory integration rather than treating a Worker as an Activity.

`@HiltViewModel` registers a constructor-injected ViewModel for the supported factory path. I obtain it through ViewModelProvider, `by viewModels()` or an appropriate navigation entry. The ViewModelStoreOwner determines whether rotation reuses the same instance and when that instance is cleared. Calling the constructor directly can produce an ordinary Kotlin object, but it bypasses the store, factory and saved-state integration; it is inaccurate to say it must immediately leak or die. SavedStateHandle supports restorable UI state within its saved-state constraints, not a durable ledger for a payment. I test the Hilt graph and owner behavior on Android, including cold start, rotation, navigation and process recreation, and persist confirmed business records outside the ViewModel.

## How to answer in the interview

- Name the framework owner for Application, Android entry points and ViewModels.
- State host and receiver exceptions.
- Describe the correct ViewModel retrieval and owner.
- Separate saved UI state from durable business records.

## Deep-dive talking points

Application graph; Activity and Fragment entry points; receiver SingletonComponent; ViewModelProvider and ViewModelStoreOwner; Navigation owner; SavedStateHandle; Worker integration; process recreation.

## Follow-up questions

- **Interviewer:** "Can I annotate a WorkManager Worker with `@AndroidEntryPoint`?"
  **Answer:** "Use the WorkManager Hilt integration with `@HiltWorker`, assisted injection and `HiltWorkerFactory` instead."

- **Interviewer:** "What if I construct a Hilt ViewModel directly?"
  **Answer:** "It is an object outside ViewModelProvider management, so store identity and saved-state integration are bypassed; immediate leak or destruction is not implied."

- **Interviewer:** "Does BroadcastReceiver have its own Hilt component?"
  **Answer:** "No. Hilt injects receivers from `SingletonComponent`."
