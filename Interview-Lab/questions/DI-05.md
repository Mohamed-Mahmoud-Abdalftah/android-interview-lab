# DI-05

## Original interview question

What are @HiltAndroidApp, @AndroidEntryPoint, and @HiltViewModel?

## What the interviewer evaluates

- Assign each Hilt annotation to Application, Android component, and ViewModel integration.
- Explain generated graph entry points and correct creation via lifecycle-aware factories.
- Avoid manually constructing or directly requesting a Hilt ViewModel from Dagger.

## Explanation in Arabic

`@HiltAndroidApp` على `Application` يبدأ توليد الـapplication-level Hilt component ويطلب إن Application المسجلة في manifest هي نفسها annotated class. `@AndroidEntryPoint` على Activity/Fragment/Service وغيرها من Android classes المدعومة يجعل Hilt يحقنها عند إنشائها، ويتطلب parent entry point متوافقًا. `@HiltViewModel` على ViewModel مع `@Inject constructor` يخلي lifecycle-aware ViewModel factory توفر dependencies و`SavedStateHandle` عند الطلب عبر `viewModels()` أو تكامل Compose. لا تنشئ ViewModel بـ`MyViewModel()` أو تطلبها كـSingleton من graph؛ كده تفقد lifecycle/store والـsaved state.

## Practical walkthrough

`@HiltAndroidApp` على Application تفتح generated app graph. `@AndroidEntryPoint` على Activity/Fragment/Service المدعومين تسمح field injection؛ Compose function نفسها مش محتاجة annotation. `@HiltViewModel` مع `@Inject constructor` تربط ViewModel بمالكها. لو استخدمت ViewModel factory يدوي جنب Hilt أو طلبتها من graph مباشرة، ممكن تكسر ownership وSavedStateHandle.

## Why it matters and how it works

Android owns construction of Application and UI components, while the ViewModelProvider owns ViewModel identity and retention. Hilt generates components tied to those lifecycles and provides injection hooks. `@HiltAndroidApp` initializes the root; `@AndroidEntryPoint` attaches supported Android owners; `@HiltViewModel` integrates constructor injection with ViewModel factories and SavedStateHandle. Each annotation has setup requirements, including Gradle plugin/compiler and parent component relationships.

## Worked example

`@HiltAndroidApp class ShopApp : Application()` anchors the graph; `@AndroidEntryPoint class CatalogActivity : ComponentActivity()` participates as an entry point; `@HiltViewModel class CatalogViewModel @Inject constructor(repo: CatalogRepository, state: SavedStateHandle) : ViewModel()` is obtained from the Activity or NavBackStackEntry using lifecycle-aware APIs. This abbreviated shape omits imports, manifest, Gradle, and actual UI; it is explanatory rather than standalone compilable.

## Trade-offs and decision criteria

Hilt greatly reduces manual Android factory wiring but relies on code generation and standard component lifetimes. A plain ViewModel with manual factory is valid when Hilt is not in use. A composable is not itself an `@AndroidEntryPoint`; get ViewModels through its owner integration. For libraries or SDK-created classes, use an entry point or a narrow factory instead of incorrectly annotating unsupported instances.

## Failure modes

An Activity is annotated but its Application lacks the correct Hilt setup. A Fragment entry point is hosted by a non-Hilt Activity. A ViewModel is manually constructed, producing separate state and missing SavedStateHandle. A ViewModel binding is accessed from the wrong component. Test cold start, navigation scoping, rotation, and process recreation; compile all variants to catch generated binding errors.

## Production perspective

For a checkout flow, scope the ViewModel to the intended navigation destination and pass only stable route arguments through SavedStateHandle. Keep payment operation identity in repository storage so process death does not depend on a retained ViewModel. Integrate Hilt at app and host entry points, then verify correct instance sharing across rotation and distinct instances across separate checkout routes.

## Interview answer — short

“`@HiltAndroidApp` creates the application root, `@AndroidEntryPoint` injects supported Android components, and `@HiltViewModel` connects constructor-injected ViewModels to lifecycle-aware creation and saved state.”

## Interview answer — structured

“The Application annotated with `@HiltAndroidApp` is the root of Hilt's generated Android graph. An `@AndroidEntryPoint` Activity or Fragment receives dependencies when Android creates it. `@HiltViewModel` allows a ViewModel with an injected constructor to be created by the lifecycle-aware ViewModel factory, including its SavedStateHandle when used. I obtain it from the correct Activity or navigation owner rather than constructing it directly, because owner choice controls sharing and retention. The host chain and Gradle/compiler setup must be correct. I verify rotation and process recreation separately: the ViewModel survives an ordinary configuration change but not arbitrary process death.”

## Interview answer — deep senior

“These annotations connect three ownership boundaries that Android creates differently. `@HiltAndroidApp` prepares the process-level Hilt root on the Application registered in the manifest. `@AndroidEntryPoint` hooks field injection into supported platform components after Android instantiates them, with parent entry points and generated components following the hierarchy. `@HiltViewModel` is not a global binding request; it integrates constructor injection with a ViewModelProvider factory so the ViewModel belongs to an Activity, Fragment, or navigation entry and can receive SavedStateHandle. I choose that owner deliberately to avoid sharing checkout state across unrelated routes. I keep durable operation state in a repository because a ViewModel does not survive process termination. I compile each variant, test navigation and rotation identity, and test a cold route after process death. Unsupported SDK-created objects receive dependencies through a narrow entry point or factory rather than a misleading annotation. For a checkout screen, I would request the Hilt ViewModel from the correct navigation back-stack owner and pass a route ID through `SavedStateHandle`. I would rotate the device and pop/re-enter the destination to check whether state survives or resets at the expected boundary. Injecting a ViewModel as an ordinary field bypasses that owner and can turn a valid dependency graph into incorrect screen state.”

## How to answer in the interview

- **Why:** Android owns component and ViewModel creation.
- **How:** app root, Android entry point, Hilt ViewModel provider.
- **Trade-off:** generated wiring requires correct host/owner setup.
- **Failure case:** manually requesting ViewModel from graph.
- **Production solution:** lifecycle and navigation-owner tests.

## Deep-dive talking points

Discuss root graph, Android-owned construction, parent entry points, ViewModelProvider ownership, saved state, and unsupported objects.

## Follow-up questions

- Can a composable be annotated `@AndroidEntryPoint`? **Answer:** no; use its Android/navigation owner and Hilt ViewModel integration.
- Does `@HiltViewModel` make a ViewModel process-global? **Answer:** no; its lifetime is tied to the selected ViewModelStoreOwner.
- What happens after process death? **Answer:** the graph and ViewModel are recreated; small saved keys can restore context, while durable data must be reloaded.

## Self-check rubric

Place each annotation, choose a ViewModel owner, explain host setup, and describe rotation versus process death.
