# DI-17

## Original interview question

An SDK constructs objects internally and cannot use Hilt. How do you integrate it?

## What the interviewer evaluates

- Respect construction ownership at the SDK boundary.
- Choose a supported bridge instead of forcing field injection into hidden SDK objects.
- Address callback lifetime and testability.

## Concept and technical explanation

Integrating third-party SDKs or legacy framework components that instantiate classes internally without Hilt support requires creating an on-demand dependency bridge. Many third-party libraries (such as custom WorkManager Workers, Glide ModelLoaders, Firebase Messaging services, or specialized payment SDKs) instantiate objects using their own internal reflection or OS factories, preventing standard constructor injection or @AndroidEntryPoint field injection. Hilt resolves this architectural impedance mismatch through Entry Points. By defining an interface annotated with @EntryPoint and @InstallIn, and accessing it at runtime via EntryPointAccessors, non-Hilt managed instances can query the application's dependency graph directly and safely retrieve required dependencies on demand.

## Practical walkthrough (English)

Bridging unmanaged SDK classes to Hilt via EntryPoint:
```kotlin
// 1. Declare an EntryPoint interface specifying dependencies needed by the SDK
@EntryPoint
@InstallIn(SingletonComponent::class)
interface SdkBridgeEntryPoint {
    fun analyticsTracker(): AnalyticsTracker
    fun authRepository(): AuthRepository
}

// 2. Third-party SDK class instantiated internally by the library
class ThirdPartyPaymentSdkCallback(private val context: Context) : PaymentCallbackListener {

    // Retrieve dependencies on demand via EntryPointAccessors
    private val entryPoint: SdkBridgeEntryPoint by lazy {
        EntryPointAccessors.fromApplication(
            context.applicationContext,
            SdkBridgeEntryPoint::class.java
        )
    }

    override fun onPaymentCompleted(transactionId: String) {
        val tracker = entryPoint.analyticsTracker()
        val authRepo = entryPoint.authRepository()
        
        tracker.trackEvent("payment_success", mapOf("txId" to transactionId))
        authRepo.refreshAccountTier()
    }
}
```

## Practical walkthrough

استخدام @EntryPoint لسحب التبعيات داخل كائن غير مدار بواسطة Hilt:
```kotlin
// 1. تعريف نقطة الدخول (Entry Point Interface):
@EntryPoint
@InstallIn(SingletonComponent::class)
interface CustomSdkEntryPoint {
    fun getAnalyticsTracker(): AnalyticsTracker
    fun getAuthTokenProvider(): AuthTokenProvider
}

// 2. كلاس ينشئه الـ SDK الخارجي داخلياً بدون علم Hilt:
class ExternalVendorCallbackHandler : VendorSdkCallback {
    override fun onVendorEvent(context: Context, eventPayload: String) {
        // استخراج الـ EntryPoint من ApplicationContext بأمان:
        val appContext = context.applicationContext
        val entryPoint = EntryPoints.get(
            appContext,
            CustomSdkEntryPoint::class.java
        )
        
        // استخدام التبعيات المحقونة من Hilt بشكل طبيعي:
        val tracker = entryPoint.getAnalyticsTracker()
        tracker.logEvent("vendor_event: $eventPayload")
    }
}
```

## Why it matters and how it works

DI only controls objects it creates or objects exposed through supported injection hooks. Hilt entry points expose selected graph bindings to code Hilt does not instantiate. The chosen component defines binding availability and lifetime. An SDK callback may outlive a screen, so giving it an Activity-scoped collaborator through an application-root accessor would be invalid or leak the owner.

## Worked example

A payment SDK creates `SdkPaymentListener`. An app-owned `PaymentSdkBridge` receives `PaymentEvents` and `Clock` from Hilt, registers a listener adapter with the SDK, translates callbacks into domain results, and unregisters at flow end. If the SDK constructs an Android `ContentProvider` before normal injection, a minimal entry point may resolve an application-safe factory; the bridge keeps that lookup in one place.

### Kotlin / Hilt example

Use a narrow entry point when the SDK creates its own callback and offers no factory. `Telemetry` is an app-owned process-safe interface.

```kotlin
import android.content.Context
import dagger.hilt.EntryPoint
import dagger.hilt.InstallIn
import dagger.hilt.android.EntryPointAccessors
import dagger.hilt.components.SingletonComponent

interface Telemetry { fun record(event: String) }

@EntryPoint
@InstallIn(SingletonComponent::class)
interface SdkDependencies {
    fun telemetry(): Telemetry
}

fun onSdkEvent(applicationContext: Context, event: String) {
    val deps = EntryPointAccessors.fromApplication(
        applicationContext, SdkDependencies::class.java
    )
    deps.telemetry().record(event)
}
```

Do not pass an Activity Context or screen listener into this process-lifetime bridge.

## Trade-offs and decision criteria

Prefer SDK constructor/factory parameters if offered; they are explicit and easy to test. Use a Hilt entry point for unavoidable externally created objects, with narrow API and lifecycle mapping. Wrapping adds code but isolates SDK types, error translation, and version changes. Reflection or a static global graph hides dependencies and complicates tests.

## Failure modes

An SDK listener keeps an Activity after checkout closes. Entry point lookup targets the wrong component. A callback runs on an unexpected thread and mutates UI state directly. The adapter maps SDK success before server-side confirmation. A fake SDK cannot be substituted because app code calls its static singleton everywhere.

## Production perspective

Own one integration boundary, document SDK creation hooks and callback contract, add unregister/cancellation tests, and verify behavior under process recreation and duplicate callbacks. For payments, keep server verification authoritative and avoid treating SDK UI completion as settlement.

## Interview answer — short

When an SDK constructs objects internally and cannot use Hilt annotations, use Hilt Entry Points. Define an interface annotated with @EntryPoint and @InstallIn to declare the required dependencies. Inside the unmanaged SDK class, retrieve an instance of this interface using EntryPointAccessors.fromApplication() or fromActivity(), and access the required dependencies on demand.

## Interview answer — structured

Integrating third-party SDKs that manage their own object instantiation requires bridging the boundary between unmanaged external code and Hilt's dependency graph.
In standard Android development, Hilt relies on controlling class construction via constructor injection or framework hooks using @AndroidEntryPoint. However, many external SDKs instantiate callbacks, workers, or custom listeners internally using reflection or factory registries, making it impossible to add Hilt annotations directly to those classes.
To solve this, Hilt provides the @EntryPoint mechanism. Developers define an interface annotated with @EntryPoint and specify the host component using @InstallIn(SingletonComponent::class). This interface declares getter methods for the exact dependencies the SDK component requires.
Inside the unmanaged SDK class where an Android Context is available, the developer accesses the graph using EntryPointAccessors.fromApplication(). Hilt resolves the underlying component and casts it to the entry point interface, allowing the SDK class to retrieve its operational dependencies on demand with full compile-time validation.

## Interview answer — deep senior

Under the hood, every class annotated with @HiltAndroidApp or @AndroidEntryPoint implements an internal Hilt interface called GeneratedComponentManager. This manager holds the actual Dagger component instance in memory throughout the lifetime of the host component.
When you call EntryPointAccessors.fromApplication(context, SdkBridgeEntryPoint::class.java), Hilt extracts the application instance, casts it to GeneratedComponentManager, and retrieves the root SingletonComponent. It then executes a safe cast of that component instance to your @EntryPoint interface. Because Hilt automatically makes the generated component implement all discovered @EntryPoint interfaces on the classpath, the cast succeeds seamlessly without reflection.
Senior engineers exercise caution when using Entry Points. While they provide an indispensable bridge for unmanaged SDKs and ContentProviders, overusing them inside ordinary app code degrades architectural purity by introducing Service Locator characteristics, hiding dependencies behind procedural lookups.
Staff engineers encapsulate all EntryPoint lookups within dedicated adapter or bridge classes located at the boundary of the external SDK integration. This ensures that core domain and presentation logic remain purely constructor-injected, keeping the wider codebase clean, testable, and resilient against unexpected third-party SDK lifecycle quirks. This boundary isolation also makes it trivial to replace or stub the SDK in integration tests without refactoring production components, ensuring clean separation of concerns and robust runtime boundaries.

## How to answer in the interview

- **Why:** external SDK controls construction.
- **How:** injected adapter/factory or narrow entry point.
- **Trade-off:** entry point escape hatch reduces constructor visibility.
- **Failure case:** callback holds dead Activity.
- **Production solution:** lifecycle and SDK initialization tests.

## Follow-up questions

- **Interviewer:** "Can an `@EntryPoint` be scoped to an `ActivityComponent` instead of `SingletonComponent`?"
  **Answer:** "Yes. If the SDK object needs an Activity-scoped dependency, annotate the EntryPoint with `@InstallIn(ActivityComponent::class)` and pass the Activity instance to `EntryPoints.get(activity, EntryPoint::class.java)`."

- **Interviewer:** "What is the danger of using `@EntryPoint` everywhere in your own code?"
  **Answer:** "It turns your architecture into a Service Locator anti-pattern. EntryPoints should be strictly reserved for framework and SDK boundaries that cannot use constructor injection."

Identify the SDK owner, select a bridge, map component lifetime, and test late or duplicate callbacks.
