# DI-17

## Original interview question

An SDK constructs objects internally and cannot use Hilt. How do you integrate it?

## What the interviewer evaluates

- Respect construction ownership at the SDK boundary.
- Choose a supported bridge instead of forcing field injection into hidden SDK objects.
- Address callback lifetime and testability.

## Explanation in Arabic

لو SDK هو اللي ينشئ object داخليًا، Hilt لا يستطيع يضيف constructor injection له بأثر رجعي. اعمل adapter تملكه أنت عند boundary: Hilt يكوّن dependencies والـSDK factory يأخذ ما يقبله من callbacks/configuration. لو Android callback ينشأ خارج Hilt ويحتاج dependency، `@EntryPoint` مع `EntryPointAccessors` ممكن يقرأ bindings من component مناسب بشرط lifecycle صحيح. لا تستخدم entry point عشوائيًا كـservice locator منتشر؛ اعزلها في bridge واحدة واختبر cleanup، threading، وأخطاء SDK.

### Practical walkthrough in Egyptian Arabic

لو SDK هو اللي يعمل `new` للـcallback، `@AndroidEntryPoint` مش هتشتغل على object عادية بيخلقها SDK. لو SDK يسمح تمرير factory، مرر adapter من app وحقن deps فيه. لو مفيش factory، `@EntryPoint` ضيقة على `SingletonComponent` تجيب process-safe dependency من Application Context عند callback، وما تسحبش Activity-scoped binding. اختبر callback بعد rotation أو process recreation وتعامل مع SDK teardown.

## Why it matters and how it works

DI only controls objects it creates or objects exposed through supported injection hooks. Hilt entry points expose selected graph bindings to code Hilt does not instantiate. The chosen component defines binding availability and lifetime. An SDK callback may outlive a screen, so giving it an Activity-scoped collaborator through an application-root accessor would be invalid or leak the owner.

## Worked example

A payment SDK creates `SdkPaymentListener`. An app-owned `PaymentSdkBridge` receives `PaymentEvents` and `Clock` from Hilt, registers a listener adapter with the SDK, translates callbacks into domain results, and unregisters at flow end. If the SDK constructs an Android `ContentProvider` before normal injection, a minimal entry point may resolve an application-safe factory; the bridge keeps that lookup in one place.

### Kotlin / Hilt example

Use a narrow entry point when the SDK creates its own callback and offers no factory. `Telemetry` is an app-owned process-safe interface.

```kotlin
import android.content.Context
import dagger.hilt.EntryPoint
import dagger.hilt.InstallIn
import dagger.hilt.android.EntryPointAccessors
import dagger.hilt.components.SingletonComponent

interface Telemetry { fun record(event: String) }

@EntryPoint
@InstallIn(SingletonComponent::class)
interface SdkDependencies {
    fun telemetry(): Telemetry
}

fun onSdkEvent(applicationContext: Context, event: String) {
    val deps = EntryPointAccessors.fromApplication(
        applicationContext, SdkDependencies::class.java
    )
    deps.telemetry().record(event)
}
```

Do not pass an Activity Context or screen listener into this process-lifetime bridge.

## Trade-offs and decision criteria

Prefer SDK constructor/factory parameters if offered; they are explicit and easy to test. Use a Hilt entry point for unavoidable externally created objects, with narrow API and lifecycle mapping. Wrapping adds code but isolates SDK types, error translation, and version changes. Reflection or a static global graph hides dependencies and complicates tests.

## Failure modes

An SDK listener keeps an Activity after checkout closes. Entry point lookup targets the wrong component. A callback runs on an unexpected thread and mutates UI state directly. The adapter maps SDK success before server-side confirmation. A fake SDK cannot be substituted because app code calls its static singleton everywhere.

## Production perspective

Own one integration boundary, document SDK creation hooks and callback contract, add unregister/cancellation tests, and verify behavior under process recreation and duplicate callbacks. For payments, keep server verification authoritative and avoid treating SDK UI completion as settlement.

## Interview answer — short

“I put an app-owned adapter around the SDK. Hilt builds that adapter's collaborators; if the SDK creates the callback itself, a narrow entry point can bridge into the right component.”

## Interview answer — structured

“I first look for the SDK's factory or listener API. I inject an app-owned bridge, pass a small adapter to the SDK, and translate SDK callbacks into domain events. If external construction prevents ordinary injection, I use a Hilt entry point scoped to the relevant application or Activity component and keep the lookup at that boundary. I unregister the callback, handle its thread and duplicate delivery, and use a fake SDK in tests. This avoids spreading SDK globals throughout features.”

## Interview answer — deep senior

“The deciding fact is who constructs the object. Hilt cannot constructor-inject a hidden object the SDK creates, so I do not pretend adding `@Inject` to my wrapper changes the SDK's internals. I find the documented extension point—factory, configuration object, listener, or callback—and build an adapter on my side with graph-provided dependencies. If an externally created Android entry point must retrieve a binding, Hilt's entry-point API is an escape hatch; I expose only an application-safe factory or service from the component whose lifetime matches it. I keep that lookup in one integration class so other modules continue to use normal constructor injection. The bridge owns registration and removal, maps SDK error codes, and makes callback threading explicit. A payment example also needs idempotent handling and backend confirmation; a UI callback cannot establish final settlement. Tests substitute a fake SDK, send duplicate and late callbacks, and verify that closing the flow releases Activity references. That gives a contained seam for SDK upgrades and a clear boundary between SDK mechanics and application policy. If an analytics SDK invokes a callback after the Activity rotates, a listener capturing the old screen can leak it or update invisible UI. I would register a process-safe adapter that retrieves telemetry through an application entry point, and keep screen callbacks separately tied to the live Activity. The adapter also gives me a test seam for initialization, teardown, and duplicate SDK delivery.”

## How to answer in the interview

- **Why:** external SDK controls construction.
- **How:** injected adapter/factory or narrow entry point.
- **Trade-off:** entry point escape hatch reduces constructor visibility.
- **Failure case:** callback holds dead Activity.
- **Production solution:** lifecycle and SDK initialization tests.

## Deep-dive talking points

Discuss externally owned construction, entry points, component choice, callback cleanup, threading, and payment confirmation.

## Follow-up questions

- What is an entry point for? **Answer:** exposing selected Hilt bindings to code instantiated outside Hilt-supported injection paths.
- Why wrap an SDK even if it has callbacks? **Answer:** to isolate types, translate results, manage lifetime, and enable a fake in tests.
- Can a payment success callback be treated as final settlement? **Answer:** no; authoritative backend/provider confirmation is required.

## Self-check rubric

Identify the SDK owner, select a bridge, map component lifetime, and test late or duplicate callbacks.
