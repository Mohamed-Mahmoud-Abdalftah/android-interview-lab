# DI-12

## Original interview question

How do scopes interact with Context and lifecycle ownership?

## What the interviewer evaluates

- Align injected Context and stateful dependency lifetime with Hilt component ownership.
- Distinguish `@ApplicationContext` and `@ActivityContext` capabilities.
- Identify indirect Activity capture through providers, listeners, and callbacks.

## Explanation in Arabic

الـscope تقول instance هتعيش قد إيه؛ نوع الـContext يقول أي environment تملك. `@ApplicationContext` مناسب لعمليات process-level مثل app-private storage، ويمكن الاحتفاظ به في Singleton. `@ActivityContext` مرتبط بنافذة وtheme وActivity معينة، فلا ينبغي حقنه في Singleton طويل العمر. ActivityScoped object قد يحتفظ به حتى نهاية Activity instance، لكن ViewModelScoped عبر rotation لا ينبغي أن يحتفظ بـActivity Context القديمة. حتى لو field المباشر `Context` غير موجود، lambda أو listener من Activity داخل Singleton يعمل نفس leak. راجع سلسلة dependencies وليس الكلاس السطحية فقط.

## Practical walkthrough

لو SessionManager عايش Singleton ومسِك Activity Context، rotation هتسيب الـActivity القديمة في الذاكرة. استخدم `@ApplicationContext` للـresources اللي آمنة على process lifetime، أو انقل UI-dependent object إلى Activity scope. `@ActivityRetainedScoped` يعيش مع Activity المنطقية عبر rotation لكن برضه ما يمسكش View/Activity instance القديمة. اختبر leak وlogout/process death بدل الاكتفاء بأن graph بتبني.

## Why it matters and how it works

Hilt components cache scoped bindings for their lifetime; a longer-lived binding retaining a shorter-lived Android owner prevents that owner and its views from being collected. Qualifiers distinguish which Context is injected. Application Context has no Activity window or current UI lifecycle, so replacing Activity Context with it is appropriate only for compatible APIs. Runtime graph compilation may reject some scope mismatches, but indirect captures through interfaces can still be semantically wrong.

## Worked example

A Singleton `ImageDiskCache` receives `@ApplicationContext Context` and a bounded directory path. An ActivityScoped `PermissionExplainer` receives `@ActivityContext Context` because it shows UI for the current Activity. A `CheckoutViewModel` stores only repository and `SavedStateHandle`, not an Activity reference. The classes are conceptual; permission UX must use a live owner and lifecycle-aware launchers in real code.

## Trade-offs and decision criteria

Using Application Context avoids screen retention for app-scope work, but it cannot host many UI operations. Activity-scoped objects can simplify window-related coordination but recreate at rotation. Passing a live Activity to a one-shot function may be clearer than injecting it into a long-lived object. Unscoped lightweight dependencies reduce retention, but repeated expensive creation may be undesirable.

## Failure modes

A Singleton provider accepts `Context` and is passed an Activity during manual setup. A long-lived analytics callback captures `Activity` despite an otherwise safe application-scoped client. A ViewModel survives rotation while retaining Activity Context from its old screen. Conversely, a dialog created with Application Context fails due to missing window/theming. Test rotation, navigation away, and heap paths; inspect transitive provider arguments.

## Production perspective

Document scope, Context qualifier, and release trigger for every stateful provider. Use a code-review rule that Singleton providers cannot accept Activity/View or callbacks capturing them. Add a repeated-rotation leak test and integrated Hilt graph test. Monitor memory regressions and ensure UI behavior still uses a live Activity owner.

## Interview answer — short

“A binding's scope must not outlive the Context or lifecycle owner it retains. Application Context can serve app-scope work; Activity Context belongs to a live UI owner and must not flow into a Singleton.”

## Interview answer — structured

“Hilt scopes cache objects in components, while Context qualifiers select the environment they need. A Singleton can safely retain Application Context for compatible storage or resource work, but retaining Activity Context would keep an old Activity and view tree alive. Activity Context is appropriate for window- or theme-dependent UI work owned by that Activity. A ViewModel often survives rotation, so it should not hold the old Activity even if an injection path makes it easy. I inspect the entire dependency chain for listeners or lambdas that capture a screen, test repeated rotation, and confirm old Activities are collectable.”

## Interview answer — deep senior

“I review scope and Context together as a lifetime constraint. A SingletonComponent binding can remain for the process; if it directly or transitively retains an Activity Context, the destroyed screen becomes reachable from a process root. Hilt's `@ApplicationContext` and `@ActivityContext` make the intended source explicit, but they cannot fix an indirect listener capture or a manual provider that stores a live Activity. I use application Context for process-level disk cache or resource access where the API allows it, and keep dialogs, permission launchers, and window operations in a live Activity owner. ViewModel-scoped collaborators need special care because the ViewModel survives ordinary rotation while Activity instances change. I test identity and memory across rotation and navigation, inspect heap retaining paths, and verify that a context swap did not break theme or window behavior. Narrow ownership is more reliable than a global weak reference workaround. I would trace an Activity Context retained through a listener even if the singleton constructor accepts only an interface. The concrete object still carries the destroyed Activity after rotation. I would replace process-safe resource access with application context, move window work behind an Activity-owned adapter, and verify release of the old Activity with a leak check. Logout also needs a reset policy for any process-scoped session state.”

## How to answer in the interview

- **Why:** scope is an ownership contract.
- **How:** map Context and consumers to component lifetimes.
- **Trade-off:** reuse versus retained memory/state.
- **Failure case:** singleton captures destroyed Activity indirectly.
- **Production solution:** rotation leak checks and logout reset tests.

## Deep-dive talking points

Discuss component lifetime, Context qualifiers, indirect callback capture, ViewModel rotation, and window capability.

## Follow-up questions

- Can a Singleton use `@ActivityContext` safely? **Answer:** no; it would retain a shorter-lived Activity across recreation and is not an appropriate binding relationship.
- Is Application Context a replacement for every UI operation? **Answer:** no; windows, dialogs, and lifecycle-based APIs need a live Activity owner.
- Why inspect transitive dependencies? **Answer:** a Singleton may retain an Activity through an injected listener or lambda even without a direct Context field.

## Self-check rubric

Map Context to scope, trace a transitive leak, choose a UI owner, and verify a rotation scenario.
