# DI-12

## Original interview question

How do scopes interact with Context and lifecycle ownership?

## What the interviewer evaluates

- Align injected Context and stateful dependency lifetime with Hilt component ownership.
- Distinguish `@ApplicationContext` and `@ActivityContext` capabilities.
- Identify indirect Activity capture through providers, listeners, and callbacks.

## Concept and technical explanation

Scopes in Dagger and Hilt define the memoization boundaries and lifecycle ownership of dependency instances relative to Android framework components. Scopes do not keep objects alive independently; rather, an instance's lifespan is strictly governed by the lifecycle of its enclosing component container. In Android architectures, Context hierarchy dictates safe scoping boundaries. SingletonComponent outlives all UI components and is safely coupled only to ApplicationContext. ActivityRetainedComponent and ViewModelComponent survive configuration changes, meaning they must never capture Activity Context. ActivityComponent and FragmentComponent mirror window lifecycles and can safely provide Activity-bound dependencies. Injecting a short-lived scoped dependency or an Activity Context into a longer-lived component creates severe memory leaks and lifecycle violations that Hilt catches at compile time.

## Practical walkthrough (English)

Safe scoping boundaries and Context separation:
```kotlin
// Safe: Long-lived singleton depends only on ApplicationContext
@Singleton
class SecurePreferences @Inject constructor(
    @ApplicationContext private val context: Context // Lives as long as the process
)

// Dangerous & Prohibited: Holding Activity Context in ViewModel or Singleton
// Will trigger compilation error in Hilt due to component hierarchy rules
class BadViewModel @Inject constructor(
    // Compile Error: ActivityContext cannot be provided to ViewModelComponent
    @ActivityContext private val context: Context 
)

// Correct: Activity-scoped utility safely binds to Activity lifecycle
@ActivityScoped
class DialogDisplayer @Inject constructor(
    @ActivityContext private val context: Context // Destroyed when Activity finishes
) {
    fun showPrompt(message: String) {
        MaterialAlertDialogBuilder(context).setMessage(message).show()
    }
}
```

## Explanation in Arabic

كيف تتفاعل نطاقات Hilt مع كائنات الـ Context وملكية دورة الحياة (Lifecycle Ownership) في Android؟

1. أنواع الـ Context في أندرويد:
   - **Application Context**: يعيش طوال فترة عمل الـ Process. آمن للاستخدام في العمليات العامة ومكتبات الـ Database والـ Network.
   - **Activity Context**: يعيش فقط من `onCreate` إلى `onDestroy`. يحتوي على معلومات الـ Window والـ Themes والـ UI Layouts.

2. كارثة تسريب الذاكرة (Memory Leak via Scope Mismatch):
   - إذا قمت بحقن `Activity Context` داخل كائن معلّم بنطاق `@Singleton`، فإن كائن الـ Singleton سيحتفظ بمرجع للـ Activity حتى بعد تدميرها (مثل عند دوران الشاشة أو الضغط على Back).
   - النتيجة: تسريب الـ Activity كاملة بجميع الـ Views والصور والـ Drawables في الذاكرة (تسريب عشرات الميجابايتات وصولاً إلى OOM Crash).

3. الحماية المعمارية في Hilt:
   - يوفر Hilt تعليقات نوعية واقية:
     * `@ApplicationContext context: Context`: يُحقن بأمان في أي مكان في شجرة التبعيات (خاصة في الـ Singletons).
     * `@ActivityContext context: Context`: متاح فقط داخل `ActivityComponent` وتوابعه، وممنوع حقنه داخل الـ `SingletonComponent` في وقت التجميع.

## Practical walkthrough

المقارنة بين الحقن الخاطئ المسبب للتسريب والحقن الآمن عبر Hilt Qualifiers:
```kotlin
// ❌ كارثة تسريب ذاكرة: Singleton يحتفظ بـ Activity Context:
@Singleton
class LeakyToastManager @Inject constructor(
    private val context: Context // لو تم تمرير Activity هنا -> Activity تسربت للأبد في الذاكرة!
)

// ✅ حقن آمن في Singleton باستخدام @ApplicationContext:
@Singleton
class SafeNotificationManager @Inject constructor(
    @ApplicationContext private val context: Context // آمن 100% طوال حياة التطبيق
) {
    fun notify(...) { /* استخدام Application Context لإرسال تنبيه */ }
}

// ✅ حقن ActivityContext فقط داخل كائن معلّم بـ @ActivityScoped:
@ActivityScoped
class DialogPresenter @Inject constructor(
    @ActivityContext private val context: Context // مسموح: كلاهما يموت معاً في onDestroy
) {
    fun showDialog() { AlertDialog.Builder(context).show() }
}
```

## Why it matters and how it works

Hilt components cache scoped bindings for their lifetime; a longer-lived binding retaining a shorter-lived Android owner prevents that owner and its views from being collected. Qualifiers distinguish which Context is injected. Application Context has no Activity window or current UI lifecycle, so replacing Activity Context with it is appropriate only for compatible APIs. Runtime graph compilation may reject some scope mismatches, but indirect captures through interfaces can still be semantically wrong.

## Worked example

A Singleton `ImageDiskCache` receives `@ApplicationContext Context` and a bounded directory path. An ActivityScoped `PermissionExplainer` receives `@ActivityContext Context` because it shows UI for the current Activity. A `CheckoutViewModel` stores only repository and `SavedStateHandle`, not an Activity reference. The classes are conceptual; permission UX must use a live owner and lifecycle-aware launchers in real code.

## Trade-offs and decision criteria

Using Application Context avoids screen retention for app-scope work, but it cannot host many UI operations. Activity-scoped objects can simplify window-related coordination but recreate at rotation. Passing a live Activity to a one-shot function may be clearer than injecting it into a long-lived object. Unscoped lightweight dependencies reduce retention, but repeated expensive creation may be undesirable.

## Failure modes

A Singleton provider accepts `Context` and is passed an Activity during manual setup. A long-lived analytics callback captures `Activity` despite an otherwise safe application-scoped client. A ViewModel survives rotation while retaining Activity Context from its old screen. Conversely, a dialog created with Application Context fails due to missing window/theming. Test rotation, navigation away, and heap paths; inspect transitive provider arguments.

## Production perspective

Document scope, Context qualifier, and release trigger for every stateful provider. Use a code-review rule that Singleton providers cannot accept Activity/View or callbacks capturing them. Add a repeated-rotation leak test and integrated Hilt graph test. Monitor memory regressions and ensure UI behavior still uses a live Activity owner.

## Interview answer — short

Scopes link instance memoization to the lifecycle of specific Android components. SingletonComponent lives for the entire application process and must only capture ApplicationContext. ActivityRetainedComponent survives configuration changes and cannot hold Activity Context. ActivityComponent and FragmentComponent match the UI lifecycle and can safely inject Activity Context. Hilt validates these scoping boundaries at compile time to prevent memory leaks.

## Interview answer — structured

Understanding how scopes interact with Context requires mapping Dagger components directly to Android runtime lifecycles.
Each Hilt scope corresponds to an underlying component with a distinct lifecycle. When a binding is annotated with a scope like @Singleton or @ActivityScoped, Dagger memoizes that instance inside the corresponding component instance, ensuring that subsequent injection requests return the identical object.
The critical architectural rule is that dependencies must never outlive their dependencies. SingletonComponent exists for the entire process duration, which means it must never reference an Activity Context, View hierarchy, or Fragment instance. Doing so retains destroyed UI objects across screen transitions and rotations, causing severe memory leaks.
Conversely, child components can freely consume parent dependencies. An @ActivityScoped class can inject both the Activity Context and @Singleton repositories. Hilt enforces this hierarchy at compile time: attempting to inject an @ActivityScoped dependency into a @Singleton or @ViewModelScoped class causes an immediate compilation failure, protecting the codebase from lifecycle mismatches.

## Interview answer — deep senior

Under the hood, Dagger implements component hierarchies using parent-child subcomponent relationships where child components maintain direct references to their parent component instances. When a dependency is resolved, Dagger traverses upward from child to parent, but never downward.
Because SingletonComponent has no visibility into ActivityComponent or FragmentComponent, it is structurally impossible for a Singleton to receive an Activity-scoped binding through direct injection. However, improper manual passing or caching of an Activity Context inside a singleton service bypasses this safety, leaking the entire Activity window, decor view, and graphic buffers.
The introduction of ActivityRetainedComponent and ViewModelComponent created a nuanced intermediate tier. These components survive Activity destruction during configuration changes such as screen rotations. Consequently, Hilt strictly forbids injecting @ActivityContext or Activity instances into ViewModels, because retaining an Activity reference across a configuration change leaks the destroyed Activity instance.
Staff engineers enforce strict context hygiene by mandating @ApplicationContext on all foundational data sources, network clients, and storage engines. Activity Context is strictly confined to transient UI presenters, custom views, and dialog coordinators bound to ActivityComponent, ensuring zero memory retention when the user navigates away. This strict boundary isolation prevents subtle memory leaks and guarantees deterministic garbage collection across all screen lifecycle transitions throughout the user journey.

- **Trade-off:** reuse versus retained memory/state.
- **Failure case:** singleton captures destroyed Activity indirectly.

## Follow-up questions

- **Interviewer:** "Can you inflate a layout using ApplicationContext?"
  **Answer:** "Technically yes, but it will lack the Activity's theme and styling attributes, resulting in broken typography, incorrect colors, and layout bugs."

- **Interviewer:** "Can `@ApplicationContext` leak an Activity?"
  **Answer:** "No. The ApplicationContext is a process-wide singleton created by the Android OS that lives until the entire application process terminates."
