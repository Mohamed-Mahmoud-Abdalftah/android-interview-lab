# DI-12

## Original interview question

How do scopes interact with Context and lifecycle ownership?

## What the interviewer evaluates

- Align injected Context and stateful dependency lifetime with Hilt component ownership.
- Distinguish `@ApplicationContext` and `@ActivityContext` capabilities.
- Identify indirect Activity capture through providers, listeners, and callbacks.

## Explanation in Arabic

كيف تتفاعل نطاقات Hilt مع كائنات الـ Context وملكية دورة الحياة (Lifecycle Ownership) في Android؟

1. أنواع الـ Context في أندرويد:
   - **Application Context**: يعيش طوال فترة عمل الـ Process. آمن للاستخدام في العمليات العامة ومكتبات الـ Database والـ Network.
   - **Activity Context**: يعيش فقط من `onCreate` إلى `onDestroy`. يحتوي على معلومات الـ Window والـ Themes والـ UI Layouts.

2. كارثة تسريب الذاكرة (Memory Leak via Scope Mismatch):
   - إذا قمت بحقن `Activity Context` داخل كائن معلّم بنطاق `@Singleton`، فإن كائن الـ Singleton سيحتفظ بمرجع للـ Activity حتى بعد تدميرها (مثل عند دوران الشاشة أو الضغط على Back).
   - النتيجة: تسريب الـ Activity كاملة بجميع الـ Views والصور والـ Drawables في الذاكرة (تسريب عشرات الميجابايتات وصولاً إلى OOM Crash).

3. الحماية المعمارية في Hilt:
   - يوفر Hilt تعليقات نوعية واقية:
     * `@ApplicationContext context: Context`: يُحقن بأمان في أي مكان في شجرة التبعيات (خاصة في الـ Singletons).
     * `@ActivityContext context: Context`: متاح فقط داخل `ActivityComponent` وتوابعه، وممنوع حقنه داخل الـ `SingletonComponent` في وقت التجميع.

## Practical walkthrough

المقارنة بين الحقن الخاطئ المسبب للتسريب والحقن الآمن عبر Hilt Qualifiers:
```kotlin
// ❌ كارثة تسريب ذاكرة: Singleton يحتفظ بـ Activity Context:
@Singleton
class LeakyToastManager @Inject constructor(
    private val context: Context // لو تم تمرير Activity هنا -> Activity تسربت للأبد في الذاكرة!
)

// ✅ حقن آمن في Singleton باستخدام @ApplicationContext:
@Singleton
class SafeNotificationManager @Inject constructor(
    @ApplicationContext private val context: Context // آمن 100% طوال حياة التطبيق
) {
    fun notify(...) { /* استخدام Application Context لإرسال تنبيه */ }
}

// ✅ حقن ActivityContext فقط داخل كائن معلّم بـ @ActivityScoped:
@ActivityScoped
class DialogPresenter @Inject constructor(
    @ActivityContext private val context: Context // مسموح: كلاهما يموت معاً في onDestroy
) {
    fun showDialog() { AlertDialog.Builder(context).show() }
}
```

## Why it matters and how it works

Hilt components cache scoped bindings for their lifetime; a longer-lived binding retaining a shorter-lived Android owner prevents that owner and its views from being collected. Qualifiers distinguish which Context is injected. Application Context has no Activity window or current UI lifecycle, so replacing Activity Context with it is appropriate only for compatible APIs. Runtime graph compilation may reject some scope mismatches, but indirect captures through interfaces can still be semantically wrong.

## Worked example

A Singleton `ImageDiskCache` receives `@ApplicationContext Context` and a bounded directory path. An ActivityScoped `PermissionExplainer` receives `@ActivityContext Context` because it shows UI for the current Activity. A `CheckoutViewModel` stores only repository and `SavedStateHandle`, not an Activity reference. The classes are conceptual; permission UX must use a live owner and lifecycle-aware launchers in real code.

## Trade-offs and decision criteria

Using Application Context avoids screen retention for app-scope work, but it cannot host many UI operations. Activity-scoped objects can simplify window-related coordination but recreate at rotation. Passing a live Activity to a one-shot function may be clearer than injecting it into a long-lived object. Unscoped lightweight dependencies reduce retention, but repeated expensive creation may be undesirable.

## Failure modes

A Singleton provider accepts `Context` and is passed an Activity during manual setup. A long-lived analytics callback captures `Activity` despite an otherwise safe application-scoped client. A ViewModel survives rotation while retaining Activity Context from its old screen. Conversely, a dialog created with Application Context fails due to missing window/theming. Test rotation, navigation away, and heap paths; inspect transitive provider arguments.

## Production perspective

Document scope, Context qualifier, and release trigger for every stateful provider. Use a code-review rule that Singleton providers cannot accept Activity/View or callbacks capturing them. Add a repeated-rotation leak test and integrated Hilt graph test. Monitor memory regressions and ensure UI behavior still uses a live Activity owner.

## Interview answer — short

Hilt prevents memory leaks by pairing Context lifecycles with component scopes. @ApplicationContext lives with the process and is safe for @Singleton bindings. @ActivityContext is tied to an individual UI window and must only be injected into @ActivityScoped or unscoped UI collaborators, never into Singletons or ViewModels.

## Interview answer — structured

The interaction between DI scopes and Android Context is the primary defense line against severe memory leaks:

1. **Application Context vs. Activity Context**: `ApplicationContext` is tied to process lifetime and lacks UI theme information, making it safe for singletons like databases and notification services. `ActivityContext` holds references to the view hierarchy, window manager, and theme attributes.

2. **The Scope Mismatch Bug**: If an Activity Context is injected into an object with a longer lifetime—such as an `@Singleton` repository or an `@ViewModelScoped` state holder—the destroyed Activity cannot be garbage collected after screen rotation or back-press navigation. This leaks megabytes of bitmap memory and view trees.

3. **Hilt's Type-Safe Guards**: Hilt provides `@ApplicationContext` and `@ActivityContext` qualifiers. If you attempt to inject `@ActivityContext` into a class provided inside `SingletonComponent`, Dagger catches the invalid scope boundary and **fails at compile time**, preventing the leak before code ever ships to production.

## Interview answer — deep senior

A subtle production hazard occurs through **Indirect Context Capturing via Callbacks or Listeners**.

Even if a `@Singleton` class only injects primitive dependencies, if an Activity registers a non-static callback or lifecycle observer on that singleton and forgets to deregister in `onDestroy`, the singleton retains the Activity instance implicitly through the callback closure (`this@MyActivity`).

To mitigate this in robust architectures:
- Never register long-lived listeners with raw Activity callbacks.
- Expose Kotlin Flows (`SharedFlow` or `StateFlow`) from the Singleton repository, allowing UI layers to collect using `repeatOnLifecycle(Lifecycle.State.STARTED)` which cancels and detaches observation cleanly whenever the UI goes into the background.

## How to answer in the interview

- **Why:** scope is an ownership contract.
- **How:** map Context and consumers to component lifetimes.
- **Trade-off:** reuse versus retained memory/state.
- **Failure case:** singleton captures destroyed Activity indirectly.
- **Production solution:** rotation leak checks and logout reset tests.

## Deep-dive talking points

Discuss component lifetime, Context qualifiers, indirect callback capture, ViewModel rotation, and window capability.

## Follow-up questions

- **Interviewer:** "Can you inflate a layout using ApplicationContext?"
  **Answer:** "Technically yes, but it will lack the Activity's theme and styling attributes, resulting in broken typography, incorrect colors, and layout bugs."

- **Interviewer:** "Can `@ApplicationContext` leak an Activity?"
  **Answer:** "No. The ApplicationContext is a process-wide singleton created by the Android OS that lives until the entire application process terminates."
