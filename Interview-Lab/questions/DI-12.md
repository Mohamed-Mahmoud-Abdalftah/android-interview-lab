# DI-12

## Original interview question

How do scopes interact with Context and lifecycle ownership?

## What the interviewer evaluates

- Align injected Context and stateful dependency lifetime with Hilt component ownership.
- Distinguish `@ApplicationContext` and `@ActivityContext` capabilities.
- Identify indirect Activity capture through providers, listeners, and callbacks.

## Concept and technical explanation

A Hilt scope caches a binding within one instance of its installed component. It does not independently keep an Android component alive, and `@InstallIn` alone does not scope every binding. `SingletonComponent` lives for the application process; `ActivityRetainedComponent` survives configuration changes for an activity's retained lifetime; `ViewModelComponent` lives for one ViewModel; `ActivityComponent` is recreated with an Activity. Parent bindings are visible to descendants, not the reverse. `@ApplicationContext Context` is available from the singleton tier. `@ActivityContext Context` belongs to ActivityComponent and descendants, so it is unavailable to a `@HiltViewModel` built in ViewModelComponent. Hilt catches graph mismatches, but manual references or callbacks can still leak an Activity.

## Practical walkthrough (English)

Safe scoping boundaries and Context separation:
```kotlin
// Safe: Long-lived singleton depends only on ApplicationContext
@Singleton
class SecurePreferences @Inject constructor(
    @ApplicationContext private val context: Context // Lives as long as the process
)

// Dangerous & Prohibited: Holding Activity Context in ViewModel or Singleton
// Will trigger compilation error in Hilt due to component hierarchy rules
@HiltViewModel
class BadViewModel @Inject constructor(
    // No ActivityContext binding is visible in ViewModelComponent
    @ActivityContext private val context: Context
) : ViewModel()

// Correct: Activity-scoped utility safely binds to Activity lifecycle
@ActivityScoped
class DialogDisplayer @Inject constructor(
    @ActivityContext private val context: Context // Bound to this ActivityComponent; do not retain elsewhere
) {
    fun showPrompt(message: String) {
        MaterialAlertDialogBuilder(context).setMessage(message).show()
    }
}
```

## Explanation in Arabic

الـscope في Hilt معناها إن binding يتشارك كائن واحد داخل **نسخة واحدة** من component المحدد، مش إن annotation نفسها بتعيش الكائن للأبد. `@InstallIn` يحدد مكان الربط، وما بيعملش scope لكل دوال module تلقائياً.

`SingletonComponent` عمره عمر عملية التطبيق، و`ActivityRetainedComponent` بيكمل عبر configuration change، و`ViewModelComponent` عمره عمر ViewModel، و`ActivityComponent` يتبني من جديد لكل Activity instance. الـchild يشوف bindings الأب، لكن الأب ما يشوفش bindings الابن.

`@ApplicationContext` متاح من المستوى الطويل العمر، مناسب لقاعدة بيانات أو تخزين يحتاج context. `@ActivityContext` متاح في `ActivityComponent` وأبنائه، مش في `ViewModelComponent`. لو `@HiltViewModel` طلبه مباشرة، graph هيفشل وقت البناء. ده ما يمنعش leak لو مطور مرّر Activity يدوياً لكائن طويل العمر أو خزن callback ماسكها.

## Practical walkthrough

في مثال Hilt، `SecurePreferences` المعلّم `@Singleton` يستقبل `@ApplicationContext`، و`DialogDisplayer` المعلّم `@ActivityScoped` يستقبل `@ActivityContext` لأنه تابع للشاشة الحالية. أما `@HiltViewModel` لو طلب `@ActivityContext` فمفيش binding ظاهر له في `ViewModelComponent`، والبناء يفشل.

بعد الإصلاح، خليك واعي للمراجع اليدوية: لو خزنت `DialogDisplayer` أو `Activity` في singleton خارج Hilt، ممكن تفضل الشاشة القديمة موجودة بعد rotation. الـscope يحدد إعادة الاستخدام داخل component، مش ضمان إن Garbage Collector هيحرر كل شيء فوراً. اختبر مسار rotation/process death منفصلين؛ دي أمثلة source-level وليست نتيجة جهاز.

## Why it matters and how it works

Hilt components cache scoped bindings for their lifetime; a longer-lived binding retaining a shorter-lived Android owner prevents that owner and its views from being collected. Qualifiers distinguish which Context is injected. Application Context has no Activity window or current UI lifecycle, so replacing Activity Context with it is appropriate only for compatible APIs. Runtime graph compilation may reject some scope mismatches, but indirect captures through interfaces can still be semantically wrong.

## Worked example

A Singleton `ImageDiskCache` receives `@ApplicationContext Context` and a bounded directory path. An ActivityScoped `PermissionExplainer` receives `@ActivityContext Context` because it shows UI for the current Activity. A `CheckoutViewModel` stores only repository and `SavedStateHandle`, not an Activity reference. The classes are conceptual; permission UX must use a live owner and lifecycle-aware launchers in real code.

## Trade-offs and decision criteria

Using Application Context avoids screen retention for app-scope work, but it cannot host many UI operations. Activity-scoped objects can simplify window-related coordination but recreate at rotation. Passing a live Activity to a one-shot function may be clearer than injecting it into a long-lived object. Unscoped lightweight dependencies reduce retention, but repeated expensive creation may be undesirable.

## Failure modes

A Singleton provider accepts `Context` and is passed an Activity during manual setup. A long-lived analytics callback captures `Activity` despite an otherwise safe application-scoped client. A ViewModel survives rotation while retaining Activity Context from its old screen. Conversely, a dialog created with Application Context fails due to missing window/theming. Test rotation, navigation away, and heap paths; inspect transitive provider arguments.

## Production perspective

Document scope, Context qualifier, and release trigger for every stateful provider. Use a code-review rule that Singleton providers cannot accept Activity/View or callbacks capturing them. Add a repeated-rotation leak test and integrated Hilt graph test. Monitor memory regressions and ensure UI behavior still uses a live Activity owner.

## Interview answer — short

A scope reuses a binding within one Hilt component instance. `SingletonComponent` lasts for the process, `ActivityRetainedComponent` spans configuration changes, `ViewModelComponent` lasts for one ViewModel, and `ActivityComponent` for one Activity instance. `@ApplicationContext` is available from the singleton tier; `@ActivityContext` is visible in ActivityComponent and descendants, not a Hilt ViewModel. Hilt catches direct graph mismatches, but manual references can still leak an Activity.

## Interview answer — structured

I match a binding's scope to the owner that needs shared identity. A scoped binding is cached in one component instance; an unscoped binding in the same installed module can still be recreated per request. ActivityRetainedComponent persists across rotation, while ActivityComponent is recreated. ViewModelComponent follows one ViewModel's lifetime.

A process-level database uses `@ApplicationContext`; a dialog presenter in the current Activity may need `@ActivityContext`. A `@HiltViewModel` cannot directly request the latter because its component cannot see ActivityComponent bindings. This compile-time protection does not cover references manually passed to a singleton or captured in a callback. I inspect those lifetimes and avoid guaranteeing immediate garbage collection or absolute leak freedom from a qualifier alone.

## Interview answer — deep senior

Hilt's predefined component hierarchy supplies bindings from ancestors to descendants. A scope caches a binding once per component instance: `@Singleton` in `SingletonComponent`, `@ActivityRetainedScoped` in `ActivityRetainedComponent`, `@ViewModelScoped` in one `ViewModelComponent`, and `@ActivityScoped` in an `ActivityComponent`. An unscoped binding installed in one of these components can still be constructed for each request. Scoping has retention and generated-code costs, so use it when identity or state sharing is required.

`ActivityRetainedComponent` spans configuration changes, while the ordinary ActivityComponent does not. A `@HiltViewModel` cannot directly request `@ActivityContext` because that binding is in a different branch of the hierarchy. `@ApplicationContext` is visible from the singleton tier. Hilt's compile-time graph protects these direct bindings, but an Activity can still leak if code passes it manually to a singleton, stores it in a static field, or retains a callback.

The application context itself is process-level and normally safe for long-lived services, yet claiming it makes an entire object incapable of leaking an Activity is wrong; other fields may retain one. Likewise, destruction of an ActivityComponent bounds its scoped cache, but does not guarantee immediate garbage collection if external references remain. For UI dialogs or themed inflation use the current Activity context within a short-lived owner. For persistence and database creation use the application context where appropriate.

## How to answer in the interview

- **Scope:** One reused instance per component instance, only for bindings actually annotated with a scope.
- **Hierarchy:** Parent bindings flow down; child bindings do not flow up or sideways.
- **Context:** Use `@ApplicationContext` for compatible process-level work and current Activity context for UI/window work.
- **Failure case:** ViewModel requesting `@ActivityContext` fails graph construction; a manually captured Activity can still leak.
- **Limit:** Component destruction bounds its cache, not the exact moment of garbage collection.

## Follow-up questions

- **Interviewer:** "Why can't a Hilt ViewModel request @ActivityContext?"
  **Answer:** "Its ViewModelComponent does not have visibility into the sibling ActivityComponent where @ActivityContext is bound. Retaining an Activity across rotation would also be unsafe."

- **Interviewer:** "Does @InstallIn(SingletonComponent) make a binding singleton?"
  **Answer:** "No. Scope it with @Singleton if one instance per SingletonComponent is required; otherwise it remains unscoped."

- **Interviewer:** "Can @ApplicationContext guarantee no Activity leak?"
  **Answer:** "It does not itself refer to an Activity, but the receiving object could retain an Activity through another field or callback."

- **Interviewer:** "When does @ActivityRetainedScoped end?"
  **Answer:** "At the end of the retained activity lifetime; it spans configuration changes but does not survive process death."
