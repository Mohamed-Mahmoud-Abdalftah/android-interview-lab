# BG-15

## Original interview question

An upload must survive process death and network loss. Design its lifecycle.

## What the interviewer evaluates

Design resumable upload across process death, network loss and ambiguous server completion.

## Why it matters and how it works

URI access must remain valid after restart, such as persisted permission when applicable or copying to app storage. Server resumable protocol must define chunk checksums, offset and finalization idempotency. Work retries and network transitions are normal. A completed local transfer is not final success until server confirms processing.

## Worked example

Conceptual worker repository interface; implementation relies on app URI/storage and server resumable API.

```kotlin
interface UploadStore {
    suspend fun pendingIds(): List<String>
    suspend fun acknowledgedOffset(id: String): Long

    suspend fun markComplete(id: String, receipt: String)

// Worker queries server offset/status before resuming each upload.
```

## Trade-offs and decision criteria

Chunking adds protocol complexity but avoids restarting large files. A single POST is simpler for small uploads but may waste bandwidth after loss. WorkManager schedules durability yet may be delayed; eligible user-visible long work can need a foreground path and notification.

## Failure modes

A content URI permission may vanish after process death, making the worker unable to reopen input. Progress based only on bytes sent can overstate completion. Retrying finalization with a new upload ID can create duplicate media records.

## Production perspective

A video app persists URI access and operation ID, uploads checksummed chunks, reconciles server offset after reconnect and finalizes with stable key. UI observes Room status, while WorkManager/foreground notification reports ongoing work. Tests kill process at chunk and finalization boundaries.

## Interview answer — short

“I persist upload identity, file access and server-acknowledged offset, then use WorkManager for restartable transfer. After reconnect I query server status and resume with the same ID, confirming finalization before marking success.”

## Interview answer — structured

“A large upload needs a durable operation record and a resumable server protocol. I save a stable upload ID, durable access to the file URI, server session token and last acknowledged offset. A network-constrained worker uploads chunks and records progress after the server acknowledges them. On process restart it queries the server before resuming because local bytes-sent counters may be ahead. I choose a foreground notification path when the operation is eligible and user-visible, and I only mark Complete after final server confirmation.”

## Interview answer — deep senior

“I treat upload as a state machine: accepted locally, session created, chunks acknowledged, finalizing, complete or recoverable error. Every transition survives process death. The app must retain file access, either with persisted URI permission where supported or an app-owned copy; otherwise WorkManager can wake up with no readable input. The server protocol defines offsets, checksums and idempotent finalization. A worker may retry after ambiguous response, so it asks server status and reuses the same operation ID. I report acknowledged progress, not optimistic socket bytes, and handle Wi-Fi/cellular policy and battery constraints. Tests disconnect at chunk boundaries, revoke URI access, kill before/after finalization and verify no duplicate server object. The first design choice is durable access to the bytes. A Photo Picker URI grant may not survive every lifecycle or installation state, so I either use documented persistable access where available or copy the content into app-managed storage before scheduling. I record a stable upload ID, file metadata and remote session token, then use a resumable protocol or safe restart policy. After process death the Worker reconstructs from the repository; the UI simply observes progress. Network loss causes a retry with the same remote identity, not a fresh duplicate object. I test low storage, canceled selection, permission loss, partial upload, late server success and cleanup of local temporary files.”
