# BG-15

## Original interview question

An upload must survive process death and network loss. Design its lifecycle.

## What the interviewer evaluates

Design resumable upload across process death, network loss and ambiguous server completion.

## Concept and technical explanation

Architecting an upload pipeline that survives operating system process death, arbitrary network disruptions, and device reboots requires an offline-first resilient architecture combining chunked resumable upload protocols with WorkManager durable execution and Room local persistence. Relying on transient coroutine scopes or standard streaming uploads fails under mobile conditions because low-memory process kills force uploads to restart from byte zero. A production-grade design divides the lifecycle into five synchronized phases: local metadata commit in Room (generating upload UUID, total file length, and zero-offset state), durable work scheduling via WorkManager with network constraints and exponential backoff, remote session initiation or offset reconciliation via resumable protocols (such as Tus or HTTP Content-Range), iterative binary chunk transmission with incremental checkpointing in Room, and transactional terminal completion notifying the presentation layer reactively.

## Practical walkthrough (English)

Implementing a resilient resumable upload pipeline:
```kotlin
// 1. Resumable Chunked Upload Worker
class ResumableUploadWorker(
    appContext: Context,
    params: WorkerParameters,
    private val uploadDao: UploadDao,
    private val uploadApi: ResumableUploadApi
) : CoroutineWorker(appContext, params) {

    override suspend fun doWork(): Result = withContext(Dispatchers.IO) {
        val uploadId = inputData.getString("UPLOAD_ID") ?: return@withContext Result.failure()
        val uploadRecord = uploadDao.getUpload(uploadId) ?: return@withContext Result.failure()
        val file = File(uploadRecord.filePath)

        // Step A: Reconcile current byte offset with remote server
        var currentOffset = uploadApi.getServerOffset(uploadRecord.remoteUploadUrl)
        val chunkSize = 1024 * 1024 * 2 // 2MB chunks

        // Step B: Stream chunks sequentially with cooperative cancellation checks
        while (currentOffset < file.length()) {
            if (isStopped) return@withContext Result.retry()

            val endOffset = minOf(currentOffset + chunkSize, file.length())
            val chunkBytes = file.readBytesRange(currentOffset, endOffset)

            val success = uploadApi.uploadChunk(
                url = uploadRecord.remoteUploadUrl,
                chunk = chunkBytes,
                rangeHeader = "bytes $currentOffset-${endOffset - 1}/${file.length()}"
            )

            if (!success) return@withContext Result.retry()

            currentOffset = endOffset
            // Step C: Persist local checkpoint and update UI progress
            uploadDao.updateOffset(uploadId, currentOffset)
            val percent = ((currentOffset * 100) / file.length()).toInt()
            setProgress(workDataOf("PERCENT" to percent))
        }

        uploadDao.markCompleted(uploadId)
        Result.success()
    }
}
```

## Explanation in Arabic

تصميم نظام رفع ملفات ضخمة (Resumable Large File Upload) يصمد أمام موت الـ Process وانقطاع الشبكة واستجابات السيرفر المجهولة:

1. المخطط المعماري الكامل (Resumable Upload Architecture):
   - **المرحلة 1: تسجيل بيانات الرفع في Room (Upload Metadata Entity)**:
     * عند اختيار ملف (فيديو أو مستند 100MB)، نحفظ سجلاً في Room: `uploadId: UUID`, `fileUri`, `fileSizeBytes`, `bytesAcked = 0`, `serverSessionUrl = null`, `status = PENDING`.
     * حفظ أذونات الـ URI الدائمة (`takePersistableUriPermission`).
   - **المرحلة 2: بدء جلسة الرفع على السيرفر (Upload Session Handshake)**:
     * يطلب الـ Worker من السيرفر فتح جلسة رفع: `POST /uploads/session` مع الحجم ونوع الملف.
     * يعيد السيرفر رابط جلسة مخصص: `serverSessionUrl`. يتم حفظ هذا الرابط في Room فوراً.
   - **المرحلة 3: رفع الملف كأجزاء متتالية (Chunked Upload)**:
     * رفع الملف في أجزاء (مثل 5MB لكل Chunk) باستخدام `Content-Range: bytes 0-5242880/104857600`.
     * مع كل جزء يؤكده السيرفر، يتم تحديث `bytesAcked` في Room.
   - **المرحلة 4: التعافي عند انقطاع الشبكة أو موت الـ Process**:
     * إذا انقطعت الشبكة أو مات الـ Process: عند عودة الـ Worker، **لا يبدأ الرفع من البداية**!
     * يرسل استعلام استقصائي للسيرفر: `HEAD <serverSessionUrl>` أو فحص Range.
     * يجيب السيرفر: 'وصلني 45MB'. يقوم الـ Worker بفتح الملف واستئناف القراءة بدءاً من البايت 45,000,001 فوراً!

## Practical walkthrough

تنفيذ بروتوكول استئناف رفع الملفات الكبيرة في CoroutineWorker:
```kotlin
@HiltWorker
class ResumableUploadWorker @AssistedInject constructor(
    @Assisted context: Context,
    @Assisted params: WorkerParameters,
    private val uploadDao: UploadDao,
    private val uploadClient: ResumableHttpClient
) : CoroutineWorker(context, params) {

    override suspend fun doWork(): Result {
        val uploadId = inputData.getString("upload_id") ?: return Result.failure()
        val record = uploadDao.getUpload(uploadId) ?: return Result.failure()

        return try {
            // 1. الحصول على رابط الجلسة (أو إنشاء جلسة جديدة لو لم تكن موجودة):
            val sessionUrl = record.sessionUrl ?: run {
                val newUrl = uploadClient.initiateSession(record.fileName, record.fileSizeBytes)
                uploadDao.updateSessionUrl(uploadId, newUrl)
                newUrl
            }

            // 2. استعلام السيرفر عن الإزاحة المؤكدة الحالية (Current Acked Offset):
            val serverOffset = uploadClient.queryCurrentOffset(sessionUrl)
            uploadDao.updateBytesAcked(uploadId, serverOffset)

            if (serverOffset >= record.fileSizeBytes) {
                uploadDao.markCompleted(uploadId)
                return Result.success()
            }

            // 3. استئناف الرفع من نقطة الانقطاع بدقة:
            val file = File(record.localFilePath)
            uploadClient.uploadRemainingChunks(
                sessionUrl = sessionUrl,
                file = file,
                startOffset = serverOffset,
                onChunkAcked = { ackedBytes ->
                    uploadDao.updateBytesAcked(uploadId, ackedBytes)
                    setProgress(workDataOf("progress" to ((ackedBytes * 100) / record.fileSizeBytes).toInt()))
                }
            )
            uploadDao.markCompleted(uploadId)
            Result.success()
        } catch (e: IOException) {
            Result.retry() // إعادة المحاولة لاحقاً واستئناف الرفع من آخر بايت مسجل!
        }
    }
}
```

## Why it matters and how it works

URI access must remain valid after restart, such as persisted permission when applicable or copying to app storage. Server resumable protocol must define chunk checksums, offset and finalization idempotency. Work retries and network transitions are normal. A completed local transfer is not final success until server confirms processing.

## Trade-offs and decision criteria

Chunking adds protocol complexity but avoids restarting large files. A single POST is simpler for small uploads but may waste bandwidth after loss. WorkManager schedules durability yet may be delayed; eligible user-visible long work can need a foreground path and notification.

## Failure modes

A content URI permission may vanish after process death, making the worker unable to reopen input. Progress based only on bytes sent can overstate completion. Retrying finalization with a new upload ID can create duplicate media records.

## Production perspective

A video app persists URI access and operation ID, uploads checksummed chunks, reconciles server offset after reconnect and finalizes with stable key. UI observes Room status, while WorkManager/foreground notification reports ongoing work. Tests kill process at chunk and finalization boundaries.

## Interview answer — short

Design a resilient upload pipeline by combining chunked resumable upload protocols with Room database checkpoints and WorkManager. Persist the file metadata, remote session URL, and byte offset in Room before enqueuing a OneTimeWorkRequest with connected network constraints. The worker queries the server for the current byte offset, streams chunks sequentially, updates Room checkpoints after each chunk, and resumes seamlessly after crashes or network drops.

## Interview answer — structured

Designing an upload system that survives process termination and connectivity loss requires decoupling data transmission from in-memory presentation scopes.
The lifecycle begins by recording the upload intent inside a local Room database. The repository generates a unique upload session UUID, saves the file URI and byte length, and sets the initial state to QUEUED with an offset of zero.
Next, the repository enqueues a OneTimeWorkRequest configured with NetworkType.CONNECTED and Exponential backoff criteria. WorkManager persists this request in its internal SQLite database, ensuring execution resumes after device reboots or process termination.
When the worker executes, it connects to the backend using a resumable upload protocol like Tus or Content-Range. Before transmitting payload data, it queries the backend to determine how many bytes were already received.
The worker then streams the file in fixed-size chunks. After each chunk acknowledgment, the worker commits the new byte offset to Room and reports transient progress via setProgress. If connectivity drops or the system kills the process, the rescheduled worker queries the latest offset and resumes transmission without restarting from byte zero.

## Interview answer — deep senior

Under the hood, mobile network interfaces undergo frequent radio state transitions and radio link interruptions (RRC state changes from DCH to FACH to PCH/Idle). If an application attempts to upload large video or document payloads using a single monolithic HTTP POST, any momentary signal drop or system process reclamation aborts the TCP connection, forcing the client to retransmit the entire payload from the beginning and rapidly depleting user cellular quotas.
Senior engineers solve this by implementing chunked resumable architectures backed by durable storage. In this architecture, the local Room database acts as the state arbiter. When WorkManager initiates ResumableUploadWorker, the worker reads the local record and issues a HEAD or status request to the server upload URL. The server responds with the exact byte count already committed to cloud storage.
This handshake resolves the distributed state discrepancy: if the client previously transmitted a 4MB chunk but crashed before committing the local Room offset, the server authoritative response updates the client, preventing duplicate chunk transmission.
Additionally, file I/O within the worker utilizes random-access byte channel streams (FileChannel) rather than loading entire multi-gigabyte files into memory, eliminating OutOfMemoryError risks.
When constraints break or the user enters airplane mode, WorkManager triggers cooperative cancellation on CoroutineWorker. The worker finishes writing the current chunk status, releases file descriptors, and returns Result.retry(), allowing WorkManager exponential backoff to handle network recovery gracefully while presentation screens observe the Room entity reactively throughout.

## Follow-up questions

- **Interviewer:** "What is the Tus protocol (tus.io)?"
  **Answer:** "An open standard protocol for resumable file uploads over HTTP utilizing HEAD requests to inspect offsets and PATCH requests to upload binary chunks."

- **Interviewer:** "Why shouldn't you upload a 2GB video in a single raw HTTP POST request?"
  **Answer:** "A single connection drop at 99% forces re-uploading the entire 2GB file from zero; chunked uploads isolate failures to a single 5MB chunk."
