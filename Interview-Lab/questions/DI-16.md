# DI-16

## Original interview question

How do you integrate DI with multiple Gradle modules?

## What the interviewer evaluates

- Trace compile-time binding visibility from regular library modules to the Application module.
- Separate optional contract/implementation boundaries from Hilt requirements.
- Distinguish Play dynamic features and diagnose variant-specific missing or duplicate bindings.

## Concept and technical explanation

For regular Gradle modules, the module compiling the `Application` class must have all Hilt modules and constructor-injected classes in its transitive dependencies. An `@InstallIn` module can live beside its implementation in a regular Android library. Hilt generates the application graph from compile-visible contributions; a source file elsewhere in the repository is not sufficient. An interface-only contract module and a separate implementation module can reduce coupling where there is a real boundary, but Hilt does not require every feature to use that split. The app chooses the relevant implementation dependency for each build variant. Play dynamic feature modules invert the usual dependency direction and need the documented Hilt `@EntryPoint` plus Dagger component-dependency bridge.

## Practical walkthrough (English)

For a regular library setup, `:feature:catalog` depends on `:core:catalog:api`; `:core:catalog:impl` depends on that API and owns the binding; `:app` depends on the feature and implementation. The example below is illustrative Android code; this repository does not compile a Hilt Android graph.
```kotlin
// :core:catalog:api
interface CatalogRepository { fun item(id: String): Item? }

// :core:catalog:impl
class RoomCatalogRepository @Inject constructor(
    private val dao: CatalogDao
) : CatalogRepository { /* implementation */ }

@Module
@InstallIn(SingletonComponent::class)
abstract class CatalogBindings {
    @Binds abstract fun bindCatalogRepository(
        impl: RoomCatalogRepository
    ): CatalogRepository
}

// :app depends on :feature:catalog and :core:catalog:impl.
```
For a Play dynamic feature, declare an app-visible `@EntryPoint` for the required base bindings and make a Dagger component in the feature depend on it. Do not treat that feature as an ordinary library module.

## Practical walkthrough

مثال مصغّر للـ Regular Modules:
```kotlin
// :core:catalog:api
interface CatalogRepository { fun item(id: String): Item? }

// :core:catalog:impl
class RoomCatalogRepository @Inject constructor(
    private val dao: CatalogDao
) : CatalogRepository { /* implementation */ }

@Module
@InstallIn(SingletonComponent::class)
abstract class CatalogBindings {
    @Binds abstract fun bindCatalogRepository(
        impl: RoomCatalogRepository
    ): CatalogRepository

// :app depends on :feature:catalog and :core:catalog:impl.
// :feature:catalog depends on :core:catalog:api.
```
لو `:app` مش واصلة لها `:core:catalog:impl` في الـ Variant المطلوب، راجع الـ Gradle Dependency Graph قبل ما تغيّر الكود. مثال الـ Dynamic Feature مختلف: `@EntryPoint` في مسار يقدر الـ Base يجمعه، وDagger Component في الـ Feature يعتمد عليه.

## Why it matters and how it works

Hilt graph generation follows the compile-time dependency path. If the app does not reach an implementation module for a release variant, its binding is missing even if the module exists in the repository. A second unqualified binding for the same key creates a duplicate-binding error. Module boundaries may improve ownership, isolation and incremental builds, but their performance impact is workload-dependent.

## Worked example

A catalog feature requests `CatalogRepository`; a regular implementation library supplies the `@Binds` contribution; the app includes that library. Debug builds, but release fails with a missing binding. First inspect the release dependency graph, then check qualifiers and component installation. If catalog becomes a Play dynamic feature, expose the needed base dependencies through an app-visible `@EntryPoint` and a feature Dagger component. Building the app alone does not exercise feature installation.

## Trade-offs and decision criteria

Create contract modules where multiple consumers benefit from a stable boundary. Extra modules add Gradle configuration and API maintenance. Keep a binding close to its implementation while ensuring the app sees it transitively. Choose scopes and qualifiers for actual lifetime and identity needs. Measure incremental build behavior before claiming a speed gain.

## Failure modes

An implementation module is excluded from one variant, causing a missing binding. Two reachable modules bind the same unqualified key. A feature imports another feature’s implementation and introduces a cycle. A Play dynamic feature assumes Hilt will process its annotations through the ordinary library path.

## Production perspective

Document dependency direction and binding ownership. Build supported app variants and run an Android injection smoke path for important graphs. Test dynamic-feature installation and its entry-point bridge on Android. A JVM contract test does not verify Hilt-generated components, variant wiring or Play feature delivery.

## Interview answer — short

In regular Gradle modules, the module compiling the `Application` class must transitively see every Hilt module and constructor-injected class needed for the graph. A feature may depend on a contract while an implementation library contributes an `@InstallIn` binding and the app includes that library. The contract/implementation split is optional. A Play dynamic feature needs an app-visible Hilt `@EntryPoint` and a Dagger component dependency because its dependency direction differs.

## Interview answer — structured

I first draw the Gradle dependency graph for the build variant. For regular libraries, Hilt can collect compile-visible contributions when the `Application` module transitively depends on the modules containing bindings and constructor-injected classes. If a catalog feature needs a repository contract, I may put that contract in `:core:catalog:api`, the implementation and `@Binds` binding in `:core:catalog:impl`, and include the implementation from `:app`. That split is an architecture choice, not a universal Hilt rule. I inspect missing bindings by checking the variant’s dependency path, component, scope and qualifier; duplicate bindings require an explicit owner or justified qualifiers. Play dynamic features are different: the base exposes dependencies with `@EntryPoint`, and the feature builds a Dagger component that depends on it. I verify supported app variants and the Android injection path rather than inferring correctness from a JVM-only test.

## Interview answer — deep senior

The key property is compile-time visibility. Android’s Hilt multi-module guidance says the Gradle module compiling the `Application` class needs all Hilt modules and constructor-injected classes in its transitive dependencies. A Hilt module in a regular library can contribute a binding through `@InstallIn`, but merely storing the source somewhere in the repository cannot make it part of the generated application graph. This also means that saying Hilt can never be used in an AAR is too broad: a regular library can carry contributions when the consuming app has the required dependency and Hilt setup.

I would use a separate contract module when it represents a stable boundary for several consumers. For example, a catalog feature depends on `CatalogRepository` while a Room-backed implementation module owns `@Binds`; the app selects the implementation dependency. I would not split every feature mechanically. The extra modules have configuration and API costs, and any build-cache gain must be measured on representative changes and variants. `@Binds` proves only a graph mapping is declared; it does not prove the repository implements the right business behavior or that the lifetime and qualifier are appropriate. A release-only missing binding sends me to the release dependency graph before I add more bindings. A duplicate binding sends me to ownership and key identity.

Play dynamic features require a separate answer. Their dependency direction is inverted, so Hilt cannot process annotations in the feature through the normal app graph path. The documented bridge places an `@EntryPoint` where Hilt can process it and creates a Dagger component in the feature with a component dependency on that entry point. I would verify the base variants, then install and exercise the feature on Android. A plain JVM test can validate a contract consumer, but it cannot claim the generated Hilt graph or delivery bridge works.

## How to answer in the interview

- State the application module’s transitive visibility requirement.
- Show an optional contract/implementation boundary with one binding owner.
- Diagnose missing and duplicate bindings by variant, component and qualifier.
- Explain the dynamic-feature `@EntryPoint` plus Dagger bridge.
- Describe Android verification and measured build trade-offs.

## Deep-dive talking points

Compile-visible Hilt contributions; transitive dependency paths; optional API/implementation split; variant-specific bindings; scope and qualifier identity; dynamic-feature component dependencies; build measurement.

## Follow-up questions

- **Interviewer:** "Must every feature have `:api` and `:impl` modules?"
  **Answer:** "No. Split only where the contract is useful enough to justify extra modules; Hilt requires compile-time visibility, not that naming scheme."

- **Interviewer:** "Can a published Android library contain Hilt modules?"
  **Answer:** "A regular library may contribute Hilt bindings when the consuming app includes it transitively and has the required Hilt setup. Play dynamic features are a different dependency shape."

- **Interviewer:** "Why does only release report a missing binding?"
  **Answer:** "Inspect release-specific dependencies, then the qualifier and installation component; build and exercise that variant."

## Self-check rubric

Identify the app compile path, one binding owner, the optional boundary, a variant failure, and the distinct dynamic-feature bridge. Avoid unsupported build-speed guarantees.
