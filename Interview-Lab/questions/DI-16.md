# DI-16

## Original interview question

How do you integrate DI with multiple Gradle modules?

## What the interviewer evaluates

- Place interfaces and implementations on correct dependency paths.
- Explain Hilt aggregation visibility and base-app compile requirements.
- Distinguish regular library modules from dynamic features.

## Concept and technical explanation

Integrating dependency injection across multiple Gradle modules is a defining challenge in enterprise Android architecture. A robust multi-module DI structure decouples high-level feature modules from concrete low-level implementations while enabling parallel builds and independent testability. Under Hilt and Dagger, feature modules depend solely on abstract API interfaces declared in lightweight API modules (such as :feature:auth:api). Concrete implementation modules (such as :feature:auth:impl) satisfy these contracts and declare @InstallIn Hilt modules that bind interfaces to implementations via @Binds. The root :app module depends on all implementation modules, serving as the dependency aggregation and composition root where Hilt synthesizes the monolithic application graph during final APK assembly.

## Practical walkthrough (English)

Architectural separation of API, Implementation, and App modules:
```
Module Dependency Topology:
:feature:login:impl  --->  :feature:login:api  <---  :feature:profile:impl
         |
         v
:core:network:api    <---  :core:network:impl
         ^
         |
      (:app aggregates all implementation modules at the build root)
```
Code bindings across module boundaries:
```kotlin
// In :core:database:api (lightweight contract)
interface UserLocalDataSource {
    suspend fun getUser(id: String): UserEntity?
}

// In :core:database:impl (heavy Room implementation, hidden from feature modules)
@Module
@InstallIn(SingletonComponent::class)
abstract class DatabaseBindingModule {
    @Binds
    abstract fun bindUserLocalDataSource(
        impl: RoomUserLocalDataSourceImpl
    ): UserLocalDataSource
}

// In :feature:profile:impl (consumes only the API, never touches Room directly)
@HiltViewModel
class ProfileViewModel @Inject constructor(
    private val localDataSource: UserLocalDataSource // Loose coupling
) : ViewModel()
```

## Practical walkthrough

تنظيم التبعيات والـ Hilt Modules في هيكل Multi-Module نظيف:
```kotlin
// 📁 في موديول ':feature:login' (يعتمد فقط على :core:auth-api):
@HiltViewModel
class LoginViewModel @Inject constructor(
    private val authService: AuthService // واجهة فقط من موديول الـ API!
) : ViewModel() { /* ... */ }

// 📁 في موديول ':core:auth-impl' (يحتوي على التنفيذ الفعلي وموديول Hilt):
class AuthServiceImpl @Inject constructor(
    private val httpClient: OkHttpClient
) : AuthService { /* ... */ }

@Module
@InstallIn(SingletonComponent::class)
abstract class AuthBindingModule {
    @Binds @Singleton
    abstract fun bindAuthService(impl: AuthServiceImpl): AuthService
}

// 📁 في موديول ':app':
// dependencies {
//     implementation(projects.feature.login)
//     implementation(projects.core.authImpl)
// }
// يقوم Hilt تلقائياً بجمع AuthBindingModule وحقنه في LoginViewModel أثناء التجميع في :app!
```

## Why it matters and how it works

Gradle module edges determine compile visibility and compilation boundaries; Hilt's generated components collect bindings from reachable modules. An abstraction module can expose an interface without depending on implementation. The app composition root selects a binding, while a feature depends on the contract. Hidden bindings lead to compile errors, duplicate bindings cause ambiguity, and dependency cycles undermine modularity.

## Worked example

`:feature:catalog` depends on `:domain:catalog-api`; `:data:catalog` implements `CatalogRepository` and provides its binding. `:app` includes both feature and implementation modules, so Hilt can aggregate the binding. A separate test substitutes an in-memory implementation. If the feature is installed on demand, use the documented dynamic-feature bridge rather than assuming the same Hilt aggregation path.

## Trade-offs and decision criteria

Binding near an implementation keeps ownership clear; selecting implementations in the app allows variant composition. Too many tiny modules inflate build configuration and API surface. Annotation processing/KSP must be configured consistently, but exact plugin choices depend on supported library versions. Prefer compile-visible, acyclic dependencies over service-locator workarounds.

## Failure modes

An implementation module is absent from the app graph, producing a missing binding. Two modules bind the same unqualified interface. A feature imports data internals and creates a cycle. A dynamic-feature module assumes it can use a base-generated component without an entry point bridge.

## Production perspective

Maintain a dependency graph and module ownership guide. Test app assembly plus a small injection smoke path in CI, include variant-specific bindings, and track incremental build cost before multiplying modules. Keep graph errors actionable by naming contract and qualifier explicitly.

## Interview answer — short

To integrate DI across multiple Gradle modules, separate features into public API interface modules and internal implementation modules. Feature consumers depend only on lightweight API modules. Implementation modules provide Hilt @InstallIn bindings using @Binds to connect interfaces to concrete classes. The root application module aggregates all implementation modules, serving as the dependency graph assembly root.

## Interview answer — structured

Scalable multi-module dependency injection relies on establishing clear API and implementation module boundaries.
In large Android codebases, allowing feature modules to depend directly on each other's concrete implementations degrades build speeds and introduces tight coupling. To prevent this, architects divide features into lightweight API modules containing only public interfaces and models, and implementation modules containing internal business logic, database queries, and Hilt modules.
Consuming modules depend strictly on the abstract API module. They inject interface contracts into their ViewModels and UseCases without any knowledge of the underlying networking or database technologies.
The implementation module declares an abstract Hilt module annotated with @InstallIn(SingletonComponent::class), binding the concrete class to the interface via @Binds.
Finally, the root :app module includes dependencies on all implementation modules. Because Hilt uses classpath scanning and bytecode aggregation, the application module compiles all contributing bindings into a unified Directed Acyclic Graph, preserving strict boundaries across feature teams.

## Interview answer — deep senior

Under the hood, Hilt solves the classic Dagger multi-module dilemma through Gradle plugin bytecode aggregation. In raw Dagger 2, a root component was required to explicitly declare every contributing module in its @Component(modules = [...]) annotation, which forced the root module or base configuration to manually maintain an unwieldy list of hundreds of module classes.
Hilt eliminates this manual wiring by utilizing an aggregation mechanism driven by KSP or annotation processors. When an implementation module declares an @InstallIn(SingletonComponent::class) module, Hilt generates metadata annotations on dummy classes. During final packaging in the :app module, Hilt scans the compiled classpath, discovers all contributing modules, and automatically generates the root component class incorporating every binding.
Senior engineers exploit this architecture to maximize Gradle remote build caching and parallel execution. Because feature modules depend only on abstract API modules, changing an internal implementation detail in a database module does not invalidate the compilation cache of feature modules that consume its interface.
Staff engineers enforce these compilation firewalls through Gradle architecture plugins or custom lint rules, forbidding direct implementation-to-implementation dependencies and ensuring that the DI graph remains clean, modular, and performant. This strict modular encapsulation enables enterprise Android repositories to scale to hundreds of modules while maintaining rapid build times.

## How to answer in the interview

- **Why:** generated graph requires compile-time visibility.
- **How:** contracts, implementation modules, app aggregation.
- **Trade-off:** modular isolation versus wiring visibility.
- **Failure case:** release variant misses a binding.
- **Production solution:** build every variant and exercise dynamic-feature seam.

Cover compile visibility, aggregation, contract placement, app composition, duplicate bindings, and dynamic-feature exceptions.

## Follow-up questions

- **Interviewer:** "Why shouldn't feature modules depend on each other's implementation modules?"
  **Answer:** "It creates tight coupling, circular dependency risks, and invalidates Gradle build caches, causing full rebuilds whenever any feature changes."

- **Interviewer:** "Can you use Hilt in an Android library module that will be distributed as an AAR?"
  **Answer:** "No, Hilt requires the root application module to assemble the graph. Reusable public libraries should use pure constructor injection or manual factory patterns."
