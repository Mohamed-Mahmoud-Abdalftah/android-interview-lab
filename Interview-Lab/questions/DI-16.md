# DI-16

## Original interview question

How do you integrate DI with multiple Gradle modules?

## What the interviewer evaluates

- Place interfaces and implementations on correct dependency paths.
- Explain Hilt aggregation visibility and base-app compile requirements.
- Distinguish regular library modules from dynamic features.

## Explanation in Arabic

كيف تدمج وتدير حقن التبعيات (DI) عبر موديولات Gradle المتعددة (Multi-Module Architecture) في Hilt؟

1. التحدي المعماري في الـ Multi-Module:
   - في المشاريع المقسمة وفق Clean Architecture و Feature Modularization:
     * موديول الـ Feature (`:feature:checkout`) لا يجب أن يعرف تفاصيل موديول الـ Implementation الخرساني (`:data:payment`).
     * موديول الـ App الأساسي (`:app`) يجمع كل الموديولات.

2. آلية عمل Hilt في الـ Multi-Module:
   - **Decentralized Modules via `@InstallIn`**: بفضل تعليمة `@InstallIn(SingletonComponent::class)`، يمكن لأي مكتبة أو موديول Gradle فرعي أن يعلن عن الـ Bindings الخاصة به محلياً داخل الموديول نفسه.
   - **Compilation Aggregation**: عندما يقوم موديول `:app` بالتجميع، يقوم Hilt بمسح الـ Classpath وجمع جميع الـ Modules المعلمة بـ `@InstallIn` عبر جميع موديولات Gradle ودمجها في الـ Dagger Component النهائي تلقائياً!

3. أفضل ممارسة لتنظيم الـ Modules والـ DI:
   - الموديول العام أو الـ API (`:core:network-api`) يعرّف الـ Interfaces فقط.
   - موديول الـ Implementation (`:core:network-impl`) يطبق الـ Interface ويوفر Hilt Module يربط الـ Interface بالـ Implementation عبر `@Binds`.
   - موديول الـ Feature يعتمد فقط على `:core:network-api` ويحقن الـ Interface مباشرة دون معرفة كلاسات الـ Implementation!

## Practical walkthrough

تنظيم التبعيات والـ Hilt Modules في هيكل Multi-Module نظيف:
```kotlin
// 📁 في موديول ':feature:login' (يعتمد فقط على :core:auth-api):
@HiltViewModel
class LoginViewModel @Inject constructor(
    private val authService: AuthService // واجهة فقط من موديول الـ API!
) : ViewModel() { /* ... */ }

// 📁 في موديول ':core:auth-impl' (يحتوي على التنفيذ الفعلي وموديول Hilt):
class AuthServiceImpl @Inject constructor(
    private val httpClient: OkHttpClient
) : AuthService { /* ... */ }

@Module
@InstallIn(SingletonComponent::class)
abstract class AuthBindingModule {
    @Binds @Singleton
    abstract fun bindAuthService(impl: AuthServiceImpl): AuthService
}

// 📁 في موديول ':app':
// dependencies {
//     implementation(projects.feature.login)
//     implementation(projects.core.authImpl)
// }
// يقوم Hilt تلقائياً بجمع AuthBindingModule وحقنه في LoginViewModel أثناء التجميع في :app!
```

## Why it matters and how it works

Gradle module edges determine compile visibility and compilation boundaries; Hilt's generated components collect bindings from reachable modules. An abstraction module can expose an interface without depending on implementation. The app composition root selects a binding, while a feature depends on the contract. Hidden bindings lead to compile errors, duplicate bindings cause ambiguity, and dependency cycles undermine modularity.

## Worked example

`:feature:catalog` depends on `:domain:catalog-api`; `:data:catalog` implements `CatalogRepository` and provides its binding. `:app` includes both feature and implementation modules, so Hilt can aggregate the binding. A separate test substitutes an in-memory implementation. If the feature is installed on demand, use the documented dynamic-feature bridge rather than assuming the same Hilt aggregation path.

## Trade-offs and decision criteria

Binding near an implementation keeps ownership clear; selecting implementations in the app allows variant composition. Too many tiny modules inflate build configuration and API surface. Annotation processing/KSP must be configured consistently, but exact plugin choices depend on supported library versions. Prefer compile-visible, acyclic dependencies over service-locator workarounds.

## Failure modes

An implementation module is absent from the app graph, producing a missing binding. Two modules bind the same unqualified interface. A feature imports data internals and creates a cycle. A dynamic-feature module assumes it can use a base-generated component without an entry point bridge.

## Production perspective

Maintain a dependency graph and module ownership guide. Test app assembly plus a small injection smoke path in CI, include variant-specific bindings, and track incremental build cost before multiplying modules. Keep graph errors actionable by naming contract and qualifier explicitly.

## Interview answer — short

In multi-module projects, Hilt uses decentralized aggregation: individual library and data modules declare bindings locally via @InstallIn, and the :app module aggregates them all at compile time into the root component. Feature modules depend only on API interface modules, ensuring encapsulation and fast incremental builds.

## Interview answer — structured

Integrating Hilt across multiple Gradle modules relies on Hilt's decentralized compilation model.

First, with Decentralized Binding Declaration, unlike pure Dagger where a central root component had to import every submodule, Hilt modules use `@InstallIn(SingletonComponent::class)` inside their respective Gradle library modules. Modules contribute bindings independently without central registration. Next, strict Inversion of Dependencies is a feature module (`:feature:checkout`) depends only on an API module (`:data:payment-api`) containing pure interfaces. The implementation module (`:data:payment-impl`) contains the concrete classes and the `@Module` with `@Binds`. The `:app` module depends on both, allowing Hilt to resolve the graph while the feature module remains isolated from implementation details.
Finally, with Incremental Build Optimization, feature modules do not depend on sibling feature implementations. If code inside `:data:payment-impl` changes, Gradle only recompiles that module and `:app`, leaving unaffected feature modules in the Gradle build cache.


## Interview answer — deep senior

Under the hood, Hilt achieves cross-module aggregation via **Metadata Indexing**.

During Gradle compilation of a library module, the Hilt symbol processor generates marker classes in an internal package (`dagger.hilt.internal.aggregatedroot` or `hilt_aggregated_deps`). These marker classes encode module references into the module's JAR metadata. When the final `:app` module builds, Hilt reads the transitively collected metadata from the classpath, constructs the master Dagger component, and verifies the entire graph.

A critical nuance: **Dynamic Feature Modules (Play Feature Delivery)** invert standard dependency edges (`:app` does NOT depend on `:dynamic_feature`; rather, the dynamic feature depends on `:app`). Because `:app` cannot aggregate metadata from downstream dynamic features, standard Hilt `@InstallIn` does not work inside dynamic features. Instead, you must use `@EntryPoint` to pull dependencies from the base app.


## How to answer in the interview

- **Why:** generated graph requires compile-time visibility.
- **How:** contracts, implementation modules, app aggregation.
- **Trade-off:** modular isolation versus wiring visibility.
- **Failure case:** release variant misses a binding.
- **Production solution:** build every variant and exercise dynamic-feature seam.

## Deep-dive talking points

Cover compile visibility, aggregation, contract placement, app composition, duplicate bindings, and dynamic-feature exceptions.

## Follow-up questions

- **Interviewer:** "Why shouldn't feature modules depend on each other's implementation modules?"
  **Answer:** "It creates tight coupling, circular dependency risks, and invalidates Gradle build caches, causing full rebuilds whenever any feature changes."

- **Interviewer:** "Can you use Hilt in an Android library module that will be distributed as an AAR?"
  **Answer:** "No, Hilt requires the root application module to assemble the graph. Reusable public libraries should use pure constructor injection or manual factory patterns."
