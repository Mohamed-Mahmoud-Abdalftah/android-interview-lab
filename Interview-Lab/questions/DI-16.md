# DI-16

## Original interview question

How do you integrate DI with multiple Gradle modules?

## What the interviewer evaluates

- Place interfaces and implementations on correct dependency paths.
- Explain Hilt aggregation visibility and base-app compile requirements.
- Distinguish regular library modules from dynamic features.

## Explanation in Arabic

قسّم العقود في modules تقدر features تعتمد عليها، وخلي implementations في data أو platform modules؛ application تجمع bindings اللازمة للتطبيق. Hilt يحتاج classpath يرى `@HiltAndroidApp` وما يلزم من Hilt modules وconstructor-injected classes وقت compilation. لذلك مجرد وجود runtime dependency في مكان بعيد لا يكفي إذا الـaggregation لا يراه. feature module العادي يستطيع استخدام Hilt مع plugin والتبعيات المناسبة، لكن dynamic feature له اتجاه dependency مختلف واحتياج خاص لـentry point/component dependency. اختبر graph في build الفعلي، لا تعتمد على رسم architecture فقط.

## Practical walkthrough

في multi-module عادية، module للـdata تصدّر repository contract، وfeature تعتمد على contract بدل internal Retrofit. الـapp module اللي بيجمع graph لازم يقدر يشوف Hilt bindings transitively وقت compile، وكل module يستخدم Hilt plugin/processor المناسب حسب الـdocs. لو binding ناقصة في variant معين، build error بيظهر عند التجميع. dynamic feature استثناء مهم لأن base app ما تشوفش feature source؛ لها entry-point/component dependency.

## Why it matters and how it works

Gradle module edges determine compile visibility and compilation boundaries; Hilt's generated components collect bindings from reachable modules. An abstraction module can expose an interface without depending on implementation. The app composition root selects a binding, while a feature depends on the contract. Hidden bindings lead to compile errors, duplicate bindings cause ambiguity, and dependency cycles undermine modularity.

## Worked example

`:feature:catalog` depends on `:domain:catalog-api`; `:data:catalog` implements `CatalogRepository` and provides its binding. `:app` includes both feature and implementation modules, so Hilt can aggregate the binding. A separate test substitutes an in-memory implementation. If the feature is installed on demand, use the documented dynamic-feature bridge rather than assuming the same Hilt aggregation path.

## Trade-offs and decision criteria

Binding near an implementation keeps ownership clear; selecting implementations in the app allows variant composition. Too many tiny modules inflate build configuration and API surface. Annotation processing/KSP must be configured consistently, but exact plugin choices depend on supported library versions. Prefer compile-visible, acyclic dependencies over service-locator workarounds.

## Failure modes

An implementation module is absent from the app graph, producing a missing binding. Two modules bind the same unqualified interface. A feature imports data internals and creates a cycle. A dynamic-feature module assumes it can use a base-generated component without an entry point bridge.

## Production perspective

Maintain a dependency graph and module ownership guide. Test app assembly plus a small injection smoke path in CI, include variant-specific bindings, and track incremental build cost before multiplying modules. Keep graph errors actionable by naming contract and qualifier explicitly.

## Interview answer — short

“I keep contracts on feature-visible APIs, implementations in data modules, and ensure the app graph can compile and aggregate every selected Hilt binding.”

## Interview answer — structured

“DI across Gradle modules follows compile dependencies. A feature should depend on a stable repository interface, while an implementation module binds it and the app brings both into the graph. Hilt's generated component needs visibility of its modules and injectable classes, so I validate the actual app variant build. I watch for missing or duplicate bindings and prevent a feature-to-data dependency cycle. Dynamic features need the documented entry-point bridge because their dependency direction is different.”

## Interview answer — deep senior

“I start with the module DAG. An API module owns the contract a feature needs; an implementation module owns network, database, and the binding, and the application composition root includes the selected implementation. This lets the feature compile without data internals and lets tests supply a controlled replacement. Hilt still has a concrete compilation requirement: the app's component generation must see the modules and constructor-injected classes through the supported build graph. I therefore test assembly of each relevant variant and treat missing-binding errors as evidence of a dependency or qualifier problem. I avoid scattering duplicate bindings across features, and I keep scopes aligned with the component actually installed. Dynamic-feature delivery is a special case; I use its documented entry-point and Dagger component-dependency pattern rather than assuming ordinary library-module aggregation works. The trade-off is build complexity: module boundaries are useful when they isolate ownership or improve build/test independence, but a forest of trivial modules can make DI configuration harder to reason about. CI checks the graph and dependency cycles, not just isolated module compilation. A common failure appears only in a release flavor: the app sees a debug module that binds a fake API, but the release graph lacks a real binding or retains the wrong qualifier. I would compile each delivery variant and run a small integrated graph test. In an on-demand feature I would use the documented entry-point bridge, since the base app cannot aggregate source it does not depend on.”

## How to answer in the interview

- **Why:** generated graph requires compile-time visibility.
- **How:** contracts, implementation modules, app aggregation.
- **Trade-off:** modular isolation versus wiring visibility.
- **Failure case:** release variant misses a binding.
- **Production solution:** build every variant and exercise dynamic-feature seam.

## Deep-dive talking points

Cover compile visibility, aggregation, contract placement, app composition, duplicate bindings, and dynamic-feature exceptions.

## Follow-up questions

- Why can an app build report a missing binding although an implementation file exists? **Answer:** the app graph may not compile against its module, or qualifier/component selection may differ.
- Where should a feature's repository interface live? **Answer:** in a stable API visible to the feature and implementation without a dependency cycle.
- Is a dynamic feature identical to a regular library module? **Answer:** no; its reversed dependency relationship needs a documented bridge.

## Self-check rubric

Draw an acyclic module graph, identify the binding owner, and explain a missing-binding diagnosis and dynamic-feature caveat.
