# DI-07

## Original interview question

Compare @Singleton, @ActivityScoped, and @ViewModelScoped.

## What the interviewer evaluates

- Tie each scope to a concrete Hilt component and instance-sharing boundary.
- Distinguish Activity instance lifetime from ViewModel lifetime across configuration change.
- Avoid promoting mutable UI/session state to Singleton for convenience.

## Explanation in Arabic

`@Singleton` يعطي نفس instance داخل `SingletonComponent` طول عمر process graph تقريبًا؛ مناسب client أو database مشتركة، مع مراعاة thread safety وlogout. `@ActivityScoped` instance واحدة لكل Activity instance، وتذهب عند تدميرها بما في ذلك rotation. `@ViewModelScoped` instance واحدة داخل ViewModelComponent، فتبقى مع ViewModel عبر rotation المعتادة وتختفي عند `onCleared`. لو محتاج مشاركة بين ViewModels في نفس Activity عبر rotation، راجع `@ActivityRetainedScoped` بدل الخلط مع `@ActivityScoped`. الـscope لا تعني “الكلاس thread-safe” ولا “state دائم بعد process death”. اختارها من عمر البيانات المطلوبة.

## Why it matters and how it works

Hilt caches a scoped binding within one instance of its matching generated component. `SingletonComponent` is process-level; `ActivityComponent` follows an Activity instance; `ViewModelComponent` follows a ViewModel. New Activity instances after rotation get new Activity-scoped objects, while a retained ViewModel normally keeps its own scoped collaborator. All components and in-memory instances are rebuilt after process termination. Scope controls identity and retention, not persistence or synchronization.

## Worked example

An `@Singleton` OkHttp client shares connection resources; an `@ActivityScoped` permission coordinator owns callbacks for one current Activity; a `@ViewModelScoped` checkout draft controller is shared among collaborators of one CheckoutViewModel. A second checkout screen gets a different controller. Important payment intent and idempotency key remain in durable storage rather than solely in that controller. This is an ownership design, not a compiled Hilt module.

## Trade-offs and decision criteria

Broader scope avoids repeated expensive construction but holds memory and mutable state longer. An unscoped stateless mapper may need no cache at all. ActivityScoped is wrong for state expected to survive rotation; ViewModelScoped is wrong for data shared across multiple ViewModels. A Singleton holding account-specific state needs explicit session invalidation and concurrency controls.

## Failure modes

A Singleton captures Activity Context and leaks old screens. An ActivityScoped request manager resets during rotation and duplicates work. A ViewModelScoped repository holds the only copy of a pending payment and loses it after process death. Two ViewModels assume they share one draft but each has its own instance. Test object identity over rotation, across destinations, and after logout/process recreation.

## Production perspective

Write a scope table for each stateful binding, including its owner, invalidation trigger, and persistence source. Prefer narrow scopes unless sharing has a concrete need. Instrument session transitions and ensure no prior account state survives in Singleton caches. Pair graph tests with lifecycle UI tests for rotation and distinct navigation destinations.

## Interview answer — short

“Singleton is shared within the app process graph, ActivityScoped within one Activity instance, and ViewModelScoped within one ViewModel. Their identities and lifetimes differ across rotation and process death.”

## Interview answer — structured

“Hilt scopes cache an instance in a matching component. `@Singleton` belongs to SingletonComponent and is useful for a configured process-level client. `@ActivityScoped` belongs to one ActivityComponent, so a recreated Activity after rotation gets a new instance. `@ViewModelScoped` belongs to one ViewModel and commonly survives an ordinary rotation with that ViewModel. None of them persists data after process death or makes mutable state thread-safe. I choose the smallest owner that needs shared identity, and store durable operations separately. If multiple ViewModels need one rotation-retained collaborator, I consider ActivityRetainedScoped rather than misusing ActivityScoped.”

## Interview answer — deep senior

“Scope is a statement about instance identity within a component, not a blanket performance annotation. A Singleton can share an OkHttp client across the process, but any mutable account state inside it needs synchronization and clearing on logout. ActivityScoped is tied to an Activity instance and therefore recreates on configuration change. ViewModelScoped ties a collaborator to one ViewModel's lifetime; it is useful for screen-specific state that should be shared among that ViewModel's dependencies across ordinary rotation. It is not shared with a second ViewModel and does not survive process death. I also consider ActivityRetainedScoped when several ViewModels need one rotation-retained owner. I audit transitive references: a Singleton with an Activity Context leaks, and a ViewModelScoped pending payment record is insufficiently durable. Tests assert instance identity across screen creation, rotation, logout, and process restoration, while the repository owns irreversible transaction state.”

## Follow-up questions

- Does ActivityScoped survive rotation? **Answer:** no; it follows the Activity instance, which is normally recreated.
- Do two ViewModels share one ViewModelScoped object? **Answer:** no; each ViewModelComponent has its own scoped instance.
- Is Singleton suitable for a mutable authentication session? **Answer:** only with explicit synchronization, invalidation, and no short-lived Context capture; durable session state belongs elsewhere.
