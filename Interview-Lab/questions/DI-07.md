# DI-07

## Original interview question

Compare @Singleton, @ActivityScoped, and @ViewModelScoped.

## What the interviewer evaluates

- Tie each scope to a concrete Hilt component and instance-sharing boundary.
- Distinguish Activity instance lifetime from ViewModel lifetime across configuration change.
- Avoid promoting mutable UI/session state to Singleton for convenience.

## Explanation in Arabic

مقارنة دقيقة وشاملة بين نطاقات Hilt الثلاثة الأكثر أهمية:
`@Singleton`، و `@ViewModelScoped`، و `@ActivityScoped`:

1. `@Singleton` (مرتبط بـ `SingletonComponent`):
   - **فترة الحياة**: طوال فترة بقاء عملية التطبيق في الذاكرة (Application Process Lifetime).
   - **متى يُستخدم**: للموارد المشتركة الثقيلة التي يجب أن تكون نسخة واحدة فقط في التطبيق كله (مثل `RoomDatabase`, `OkHttpClient`, `DataStore`, `UserSessionRepository`).
   - **الخطر**: احتفاظه بأي كائن يحتوي على مرجع لـ Activity أو View يسبب تسريب ذاكرة دائم (Permanent Memory Leak).

2. `@ViewModelScoped` (مرتبط بـ `ViewModelComponent`):
   - **فترة الحياة**: يعيش طالما أن الـ ViewModel لا يزال حياً في الـ `ViewModelStore`.
   - **الميزة العبقرية**: **يعبر تغيرات التكوين (Survives Configuration Changes)** مثل دوران الشاشة (Screen Rotation) وتغيير اللغة.
   - **متى يُستخدم**: لكائنات إدارة الحالة ومنطق الأعمال التفاعلي الخاص بشاشة أو ميزة معينة والتي يجب ألا يُعاد إنشاؤها عند تدوير الشاشة.

3. `@ActivityScoped` (مرتبط بـ `ActivityComponent`):
   - **فترة الحياة**: مرتبط بنسخة الـ Activity الواحدة من `onCreate` حتى `onDestroy`.
   - **السلوك مع الدوران**: **يتم تدميره وإعادة إنشائه بالكامل مع كل دوران للشاشة!**
   - **متى يُستخدم**: للكائنات المرتبطة مباشرة بالـ UI والـ Window الخاص بنسخة الـ Activity (مثل Navigator الذي يحتفظ بمرجع للـ Activity للتعامل مع الـ Intents والـ Transitions).

## Practical walkthrough

المقارنة العملية لتأثير دوران الشاشة على كل Scope:
```kotlin
// 1. Singleton: نسخة واحدة تعيش طوال عمر تشغيل التطبيق:
@Singleton
class NetworkMonitor @Inject constructor(@ApplicationContext context: Context)

// 2. ViewModelScoped: يعبر دوران الشاشة، مثالي للمنطق الخاص بالشاشة:
@ViewModelScoped
class OrderFlowCoordinator @Inject constructor(
    private val cartRepository: CartRepository
)

// 3. ActivityScoped: يموت ويُعاد إنشاؤه مع كل دوران للشاشة:
@ActivityScoped
class ScreenNavigator @Inject constructor(
    private val activity: Activity // آمن هنا لأن كلاهما يموت معاً في onDestroy
)

// جدول مقارنة الـ Scopes وسلوكها:
// Scope               Component                Survives Rotation?   Typical Target
// @Singleton          SingletonComponent       YES                  Database, Network, Session
// @ViewModelScoped   ViewModelComponent       YES                  Screen state holder, UseCase cache
// @ActivityScoped    ActivityComponent        NO                   Dialog manager, UI Navigator
```

## Why it matters and how it works

Hilt caches a scoped binding within one instance of its matching generated component. `SingletonComponent` is process-level; `ActivityComponent` follows an Activity instance; `ViewModelComponent` follows a ViewModel. New Activity instances after rotation get new Activity-scoped objects, while a retained ViewModel normally keeps its own scoped collaborator. All components and in-memory instances are rebuilt after process termination. Scope controls identity and retention, not persistence or synchronization.

## Worked example

An `@Singleton` OkHttp client shares connection resources; an `@ActivityScoped` permission coordinator owns callbacks for one current Activity; a `@ViewModelScoped` checkout draft controller is shared among collaborators of one CheckoutViewModel. A second checkout screen gets a different controller. Important payment intent and idempotency key remain in durable storage rather than solely in that controller. This is an ownership design, not a compiled Hilt module.

### Kotlin / Hilt example

These annotations mark instance identity inside different Hilt components; they do not persist data after process death.

```kotlin
import dagger.hilt.android.scopes.ActivityRetainedScoped
import dagger.hilt.android.scopes.ActivityScoped
import dagger.hilt.android.scopes.ViewModelScoped
import javax.inject.Inject
import javax.inject.Singleton

@Singleton class ApiClient @Inject constructor()
@ActivityScoped class ScreenWindowTracker @Inject constructor()
@ActivityRetainedScoped class ActivitySession @Inject constructor()
@ViewModelScoped class DetailCache @Inject constructor()
```

Inject each type only from a component that can see its binding; a singleton cannot depend on `ScreenWindowTracker`.

## Trade-offs and decision criteria

Broader scope avoids repeated expensive construction but holds memory and mutable state longer. An unscoped stateless mapper may need no cache at all. ActivityScoped is wrong for state expected to survive rotation; ViewModelScoped is wrong for data shared across multiple ViewModels. A Singleton holding account-specific state needs explicit session invalidation and concurrency controls.

## Failure modes

A Singleton captures Activity Context and leaks old screens. An ActivityScoped request manager resets during rotation and duplicates work. A ViewModelScoped repository holds the only copy of a pending payment and loses it after process death. Two ViewModels assume they share one draft but each has its own instance. Test object identity over rotation, across destinations, and after logout/process recreation.

## Production perspective

Write a scope table for each stateful binding, including its owner, invalidation trigger, and persistence source. Prefer narrow scopes unless sharing has a concrete need. Instrument session transitions and ensure no prior account state survives in Singleton caches. Pair graph tests with lifecycle UI tests for rotation and distinct navigation destinations.

## Interview answer — short

@Singleton binds an instance to the application process lifetime for shared resources like databases. @ViewModelScoped binds to the ViewModel lifecycle and survives configuration changes (rotations), ideal for screen-level logic. @ActivityScoped binds strictly to an Activity's window lifecycle and is recreated on screen rotation, designed for UI/Navigation helpers holding an Activity reference.

## Interview answer — structured

The difference between these three scopes centers on lifecycle boundaries and behavior during Android configuration changes:

1. **`@Singleton` (`SingletonComponent`)**: Lives for the entire duration of the application process. It is reserved for expensive, stateless, or application-wide singletons such as `RoomDatabase`, `Retrofit`, and repository caches. Never inject an Activity Context into a Singleton.

2. **`@ViewModelScoped` (`ViewModelComponent`)**: Bound to the Jetpack ViewModel lifecycle. Its defining trait is that it **survives configuration changes (screen rotations)**. It is ideal for screen-specific use cases, state coordinators, and pagination managers that must retain state across rotations without leaking the UI.

3. **`@ActivityScoped` (`ActivityComponent`)**: Bound to a single concrete `Activity` instance. It **does NOT survive configuration changes**—it is destroyed when the Activity is destroyed and recreated during recreation. It is meant exclusively for collaborators that require a direct reference to the current `Activity` window, such as custom navigators, dialog coordinators, or view animation controllers.

## Interview answer — deep senior

A critical pitfall in Android architectural design is **Scope Inflation** (making everything `@Singleton` out of convenience).

When you annotate a stateful class with `@Singleton`, its memory is never reclaimed by GC until the process dies. In contrast, un-scoped bindings (`Unscoped`) create a lightweight new instance on demand, allowing the ART garbage collector to collect them as soon as their consumers leave scope.

Furthermore, note the relationship between `@ViewModelScoped` and `@ActivityRetainedScoped`. `@ActivityRetainedComponent` is the parent of `ViewModelComponent`. Both survive configuration changes, but `@ActivityRetainedScoped` instances are shared across **all ViewModels** belonging to that Activity, whereas `@ViewModelScoped` dependencies are scoped strictly to their individual ViewModel instance.

## How to answer in the interview

- **Why:** scope controls instance identity and retained state.
- **How:** map Singleton, Activity, ViewModel, ActivityRetained lifetimes.
- **Trade-off:** wider scope shares more but can retain too much.
- **Failure case:** Singleton used for per-user or per-screen state.
- **Production solution:** identity tests across owners and recreation.

## Deep-dive talking points

Discuss matching component, rotation identity, ActivityRetained alternative, process death, thread safety, and session invalidation.

## Follow-up questions

- **Interviewer:** "What happens if a class has no scope annotation in Hilt?"
  **Answer:** "It is unscoped. Hilt creates a fresh new instance every time that dependency is requested anywhere in the graph."

- **Interviewer:** "Can an `@ActivityScoped` dependency be injected into a `@ViewModelScoped` class?"
  **Answer:** "No. A longer-lived component (`ViewModelComponent`, which survives rotation) cannot hold a reference to a shorter-lived component (`ActivityComponent`, which dies on rotation), as this would leak the destroyed Activity."
