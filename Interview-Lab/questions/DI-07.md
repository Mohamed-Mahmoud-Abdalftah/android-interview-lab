# DI-07

## Original interview question

Compare @Singleton, @ActivityScoped, and @ViewModelScoped.

## What the interviewer evaluates

- Map each scope to a Hilt component instance and predict object identity.
- Distinguish Activity recreation from ViewModel retention and process death.
- Choose state ownership without assuming persistence, thread safety or automatic leak prevention.

## Concept and technical explanation

A Hilt scope shares a binding instance within one instance of its matching component. `@Singleton` belongs to `SingletonComponent` for the application process graph. `@ActivityScoped` belongs to one ActivityComponent and is recreated with a new Activity instance. `@ViewModelScoped` belongs to one ViewModelComponent, normally surviving a configuration change when that ViewModel is retained; a different ViewModel has a different component. `@ActivityRetainedScoped` is a separate option for sharing under a retained Activity owner. Installation does not scope a binding automatically. None of these scopes persists data across process death or makes mutable code thread-safe.

## Practical walkthrough (English)

An illustrative scope table:
```text
Scope                 Component                 Rotation          Another ViewModel
@Singleton            SingletonComponent        same process      shared
@ActivityScoped       ActivityComponent         new Activity      not a VM binding
@ViewModelScoped      ViewModelComponent        retained VM       separate instance
```
A shared network client, an Activity-bound navigator and one ViewModel draft controller have different owners. Process death rebuilds all three in-memory graphs. Validate identity on Android rather than treating this table as a compiled Hilt test.

## Why it matters and how it works

A broader scope retains an instance and state longer; a narrower one may break intended sharing. Scope controls identity within a component instance, not durable persistence or synchronization. Rotation separates Activity and retained ViewModel behavior, and process death clears all in-memory component instances.

## Worked example

A checkout flow uses a shared network client, an Activity-specific navigator and a draft controller owned by one CheckoutViewModel. After rotation in the same process, the client remains, the navigator is replaced, and the retained ViewModel keeps its controller. A second ViewModel has another controller. A confirmed payment intent belongs in durable repository storage.

### Kotlin / Hilt example

These annotations mark instance identity inside different Hilt components; they do not persist data after process death.

```kotlin
import dagger.hilt.android.scopes.ActivityRetainedScoped
import dagger.hilt.android.scopes.ActivityScoped
import dagger.hilt.android.scopes.ViewModelScoped
import javax.inject.Inject
import javax.inject.Singleton

@Singleton class ApiClient @Inject constructor()
@ActivityScoped class ScreenWindowTracker @Inject constructor()
@ActivityRetainedScoped class ActivitySession @Inject constructor()
@ViewModelScoped class DetailCache @Inject constructor()
```

Inject each type only from a component that can see its binding; a singleton cannot depend on `ScreenWindowTracker`.

## Trade-offs and decision criteria

`@Singleton` shares costly resources but retains memory and mutable state. `@ActivityScoped` fits Activity-instance collaborators, not rotation-surviving state. `@ViewModelScoped` fits one ViewModel’s state, not cross-ViewModel sharing; consider `@ActivityRetainedScoped` only when that owner matches the requirement. Leave cheap stateless bindings unscoped if shared identity is unnecessary and measure construction costs before optimizing.

## Failure modes

An account cache in a singleton is not invalidated on logout. Activity-scoped state resets during rotation. Two ViewModels assume a shared draft despite each owning a ViewModel-scoped instance. Process death removes all in-memory scopes. A singleton retains an Activity indirectly through a runtime callback outside graph validation.

## Production perspective

For every stateful binding, record owner, lifetime, invalidation trigger and recovery source. Build the Android graph, then test identity across rotation, separate routes and logout. Review references held by long-lived objects. Store confirmed business operations durably and do not equate scope with thread safety.

## Interview answer — short

`@Singleton` shares one instance per SingletonComponent in the app process. `@ActivityScoped` shares one instance per ActivityComponent and is replaced when that Activity is recreated. `@ViewModelScoped` shares one instance within a single ViewModelComponent; a retained ViewModel can keep it across rotation, while a second ViewModel gets another instance. Cross-ViewModel sharing under an Activity may call for `@ActivityRetainedScoped`. None of these scopes provides persistence after process death or automatic thread safety.

## Interview answer — structured

The unit of scoping is a component instance. `@Singleton` in SingletonComponent shares an application-graph instance during one process lifetime. `@ActivityScoped` in ActivityComponent belongs to one Activity instance; rotation normally creates a new one. `@ViewModelScoped` in ViewModelComponent belongs to one ViewModel and survives rotation only when its ViewModelStoreOwner retains that ViewModel. Another ViewModel gets another component and instance. If several ViewModels under one Activity need a collaborator, I consider ActivityRetainedComponent rather than assuming ViewModel scope shares it. An unscoped binding is not cached merely because its module is installed in SingletonComponent. I choose the narrowest owner that satisfies required identity, invalidate account state on logout, and persist confirmed operations outside memory. I verify identity and process-recreation behavior on Android.

## Interview answer — deep senior

A scope is an identity guarantee relative to a generated component instance, not a global uniqueness or durability promise. `@Singleton` matches SingletonComponent and shares a binding within one application-process graph. Another process or a restarted process has another graph. `@ActivityScoped` matches an ActivityComponent associated with an Activity instance, so a normal configuration recreation gives a new component and object. `@ViewModelScoped` matches one ViewModelComponent; that component can remain while the same ViewModel is retained across rotation. A second ViewModel receives a second component and its own collaborator.

I would place an app-wide network client in SingletonComponent if its configuration and sharing really have application ownership. An Activity-bound navigator belongs to the current Activity instance. A mutable checkout draft controller belongs to one checkout ViewModel if its state is private to that route. If multiple ViewModels truly need the same collaborator under one retained Activity owner, ActivityRetainedComponent is an option, but I check that the intended boundary is not a separate navigation or account session. Scope alone does not make a client safe under concurrent access.

Unscoped bindings can be created for each request; `@InstallIn(SingletonComponent::class)` does not imply `@Singleton`. Broader scoping retains memory and can add generated-code cost, so I scope for required identity or measured construction expense. Hilt visibility can reject a direct SingletonComponent request for an Activity-only binding, but it cannot prove no callback or global cache retains an Activity at runtime. Component destruction ends its scoped-cache lifetime without guaranteeing immediate garbage collection if other references remain. I test identity on Android across rotation, two routes and logout, and keep confirmed payment or order records in durable storage for process-death recovery.

## How to answer in the interview

- Map each scope to its component instance.
- Predict identity across rotation, another ViewModel and process death.
- Name ActivityRetained as a distinct sharing option.
- Explain state invalidation, persistence and thread-safety limits.

## Deep-dive talking points

Per-component scope; Activity versus retained ViewModel; ActivityRetained cross-ViewModel sharing; unscoped bindings; process death; logout invalidation; runtime references and concurrency.

## Follow-up questions

- **Interviewer:** "Does a module installed in SingletonComponent make all its bindings singletons?"
  **Answer:** "No. A binding needs its own matching scope to share identity in the component."

- **Interviewer:** "Can ActivityScoped be injected into a ViewModelScoped collaborator?"
  **Answer:** "Not through the ordinary Hilt hierarchy; Activity and ViewModel components are sibling branches, and the Activity instance is shorter-lived."

- **Interviewer:** "How do two ViewModels share one collaborator?"
  **Answer:** "Consider ActivityRetainedComponent when its lifetime matches the intended owner, then test identity and teardown."

## Self-check rubric

Map three scopes to components, predict rotation and process-death identity, identify an ActivityRetained alternative, and avoid persistence, thread-safety or garbage-collection guarantees.
