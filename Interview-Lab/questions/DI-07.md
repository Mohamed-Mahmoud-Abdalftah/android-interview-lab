# DI-07

## Original interview question

Compare @Singleton, @ActivityScoped, and @ViewModelScoped.

## What the interviewer evaluates

- Tie each scope to a concrete Hilt component and instance-sharing boundary.
- Distinguish Activity instance lifetime from ViewModel lifetime across configuration change.
- Avoid promoting mutable UI/session state to Singleton for convenience.

## Concept and technical explanation

Scopes in Hilt and Dagger manage the lifecycle, reuse, and memoization of object instances within their associated components. An unscoped binding creates a brand-new instance every time the dependency is requested. Applying a scope annotation instructs the DI container to instantiate the dependency exactly once within the boundary of that specific component instance, caching and sharing it across all consumers within that component's lifecycle. @Singleton binds an instance to SingletonComponent, persisting for the entire application process lifetime. @ActivityScoped binds an instance to ActivityComponent, surviving only for the lifetime of that specific Activity instance and getting destroyed during configuration changes like screen rotations. @ViewModelScoped binds an instance to ViewModelComponent, surviving configuration changes alongside the host ViewModel and getting cleared only when the ViewModel is permanently retired.

## Practical walkthrough (English)

Contrasting Scopes and their lifecycles in Hilt:
```kotlin
// 1. @Singleton: Exactly one instance per application process (e.g., Database, Network client)
@Singleton
class AppSettingsRepository @Inject constructor()

// 2. @ViewModelScoped: Shared across a single ViewModel's lifecycle, survives screen rotation
@ViewModelScoped
class UserSessionStateHolder @Inject constructor()

@HiltViewModel
class ProfileViewModel @Inject constructor(
    private val session: UserSessionStateHolder // Same instance injected across rotation
) : ViewModel()

// 3. @ActivityScoped: Recreated whenever Activity recreates (e.g., on screen rotation)
@ActivityScoped
class ScreenNavigator @Inject constructor(
    private val activity: Activity // Safe to hold Activity reference: dies with Activity!
)
```

// @ActivityScoped    ActivityComponent        NO                   Dialog manager, UI Navigator

## Why it matters and how it works

Hilt caches a scoped binding within one instance of its matching generated component. `SingletonComponent` is process-level; `ActivityComponent` follows an Activity instance; `ViewModelComponent` follows a ViewModel. New Activity instances after rotation get new Activity-scoped objects, while a retained ViewModel normally keeps its own scoped collaborator. All components and in-memory instances are rebuilt after process termination. Scope controls identity and retention, not persistence or synchronization.

## Worked example

An `@Singleton` OkHttp client shares connection resources; an `@ActivityScoped` permission coordinator owns callbacks for one current Activity; a `@ViewModelScoped` checkout draft controller is shared among collaborators of one CheckoutViewModel. A second checkout screen gets a different controller. Important payment intent and idempotency key remain in durable storage rather than solely in that controller. This is an ownership design, not a compiled Hilt module.

### Kotlin / Hilt example

These annotations mark instance identity inside different Hilt components; they do not persist data after process death.

```kotlin
import dagger.hilt.android.scopes.ActivityRetainedScoped
import dagger.hilt.android.scopes.ActivityScoped
import dagger.hilt.android.scopes.ViewModelScoped
import javax.inject.Inject
import javax.inject.Singleton

@Singleton class ApiClient @Inject constructor()
@ActivityScoped class ScreenWindowTracker @Inject constructor()
@ActivityRetainedScoped class ActivitySession @Inject constructor()
@ViewModelScoped class DetailCache @Inject constructor()
```

Inject each type only from a component that can see its binding; a singleton cannot depend on `ScreenWindowTracker`.

## Trade-offs and decision criteria

Broader scope avoids repeated expensive construction but holds memory and mutable state longer. An unscoped stateless mapper may need no cache at all. ActivityScoped is wrong for state expected to survive rotation; ViewModelScoped is wrong for data shared across multiple ViewModels. A Singleton holding account-specific state needs explicit session invalidation and concurrency controls.

## Failure modes

A Singleton captures Activity Context and leaks old screens. An ActivityScoped request manager resets during rotation and duplicates work. A ViewModelScoped repository holds the only copy of a pending payment and loses it after process death. Two ViewModels assume they share one draft but each has its own instance. Test object identity over rotation, across destinations, and after logout/process recreation.

## Production perspective

Write a scope table for each stateful binding, including its owner, invalidation trigger, and persistence source. Prefer narrow scopes unless sharing has a concrete need. Instrument session transitions and ensure no prior account state survives in Singleton caches. Pair graph tests with lifecycle UI tests for rotation and distinct navigation destinations.

## Interview answer — short

@Singleton caches an instance for the entire application process lifetime within SingletonComponent, ideal for databases and API clients. @ActivityScoped caches an instance for a single Activity lifetime within ActivityComponent and is destroyed on screen rotation. @ViewModelScoped caches an instance across a ViewModel lifetime within ViewModelComponent, surviving screen rotations and clearing only when the ViewModel finishes.

## Interview answer — structured

Scopes in Hilt dictate how instances are cached and shared across application lifecycles.
By default, bindings in Dagger and Hilt are unscoped. Every time a class requests an unscoped dependency, the framework executes its provider logic and constructs a fresh instance. When a scope annotation is applied, Hilt memoizes the instance within the associated component.
The @Singleton scope attaches to SingletonComponent. A singleton dependency is instantiated once per application process, making it appropriate for expensive, stateless, or thread-safe resources such as OkHttpClient, Retrofit, Room databases, and global repositories.
The @ActivityScoped annotation attaches to ActivityComponent. The instance is created once per Activity lifecycle and destroyed when the Activity finishes or recreates during configuration changes like screen rotations. It is ideal for UI delegates requiring a direct reference to the active Activity context.
The @ViewModelScoped annotation attaches to ViewModelComponent. It persists across configuration changes alongside the ViewModel, ensuring that shared business helpers remain intact during screen rotations and are discarded only when the ViewModel clears.

## Interview answer — deep senior

Under the hood, Dagger implements scoping using a DoubleCheck memoization wrapper pattern. When a binding is scoped, Dagger generates provider code that checks an internal volatile field: if null, it synchronizes on the component lock, instantiates the object once, caches the reference, and returns it for all subsequent requests within that component instance.
Senior engineers recognize that scoping carries non-trivial memory costs. Scoped instances cannot be garbage-collected as long as their host component remains active. Overusing @Singleton transforms the dependency injection graph into a repository of permanent memory overhead, degrading low-memory performance and causing memory pressure on low-end devices.
Furthermore, understanding lifecycle boundaries prevents catastrophic memory leaks. Holding an @ActivityScoped dependency inside an @Singleton or @ViewModelScoped class creates a memory leak because the shorter-lived Activity context is retained by the longer-lived container. Hilt's compile-time graph validation strictly prevents child scoped bindings from being injected into parent components, safeguarding against this error at compile time.
Staff engineers enforce a minimal-scoping policy across all modules: leave bindings unscoped by default unless instance memoization is an absolute functional requirement (such as sharing mutable state across a screen) or the object carries severe creation costs (such as cryptographic engines, Room databases, or network connection pools), thereby maximizing memory reclamation throughout user journeys.

## How to answer in the interview

- **Why:** scope controls instance identity and retained state.
- **How:** map Singleton, Activity, ViewModel, ActivityRetained lifetimes.
- **Trade-off:** wider scope shares more but can retain too much.
- **Failure case:** Singleton used for per-user or per-screen state.
- **Production solution:** identity tests across owners and recreation.

## Follow-up questions

- **Interviewer:** "What happens if a class has no scope annotation in Hilt?"
  **Answer:** "It is unscoped. Hilt creates a fresh new instance every time that dependency is requested anywhere in the graph."

- **Interviewer:** "Can an `@ActivityScoped` dependency be injected into a `@ViewModelScoped` class?"
  **Answer:** "No. A longer-lived component (`ViewModelComponent`, which survives rotation) cannot hold a reference to a shorter-lived component (`ActivityComponent`, which dies on rotation), as this would leak the destroyed Activity."
