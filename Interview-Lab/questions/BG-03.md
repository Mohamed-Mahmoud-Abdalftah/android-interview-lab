# BG-03

## Original interview question

Compare OneTimeWorkRequest and PeriodicWorkRequest.

## What the interviewer evaluates

Compare one-off and periodic requests and explain minimum/flexible intervals.

## Concept and technical explanation

OneTimeWorkRequest and PeriodicWorkRequest represent the two foundational request modalities in WorkManager, differing fundamentally in execution lifecycle, scheduling guarantees, and platform constraints. OneTimeWorkRequest runs exactly once per lifecycle, supports sequential and parallel work chaining via beginWith().then(), allows initial delays, and can be configured as Expedited Work for immediate priority execution. In contrast, PeriodicWorkRequest executes recurringly at defined intervals. To preserve battery life and prevent resource exhaustion, the Android platform enforces a strict minimum repeat interval of 15 minutes (MIN_PERIODIC_INTERVAL_MILLIS). Periodic work cannot be chained, cannot execute as expedited work, and supports a flex interval that defines an execution window [repeatInterval - flexInterval, repeatInterval] allowing the OS to batch work during battery-efficient radio wakeups.

## Practical walkthrough (English)

Comparing OneTimeWorkRequest chaining with PeriodicWorkRequest scheduling:
```kotlin
// 1. OneTimeWorkRequest: Chained execution with initial delay
val compressRequest = OneTimeWorkRequestBuilder<CompressImageWorker>()
    .setInputData(workDataOf("image_id" to 101))
    .build()

val uploadRequest = OneTimeWorkRequestBuilder<UploadImageWorker>()
    .setConstraints(Constraints.Builder().setRequiredNetworkType(NetworkType.CONNECTED).build())
    .build()

// Chaining: Compress first, then upload
WorkManager.getInstance(context)
    .beginWith(compressRequest)
    .then(uploadRequest)
    .enqueue()

// 2. PeriodicWorkRequest: Recurring background sync with Flex window
// Runs every 1 hour, but flexibly allowed to execute in the last 15 minutes of that hour
val periodicSyncRequest = PeriodicWorkRequestBuilder<SyncCatalogWorker>(
    repeatInterval = 1, repeatIntervalTimeUnit = TimeUnit.HOURS,
    flexTimeInterval = 15, flexTimeIntervalUnit = TimeUnit.MINUTES
).setConstraints(
    Constraints.Builder().setRequiresBatteryNotLow(true).build()
).build()

WorkManager.getInstance(context).enqueueUniquePeriodicWork(
    "catalog_sync",
    ExistingPeriodicWorkPolicy.UPDATE,
    periodicSyncRequest
)
```

## Explanation in Arabic

مقارنة متعمقة بين `OneTimeWorkRequest` و `PeriodicWorkRequest` في WorkManager:

1. `OneTimeWorkRequest` (طلب التنفيذ لمرة واحدة):
   - **كيف يعمل**: يمثل مهمة تنفذ مرة واحدة فقط (Single Execution). يمكن إعادة محاولتها تلقائياً عند الفشل عبر `Result.retry()`.
   - **أفضل استخدام**: العمليات المرتبطة بحدث محدد: رفع صورة معينة، مزامنة تعديل قام به المستخدم، أو ضغط ملف تم إنشاؤه للتو.
   - **الميزات الخاصة**: يدعم السلاسل والاعتماديات المعقدة (Chaining via `beginWith(...).then(...)`)، ويدعم التنفيذ المعجل السريع (Expedited Work).

2. `PeriodicWorkRequest` (طلب التنفيذ الدوري المستمر):
   - **كيف يعمل**: يمثل مهمة تتكرر باستمرار على فترات زمنية محددة.
   - **الحدود الصارمة في نظام أندرويد**:
     * **الحد الأدنى للفترة هو 15 دقيقة (Minimum 15-minute interval)**: إذا كتبت `PeriodicWorkRequestBuilder(5, TimeUnit.MINUTES)`، سيقوم WorkManager تلقائياً بفرض حد الـ 15 دقيقة لحماية بطارية الجهاز!
     * **المرونة الزمنية (Flex Interval)**: يدعم تحديد نافذة مرنة (Flex Window - الحد الأدنى 5 دقائق)، مثل: 'شغل المهمة كل ساعتين، ولكن اسمح بتشغيلها في آخر 15 دقيقة من الساعتين عند توفر Wi-Fi'.
   - **أفضل استخدام**: المهام الدورية غير العاجلة: مسح الكاش القديم كل 24 ساعة، أو مزامنة التفضيلات كل 6 ساعات.
   - **قيود**: `PeriodicWorkRequest` **لا يدعم Chaining** ولا يدعم Expedited Work.

## Practical walkthrough

المقارنة البرمجية بين بناء OneTimeWorkRequest و PeriodicWorkRequest:
```kotlin
// 1. OneTimeWorkRequest: يدعم السلاسل، والتنفيذ المعجل، وإعادة المحاولة:
val compressWork = OneTimeWorkRequestBuilder<CompressImageWorker>().build()
val uploadWork = OneTimeWorkRequestBuilder<UploadImageWorker>().build()

// تشغيل متسلسل (Chaining): ضغط الصورة أولاً ثم رفعها:
WorkManager.getInstance(context)
    .beginWith(compressWork)
    .then(uploadWork)
    .enqueue()

// 2. PeriodicWorkRequest: تكرار دوري مع نافذة مرنة (Flex Interval):
val dailyCleanupRequest = PeriodicWorkRequestBuilder<CleanupCacheWorker>(
    repeatInterval = 24, repeatIntervalTimeUnit = TimeUnit.HOURS,
    flexTimeInterval = 2, flexTimeIntervalUnit = TimeUnit.HOURS // تشغيل مرن في آخر ساعتين
).setConstraints(
    Constraints.Builder()
        .setRequiresCharging(true) // لا يعمل إلا عند توصيل الهاتف بالشاحن ليلاً
        .setRequiresDeviceIdle(true) // والهاتف غير مستخدم
        .build()
).build()

WorkManager.getInstance(context).enqueueUniquePeriodicWork(
    "daily_cache_cleanup",
    ExistingPeriodicWorkPolicy.KEEP,
    dailyCleanupRequest
)
```

## Why it matters and how it works

Periodic work recurs while scheduled and can have constraints; its next run depends on system policy and previous attempts. One-time work can be chained or enqueued uniquely. For immediate user-initiated work, expedited options exist with quotas/fallback behavior. Persist actual sync cursor and last-success separately.

## Worked example

Android illustration; `DailySyncWorker` is app-defined and constraints/dependencies are configured in production.

```kotlin
import androidx.work.PeriodicWorkRequestBuilder
import java.util.concurrent.TimeUnit

val periodicSync = PeriodicWorkRequestBuilder<DailySyncWorker>(
    24, TimeUnit.HOURS,
).build()
// WorkManager scheduling is flexible, not a wall-clock alarm.
```

## Trade-offs and decision criteria

One-time work is easier to reason about for a queued operation; periodic work reduces manual rescheduling for maintenance but cannot promise an exact clock time. Server push or user-open refresh may complement periodic sync.

## Failure modes

Using periodic work for a 9:00 AM medication alarm risks delay. Running a one-time worker then manually rescheduling it without durable state can duplicate schedules. Assuming a period is an SLA ignores Doze and constraints.

## Production perspective

A news app uses periodic work for best-effort daily prefetch plus on-open refresh. A pending upload uses one-time unique work. A user-facing exact reminder uses alarm APIs under platform permission/power rules.

## Interview answer — short

OneTimeWorkRequest executes once, supports chaining through beginWith and then, allows initial execution delays, and supports expedited priority execution. PeriodicWorkRequest executes on a recurring schedule with a mandatory platform minimum interval of 15 minutes. It cannot be chained or run as expedited work, but supports a flex interval that allows the operating system to batch execution windows for battery optimization.

## Interview answer — structured

WorkManager divides background scheduling into one-time and recurring executions, each engineered for distinct operational requirements.
OneTimeWorkRequest represents single-run tasks. It offers maximum flexibility: requests can be chained sequentially or in parallel graphs using beginWith and then. It supports initial execution delays and can be configured with setExpedited for immediate high-priority processing. When combined with unique work policies like APPEND or REPLACE, it excels at user-initiated actions like photo uploads and database migrations.
In contrast, PeriodicWorkRequest is designed for routine maintenance tasks such as log rotation, cache pruning, and daily data prefetching. The Android operating system enforces a hard minimum interval of 15 minutes to prevent battery drain. Unlike one-time requests, periodic work cannot be chained, and it does not support expedited execution.
A key architectural feature of periodic requests is the flex interval. By defining a flex period—which cannot be less than five minutes—developers grant the system an execution window within each cycle, allowing JobScheduler to batch work with other apps during Doze maintenance windows.

## Interview answer — deep senior

Under the hood, understanding the execution mechanics of PeriodicWorkRequest is critical for avoiding subtle scheduling bugs. Many developers mistakenly believe that specifying a repeat interval of one hour means the worker will execute precisely on the hour mark.
In reality, periodic execution times drift. When a device enters Doze mode, background alarms and JobScheduler triggers are batched into infrequent maintenance windows. If a periodic interval expires while the device is in deep Doze, the task is held until the next window opens.
The flex interval (MIN_PERIODIC_FLEX_MILLIS, which defaults to 5 minutes) formalizes this flexibility. If you configure a repeat interval of 60 minutes with a flex interval of 15 minutes, the operating system is permitted to trigger the worker anywhere between the 45th and 60th minute of each cycle. This allows the OS radio scheduler to bundle your network request alongside other apps that have already powered up the cellular modem, conserving significant battery.
Furthermore, handling unique periodic work requires careful policy selection. With Android Jetpack WorkManager 2.8+, ExistingPeriodicWorkPolicy.UPDATE allows updating constraints or intervals without canceling in-flight workers or resetting execution timers, solving a long-standing issue where ExistingPeriodicWorkPolicy.REPLACE would prematurely reset the repeat cycle.
Staff engineers enforce that clock-critical deadlines (such as taking a dose of medication at precisely 8:00 AM) are never scheduled via PeriodicWorkRequest, delegating them strictly to AlarmManager.

## How to answer in the interview

- **Why:** repeat model must match business need.
- **How:** choose one-time event or inexact periodic refresh.
- **Trade-off:** polling simplicity versus battery and latency.
- **Failure case:** periodic work assumed exact.
- **Production solution:** enqueue urgent durable obligation directly.

## Follow-up questions

- **Interviewer:** "What happens if you set a PeriodicWorkRequest interval to 5 minutes?"
  **Answer:** "WorkManager silently clamps the interval to the 15-minute minimum and logs a warning."

- **Interviewer:** "How do you stop a scheduled PeriodicWorkRequest?"
  **Answer:** "Call `workManager.cancelUniqueWork("unique_work_name")` or `cancelWorkById(uuid)`."
