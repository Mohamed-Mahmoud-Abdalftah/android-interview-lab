# BG-03

## Original interview question

Compare OneTimeWorkRequest and PeriodicWorkRequest.

## What the interviewer evaluates

Compare one-off and periodic requests and explain minimum/flexible intervals.

## Explanation in Arabic

`OneTimeWorkRequest` لمهمة واحدة ممكن تتعاد بعد retry، زي upload pending edit. `PeriodicWorkRequest` للsync الدوري المرن؛ Android ممكن تؤخرها أو تجمعها حسب battery/Doze، ومش timer دقيق. الـminimum interval في WorkManager عادة 15 دقيقة للـperiodic، وده لا يعني أنها هتعمل كل 15 دقيقة بالضبط. للوقت الدقيق الحقيقي نراجع AlarmManager وأهليته.

## Practical walkthrough

OneTime للرفع أو sync محدد مرة مع retries، وPeriodic لفحص دوري غير حساس للوقت مثل refresh. periodic interval له حد أدنى وتوقيت التشغيل يتأثر بالconstraints وDoze؛ مش cron ثانية بثانية. لو بيانات جديدة تصل من server، push أو server event قد يكون أفضل من polling. لعملية payment reversal معلقة، لا تنتظر الدورة القادمة؛ سجّل one-time work وbackend reconciliation.

## Why it matters and how it works

Periodic work recurs while scheduled and can have constraints; its next run depends on system policy and previous attempts. One-time work can be chained or enqueued uniquely. For immediate user-initiated work, expedited options exist with quotas/fallback behavior. Persist actual sync cursor and last-success separately.

## Worked example

Android illustration; `DailySyncWorker` is app-defined and constraints/dependencies are configured in production.

```kotlin
import androidx.work.PeriodicWorkRequestBuilder
import java.util.concurrent.TimeUnit

val periodicSync = PeriodicWorkRequestBuilder<DailySyncWorker>(
    24, TimeUnit.HOURS,
).build()
// WorkManager scheduling is flexible, not a wall-clock alarm.
```

## Trade-offs and decision criteria

One-time work is easier to reason about for a queued operation; periodic work reduces manual rescheduling for maintenance but cannot promise an exact clock time. Server push or user-open refresh may complement periodic sync.

## Failure modes

Using periodic work for a 9:00 AM medication alarm risks delay. Running a one-time worker then manually rescheduling it without durable state can duplicate schedules. Assuming a period is an SLA ignores Doze and constraints.

## Production perspective

A news app uses periodic work for best-effort daily prefetch plus on-open refresh. A pending upload uses one-time unique work. A user-facing exact reminder uses alarm APIs under platform permission/power rules.

## Interview answer — short

“OneTimeWorkRequest is for a single logical job; PeriodicWorkRequest is flexible recurring work. Periodic work has a minimum interval and is not exact. I persist last-success state and choose alarms only for genuine precise reminders.”

## Interview answer — structured

“I choose a one-time request for a specific upload or outbox drain, potentially retried with backoff. PeriodicWorkRequest is for recurring maintenance such as cache refresh, but the OS may delay it because of constraints and power state; its interval is not a clock guarantee. WorkManager’s periodic minimum interval is generally 15 minutes. If a user expects a precise alarm, I assess AlarmManager and exact-alarm eligibility instead. I track last successful sync in my own store so UI does not equate a scheduled run with fresh data.”

## Interview answer — deep senior

“The distinction is logical operation versus recurring policy. A one-time request can still run multiple attempts after retry or process death, so the operation needs an ID and idempotent effect. Periodic work is a persistent recurrence managed by the OS, with a minimum interval and flex/timing uncertainty under Doze and constraints. It should not be used for second-perfect polling or critical deadline notifications. For a news feed I combine periodic best-effort prefetch, push hints and on-open revalidation, with Room as the UI source. I test work under offline and battery restrictions and monitor actual last-success timestamps rather than relying on scheduled times. For example, tapping Upload creates a one-time request with an operation ID; a periodic refresh of noncritical catalog metadata can tolerate the system choosing its execution time. Periodic work has a minimum interval and is not a clock or push channel. If a payment reversal becomes due, I enqueue its obligation immediately instead of hoping the next periodic poll runs soon. I also decide whether a missed cycle should be skipped or whether state should be reconciled from the server. The trade-off is battery and schedule flexibility. Tests should assert the business state after delayed execution, not assume an exact wall-clock callback.”

## How to answer in the interview

- **Why:** repeat model must match business need.
- **How:** choose one-time event or inexact periodic refresh.
- **Trade-off:** polling simplicity versus battery and latency.
- **Failure case:** periodic work assumed exact.
- **Production solution:** enqueue urgent durable obligation directly.
