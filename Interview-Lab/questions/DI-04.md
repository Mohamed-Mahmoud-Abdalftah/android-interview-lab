# DI-04

## Original interview question

What do @Inject, @Module, @Provides, and @Binds do?

## What the interviewer evaluates

- Map each annotation to constructor/member request or graph binding declaration.
- Choose `@Binds` for interface-to-implementation delegation and `@Provides` for constructed/third-party types.
- Mention component installation and scope without conflating binding with object lifetime.

## Explanation in Arabic

شرح مفصل لوظائف التعليقات التوضيحية الأساسية في Dagger و Hilt:
`@Inject`، و `@Module`، و `@Provides`، و `@Binds`:

1. `@Inject` (طلب أو إعلان الحقن):
   - **في الـ Constructor**: يعلم Dagger بكيفية بناء الكائن وما هي التبعيات التي يحتاجها. يتيح لـ Dagger إضافة الكائن إلى شجرة التبعيات تلقائياً دون الحاجة لكتابة كود في Module.
   - **في الـ Fields**: يعلم Dagger بحقن التبعيات في هذه المتغيرات داخل الكلاسات التي ينشئها النظام (مثل `@Inject lateinit var api: Api` في Activity).

2. `@Module` (مستودع تعريفات التبعيات):
   - كلاس أو interface يعلم Dagger بكيفية إنشاء أو ربط كائنات لا تملك وصولاً لتعديل الـ Constructor الخاص بها (مثل كلاسات خارجية من مكتبات كـ Retrofit أو OkHttp أو Room).

3. `@Provides` (دالة بناء الكائنات الحسابية أو الخارجية):
   - دالة داخل `@Module` تحتوي على كود تنفيذي ينشئ ويعيد كائناً معيناً (مثل استدعاء `Retrofit.Builder().build()`).
   - يولد Dagger كود مصنع كامل (`Factory`) لكل دالة `@Provides`.

4. `@Binds` (ربط مجرد لواجهة بتنفيذها - Interface Binding):
   - دالة مجردة (`abstract fun`) داخل `@Module abstract class` تأخذ التنفيذ الفعلي كمعامل وتعيد الـ Interface.
   - **أفضل من `@Provides` للأداء**: لا تولد دالة مصنع منفصلة في الـ Bytecode، بل تقوم بتوجيه Dagger مباشرة إلى الـ Constructor الخاص بالـ Implementation، مما يقلل حجم ملفات الـ DEX ويسرع وقت التجميع.

## Practical walkthrough

المقارنة البرمجية بين `@Provides` و `@Binds` وأماكن استخدام كل منها:
```kotlin
@Module
@InstallIn(SingletonComponent::class)
object NetworkModule {
    // ✅ استخدام @Provides: لأن OkHttpClient كلاس خارجي من مكتبة طرف ثالث:
    @Provides
    @Singleton
    fun provideOkHttpClient(): OkHttpClient {
        return OkHttpClient.Builder()
            .connectTimeout(30, TimeUnit.SECONDS)
            .build()
    }
}

// التنفيذ الفعلي لكلاس الـ Repository ولديه @Inject constructor:
class UserRepositoryImpl @Inject constructor(
    private val api: UserApi
) : UserRepository

@Module
@InstallIn(SingletonComponent::class)
abstract class RepositoryModule {
    // ✅ استخدام @Binds: لربط الـ Interface بالـ Implementation بدون توليد كود مصنع إضافي:
    @Binds
    @Singleton
    abstract fun bindUserRepository(
        impl: UserRepositoryImpl
    ): UserRepository
}
```

## Why it matters and how it works

Dagger resolves a binding graph at compile time. An injectable constructor contributes a binding for its class if all constructor parameters can be resolved. A module contributes provider or delegate bindings. `@Provides` executes a method to construct a value and can depend on other graph bindings through parameters; `@Binds` maps an interface request to a concrete injectable type with less generated boilerplate. Hilt's `@InstallIn` chooses where a module's bindings are visible; scopes determine reuse within that component.

## Worked example

`class OrdersRepositoryImpl @Inject constructor(private val api: OrdersApi) : OrdersRepository` can be paired with `@Binds abstract fun bindOrders(impl: OrdersRepositoryImpl): OrdersRepository` in a module. A separate `@Provides fun provideOrdersApi(retrofit: Retrofit): OrdersApi = retrofit.create(OrdersApi::class.java)` handles a third-party factory call. Both modules need an appropriate `@InstallIn` component, and Retrofit itself must have a binding. This is abbreviated illustrative Kotlin, not a complete compilable module.

### Kotlin / Hilt example

The app owns `Store`/`RealStore`; Retrofit is a configured third-party type. Add the Hilt compiler plugin and runtime dependencies in the Android module.

```kotlin
import dagger.Binds
import dagger.Module
import dagger.Provides
import dagger.hilt.InstallIn
import dagger.hilt.components.SingletonComponent
import javax.inject.Inject
import retrofit2.Retrofit

interface Store { fun name(): String }
class RealStore @Inject constructor() : Store {
    override fun name() = "production"
}

@Module
@InstallIn(SingletonComponent::class)
abstract class StoreBindings {
    @Binds abstract fun bindStore(impl: RealStore): Store
}

@Module
@InstallIn(SingletonComponent::class)
object NetworkModule {
    @Provides fun retrofit(): Retrofit = Retrofit.Builder()
        .baseUrl("https://example.org/")
        .build()
}
```

## Trade-offs and decision criteria

Constructor injection is simplest for owned classes. `@Binds` avoids factory code for a one-to-one abstraction mapping but cannot execute construction logic. `@Provides` supports factories/configuration but can hide work or create a new expensive instance each request unless scoped. A scope saves creation but retains memory and state for its component lifetime. Keep module installation and qualifier choices explicit.

## Failure modes

Missing binding for a transitive constructor parameter fails graph compilation. Two unqualified `OrdersApi` bindings conflict. Installing a ViewModel-specific binding only into SingletonComponent may lengthen its lifetime or use an unavailable UI dependency. A `@Provides` method reads a secret from a bundled file at graph creation. Verify the generated graph through compile/build and review security/configuration at the provider boundary.

## Production perspective

For a multi-backend app, group clients by ownership, create each configured Retrofit/OkHttp pair in app modules, bind repository interfaces to implementations, and qualify ambiguous clients. Unit-test repository behavior separately and run a graph integration compile/test for production and test variants. Keep credentials out of providers and release artifacts.

## Interview answer — short

@Inject requests dependencies on fields or tells Dagger how to construct a class via its constructor. @Module defines a container for dependency bindings. @Provides provides third-party or builder-constructed instances using executable code. @Binds is an abstract method that binds an interface to its concrete implementation with zero bytecode overhead.

## Interview answer — structured

These four annotations form the foundational vocabulary of Dagger and Hilt.

First, with @Inject, serves two purposes. On a constructor, it registers the class into Dagger's dependency graph, telling the compiler how to instantiate it. On a field, it requests member injection from the component (used in Android lifecycle classes). Next, with @Module, marks a class or interface as a provider of dependency definitions for types Dagger cannot construct via constructor injection (e.g. Interfaces, abstract classes, third-party libraries, system services).
Additionally, @Provides is used on concrete functions inside a module to instantiate objects requiring configuration or third-party builders (e.g. `Retrofit`, `RoomDatabase`). Dagger generates an explicit `Factory` class for every `@Provides` method. Finally, @Binds is used on abstract functions to bind an interface to a concrete implementation that already has an `@Inject` constructor. It has zero runtime or bytecode overhead because Dagger delegates directly to the implementation's factory without creating intermediary factory classes.


## Interview answer — deep senior

Under the hood, understanding the DEX impact between `@Provides` and `@Binds` is a classic senior distinction:

When you write a `@Provides` method:
```kotlin
@Provides fun provideRepo(impl: UserRepoImpl): UserRepo = impl
```
Dagger generates a dedicated class `NetworkModule_ProvideRepoFactory.java` implementing `Factory<UserRepo>`. This adds extra method counts, field allocations, and class loading overhead during app startup.

When you write `@Binds`:
```kotlin
@Binds abstract fun bindRepo(impl: UserRepoImpl): UserRepo
```
Dagger generates **zero extra factory classes**. It simply aliases `UserRepo` directly to `UserRepoImpl_Factory` in its internal graph index. This reduces APK DEX size, accelerates compile times, and eliminates unnecessary bridge method execution.


## How to answer in the interview

- **Why:** graph needs instructions for owned, interface, and external types.
- **How:** Inject constructor, Binds mapping, Provides builder, InstallIn component.
- **Trade-off:** Provides allows logic but adds code.
- **Failure case:** duplicate unqualified Retrofit binding.
- **Production solution:** compile each variant and verify endpoint wiring.

## Follow-up questions

- **Interviewer:** "Can `@Binds` and `@Provides` coexist in the same module?"
  **Answer:** "Yes, but only if the module is declared as an abstract class or interface, and the `@Provides` methods are placed inside a nested companion object or marked with `@JvmStatic`."

- **Interviewer:** "What happens if a type has both an `@Inject` constructor and a `@Provides` method?"
  **Answer:** "Dagger will fail with a compile-time duplicate binding error unless one of them is disambiguated with a Qualifier annotation."
