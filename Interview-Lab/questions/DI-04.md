# DI-04

## Original interview question

What do @Inject, @Module, @Provides, and @Binds do?

## What the interviewer evaluates

- Map each annotation to constructor/member request or graph binding declaration.
- Choose `@Binds` for interface-to-implementation delegation and `@Provides` for constructed/third-party types.
- Mention component installation and scope without conflating binding with object lifetime.

## Explanation in Arabic

`@Inject` على constructor يعلّم Dagger/Hilt كيف يبني كلاس تملكه، وعلى field في Android entry point يطلب ملأه بعد إنشاء المكوّن. `@Module` يجمع قواعد توفير لا تقدر تعبر عنها بالconstructor وحده. `@Provides` دالة تنشئ object، مناسبة لـRetrofit أو Room أو SDK خارجي لا تملك constructor بتاعه. `@Binds` دالة abstract تربط interface بـimplementation قابل للحقن، من غير كود إنشاء يدوي. في Hilt تضيف `@InstallIn` لتحديد component اللي تملك binding؛ `@Singleton` أو غيره يحدد مشاركة instance، بينما وجود `@Provides` وحده لا يجعله singleton.

### Practical walkthrough in Egyptian Arabic

مثال repository interface: `@Inject constructor` يعمل `RealRepository` لأن الكلاس بتاعك؛ `@Binds` تربطه بالـinterface من غير body. Retrofit طرف ثالث يحتاج `@Provides` لأنك لازم تبنيه بـbuilder وbase URL. `@Module` تجمع bindings و`@InstallIn` تحدد component اللي يشوفها. لو نسيت qualifier عند نوعين Retrofit، Dagger تشتكي duplicate binding بدل ما تختار عشوائي.

## Why it matters and how it works

Dagger resolves a binding graph at compile time. An injectable constructor contributes a binding for its class if all constructor parameters can be resolved. A module contributes provider or delegate bindings. `@Provides` executes a method to construct a value and can depend on other graph bindings through parameters; `@Binds` maps an interface request to a concrete injectable type with less generated boilerplate. Hilt's `@InstallIn` chooses where a module's bindings are visible; scopes determine reuse within that component.

## Worked example

`class OrdersRepositoryImpl @Inject constructor(private val api: OrdersApi) : OrdersRepository` can be paired with `@Binds abstract fun bindOrders(impl: OrdersRepositoryImpl): OrdersRepository` in a module. A separate `@Provides fun provideOrdersApi(retrofit: Retrofit): OrdersApi = retrofit.create(OrdersApi::class.java)` handles a third-party factory call. Both modules need an appropriate `@InstallIn` component, and Retrofit itself must have a binding. This is abbreviated illustrative Kotlin, not a complete compilable module.

### Kotlin / Hilt example

The app owns `Store`/`RealStore`; Retrofit is a configured third-party type. Add the Hilt compiler plugin and runtime dependencies in the Android module.

```kotlin
import dagger.Binds
import dagger.Module
import dagger.Provides
import dagger.hilt.InstallIn
import dagger.hilt.components.SingletonComponent
import javax.inject.Inject
import retrofit2.Retrofit

interface Store { fun name(): String }
class RealStore @Inject constructor() : Store {
    override fun name() = "production"
}

@Module
@InstallIn(SingletonComponent::class)
abstract class StoreBindings {
    @Binds abstract fun bindStore(impl: RealStore): Store
}

@Module
@InstallIn(SingletonComponent::class)
object NetworkModule {
    @Provides fun retrofit(): Retrofit = Retrofit.Builder()
        .baseUrl("https://example.org/")
        .build()
}
```

## Trade-offs and decision criteria

Constructor injection is simplest for owned classes. `@Binds` avoids factory code for a one-to-one abstraction mapping but cannot execute construction logic. `@Provides` supports factories/configuration but can hide work or create a new expensive instance each request unless scoped. A scope saves creation but retains memory and state for its component lifetime. Keep module installation and qualifier choices explicit.

## Failure modes

Missing binding for a transitive constructor parameter fails graph compilation. Two unqualified `OrdersApi` bindings conflict. Installing a ViewModel-specific binding only into SingletonComponent may lengthen its lifetime or use an unavailable UI dependency. A `@Provides` method reads a secret from a bundled file at graph creation. Verify the generated graph through compile/build and review security/configuration at the provider boundary.

## Production perspective

For a multi-backend app, group clients by ownership, create each configured Retrofit/OkHttp pair in app modules, bind repository interfaces to implementations, and qualify ambiguous clients. Unit-test repository behavior separately and run a graph integration compile/test for production and test variants. Keep credentials out of providers and release artifacts.

## Interview answer — short

“`@Inject` marks a constructible class or injection point. `@Module` groups bindings; `@Provides` builds a value with code; `@Binds` maps an interface to an injectable implementation. `@InstallIn` and scopes determine Hilt visibility and lifetime.”

## Interview answer — structured

“I use `@Inject` on an owned class's constructor when Dagger can construct it from other bindings. If the graph needs an interface mapping or a third-party factory, I put that in a `@Module`. A `@Binds` abstract method delegates an interface to a concrete injectable implementation; a `@Provides` method executes code, such as `retrofit.create(Api::class.java)`. Hilt modules also need `@InstallIn` for component visibility. None of these annotations automatically means a singleton; scope annotations control reuse. I review qualifier and component choices because missing or ambiguous bindings fail compilation, while a wrong scope can be a runtime ownership defect.”

## Interview answer — deep senior

“These annotations describe different edges of the dependency graph. `@Inject` on a constructor tells Dagger how to build an owned type and makes its required parameters explicit; field injection is reserved for cases like platform-instantiated entry points. `@Module` contains binding rules that constructors cannot express. `@Binds` is a declaration that an interface request should use an injectable implementation, so it is ideal for a simple port-to-adapter mapping. `@Provides` is executable creation logic for third-party classes, builders, runtime configuration, or values requiring a factory call. In Hilt I install each module into the component where that binding belongs, then add a matching scope only if instance sharing is required. I check missing transitive dependencies, duplicate unqualified bindings, wrong release endpoints, and Activity references leaking through long-lived providers. Compile-time graph validation catches missing edges, but integration tests and scope review catch semantically wrong ones. In a release build, I would verify that the Retrofit provider receives the production base URL and that a `Store` request resolves to `RealStore`. The compile-time graph catches a missing binding or duplicate unqualified Retrofit binding; it cannot tell whether a valid URL is the wrong environment. That distinction is why I pair a graph build with a targeted variant assertion rather than treating successful compilation as deployment evidence.”

## How to answer in the interview

- **Why:** graph needs instructions for owned, interface, and external types.
- **How:** Inject constructor, Binds mapping, Provides builder, InstallIn component.
- **Trade-off:** Provides allows logic but adds code.
- **Failure case:** duplicate unqualified Retrofit binding.
- **Production solution:** compile each variant and verify endpoint wiring.

## Deep-dive talking points

Discuss binding graph edges, constructor versus provider method, interface delegation, install location, qualifier conflicts, and scope semantics.

## Follow-up questions

- Why can an interface not usually use constructor `@Inject` directly? **Answer:** it has no constructor; the graph needs a binding to a concrete implementation, often via `@Binds`.
- When is `@Provides` preferable to `@Binds`? **Answer:** when construction requires executable factory/configuration code or the type is third-party.
- Does an unscoped provider return the same instance each time? **Answer:** not by default; a matching scope is needed for component-level reuse.

## Self-check rubric

Explain four annotations, choose `@Binds` versus `@Provides`, locate a module, and identify a missing/ambiguous binding.
