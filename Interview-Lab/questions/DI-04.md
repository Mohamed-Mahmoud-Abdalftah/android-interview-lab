# DI-04

## Original interview question

What do @Inject, @Module, @Provides, and @Binds do?

## What the interviewer evaluates

- Map constructor injection, member injection, modules and binding methods precisely.
- Choose `@Binds` for delegation and `@Provides` for construction code.
- Explain Hilt installation, scope, qualifier and verification limits without performance guarantees.

## Concept and technical explanation

`@Inject` on a constructor tells Dagger how to construct an owned type and resolve its constructor parameters. On a field or method it requests members injection into an existing object reached through an entry point. `@Module` groups binding declarations. A common `@Binds` form is an abstract method taking an available implementation and returning the requested interface or supertype; it has no construction body. `@Provides` is a method with a body that constructs or configures a value and may itself request dependencies as parameters. In Hilt, `@InstallIn` selects the component receiving a module. A scope controls reuse within the component lifetime, and a qualifier distinguishes binding keys. These annotations do not prove the runtime configuration or business behavior is correct.

## Practical walkthrough (English)

An owned repository implementation can use constructor injection. An interface request delegates to it with `@Binds`; a third-party API created by Retrofit uses `@Provides`:
```kotlin
interface OrdersRepository { fun count(): Int }
class SqlOrdersRepository @Inject constructor(
    private val dao: OrdersDao
) : OrdersRepository { /* implementation */ }

@Module
@InstallIn(SingletonComponent::class)
abstract class OrdersBindings {
    @Binds abstract fun bindOrders(
        impl: SqlOrdersRepository
    ): OrdersRepository
}

@Module
@InstallIn(SingletonComponent::class)
object ApiModule {
    @Provides fun provideOrdersApi(retrofit: Retrofit): OrdersApi =
        retrofit.create(OrdersApi::class.java)
}
```
`OrdersDao` and `Retrofit` still need bindings. This is illustrative Android code, not a compiled Hilt graph in this repository.

## Explanation in Arabic

`@Inject` على Constructor لكلاس نملكه تعرّف Dagger إزاي تنشئه وتجيب Parameters بتاعته من الـ Graph. وعلى Field داخل Entry Point مدعوم تطلب Member Injection؛ ده لا يعني إن Dagger تقدر تنشئ الكلاس نفسه من غير Constructor أو Component مناسب.

`@Module` تجمع Binding Methods. `@Provides` دالة لها Body ترجع Object، مفيدة لكلاس خارجي أو Builder أو إعداد يتطلب كود؛ Parameters بتاعتها هي Dependencies برضه. `@Binds` غالبًا دالة Abstract ببارامتر Implementation واحد وناتجها Interface أو Supertype؛ بتعلن إن الطلب ده يروح للـ Implementation القابل للإنشاء، من غير Body. مش بديل عن `@Provides` لو لازم تنفّذ Builder أو قرار Runtime.

في Hilt تضيف `@InstallIn` علشان تحدد Component اللي فيها الـ Module. `@Singleton` أو Scope مناسبة هي اللي بتحدد إعادة استخدام الـ Instance خلال عمر الـ Component؛ أي Annotation من الأربع وحدها مش معناها Singleton. Qualifier جزء من Binding Key عند وجود أكثر من نسخة من نفس النوع. الـ Compiler يفحص الـ Graph المطلوبة، لكنه مش اختبار لصحة Config أو Backend.

## Why it matters and how it works

The annotations describe graph construction, delegation and injection requests. The component and scope decide availability and reuse; a qualifier changes binding identity. A build can validate the requested graph while an incorrect endpoint or state lifetime remains a runtime problem.

## Worked example

An `OrdersRepository` interface delegates to a constructor-injectable `SqlOrdersRepository` through `@Binds`. `OrdersApi` comes from `retrofit.create(...)`, so `@Provides` expresses the call. A missing binding for `Retrofit` is not fixed by adding another repository binding; supply or trace that dependency. A successful graph build still does not validate the base URL.

### Kotlin / Hilt example

The app owns `Store`/`RealStore`; Retrofit is a configured third-party type. Add the Hilt compiler plugin and runtime dependencies in the Android module.

```kotlin
import dagger.Binds
import dagger.Module
import dagger.Provides
import dagger.hilt.InstallIn
import dagger.hilt.components.SingletonComponent
import javax.inject.Inject
import retrofit2.Retrofit

interface Store { fun name(): String }
class RealStore @Inject constructor() : Store {
    override fun name() = "production"
}

@Module
@InstallIn(SingletonComponent::class)
abstract class StoreBindings {
    @Binds abstract fun bindStore(impl: RealStore): Store
}

@Module
@InstallIn(SingletonComponent::class)
object NetworkModule {
    @Provides fun retrofit(): Retrofit = Retrofit.Builder()
        .baseUrl("https://example.org/")
        .build()
}
```

## Trade-offs and decision criteria

Prefer constructor injection for owned classes. Use `@Binds` for simple type delegation when the implementation is available, and `@Provides` when code must construct or configure the object. `@Provides` deserves code review and behavioral tests. Scoping reuses an instance but retains it for a component lifetime. Avoid blanket DEX, factory-count and runtime-speed promises.

## Failure modes

An abstract `@Binds` declaration points to an unavailable implementation. A `@Provides` method requests an unbound `Retrofit`. Two unqualified bindings have the same key. A session object is scoped to the application and outlives logout. A provider compiles with the wrong endpoint or an embedded secret.

## Production perspective

Keep binding ownership clear and build supported variants. Review provider configuration, qualifiers and component installation. Test repository behavior separately, and run an Android injection smoke path where graph integration matters. A JVM policy test is not proof of the Hilt-generated Android graph.

## Interview answer — short

`@Inject` on a constructor supplies a construction path; on a field it requests members injection. `@Module` groups binding methods. `@Binds` usually delegates an interface request to an available implementation through an abstract method. `@Provides` runs a method body to construct or configure a value, such as a third-party client. In Hilt, `@InstallIn` chooses the component; scope and qualifier determine reuse and binding identity. None of the four annotations alone makes an object a singleton or validates its endpoint.

## Interview answer — structured

I map each annotation to one role. `@Inject constructor` tells Dagger how to create an owned class when its parameters are available. `@Inject` on a field requests injection into an object reached through an entry point; it does not let Dagger create every Android class. `@Module` contains binding declarations. For an `OrdersRepository` interface with a constructor-injected implementation, a common `@Binds` method delegates the interface to that implementation. For `retrofit.create(OrdersApi::class.java)`, `@Provides` is appropriate because there is construction code. With Hilt, I install modules in the component that needs them and add a scope only when shared identity should match that component lifetime. I use qualifiers if multiple clients share a type. Compilation can flag missing or duplicate graph bindings, but I separately test endpoint configuration and repository behavior.

## Interview answer — deep senior

The key distinction is a binding declaration versus an injection request. `@Inject constructor` supplies a construction path for an owned class; each parameter becomes a dependency required from the graph. `@Inject` on a field or method requests members injection into an existing object, such as an Android Activity reached through an appropriate Hilt entry point. It does not make Dagger construct every framework object. `@Module` collects declarations for interfaces, third-party types and configuration that constructor injection cannot express cleanly.

The common one-parameter `@Binds` method is abstract: its parameter is an implementation already available to the graph, and its return type is the requested interface or supertype. There is no method body to construct a value. Dagger documentation prefers it for simple delegation because the module does not need runtime class loading in that case; that does not justify a universal factory-count, DEX-size or latency guarantee. `@Provides` has executable construction or configuration code and can request its own parameters from the graph. A Retrofit API obtained through `retrofit.create(...)` fits this role. Kotlin can combine abstract `@Binds` and companion-object `@Provides` in one appropriately shaped module, or separate them for clarity.

In Hilt, a module also needs `@InstallIn` for the component that should see its bindings. A scope such as `@Singleton` governs reuse within its matching component lifetime; none of the four named annotations supplies that lifetime alone. A qualifier is part of a binding key when two clients share a type. If compilation reports a missing `Retrofit` binding, adding a second repository delegation is the wrong fix: trace the requested graph path and component visibility. If the graph compiles with a wrong base URL, the compiler cannot discover that. I build supported variants, test the provider configuration and business adapter behavior, and exercise important Hilt entry paths on Android. This separates graph validity from runtime correctness.

## How to answer in the interview

- Assign a distinct role to each of the four annotations.
- Show interface delegation versus a third-party builder or factory.
- Add Hilt component installation, scope and qualifier.
- Separate compile-time graph checks from configuration tests.

## Deep-dive talking points

Constructor and members injection; binding methods; abstract delegation; provider configuration; `@InstallIn`; component scope; qualifier keys; missing and duplicate bindings; graph versus behavior validation.

## Follow-up questions

- **Interviewer:** "Can `@Binds` and `@Provides` share a module?"
  **Answer:** "Yes with an appropriate Kotlin module shape, such as an interface containing `@Binds` and a companion object containing `@Provides`; separate modules are also clear."

- **Interviewer:** "Is `@Binds` guaranteed to have zero factory or runtime cost?"
  **Answer:** "No universal performance number follows. Dagger prefers it for simple delegation and can avoid loading a module instance; measure any material size or runtime claim."

- **Interviewer:** "Why does a graph with `OrdersApi` still fail?"
  **Answer:** "The provider may require an unbound `Retrofit`, or the binding may be invisible in that component or variant. After compilation, test the endpoint configuration too."
