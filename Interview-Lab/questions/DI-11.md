# DI-11

## Original interview question

How do you inject multiple implementations of the same contract?

## What the interviewer evaluates

- Distinguish compile-time selection with qualifiers from runtime strategy selection.
- Explain multibindings for a set/map of implementations and test/variant replacement.
- Avoid ambiguous unqualified bindings or leaking environment choice into every consumer.

## Explanation in Arabic

كيفية حقن تطبيقات متعددة لنفس الواجهة (Multiple Implementations of the Same Contract) في Hilt:

1. الحالات الشائعة:
   - واجهة `AnalyticsTracker` ولها تطبيقان: `FirebaseAnalyticsTracker` و `MixpanelAnalyticsTracker`.
   - واجهة `ImageLoader` ولها: `LocalCacheImageLoader` و `RemoteImageLoader`.

2. الحل الأول: استخدام الـ Qualifiers (للاختيار الصريح عند الحقن):
   - ننشئ تعليقات توضيحية مخصصة مثل `@Firebase` و `@Mixpanel`.
   - نقوم بربط كل تطبيق باستخدام التعليق الخاص به.
   - في الكلاس المستهلك، نطلب التطبيق المحدد: `@Firebase private val tracker: AnalyticsTracker`.

3. الحل الثاني: استخدام الـ Multibindings (`@IntoSet` أو `@IntoMap`):
   - إذا أردنا حقن جميع التطبيقات معاً في كائن مجمع (Composite Pattern):
   - نستخدم `@IntoSet` لربط كل تطبيق داخل `Set<AnalyticsTracker>`.
   - نقوم بحقن `Set<AnalyticsTracker>` داخل `CompositeAnalyticsTracker` الذي يقوم بالمرور على جميع المتعقبات وإرسال الحدث إليها جميعاً.
   - الميزة: إضافة أي Tracker جديد لا تتطلب تعديل الكلاس المجمع نهائياً (Open/Closed Principle).

## Practical walkthrough

تطبيق Multibindings لحقن مجموعة من التطبيقات لنفس العقد:
```kotlin
interface AnalyticsTracker {
    fun logEvent(name: String)
}

@Module
@InstallIn(SingletonComponent::class)
abstract class AnalyticsModule {
    @Binds @IntoSet
    abstract fun bindFirebaseTracker(impl: FirebaseTracker): AnalyticsTracker

    @Binds @IntoSet
    abstract fun bindMixpanelTracker(impl: MixpanelTracker): AnalyticsTracker
}

// الكلاس المجمع (Composite Pattern) يستقبل المجموعة كاملة تلقائياً عبر Hilt:
@Singleton
class CompositeAnalyticsTracker @Inject constructor(
    private val trackers: Set<@JvmSuppressWildcards AnalyticsTracker>
) : AnalyticsTracker {
    override fun logEvent(name: String) {
        trackers.forEach { it.logEvent(name) }
    }
}
```

## Why it matters and how it works

A DI graph resolves bindings by type plus qualifier. Multiple bindings for the same unqualified key conflict. Qualifiers select a known binding at injection time. Multibindings aggregate contributions and allow a registry of handlers. A runtime decision needs a separate application abstraction because Hilt's compiled graph is not a dynamic per-request switch; that abstraction can receive qualified implementations and choose safely.

## Worked example

A checkout router receives `@CardGateway CardGateway` and `@WalletGateway WalletGateway`, then chooses by the validated payment method. A notification dispatcher can receive a map of channel handlers contributed by feature modules. The card gateway must never be replaced by a sandbox instance in release merely because a Boolean flag is stale; variant wiring and server capability checks decide availability. This is an architecture example, not compiled Kotlin.

## Trade-offs and decision criteria

Qualifiers are simple and explicit when consumers know the desired implementation. A router isolates a runtime choice and its fallback/error policy. A multibinding registry supports extensible plugins but adds key collisions and ordering concerns. Separate wrapper interfaces may convey different capabilities better than one broad contract. Keep payment/security policy in domain logic rather than scattered injection annotations.

## Failure modes

Two unqualified implementations cause graph compilation failure. A test replaces only one qualified binding and still calls the real network. A map key collision silently changes dispatch semantics or fails build. A runtime router selects a sandbox gateway in production. Test every supported method, unknown method, and release variant; log safe selection metadata without credentials.

## Production perspective

Define a stable gateway contract and explicit method registry with allowlisted methods. Use qualifiers for infrastructure instances, a domain router for runtime selection, and multibindings only when extensibility justifies them. Ensure each implementation is independently tested, then run integrated release configuration tests and transaction idempotency checks.

## Interview answer — short

To inject multiple implementations of the same contract, use Qualifiers (@Qualifier) if consumers need to choose a specific implementation explicitly at compile-time. Use Multibindings (@IntoSet or @IntoMap) if you want to assemble all implementations into a collection or map, ideal for plugins and composite dispatchers.

## Interview answer — structured

Depending on whether the implementations should be selected individually or aggregated together, Dagger provides two primary patterns:

1. **Disambiguation via Qualifiers**: When different consumers require specific implementations (e.g. an in-memory test cache vs. an encrypted disk cache), annotate each binding and injection site with a dedicated `@Qualifier` (e.g. `@MemoryCache` and `@DiskCache`).

2. **Aggregation via Multibindings (`@IntoSet` / `@IntoMap`)**: When you need to collect all implementations into an extensible system (e.g. analytics dispatchers, health checkers, or payment processors). Each module registers its implementation using `@Binds @IntoSet`. The aggregator class injects `Set<@JvmSuppressWildcards MyContract>`, iterating over all providers without knowing them individually.

This adheres strictly to the Open/Closed Principle: new feature modules can contribute new implementations to the set without modifying any existing module code.

## Interview answer — deep senior

When using Dagger Multibindings in Kotlin, you must be mindful of Java generics wildcard variance.

By default, Kotlin generates wildcard generic types like `Set<? extends AnalyticsTracker>` in Java bytecode. Dagger treats `Set<AnalyticsTracker>` and `Set<? extends AnalyticsTracker>` as completely distinct binding keys, causing a confusing `[Dagger/MissingBinding]` error at compile time.

To fix this, always annotate the injected collection parameter with `@JvmSuppressWildcards`: e.g. `Set<@JvmSuppressWildcards AnalyticsTracker>`. This forces the Kotlin compiler to emit the raw invariant type `Set<AnalyticsTracker>` in bytecode, allowing Dagger's multibinding graph to resolve seamlessly.

## How to answer in the interview

- **Why:** one contract can have distinct business implementations.
- **How:** qualifiers for fixed choice, factory/map for runtime choice.
- **Trade-off:** map flexibility versus explicit constructor requirement.
- **Failure case:** unsupported payment method falls through.
- **Production solution:** variant graph and selection tests.

## Follow-up questions

- **Interviewer:** "What is the purpose of `@IntoMap` in Dagger?"
  **Answer:** "It allows binding implementations into a `Map<K, V>` using a custom `@MapKey` annotation (e.g. mapping an enum or string key to an implementation strategy)."

- **Interviewer:** "Why is `@JvmSuppressWildcards` needed in Kotlin Dagger multibindings?"
  **Answer:** "To prevent Kotlin from emitting Java wildcard generics (`? extends T`), which causes Dagger to fail to match the invariant collection key."
