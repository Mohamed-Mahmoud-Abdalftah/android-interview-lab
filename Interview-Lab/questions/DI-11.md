# DI-11

## Original interview question

How do you inject multiple implementations of the same contract?

## What the interviewer evaluates

- Distinguish compile-time selection with qualifiers from runtime strategy selection.
- Explain multibindings for a set/map of implementations and test/variant replacement.
- Avoid ambiguous unqualified bindings or leaking environment choice into every consumer.

## Concept and technical explanation

Dagger identifies a binding by type plus an optional qualifier. Use distinct qualifiers when a consumer names one specific implementation at compile time. Use multibindings when independent modules contribute elements to a `Set<T>` or entries to a `Map<K, V>` through `@IntoSet` or `@IntoMap` and a `@MapKey`. Map keys must be unique. A consumer can request `Map<K, V>` or `Map<K, Provider<V>>`; providers are useful when it should avoid constructing unselected values or request values later, but not every consumer needs them. The component must include the contributing modules; multibindings alone do not make an unreferenced feature module part of the app. Apply `@JvmSuppressWildcards` only if Kotlin wildcard projection causes a concrete Dagger key mismatch.

## Practical walkthrough (English)

Differentiating implementations via Qualifiers and Multibindings:
```kotlin
// 1. Differentiating distinct bindings via Custom Qualifiers
@Qualifier
@Retention(AnnotationRetention.BINARY)
annotation class StripeGateway

@Qualifier
@Retention(AnnotationRetention.BINARY)
annotation class PayPalGateway

@Module
@InstallIn(SingletonComponent::class)
abstract class PaymentModule {
    @Binds @StripeGateway
    abstract fun bindStripe(impl: StripePaymentGateway): PaymentGateway

    @Binds @PayPalGateway
    abstract fun bindPayPal(impl: PayPalPaymentGateway): PaymentGateway
}

// 2. Multibindings into a Map for extensible plugin architectures
@MapKey
annotation class PaymentMethodKey(val value: PaymentType)

@Module
@InstallIn(SingletonComponent::class)
abstract class PaymentMapModule {
    @Binds @IntoMap
    @PaymentMethodKey(PaymentType.STRIPE)
    abstract fun bindStripeMap(impl: StripePaymentGateway): PaymentGateway

    @Binds @IntoMap
    @PaymentMethodKey(PaymentType.PAYPAL)
    abstract fun bindPayPalMap(impl: PayPalPaymentGateway): PaymentGateway
}

// Consumer resolves strategy at runtime via injected map of providers
class PaymentProcessor @Inject constructor(
    private val gateways: Map<PaymentType, @JvmSuppressWildcards Provider<PaymentGateway>>
) {
    fun process(type: PaymentType, amount: Long) {
        val gateway = gateways[type]?.get() ?: error("Unsupported gateway: $type")
        gateway.charge(amount)
    }
}
```

## Explanation in Arabic

لو عندك تنفيذين من `PaymentGateway`، القرار الأول هو طريقة الاختيار:
- لو المستهلك عارف وقت البناء إنه عايز Stripe أو PayPal، استخدم `@Qualifier` واضح على الـbinding ونقطة الحقن. لازم نفس الـqualifier يظهر في الطرفين.
- لو فيه مجموعة plugins تُجمع من modules مختلفة، استخدم `@IntoSet` أو `@IntoMap` مع `@MapKey`. مفتاح الخريطة لازم يكون فريد؛ التكرار يطلع خطأ وقت البناء.
- تقدر تحقن `Map<Key, Gateway>` مباشرة، أو `Map<Key, Provider<Gateway>>` لو عايز تأجل الحصول على gateway غير المختار. ده مش ضمان إن كل كائن ثقيل ما اتعملش؛ الـscope والاعتمادات ممكن تكون أنشأته بالفعل.

## Practical walkthrough

في شاشة دفع، لو `CheckoutUseCase` بيستخدم Stripe فقط، اطلب `@StripeGateway PaymentGateway` مباشرة. لو نوع الدفع بييجي من اختيار المستخدم، ساهم بكل gateway في خريطة عبر `@IntoMap` و`@PaymentMethodKey`، ثم افحص وجود المفتاح قبل `charge`.

استخدم `Map<PaymentType, Provider<PaymentGateway>>` لما تجنب إنشاء الخيارات غير المستخدمة يفيدك، لكن قيّم scope الخاص بكل gateway: لو `@Singleton` واتطلب قبل كده، الـProvider هيرجع نفس النسخة. وراجع هل modules اللي بتساهم فعلاً متاحة لـHilt في تطبيقك. مثال المصدر يحتاج تعريفات `PaymentType` و`PaymentGateway` والتنفيذات قبل ما يتبني.

## Why it matters and how it works

A DI graph resolves bindings by type plus qualifier. Multiple bindings for the same unqualified key conflict. Qualifiers select a known binding at injection time. Multibindings aggregate contributions and allow a registry of handlers. A runtime decision needs a separate application abstraction because Hilt's compiled graph is not a dynamic per-request switch; that abstraction can receive qualified implementations and choose safely.

## Worked example

A checkout router receives `@CardGateway CardGateway` and `@WalletGateway WalletGateway`, then chooses by the validated payment method. A notification dispatcher can receive a map of channel handlers contributed by feature modules. The card gateway must never be replaced by a sandbox instance in release merely because a Boolean flag is stale; variant wiring and server capability checks decide availability. This is an architecture example, not compiled Kotlin.

## Trade-offs and decision criteria

Qualifiers are simple and explicit when consumers know the desired implementation. A router isolates a runtime choice and its fallback/error policy. A multibinding registry supports extensible plugins but adds key collisions and ordering concerns. Separate wrapper interfaces may convey different capabilities better than one broad contract. Keep payment/security policy in domain logic rather than scattered injection annotations.

## Failure modes

Two unqualified implementations cause graph compilation failure. A test replaces only one qualified binding and still calls the real network. A map key collision silently changes dispatch semantics or fails build. A runtime router selects a sandbox gateway in production. Test every supported method, unknown method, and release variant; log safe selection metadata without credentials.

## Production perspective

Define a stable gateway contract and explicit method registry with allowlisted methods. Use qualifiers for infrastructure instances, a domain router for runtime selection, and multibindings only when extensibility justifies them. Ensure each implementation is independently tested, then run integrated release configuration tests and transaction idempotency checks.

## Interview answer — short

Use qualifiers when an injection site needs one named implementation. Use `@IntoSet` or `@IntoMap` to assemble several contributions from modules in the graph; map keys must be unique. Dagger supports both `Map<K, V>` and `Map<K, Provider<V>>`; providers can defer value retrieval. Add `@JvmSuppressWildcards` only if Kotlin's projected type causes a binding-key mismatch.

## Interview answer — structured

Dagger's binding key includes a type and optional qualifier. If a consumer explicitly needs Stripe rather than PayPal, bind each `PaymentGateway` with a custom qualifier and request the matching qualifier. If selection happens from a runtime key, contribute each implementation with `@IntoMap` and a unique `@MapKey`, then handle unknown keys in the consumer. A set is useful when every contribution should be used, but its iteration order is not a business guarantee.

The consumer can request values directly or providers of values. A provider map can avoid creating an unselected gateway, depending on scopes and other requests; it is not compulsory. Modules must be included in the final Hilt graph. For Kotlin/JVM generics, apply `@JvmSuppressWildcards` to a problematic type use only after a concrete Dagger missing-binding error confirms projection mismatch.

## Interview answer — deep senior

Dagger distinguishes bindings across the graph by a composite key consisting of the requested type and its optional qualifier. Two unqualified bindings for the exact same type conflict immediately at compile time unless they are declared as multibinding contributions to a shared collection. Custom qualifiers make a consumer's explicit choice unambiguous and compile-time safe. `@IntoSet` aggregates independent values into an immutable Set; `@IntoMap` uses an explicit compile-time key, and duplicate map keys cause an immediate compilation error. Keep in mind that Set iteration order is never an architectural or business contract.

A map consumer may request either direct values through `Map<K, V>` or lazy providers through `Map<K, Provider<V>>`. Provider maps allow deferred instantiation and can avoid constructing unselected gateways or expensive services on cold start. They are not mandatory, and their runtime benefit depends on scoping rules and whether another dependency in the graph has already eagerly requested that instance. All contributing feature modules must be reachable in the assembled Hilt graph; annotation processing cannot bind a feature that is excluded from the compilation classpath.

Kotlin/JVM generic variance may introduce a wildcard into a generic injection key, resulting in a confusing Dagger MissingBinding error. If that happens, place `@JvmSuppressWildcards` at the exact type site rather than adding it mechanically everywhere. For a runtime-selected payment gateway strategy, always validate missing keys defensively and never rely on DI multibindings alone for financial authorization decisions.

## How to answer in the interview

- **Fixed choice:** Qualifier on binding and injection site.
- **Collection:** `@IntoSet` or `@IntoMap` with unique map keys.
- **Runtime choice:** Validate requested key, and choose `Map<K,V>` or `Map<K,Provider<V>>` based on creation needs.
- **Kotlin caveat:** Suppress wildcards only for a real generic-key mismatch.
- **Graph boundary:** Contributions exist only when their modules are reachable by the application component.

## Follow-up questions

- **Interviewer:** "When do you choose a qualifier versus a map?"
  **Answer:** "Use a qualifier for a known choice at an injection site. Use a map when several modules contribute keyed strategies and selection happens at runtime."

- **Interviewer:** "Must I inject Map<Key, Provider<Value>>?"
  **Answer:** "No. Dagger supports both Map<Key, Value> and Map<Key, Provider<Value>>. Providers help when I want to defer retrieval of unselected values."

- **Interviewer:** "Is @JvmSuppressWildcards always needed?"
  **Answer:** "Only when Kotlin's generated wildcard changes the injection key and Dagger reports a mismatch; place it on the affected type argument."

- **Interviewer:** "Can two map contributions share a key?"
  **Answer:** "No. Dagger reports duplicate map keys at compile time."
