# DI-11

## Original interview question

How do you inject multiple implementations of the same contract?

## What the interviewer evaluates

- Distinguish compile-time selection with qualifiers from runtime strategy selection.
- Explain multibindings for a set/map of implementations and test/variant replacement.
- Avoid ambiguous unqualified bindings or leaking environment choice into every consumer.

## Concept and technical explanation

Injecting multiple implementations of the same contract is a core architectural requirement when supporting multiple data providers, runtime strategies, or plugin architectures. Dagger and Hilt provide two primary compile-time mechanisms to resolve this: custom qualifiers and multibindings. Custom qualifiers differentiate multiple distinct instances of the same type at compile time by tagging injection sites and provider methods with strongly typed annotations. Multibindings, enabled via @IntoSet, @ElementsIntoSet, and @IntoMap alongside @MapKey, aggregate multiple bindings into a unified collection (such as Set<T> or Map<K, Provider<V>>) without coupling the consumer to concrete subclasses. When selection depends on dynamic runtime state, engineers combine multibindings with a strategy resolver or use assisted factories to instantiate the target variant dynamically.

## Practical walkthrough (English)

Differentiating implementations via Qualifiers and Multibindings:
```kotlin
// 1. Differentiating distinct bindings via Custom Qualifiers
@Qualifier
@Retention(AnnotationRetention.BINARY)
annotation class StripeGateway

@Qualifier
@Retention(AnnotationRetention.BINARY)
annotation class PayPalGateway

@Module
@InstallIn(SingletonComponent::class)
abstract class PaymentModule {
    @Binds @StripeGateway
    abstract fun bindStripe(impl: StripePaymentGateway): PaymentGateway

    @Binds @PayPalGateway
    abstract fun bindPayPal(impl: PayPalPaymentGateway): PaymentGateway
}

// 2. Multibindings into a Map for extensible plugin architectures
@MapKey
annotation class PaymentMethodKey(val value: PaymentType)

@Module
@InstallIn(SingletonComponent::class)
abstract class PaymentMapModule {
    @Binds @IntoMap
    @PaymentMethodKey(PaymentType.STRIPE)
    abstract fun bindStripeMap(impl: StripePaymentGateway): PaymentGateway

    @Binds @IntoMap
    @PaymentMethodKey(PaymentType.PAYPAL)
    abstract fun bindPayPalMap(impl: PayPalPaymentGateway): PaymentGateway
}

// Consumer resolves strategy at runtime via injected map of providers
class PaymentProcessor @Inject constructor(
    private val gateways: Map<PaymentType, @JvmSuppressWildcards Provider<PaymentGateway>>
) {
    fun process(type: PaymentType, amount: Long) {
        val gateway = gateways[type]?.get() ?: error("Unsupported gateway: $type")
        gateway.charge(amount)
    }
}
```

## Practical walkthrough

تطبيق Multibindings لحقن مجموعة من التطبيقات لنفس العقد:
```kotlin
interface AnalyticsTracker {
    fun logEvent(name: String)
}

@Module
@InstallIn(SingletonComponent::class)
abstract class AnalyticsModule {
    @Binds @IntoSet
    abstract fun bindFirebaseTracker(impl: FirebaseTracker): AnalyticsTracker

    @Binds @IntoSet
    abstract fun bindMixpanelTracker(impl: MixpanelTracker): AnalyticsTracker
}

// الكلاس المجمع (Composite Pattern) يستقبل المجموعة كاملة تلقائياً عبر Hilt:
@Singleton
class CompositeAnalyticsTracker @Inject constructor(
    private val trackers: Set<@JvmSuppressWildcards AnalyticsTracker>
) : AnalyticsTracker {
    override fun logEvent(name: String) {
        trackers.forEach { it.logEvent(name) }
    }
}
```

## Why it matters and how it works

A DI graph resolves bindings by type plus qualifier. Multiple bindings for the same unqualified key conflict. Qualifiers select a known binding at injection time. Multibindings aggregate contributions and allow a registry of handlers. A runtime decision needs a separate application abstraction because Hilt's compiled graph is not a dynamic per-request switch; that abstraction can receive qualified implementations and choose safely.

## Worked example

A checkout router receives `@CardGateway CardGateway` and `@WalletGateway WalletGateway`, then chooses by the validated payment method. A notification dispatcher can receive a map of channel handlers contributed by feature modules. The card gateway must never be replaced by a sandbox instance in release merely because a Boolean flag is stale; variant wiring and server capability checks decide availability. This is an architecture example, not compiled Kotlin.

## Trade-offs and decision criteria

Qualifiers are simple and explicit when consumers know the desired implementation. A router isolates a runtime choice and its fallback/error policy. A multibinding registry supports extensible plugins but adds key collisions and ordering concerns. Separate wrapper interfaces may convey different capabilities better than one broad contract. Keep payment/security policy in domain logic rather than scattered injection annotations.

## Failure modes

Two unqualified implementations cause graph compilation failure. A test replaces only one qualified binding and still calls the real network. A map key collision silently changes dispatch semantics or fails build. A runtime router selects a sandbox gateway in production. Test every supported method, unknown method, and release variant; log safe selection metadata without credentials.

## Production perspective

Define a stable gateway contract and explicit method registry with allowlisted methods. Use qualifiers for infrastructure instances, a domain router for runtime selection, and multibindings only when extensibility justifies them. Ensure each implementation is independently tested, then run integrated release configuration tests and transaction idempotency checks.

## Interview answer — short

To inject multiple implementations of the same contract, use custom qualifiers when the specific variant is determined at compile time for distinct injection targets. When consumers need to process an entire collection of implementations or resolve a strategy dynamically, use Dagger multibindings with @IntoSet or @IntoMap. Multibindings allow feature modules to contribute implementations into a centralized set or map without coupling the consumer to concrete implementations.

## Interview answer — structured

Injecting multiple implementations of a single interface requires choosing between compile-time identification and extensible runtime aggregation.
When distinct classes require different implementations of the same contract, custom qualifiers are the standard solution. By annotating provider methods and constructor parameters with distinct qualifiers, Dagger treats each implementation as an independent entry in its graph, ensuring compile-time type safety without naming collisions.
When a consumer needs to inspect, iterate over, or select from all available implementations, Dagger multibindings provide an extensible decoupled mechanism. Using @IntoSet or @IntoMap, individual modules contribute their implementations into an aggregated Set or Map. This is particularly valuable for plugin pipelines, analytics dispatchers, and network interceptor chains.
For runtime strategy selection driven by user input, injecting a Map of Providers allows the consumer to look up the required implementation on demand, instantiating the chosen strategy lazily while keeping the consuming class completely decoupled from concrete factory classes.

## Interview answer — deep senior

Under the hood, Dagger models dependency lookup keys as a composite of the requested type and its qualifier. When multiple implementations of an interface are bound, omitting qualifiers causes a duplicate binding error because the keys collide in the Directed Acyclic Graph.
With multibindings, Dagger synthesizes specialized internal providers such as SetProvider and MapProvider. Each module contributing an @IntoMap or @IntoSet entry does so independently during annotation processing. Dagger aggregates these contributions at the component assembly root without requiring the consumer or the root module to have direct compile-time knowledge of concrete classes, enabling true open-closed modularity.
When injecting maps, senior engineers always inject Map<Key, Provider<Value>> rather than Map<Key, Value>. Injecting Provider wrappers defers the instantiation of concrete implementations until the exact moment they are needed. This prevents eagerly allocating heavy dependencies like payment SDKs or database drivers when only one strategy is executed during a user session.
Staff engineers leverage multibindings across multi-module architectures to build feature-flagged plugin architectures. Feature modules contribute interceptors or health monitors to an application-level set without the base app hardcoding references to individual feature packages, maintaining clean architectural firewalls. By combining this with runtime strategy resolution, teams achieve complete extensibility where adding a new gateway requires creating a new module without modifying existing consumer code.

## How to answer in the interview

- **Why:** one contract can have distinct business implementations.
- **How:** qualifiers for fixed choice, factory/map for runtime choice.
- **Trade-off:** map flexibility versus explicit constructor requirement.
- **Failure case:** unsupported payment method falls through.
- **Production solution:** variant graph and selection tests.

## Follow-up questions

- **Interviewer:** "What is the purpose of `@IntoMap` in Dagger?"
  **Answer:** "It allows binding implementations into a `Map<K, V>` using a custom `@MapKey` annotation (e.g. mapping an enum or string key to an implementation strategy)."

- **Interviewer:** "Why is `@JvmSuppressWildcards` needed in Kotlin Dagger multibindings?"
  **Answer:** "To prevent Kotlin from emitting Java wildcard generics (`? extends T`), which causes Dagger to fail to match the invariant collection key."
