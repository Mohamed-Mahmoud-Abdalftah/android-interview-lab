# DI-11

## Original interview question

How do you inject multiple implementations of the same contract?

## What the interviewer evaluates

- Distinguish compile-time selection with qualifiers from runtime strategy selection.
- Explain multibindings for a set/map of implementations and test/variant replacement.
- Avoid ambiguous unqualified bindings or leaking environment choice into every consumer.

## Explanation in Arabic

لو عندك `PaymentGateway` حقيقي و`SandboxGateway`، واثنين لنفس interface، graph محتاجة تعرف المطلوب. لو كل consumer يحتاج واحد محدد، استخدم qualifiers مختلفة على bindings والطلبات. لو محتاج عدة handlers تتجمع، Dagger multibindings تعطي `Set` أو `Map` بدل حقن implementation عشوائي. لو الاختيار يتغير وقت التشغيل حسب حساب/بلد/feature flag، حقن factory أو router يقرر بناء على policy؛ لا تجعل Hilt graph تتغير بعد البناء بطريقة غير واضحة. وفي tests استبدل module/qualifier المقصود، ولا تعتمد على ترتيب set.

## Practical walkthrough

عندك `PaymentProcessor` منه card وwallet. لو الشاشة تحتاج واحد محدد، اعمل qualifier لكل binding واطلبه صراحة في constructor. لو المنتج يختار حسب method وقت التشغيل، لا تحاول تحقن implementation متغيرة مباشرة؛ احقن factory أو map بتختار بناءً على input موثوق. اختبر unsupported method وخطأ config، وتأكد إن release ما يربطش fake processor.

## Why it matters and how it works

A DI graph resolves bindings by type plus qualifier. Multiple bindings for the same unqualified key conflict. Qualifiers select a known binding at injection time. Multibindings aggregate contributions and allow a registry of handlers. A runtime decision needs a separate application abstraction because Hilt's compiled graph is not a dynamic per-request switch; that abstraction can receive qualified implementations and choose safely.

## Worked example

A checkout router receives `@CardGateway CardGateway` and `@WalletGateway WalletGateway`, then chooses by the validated payment method. A notification dispatcher can receive a map of channel handlers contributed by feature modules. The card gateway must never be replaced by a sandbox instance in release merely because a Boolean flag is stale; variant wiring and server capability checks decide availability. This is an architecture example, not compiled Kotlin.

## Trade-offs and decision criteria

Qualifiers are simple and explicit when consumers know the desired implementation. A router isolates a runtime choice and its fallback/error policy. A multibinding registry supports extensible plugins but adds key collisions and ordering concerns. Separate wrapper interfaces may convey different capabilities better than one broad contract. Keep payment/security policy in domain logic rather than scattered injection annotations.

## Failure modes

Two unqualified implementations cause graph compilation failure. A test replaces only one qualified binding and still calls the real network. A map key collision silently changes dispatch semantics or fails build. A runtime router selects a sandbox gateway in production. Test every supported method, unknown method, and release variant; log safe selection metadata without credentials.

## Production perspective

Define a stable gateway contract and explicit method registry with allowlisted methods. Use qualifiers for infrastructure instances, a domain router for runtime selection, and multibindings only when extensibility justifies them. Ensure each implementation is independently tested, then run integrated release configuration tests and transaction idempotency checks.

## Interview answer — short

“I use qualifiers when an injection site needs a particular implementation, multibindings when it needs a collection of handlers, and a factory/router when choice depends on runtime data.”

## Interview answer — structured

“Dagger keys bindings by type and qualifier, so two unqualified implementations of one interface are ambiguous. If a consumer knows it needs the card gateway, I qualify that binding and parameter. If a feature discovers all handlers, I use set or map multibinding with deliberate keys. If the method changes per order, I inject a router or factory that receives the implementations and applies a validated domain policy at runtime. This keeps selection out of every screen and lets tests cover unknown methods and safe fallbacks. I also verify test and release graph variants so a sandbox implementation cannot be selected accidentally.”

## Interview answer — deep senior

“I separate graph selection from business selection. The compiled DI graph can distinguish same-type bindings with semantic qualifiers; this works when a component has a fixed infrastructure need. Dagger multibindings can assemble a set or keyed map of implementations for a plugin-style registry, but I must specify collision and ordering behavior. A user's selected payment method is runtime data, so I introduce a domain router or factory that holds the qualified gateways and chooses only from supported, authorized methods. The router owns an explicit unknown-method outcome and does not fall back to an arbitrary gateway. I test each adapter's error mapping and idempotency, the router's policy, and release graph wiring separately. If two implementations differ in security capabilities, I may use distinct contracts rather than forcing both through an overbroad interface. DI supplies objects; it should not hide a critical runtime decision. For a card-only screen I would request the card-qualified processor directly. For a checkout that lets a user switch methods at runtime, I would inject a typed selector and require an explicit result for each supported method. I would test an unknown method as an error, not a fallback to card processing. This separates graph selection from business selection and makes the release provider mapping auditable.”

## How to answer in the interview

- **Why:** one contract can have distinct business implementations.
- **How:** qualifiers for fixed choice, factory/map for runtime choice.
- **Trade-off:** map flexibility versus explicit constructor requirement.
- **Failure case:** unsupported payment method falls through.
- **Production solution:** variant graph and selection tests.

## Deep-dive talking points

Discuss binding keys, qualifiers, multibinding keys, runtime router, variant safety, and test replacement.

## Follow-up questions

- Can a qualifier choose per-user payment method dynamically? **Answer:** it selects a graph binding at injection time; runtime selection needs a factory/router using validated data.
- When use map multibinding? **Answer:** when many contributors provide handlers looked up by stable keys, with collision behavior understood.
- What if no implementation supports a method? **Answer:** return an explicit unsupported outcome rather than silently choosing a default gateway.

## Self-check rubric

Choose fixed versus runtime selection, describe a multibinding case, and test unknown and release-variant paths.
