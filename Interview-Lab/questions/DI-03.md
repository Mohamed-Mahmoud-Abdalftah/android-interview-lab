# DI-03

## Original interview question

Compare Dagger and Hilt.

## What the interviewer evaluates

- Identify Hilt as an Android-focused layer on Dagger.
- Compare ownership of components and lifecycle wiring, not imagined absolute performance.
- Give a justified choice and explain what compilation, Android tests and measurement each prove.

## Concept and technical explanation

Dagger generates factories and component implementations from compile-time bindings. With direct Dagger, the application defines component topology, creation and lifetime. Hilt builds on Dagger and supplies a standard Android component hierarchy, entry points and Jetpack ViewModel integration, reducing manual wiring for supported paths. `@HiltAndroidApp`, `@AndroidEntryPoint` and `@HiltViewModel` each serve different entry points. Both can report missing graph bindings and cycles at build time; neither proves that a repository returns correct data, that a scope matches business state, or that runtime performance is identical in every app.

## Practical walkthrough (English)

A direct Dagger setup can define an `OrdersComponent` and explicitly call `inject(activity)` at the appropriate owner boundary. In Hilt, an illustrative Android setup is:
```kotlin
@HiltAndroidApp
class ShopApp : Application()

@AndroidEntryPoint
class OrdersActivity : ComponentActivity() {
    @Inject lateinit var analytics: AnalyticsTracker
}

@HiltViewModel
class OrdersViewModel @Inject constructor(
    private val repository: OrdersRepository
) : ViewModel()
```
The repository and analytics dependencies still need valid bindings. Obtain the ViewModel through a supported Jetpack API. This repository does not compile an Android Hilt graph.

## Practical walkthrough

تخيّل `OrdersRepository` بتحتاج `OrdersApi`. في Dagger مباشر، تقدر تعرّف `@Component` يملك الـ Binding وتختار مين يستدعي `inject(activity)` ومتى يعيش الـ Component. في Hilt، الـ App عليها `@HiltAndroidApp` والـ Activity المدعومة عليها `@AndroidEntryPoint`، وبتحط Module فيه `@Provides` أو `@Binds` عند الحاجة مع `@InstallIn` للـ Component المناسب:
```kotlin

@HiltAndroidApp
class ShopApp : Application()

@AndroidEntryPoint
class OrdersActivity : ComponentActivity() {
    @Inject lateinit var analytics: AnalyticsTracker

@HiltViewModel
class OrdersViewModel @Inject constructor(
    private val repository: OrdersRepository
) : ViewModel()
```
ده رسم توضيحي؛ نجاحه يتطلب Binding لكل Dependency وإعداد Hilt الصحيح، والـ ViewModel تتجاب عبر Android/Jetpack API المناسب، مش بإنشائها يدويًا أو Field Injection.

## Why it matters and how it works

The choice determines who owns graph topology and Android lifecycle wiring. Hilt reduces routine entry-point setup; direct Dagger can model a custom component lifetime. Neither annotation choice replaces explicit state ownership, behavior tests or measurement.

## Worked example

An orders app has an `OrdersViewModel` that needs `OrdersRepository`. Hilt is a good fit for a conventional Activity/ViewModel path once its bindings and scopes are defined. A checkout session with a separate lifetime may call for a custom Dagger component or a narrow bridge. During migration, one graph must own the session manager so logout does not leave independent state behind.

## Trade-offs and decision criteria

Hilt offers standardized Android integration but constrains component topology. Direct Dagger offers custom graph control but requires explicit creation, lifecycle wiring and maintenance. Manual DI may suffice for a small app. Compare annotation processing and runtime costs in the target project rather than asserting a universal winner.

## Failure modes

A session binding is installed in a longer-lived component than its state. Hilt and an older Dagger graph create separate session managers during migration. `@HiltViewModel` is added without a binding for a constructor dependency. A Play dynamic feature is treated like a regular library for Hilt annotation processing.

## Production perspective

Write down graph owners and lifetimes before migration. Move one Android entry path at a time, build supported variants, and verify identity, logout and recreation on Android. Use Hilt test setup to check the generated graph where needed. JVM business tests do not establish Android wiring or runtime performance.

## Interview answer — short

Hilt is built on Dagger. Both use generated dependency graphs, while Hilt supplies standard Android components and entry points that remove much routine Application, Activity and ViewModel wiring. Direct Dagger leaves component shape and lifetime under your control, which can help unusual ownership models but adds setup responsibility. Choose from graph ownership and lifecycle needs, then test behavior and measure performance rather than claiming that annotation choice guarantees either.

## Interview answer — structured

Dagger is the underlying compile-time DI engine: you declare bindings and component topology and decide how Android objects obtain the graph. Hilt builds on Dagger and provides a conventional Android component hierarchy with `@HiltAndroidApp`, `@AndroidEntryPoint` and `@HiltViewModel`. For a standard orders Activity and ViewModel, that often removes manual component and factory wiring, provided every constructor dependency has a binding. I would use direct Dagger if the app needs a custom graph owner or lifetime that does not map cleanly to Hilt components. During migration, I keep one owner for stateful dependencies and verify logout and recreation. Compile-time validation finds missing bindings and graph cycles, but not incorrect repository behavior. Runtime and build cost require measurements in the actual project.

## Interview answer — deep senior

The comparison starts with ownership. Dagger generates factories and component implementations from compile-time bindings; the application defines its components, scopes, creation and injection calls. Hilt is built on Dagger and supplies a standard Android component hierarchy and entry-point conventions. An annotated Application establishes the app graph, supported Android classes use `@AndroidEntryPoint`, and Hilt ViewModels use constructor injection with `@HiltViewModel` and supported Jetpack retrieval. This reduces routine plumbing but does not remove the need to bind an interface or third-party type, choose `@InstallIn` correctly, or reason about object lifetime.

For an orders feature, the ViewModel can depend on `OrdersRepository`. If the UI follows ordinary Android lifecycles, Hilt gives a straightforward integration path. If checkout state must live for a domain session independent of an Activity or Application, I first define its owner; a custom Dagger component or a bridge may be clearer than placing everything in `SingletonComponent`. Dagger itself does not tie a custom component to Android callbacks automatically. A graph that compiles may still keep user state after logout or share the wrong object instance. During migration, I would avoid parallel ownership by Hilt and the old graph, then test session identity, logout and recreation on Android.

Both tools can catch unsatisfied graph dependencies and cycles at build time. Neither validates network results or business rules. Hilt has Android test utilities, but those require the test setup and do not replace behavior tests. Play dynamic features require a separate entry-point and Dagger component-dependency bridge because their dependency direction differs from regular libraries. For a small app, manual DI can be simpler. I would compare build and runtime performance with representative variants and flows; generated code alone is not evidence of identical timings.

## How to answer in the interview

- State that Hilt builds on Dagger.
- Compare custom components with the standard Android hierarchy and ViewModel path.
- Give one scenario for Hilt and one for direct Dagger or manual DI.
- Explain scope ownership, migration identity, and verification limits.

## Deep-dive talking points

Generated graph; Android component hierarchy; entry points and ViewModels; `@InstallIn` and scope; session ownership; migration bridges; dynamic features; compile checks versus behavior tests and measurement.

## Follow-up questions

- **Interviewer:** "Can Hilt and direct Dagger coexist during migration?"
  **Answer:** "Yes with an explicit graph bridge and one owner for stateful dependencies; verify identity and logout."

- **Interviewer:** "Is Hilt always faster or slower at runtime?"
  **Answer:** "No universal timing follows from the choice. Measure startup and allocation for the relevant graph."

- **Interviewer:** "Does `@HiltViewModel` alone complete the wiring?"
  **Answer:** "No. Its constructor dependencies need reachable bindings, and the ViewModel must be obtained through the supported integration."

## Self-check rubric

Explain the shared engine, different component ownership, one scope decision, migration identity, and the limits of build validation. Avoid absolute performance claims.
