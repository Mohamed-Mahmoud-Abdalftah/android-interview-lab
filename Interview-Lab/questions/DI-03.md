# DI-03

## Original interview question

Compare Dagger and Hilt.

## What the interviewer evaluates

- Identify Hilt as an Android opinionated layer built on Dagger, not a competing runtime locator.
- Compare control over components/wiring with reduced Android boilerplate.
- Explain migration, multi-module, testing, and unsupported entry-point decisions.

## Explanation in Arabic

المقارنة الجوهرية بين Dagger و Hilt في بيئة تطوير تطبيقات Android الحديثة:

1. العلاقة بينهما:
   - **Hilt ليس إطار عمل منفصل أو منافس لـ Dagger**؛ بل هو طبقة موجهة ومعيارية (Opinionated Layer) مبنية بالكامل فوق Dagger 2 ومخصصة لتطبيقات Android من Google.
   - Hilt يولد مكونات Dagger العادية (`@Component`, `@Subcomponent`) تحت الغطاء نيابة عنك في وقت التجميع.

2. أوجه المقارنة التفصيلية:
   - **الـ Boilerplate و Components**: في Pure Dagger، كنت مضطراً لبناء `AppComponent`, `ActivityComponent`, `Subcomponents`, والـ Component Builders يدوياً وكتابة مئات الأسطر من الكود. في Hilt، كل المكونات الأساسية مدمجة مسبقاً (`SingletonComponent`, `ActivityComponent`, `ViewModelComponent`).
   - **Android Lifecycle Integration**: يدعم Hilt حقن الـ ViewModels تلقائياً عبر `@HiltViewModel` بدون كتابة Custom ViewModelFactory مخصص ومزعج كالسابق.
   - **Modularization**: في Pure Dagger، إدارة الـ Multi-module تتطلب ربط يدوي معقد. في Hilt، استخدام `@InstallIn(...)` يسمح لكل موديول بإعلان توفير كائناته مباشرة دون لمس الـ Base App Module.
   - **Instrumentation Testing**: يدمج Hilt دعم مدمج للاختبارات عبر `@HiltAndroidTest` و `@UninstallModules` و `@BindValue`، بينما كان إعداد الاختبارات في Pure Dagger كابوساً يتطلب TestComponent مخصصاً.

## Practical walkthrough

المقارنة بين إعداد الـ ViewModel في Pure Dagger وفي Hilt:
```kotlin
// ❌ في Pure Dagger القديم: تطلب الأمر كتابة Multibindings و ViewModelFactory مخصص:
@MapKey
@Target(AnnotationTarget.FUNCTION)
annotation class ViewModelKey(val value: KClass<out ViewModel>)

@Module
abstract class ViewModelModule {
    @Binds @IntoMap @ViewModelKey(OrderViewModel::class)
    abstract fun bindOrderViewModel(vm: OrderViewModel): ViewModel
    
    @Binds
    abstract fun bindFactory(factory: DaggerViewModelFactory): ViewModelProvider.Factory
}
// هذا الإعداد تطلب عشرات الملفات والـ Subcomponents المعقدة!

// ✅ في Hilt الحديث: سطر واحد فقط ويتولى Hilt كل شيء تلقائياً:
@HiltViewModel
class OrderViewModel @Inject constructor(
    private val repository: OrderRepository
) : ViewModel() {
    // جاهز للاستخدام مباشرة في الـ Activity أو Compose عبر hiltViewModel()!
}
```

## Why it matters and how it works

Dagger generates Java/Kotlin-accessible factories and component implementations from compile-time bindings. Hilt uses Dagger underneath but provides standard Android components, lifecycle-linked scopes, and annotations such as `@HiltAndroidApp`, `@AndroidEntryPoint`, and `@HiltViewModel`. Hilt removes much manual component plumbing, while a directly configured Dagger graph can express unusual ownership more freely. Both need valid bindings and explicit lifetime decisions.

## Worked example

An existing Dagger app manually builds `AppComponent` and Activity subcomponents. A Hilt migration introduces an annotated Application and Activity, moves a network module to `SingletonComponent`, and keeps a repository constructor-injected. A dynamic feature that is not processed in the same Hilt graph receives a narrow dependency interface via an entry point or Dagger component dependency. This is a migration sketch; exact module wiring must be compile-tested in the target project.

## Trade-offs and decision criteria

Hilt favors convention and quick Android integration; direct Dagger offers fine-grained custom graphs but more wiring and maintenance. Hilt's standard hierarchy may require entry points for unsupported classes or dynamic feature patterns. Both add annotation processing and generated sources to builds. For a very small app, manual DI can be simpler than either. Choose using graph complexity, team familiarity, module boundaries, and test needs.

## Failure modes

Mixing Hilt and an old Dagger graph creates duplicate singletons or inconsistent session state. Installing a module into the wrong component makes a binding unavailable or too long-lived. A library module compiles alone but the app's transitive dependencies are not visible to Hilt processing. Test production variants, compile generated graph, and verify identity of session-scoped objects after migration.

## Production perspective

Migrate one entry-point path at a time while preserving stable interfaces. Document which graph owns networking, persistence, and session state; avoid duplicate roots. Replace modules incrementally and run integrated app/tests per variant. Measure build impact and keep a rollback branch until navigation and logout behavior pass.

## Interview answer — short

Hilt is an opinionated, compile-time framework built directly on top of Dagger specifically for Android. It eliminates Dagger's massive boilerplate by providing standard predefined components (SingletonComponent, ViewModelComponent), automatic Android lifecycle integration, simplified multi-module binding via @InstallIn, and native test runners via @HiltAndroidTest.

## Interview answer — structured

Hilt is not a replacement for Dagger; it is an opinionated abstraction layer over Dagger 2 engineered by Google to standardize Android dependency injection.

Key architectural differences:
1. **Predefined Component Hierarchy**: In pure Dagger, developers spent hundreds of lines defining custom Components, Subcomponents, and custom ViewModel Factories. Hilt provides a battle-tested hierarchy mapped directly to Android lifecycles (`SingletonComponent`, `ActivityRetainedComponent`, `ViewModelComponent`, `ActivityComponent`).
2. **Decentralized Multi-Module Setup**: Pure Dagger required a central root component to declare all subcomponents. Hilt uses `@InstallIn`, allowing library and feature modules to independently contribute bindings to the shared graph without editing the base application module.
3. **First-Class Testing**: Hilt provides built-in testing APIs (`@HiltAndroidTest`, `@UninstallModules`) that allow substituting production modules with test doubles in Robolectric and Android instrumented tests without maintaining duplicate test components.

## Interview answer — deep senior

At the compilation level, Hilt acts as an annotation processor that generates standard Dagger code before Dagger's own compiler runs.

When you annotate a class with `@HiltAndroidApp`, Hilt generates a base application class that instantiates the generated Dagger `SingletonComponent`. When you use `@InstallIn(SingletonComponent::class)`, Hilt's byte-code/symbol processing collects these module definitions across all Gradle submodules into an aggregated metadata package. Dagger then consumes this generated metadata and performs standard compile-time graph validation.

However, Hilt's opinionated design limits flexibility in edge cases. Pure Dagger allows arbitrary, deeply nested subcomponent lifetimes (e.g. a custom `LoggedInSessionComponent` or a `PlaybackFlowComponent`). Hilt strictly adheres to its built-in lifecycle components. While custom components can be created in Hilt using `@DefineComponent`, they require manual lifecycle management and entry points, forfeiting some of Hilt's zero-boilerplate ergonomics.

## How to answer in the interview

- **Why:** Hilt standardizes Android graph setup on Dagger.
- **How:** contrast generated hierarchy with custom components.
- **Trade-off:** convenience versus custom lifetime control.
- **Failure case:** assuming dynamic feature annotations are processed like regular modules.
- **Production solution:** variant builds and component-boundary tests.

## Deep-dive talking points

Discuss generated graph, standard component hierarchy, custom lifetimes, migration identity, dynamic features, and build/test implications.

## Follow-up questions

- **Interviewer:** "Can you mix Pure Dagger and Hilt in the same project?"
  **Answer:** "Yes. Hilt is built on Dagger. You can expose bindings from pure Dagger components into Hilt using Entry Points or incorporate Hilt into existing Dagger subcomponents during migrations."

- **Interviewer:** "What is the compile-time impact of Hilt compared to pure Dagger?"
  **Answer:** "Hilt adds an extra metadata aggregation step, which can slightly increase build times compared to hand-rolled Dagger, but this is mitigated significantly by KSP (Kotlin Symbol Processing)."
