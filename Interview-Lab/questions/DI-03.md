# DI-03

## Original interview question

Compare Dagger and Hilt.

## What the interviewer evaluates

- Identify Hilt as an Android opinionated layer built on Dagger, not a competing runtime locator.
- Compare control over components/wiring with reduced Android boilerplate.
- Explain migration, multi-module, testing, and unsupported entry-point decisions.

## Concept and technical explanation

Comparing Dagger and Hilt centers on architectural opinionation versus raw framework flexibility. Dagger is a general-purpose, compile-time dependency injection framework for Java and Kotlin that generates purely static code without reflection, validating directed acyclic graphs during compilation. However, pure Dagger requires substantial boilerplate in Android: developers must manually define custom components, subcomponents, component builders, and scope bindings for every Activity, Fragment, and ViewModel lifecycle. Hilt is Google's official, opinionated framework built directly on top of Dagger. It standardizes Android dependency injection by providing predefined, hierarchical components aligned with Android lifecycles, automated injection entry points, dedicated Jetpack ViewModel and WorkManager integrations, and streamlined testing APIs, while retaining Dagger's complete compile-time performance and validation guarantees.

## Practical walkthrough (English)

Contrasting Dagger boilerplate with Hilt opinionated simplicity:
```kotlin
// 1. Pure Dagger 2: Requires manual Component, Subcomponent, and Subcomponent.Factory boilerplate
@Subcomponent
interface ActivitySubcomponent {
    fun inject(activity: MainActivity)
    @Subcomponent.Factory
    interface Factory { fun create(): ActivitySubcomponent }
}

// 2. Hilt: Generates and connects identical Dagger components automatically
@HiltAndroidApp
class MyApplication : Application()

@AndroidEntryPoint
class MainActivity : AppCompatActivity() {
    @Inject lateinit var analytics: AnalyticsTracker // Zero manual component glue code required!
}

@HiltViewModel
class MainViewModel @Inject constructor(
    private val repo: UserRepository // Injected directly without custom ViewModelProvider.Factory
) : ViewModel()
```

}

## Why it matters and how it works

Dagger generates Java/Kotlin-accessible factories and component implementations from compile-time bindings. Hilt uses Dagger underneath but provides standard Android components, lifecycle-linked scopes, and annotations such as `@HiltAndroidApp`, `@AndroidEntryPoint`, and `@HiltViewModel`. Hilt removes much manual component plumbing, while a directly configured Dagger graph can express unusual ownership more freely. Both need valid bindings and explicit lifetime decisions.

## Worked example

An existing Dagger app manually builds `AppComponent` and Activity subcomponents. A Hilt migration introduces an annotated Application and Activity, moves a network module to `SingletonComponent`, and keeps a repository constructor-injected. A dynamic feature that is not processed in the same Hilt graph receives a narrow dependency interface via an entry point or Dagger component dependency. This is a migration sketch; exact module wiring must be compile-tested in the target project.

## Trade-offs and decision criteria

Hilt favors convention and quick Android integration; direct Dagger offers fine-grained custom graphs but more wiring and maintenance. Hilt's standard hierarchy may require entry points for unsupported classes or dynamic feature patterns. Both add annotation processing and generated sources to builds. For a very small app, manual DI can be simpler than either. Choose using graph complexity, team familiarity, module boundaries, and test needs.

## Failure modes

Mixing Hilt and an old Dagger graph creates duplicate singletons or inconsistent session state. Installing a module into the wrong component makes a binding unavailable or too long-lived. A library module compiles alone but the app's transitive dependencies are not visible to Hilt processing. Test production variants, compile generated graph, and verify identity of session-scoped objects after migration.

## Production perspective

Migrate one entry-point path at a time while preserving stable interfaces. Document which graph owns networking, persistence, and session state; avoid duplicate roots. Replace modules incrementally and run integrated app/tests per variant. Measure build impact and keep a rollback branch until navigation and logout behavior pass.

## Interview answer — short

Hilt is an opinionated framework built directly on top of Dagger to eliminate Android boilerplate while preserving Dagger compile-time graph validation and performance. Pure Dagger requires manual definition of components, subcomponents, and custom ViewModel factories. Hilt automates this plumbing by providing predefined components tied to Android lifecycles, dedicated Jetpack annotations like @HiltViewModel, and streamlined test runners.

## Interview answer — structured

Dagger and Hilt share the identical core dependency injection engine, but they differ fundamentally in developer experience and Android-specific opinionation.
Dagger is an un-opinionated, platform-agnostic dependency injection framework. It offers total flexibility, allowing developers to design arbitrary component topologies and custom lifecycle scopes. However, integrating pure Dagger into Android requires extensive boilerplate: developers must manually write component interfaces, configure subcomponents for Activities and Fragments, manage component lifecycles in Application and Activity callbacks, and construct complex multi-binding maps to inject Jetpack ViewModels.
Hilt directly addresses these pain points by embedding Google's recommended architectural opinions onto Dagger. Hilt automatically generates a standardized hierarchy of components mapped to Android lifecycles—ranging from SingletonComponent down to FragmentComponent and ViewComponent.
Furthermore, Hilt provides seamless integration with the modern Android Jetpack ecosystem. Annotating a ViewModel with @HiltViewModel or an Activity with @AndroidEntryPoint eliminates dozens of lines of factory glue code. Finally, Hilt provides dedicated testing utilities that make replacing bindings in instrumented tests dramatically simpler.

## Interview answer — deep senior

Under the hood, Hilt is not a replacement for Dagger; it is an annotation-processing code generator and bytecode transformation layer that authors standard Dagger 2 code on your behalf. When you annotate an Application with @HiltAndroidApp, Hilt generates the root Dagger component and transforms base classes using bytecode manipulation (via Gradle transform plugins) so that @AndroidEntryPoint activities inherit from generated Hilt wrappers.
In pure Dagger, setting up an Activity required defining an ActivitySubcomponent, binding it to the AppComponent using custom builder factories, and manually retrieving the component inside onCreate to invoke inject(this). Teams frequently diverged in their Dagger architectures, creating fragmented conventions across codebases.
Hilt unifies the entire Android ecosystem around a single, standardized component hierarchy. Every Hilt component has a strictly defined parent: SingletonComponent sits at the root, parenting ActivityRetainedComponent (which survives configuration changes), which parents ActivityComponent, cascading down to FragmentComponent and ViewComponent.
Moreover, Jetpack ViewModel injection in pure Dagger required maintaining a Dagger ViewModelProvider.Factory and declaring multi-bindings with @IntoMap and custom ViewModelKey annotations. Hilt completely eliminates this fragile boilerplate through the @HiltViewModel annotation, which registers the ViewModel directly into Hilt's internal SavedStateViewModelFactory pipeline.
Staff engineers standardize exclusively on Hilt for all Android applications because it retains Dagger's strict compile-time verification and zero-reflection performance while drastically reducing onboarding friction and cognitive overhead.

## How to answer in the interview

- **Why:** Hilt standardizes Android graph setup on Dagger.
- **How:** contrast generated hierarchy with custom components.
- **Trade-off:** convenience versus custom lifetime control.
- **Failure case:** assuming dynamic feature annotations are processed like regular modules.
- **Production solution:** variant builds and component-boundary tests.

## Deep-dive talking points

Discuss generated graph, standard component hierarchy, custom lifetimes, migration identity, dynamic features, and build/test implications.

## Follow-up questions

- **Interviewer:** "Can you mix Pure Dagger and Hilt in the same project?"
  **Answer:** "Yes. Hilt is built on Dagger. You can expose bindings from pure Dagger components into Hilt using Entry Points or incorporate Hilt into existing Dagger subcomponents during migrations."

- **Interviewer:** "What is the compile-time impact of Hilt compared to pure Dagger?"
  **Answer:** "Hilt adds an extra metadata aggregation step, which can slightly increase build times compared to hand-rolled Dagger, but this is mitigated significantly by KSP (Kotlin Symbol Processing)."
