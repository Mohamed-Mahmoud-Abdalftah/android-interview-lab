# DI-03

## Original interview question

Compare Dagger and Hilt.

## What the interviewer evaluates

- Identify Hilt as an Android opinionated layer built on Dagger, not a competing runtime locator.
- Compare control over components/wiring with reduced Android boilerplate.
- Explain migration, multi-module, testing, and unsupported entry-point decisions.

## Explanation in Arabic

`Dagger` framework compile-time DI عام: تعرّف components/modules وbindings بنفسك، فتتحكم بالتفاصيل لكن wiring Android components قد يكون كثيرًا. `Hilt` مبني على Dagger ويجهز component hierarchy وAndroid entry points القياسية مثل Application وActivity وViewModel، ويقلل boilerplate. الاختيار ليس “Hilt أسرع دائمًا”؛ الأداء يعتمد على graph والـscopes. لو عندك custom components أو dynamic feature معقدة، ممكن تحتاج Dagger APIs أو Hilt entry points بجانب Hilt. في migration اعملها تدريجيًا، وراجع scope/qualifier لأن نقل annotation بلا فهم يمكن أن يغيّر lifetime أو binding.

## Practical walkthrough

Dagger هو compile-time DI engine تقدر تبني components/subcomponents بنفسك؛ Hilt فوقه وبتوفر Android component hierarchy وentry points standard. في app متعددة Activities، Hilt توفر boilerplate، لكن لو عندك custom lifetime أو dynamic feature، ممكن تحتاج Dagger component dependency. لا تقول إن Hilt وDagger بدائل منفصلة أو إن Hilt تحل Gradle graph تلقائيًا.

## Why it matters and how it works

Dagger generates Java/Kotlin-accessible factories and component implementations from compile-time bindings. Hilt uses Dagger underneath but provides standard Android components, lifecycle-linked scopes, and annotations such as `@HiltAndroidApp`, `@AndroidEntryPoint`, and `@HiltViewModel`. Hilt removes much manual component plumbing, while a directly configured Dagger graph can express unusual ownership more freely. Both need valid bindings and explicit lifetime decisions.

## Worked example

An existing Dagger app manually builds `AppComponent` and Activity subcomponents. A Hilt migration introduces an annotated Application and Activity, moves a network module to `SingletonComponent`, and keeps a repository constructor-injected. A dynamic feature that is not processed in the same Hilt graph receives a narrow dependency interface via an entry point or Dagger component dependency. This is a migration sketch; exact module wiring must be compile-tested in the target project.

## Trade-offs and decision criteria

Hilt favors convention and quick Android integration; direct Dagger offers fine-grained custom graphs but more wiring and maintenance. Hilt's standard hierarchy may require entry points for unsupported classes or dynamic feature patterns. Both add annotation processing and generated sources to builds. For a very small app, manual DI can be simpler than either. Choose using graph complexity, team familiarity, module boundaries, and test needs.

## Failure modes

Mixing Hilt and an old Dagger graph creates duplicate singletons or inconsistent session state. Installing a module into the wrong component makes a binding unavailable or too long-lived. A library module compiles alone but the app's transitive dependencies are not visible to Hilt processing. Test production variants, compile generated graph, and verify identity of session-scoped objects after migration.

## Production perspective

Migrate one entry-point path at a time while preserving stable interfaces. Document which graph owns networking, persistence, and session state; avoid duplicate roots. Replace modules incrementally and run integrated app/tests per variant. Measure build impact and keep a rollback branch until navigation and logout behavior pass.

## Interview answer — short

“Hilt is an Android-focused layer built on Dagger. Dagger gives more manual component control; Hilt supplies standard Android components and entry-point annotations, reducing wiring while retaining Dagger bindings underneath.”

## Interview answer — structured

“Dagger generates a compile-time dependency graph from components, modules, and constructor bindings. Hilt uses Dagger but standardizes the Android component hierarchy and integrates Application, Activity, Fragment, Service, and ViewModel creation. I choose Hilt for a conventional Android app where manual subcomponent wiring would add cost. Direct Dagger remains useful for unusual graphs or legacy integrations. The trade-off is less custom hierarchy control, not magically different dependency semantics. I still decide scopes and qualifiers and compile/test the app graph; moving an old module to a new component without reviewing lifetime can create leaks or duplicate session state.”

## Interview answer — deep senior

“I compare them at the composition boundary. Dagger is the underlying compile-time code generator: I define components and binding relationships and can tailor a graph closely to a product's ownership model. Hilt layers Android conventions over Dagger, generating a standard lifecycle-aligned component hierarchy and wiring platform-created entry points with fewer custom factories. That is valuable for teams with many screens and tests, but it does not make scope decisions for me. A wrong Singleton binding can retain Activity Context in either approach. During migration I map old component lifetimes to Hilt scopes, ensure there is one owner for shared clients and session data, and test release and test variants. Dynamic feature or SDK-created classes may use entry points or Dagger component dependencies instead of direct Hilt injection. I would choose manual DI for a tiny graph, Hilt for standard Android complexity, and direct Dagger only when custom composition benefits outweigh its wiring cost. A dynamic feature is a useful exception to the standard Hilt story: the base app cannot compile against feature-only symbols, so I would expose a narrow base entry point and have a feature Dagger component depend on it. For an ordinary library module, I would first check Gradle visibility and the generated binding error. This shows that Hilt simplifies conventional Android graphs while Dagger remains the underlying mechanism for custom composition boundaries.”

## How to answer in the interview

- **Why:** Hilt standardizes Android graph setup on Dagger.
- **How:** contrast generated hierarchy with custom components.
- **Trade-off:** convenience versus custom lifetime control.
- **Failure case:** assuming dynamic feature annotations are processed like regular modules.
- **Production solution:** variant builds and component-boundary tests.

## Deep-dive talking points

Discuss generated graph, standard component hierarchy, custom lifetimes, migration identity, dynamic features, and build/test implications.

## Follow-up questions

- Is Hilt independent of Dagger? **Answer:** no; Hilt builds on Dagger and generates Dagger-based components.
- Does Hilt remove scope design? **Answer:** no; developers must select the component and lifetime for each binding.
- How can a dynamic feature obtain app dependencies? **Answer:** use a narrow Hilt entry point or Dagger component-dependency interface according to module processing constraints.

## Self-check rubric

State the relationship, compare graph control, map one scope in migration, and describe a dynamic-feature integration.
