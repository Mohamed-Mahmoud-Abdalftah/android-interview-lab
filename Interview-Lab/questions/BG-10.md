# BG-10

## Original interview question

How do you persist progress and communicate it to UI?

## What the interviewer evaluates

Persist business progress and expose it through repository state rather than transient callbacks.

## Concept and technical explanation

Communicating background work progress in WorkManager requires distinguishing between transient in-flight progress and durable state persistence. For active operations, CoroutineWorker invokes setProgress with a Data object, which serializes key-value pairs into WorkManager's internal SQLite database and dispatches updates through reactive WorkInfo streams via getWorkInfoByIdFlow or getWorkInfosByTagFlow. However, WorkManager progress is strictly ephemeral and tied to the RUNNING state; once a worker transitions to SUCCEEDED, FAILED, or CANCELLED, its progress payload is discarded. For multi-step, restartable operations—such as multi-part file uploads or paginated synchronizations—durable progress must be committed directly to a local Room database as an authoritative checkpoint, allowing retried workers to resume rather than restart from scratch.

## Practical walkthrough (English)

Communicating and persisting progress in practice:
```kotlin
// 1. Worker emitting progress during execution
class FileDownloadWorker(
    appContext: Context,
    params: WorkerParameters
) : CoroutineWorker(appContext, params) {
    override suspend fun doWork(): Result = withContext(Dispatchers.IO) {
        val totalBytes = inputData.getLong("TOTAL_BYTES", 1000L)
        var downloaded = 0L

        while (downloaded < totalBytes) {
            downloaded += 100L
            val progressPercent = ((downloaded * 100) / totalBytes).toInt()
            
            // Updates transient progress observed via WorkInfo
            setProgress(workDataOf("PROGRESS" to progressPercent))
            delay(100)
        }
        Result.success(workDataOf("DOWNLOADED_BYTES" to downloaded))
    }
}

// 2. UI observing progress reactively in ViewModel
class DownloadViewModel(private val workManager: WorkManager) : ViewModel() {
    val progressFlow: Flow<Int> = workManager.getWorkInfoByIdFlow(workerId)
        .filterNotNull()
        .map { workInfo ->
            if (workInfo.state == WorkInfo.State.RUNNING) {
                workInfo.progress.getInt("PROGRESS", 0)
            } else 0
        }
}
```

## Practical walkthrough

تحديث التقدم عبر WorkManager وعبر Room وعرضه في Jetpack Compose:
```kotlin
// 1. داخل الـ CoroutineWorker: تحديث التقدم عبر WorkManager و Room:
class UploadVideoWorker(context: Context, params: WorkerParameters) : CoroutineWorker(context, params) {
    override suspend fun doWork(): Result {
        val taskId = inputData.getString("task_id")!!
        val db = EntryPoints.get(applicationContext, DbEntryPoint::class.java).database()
        
        for (percent in 1..100 step 10) {
            delay(500) // محاكاة الرفع
            
            // أ. إرسال تقدم فوري لـ WorkManager UI:
            setProgress(workDataOf("percent" to percent))
            
            // ب. حفظ التقدم الدائم في Room لحمايته عبر إعادة تشغيل التطبيق:
            db.uploadDao().updateProgress(taskId, percent)
        }
        return Result.success()
    }
}

// 2. في الـ ViewModel: مراقبة تقدم المهمة كتدفق تفاعلي:
@HiltViewModel
class UploadViewModel @Inject constructor(
    private val taskDao: UploadTaskDao,
    private val workManager: WorkManager
) : ViewModel() {
    fun observeUploadTask(taskId: String): Flow<UploadTaskEntity?> = taskDao.observeTask(taskId)
}

// 3. في Jetpack Compose UI:
@Composable
fun UploadProgressScreen(viewModel: UploadViewModel, taskId: String) {
    val task by viewModel.observeUploadTask(taskId).collectAsState(initial = null)
    
    task?.let {
        LinearProgressIndicator(progress = { it.progressPercent / 100f })
        Text("${it.progressPercent}% Uploaded")
    }
}
```

## Why it matters and how it works

For resumable upload, persist an acknowledged offset or server session ID, not merely bytes attempted locally. A worker restart reads durable state and resumes under server contract. Progress updates should be throttled to avoid database churn; final business success requires authoritative confirmation.

## Trade-offs and decision criteria

WorkInfo progress is convenient for current run but may reset on retry; Room adds durable truth at write cost. Updating every byte is wasteful, so batch by chunk/time. Avoid embedding sensitive user data in WorkManager Data.

## Failure modes

A progress bar based on bytes sent to socket may show 100% before server validates the file. A new Worker attempt can appear to jump backwards if only WorkInfo was used. Treating Result.success as payment settlement without server status is unsafe.

## Production perspective

A video upload records server session ID and last acknowledged chunk in Room, exposes a Flow to the ViewModel, and supplements with WorkInfo scheduling state. After process death it resumes from server-confirmed offset and avoids re-uploading blindly.

## Interview answer — short

Communicate in-flight worker progress to the UI using setProgress with a Data object in CoroutineWorker, and observe it reactively through WorkManager getWorkInfoByIdFlow or LiveData. Because setProgress data is ephemeral and discarded once the worker exits the RUNNING state, multi-step operations that need to survive retries or app reboots must persist their progress checkpoints directly in a local Room database.

## Interview answer — structured

Communicating background progress effectively involves choosing the right mechanism based on whether progress is transient or durable.
When presenting live feedback for an active worker, CoroutineWorker provides the suspending setProgress method. Calling this function serializes a Data map into WorkManager internal Room database and notifies registered observers. Presentation layers observe this stream by querying getWorkInfoByIdFlow or getWorkInfosByTagFlow on WorkManager, extracting the integer or percentage from WorkInfo progress payload.
The critical architectural limitation is that setProgress is available exclusively while the worker remains in the RUNNING state. As soon as the worker terminates with success or failure, the progress payload is cleared, leaving only terminal outputData.
If an operation requires durable progress tracking across retries, crashes, or device reboots, such as a multi-part file upload, developers should write checkpoint offsets to a Room entity. The UI observes the Room database as the single source of truth, while the worker updates both Room for persistence and setProgress for high-frequency UI updates.

## Interview answer — deep senior

Under the hood, setProgress performs an asynchronous write into WorkManager internal Room database table and triggers a notification dispatch through the internal LiveData and Flow bus. Because database disk writes carry non-trivial I/O overhead, high-frequency progress reporting can easily saturate SQLite write locks and degrade application responsiveness.
Senior engineers throttle progress emissions inside worker loops, updating setProgress only when progress milestones change significantly, such as every full percentage point or megabyte chunk, rather than after every individual network byte received.
Furthermore, the lifecycle divergence between setProgress and terminal outputData represents a common source of state synchronization bugs. If a presentation screen connects after a worker has completed, observing WorkInfo progress returns an empty Data object. Presentation logic must therefore inspect WorkInfo state: if the state is SUCCEEDED, the UI should read the final outputData or the underlying domain database rather than relying on progress.
For mission-critical multi-step background pipelines, staff engineers combine WorkManager with an Outbox pattern in Room. The worker writes step completions and chunk byte offsets directly to the domain database inside atomic transactions. If the operating system terminates the process midway through execution, the rescheduled worker queries Room for the latest committed checkpoint, seamlessly resuming transmission without re-uploading completed segments or corrupting backend state.

## How to answer in the interview

- **Why:** progress is not final business truth.
- **How:** observe WorkInfo and durable repository state.
- **Trade-off:** detail versus write overhead.
- **Failure case:** 100% progress shown as confirmed payment.
- **Production solution:** separate transfer and server acknowledgment.

## Deep-dive talking points

Distinguish local sent versus server acknowledged bytes and WorkInfo versus business state.

## Follow-up questions

- **Interviewer:** "Can `WorkInfo` observe the state of tasks enqueued by another component?"
  **Answer:** "Yes, WorkInfo queries are process-wide and can be observed anywhere by UUID, unique name, or tag."

- **Interviewer:** "What are the possible states in `WorkInfo.State`?"
  **Answer:** "`ENQUEUED`, `RUNNING`, `SUCCEEDED`, `FAILED`, `BLOCKED`, and `CANCELLED`."
