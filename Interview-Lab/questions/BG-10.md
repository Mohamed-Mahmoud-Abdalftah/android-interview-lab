# BG-10

## Original interview question

How do you persist progress and communicate it to UI?

## What the interviewer evaluates

Persist business progress and expose it through repository state rather than transient callbacks.

## Explanation in Arabic

WorkManager `setProgress`/WorkInfo مفيد لعرض تقدم execution الحالية، لكنه مش المصدر الوحيد للحقيقة ولا ضمان عبر إعادة worker. UI تلاحظ Room Flow أو WorkInfo مع lifecycle awareness، وتعرض Pending/Retry/Complete بوضوح.

## Practical walkthrough

Worker progress في WorkInfo مفيد لbytes uploaded أو percent، لكن UI قد تختفي ويعاد process. خزّن business state الأساسية في repository/Room، والـUI تراقبها مع WorkInfo عند الحاجة. لا تعتبر 100% bytes = server commit؛ acknowledgment منفصل. تجنب إرسال progress كل byte فتزيد DB writes. اختبر الإلغاء والعودة للشاشة وتغير الWork ID بعد replacement.

## Why it matters and how it works

For resumable upload, persist an acknowledged offset or server session ID, not merely bytes attempted locally. A worker restart reads durable state and resumes under server contract. Progress updates should be throttled to avoid database churn; final business success requires authoritative confirmation.

## Trade-offs and decision criteria

WorkInfo progress is convenient for current run but may reset on retry; Room adds durable truth at write cost. Updating every byte is wasteful, so batch by chunk/time. Avoid embedding sensitive user data in WorkManager Data.

## Failure modes

A progress bar based on bytes sent to socket may show 100% before server validates the file. A new Worker attempt can appear to jump backwards if only WorkInfo was used. Treating Result.success as payment settlement without server status is unsafe.

## Production perspective

A video upload records server session ID and last acknowledged chunk in Room, exposes a Flow to the ViewModel, and supplements with WorkInfo scheduling state. After process death it resumes from server-confirmed offset and avoids re-uploading blindly.

## Interview answer — short

“I persist meaningful progress such as server-acknowledged chunks in the repository and expose it as Flow. WorkInfo/setProgress can help current UI, but final business success comes from server confirmation and survives worker restart.”

## Interview answer — structured

“A Worker may be retried or restarted, so a transient callback is not enough for user-visible progress. I keep an operation row with phase and acknowledged bytes, update it after server confirmation, and let UI observe it through Room. WorkManager progress can reflect current execution but is not the full durable business state. I throttle updates and make a resumed worker read the stored offset. Completion is only recorded after the server confirms the upload, not when local bytes were merely written to a socket.”

## Interview answer — deep senior

“Progress has several meanings: scheduled, bytes read from disk, bytes sent, bytes acknowledged by server, and final processing complete. I expose the one that matches the UX claim. WorkManager’s progress Data is useful for active-run observation, but retry or process death requires a durable repository row and possibly a server upload session. I persist acknowledged offset at chunk boundaries, rate-limit writes, and reconcile with server on restart. UI collects lifecycle-aware and can detach without stopping the operation. Tests kill the worker after a chunk, restart and assert monotonic acknowledged progress and no duplicate finalization. I use Worker progress for transfer progress, such as uploaded bytes, and repository state for the durable business result. This matters when the app process restarts: a new screen can query both, and a replaced request may have a new Work ID. I throttle progress updates to avoid excessive database writes and define an unknown total state when content length is unavailable. One hundred percent transferred does not mean the server committed an order; I wait for an authoritative acknowledgment before labeling it complete. I test cancellation, resume, navigation away and a late server failure, and keep accessibility text aligned with the true state.”

## How to answer in the interview

- **Why:** progress is not final business truth.
- **How:** observe WorkInfo and durable repository state.
- **Trade-off:** detail versus write overhead.
- **Failure case:** 100% progress shown as confirmed payment.
- **Production solution:** separate transfer and server acknowledgment.

## Deep-dive talking points

Distinguish local sent versus server acknowledged bytes and WorkInfo versus business state.
