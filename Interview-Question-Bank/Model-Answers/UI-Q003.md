# UI-Q003 — Complete model answer

**Spoken answer:** “ListAdapter expects a new list to be submitted for changes; mutating the currently displayed list breaks a useful diff snapshot. I would create a new list with immutable row models, submit it, and test the old/new content policy.”

<p dir="rtl" lang="ar">تعديل نفس list بعد submit يخلط snapshot القديمة بالجديدة. اعمل list جديدة، وخلي row models ثابتة أو انسخ nested mutable data بحسب الحاجة.</p>

**Mechanics:** The ListAdapter API says currentList must not be mutated and changes should go through submitList. The JVM snapshotRows test only proves a detached container of immutable NoteRow values. [RecyclerView guide](https://developer.android.com/develop/ui/views/layout/recyclerview), [ListAdapter API](https://developer.android.com/reference/kotlin/androidx/recyclerview/widget/ListAdapter) and [view binding](https://developer.android.com/topic/libraries/view-binding) were checked 2026-10-10.

**Common wrong answer:** “Call notifyDataSetChanged after mutating the list; the contract is fixed.” That is a coarse workaround and can still hide ownership errors.

**Follow-up 1:** Would toList deep-copy a row with MutableList tags? No. It copies the container, so nested mutable fields remain shared unless explicitly copied or made immutable.

**Follow-up 2:** Can every submitList commit callback be awaited as a guarantee? No. Official API docs say an earlier callback may be skipped when a newer list overtakes it.

**Rubric for self-review:** Separate item identity from displayed content, state the list ownership contract, match view work to view lifecycle, and distinguish JVM policy proof from Android integration. This is visible practice, not a scored assessment.
