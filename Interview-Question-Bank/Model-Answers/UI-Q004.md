# UI-Q004 — Complete model answer

**Spoken answer:** “The Fragment can outlive its view, so the observer may update or retain an obsolete binding. I would observe view updates with viewLifecycleOwner and clear the binding reference in onDestroyView.”

<p dir="rtl" lang="ar">Fragment تقدر تفضل بعد view. observer بعمر Fragment قد تلمس binding قديمة أو تمنع جمع view. استخدم viewLifecycleOwner ونظف binding عند onDestroyView.</p>

**Mechanics:** Android view-binding documentation explicitly tells Fragments to clear binding references in onDestroyView. The Fragment view lifecycle is separate from the Fragment lifecycle. [RecyclerView guide](https://developer.android.com/develop/ui/views/layout/recyclerview), [ListAdapter API](https://developer.android.com/reference/kotlin/androidx/recyclerview/widget/ListAdapter) and [view binding](https://developer.android.com/topic/libraries/view-binding) were checked 2026-10-10.

**Common wrong answer:** “onDestroyView means the Fragment was destroyed too.” It can remain and create another view later.

**Follow-up 1:** Does this automatically cancel a network request? No. It stops view-owned observation and releases references; request ownership and stale results need separate handling.

**Follow-up 2:** How would you verify it on Android? Navigate, destroy and recreate the view under a controlled fake result, then assert no old-view render and inspect retention if a leak is suspected.

**Rubric for self-review:** Separate item identity from displayed content, state the list ownership contract, match view work to view lifecycle, and distinguish JVM policy proof from Android integration. This is visible practice, not a scored assessment.
